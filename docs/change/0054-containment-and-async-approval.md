# CHG-0054: 封じ込めを主にして確認（ask）層をなくし、非同期の承認で多数のエージェントを束ねる

- **状態**: Exploring
- **更新日**: 2026-10-31
- **基準**: コミット `c2e358f` 以降、pi 1.4.0。方針は [ADR-0022](../adr/0022-containment-first-minimal-approvals.md)（Proposed）。根拠の調査は [調査記録 AC1](../research/agents/approval-containment-survey.md)

## 目的と非目的

**目的**: エージェントの安全を、「行動の監督（承認）」から「できることの制限（封じ込め）」を主にした形へ移す。次の 4 点を、ひとつながりで進める。

1. **実際の運用と方針を一致させる。** 利用者は常に bypass で運用している。ask の一覧を、素通し・必須確認・拒否に振り分け直し、bypass が何も変えない状態にして、モードの切り替えをなくす。
2. **各種の確認の時間切れを、非同期の承認で解消する。** 今の非同期（退避）は `git_commit` だけで、bash の必須確認や gh 投稿の確認は、時間切れで拒否されるだけ。人が不在でも、作業を止めず、後でまとめて承認できる受け皿を作る。
3. **多数のエージェントを束ねる運用（オーケストレーション）に耐えるようにする。** 人の確認がスケールしない前提で、子ごとの権限、費用・深さの上限、停止スイッチ、追跡を整える。
4. **Windows（PowerShell が必須のプロジェクト）での扱いを決める。** 境界（Fence）が Windows ネイティブに無いことが、モード廃止の最大の障害になる。詳細は [CHG-0034](0034-windows-native-pi-boundary.md)。

**非目的**: 悪意あるコードへの耐性（[ADR-0012](../adr/0012-ocs-boundary-for-accidents.md)。守る対象は、エージェントのうっかり）。モデルによる自動承認（分類器）の自前実装（候補比較で保留）。Windows の境界の実装そのもの（CHG-0034）。

## 現在地

- **方向は、ADR-0022（Proposed）にまとめた。** 確認は、人が情報を足せる操作に絞り、境界が届く範囲を強制する。モードではなく、能力のプロファイル（`role`）を残す。
- **先行実装（原則に沿ったもの）は、[CHG-0053](0053-worktree-integration-gate.md) で配備済み。** feature の linked worktree の `git_commit` は確認なし、保護ブランチへの統合は必須確認。どちらも bypass と無関係。
- **運用の事実**（[調査記録 AC1](../research/agents/approval-containment-survey.md) の観測 9〜11）: 素の `pi` でも常に bypass。使い捨てコードの承認は実質素通し（利用者の報告。未計測）。観測を取ったセッションは Fence の外（実際の運用は「境界なし + bypass」）。
- **非同期の承認の現状**: 保留（退避）の仕組みは `git_commit` だけにある（[CHG-0046](0046-guarded-action-timeout.md)。時間切れで、内容を `refs/pi/pending/` に退避して続行する）。bash の必須確認は、時間切れで「拒否」になり、内容は残らない（`index.ts` の確認の分類で確認）。子は UI が無く、必須確認が自動で拒否される。
- **公開資料の知見**: 確認は約 93% が承認され（承認疲れ）、境界が固ければ監督を緩めてよい。多数のエージェントでは、確認がスケールせず、費用・再帰の上限と停止スイッチが要る。数値は Anthropic の利用者のもので、このリポジトリの運用の数値ではない（段 1 で測る）。
- **Windows**: 境界が無い（CHG-0034 の段 W1 は未着手）。PowerShell が必須のプロジェクトの扱いは、CHG-0034 の候補比較に、WSL の interop 経由の呼び出し（候補 H）などを足した。

## 未解決点

1. **素の `pi` の扱い**（段 3）。境界の中でしか動かさない（起動の入口を `pis` に一本化し、Orca・Zed の呼び出しも含める）か、境界が無いことを認めて必須確認を広げるか、今のまま（暗黙の bypass）か。実際の運用は「境界なし + bypass」なので、現状維持は、追認にすぎない。再開条件: 段 1 の数字が出たとき。
2. **非同期の承認の設計**（段 4）。保留の保存先（`refs/pi/pending/` は `git_commit` 用）、保留できない操作（時間に依存するもの）の扱い、再実行の整合（承認した内容と、実行時の状態の一致）、子からの保留を、親でなく人へ直接上げる経路。
3. **使い捨てコードの静的検査**（段 5）の精度。Python・シェルのワンライナーは、静的な検査が難しい。境界が無いとき、どこまで検査するか。
4. **ask の振り分けの基準**（段 2）。「承認率が高く、可逆」なら素通し、「ほぼ必ず拒否」なら拒否、の閾値（例: 20 件以上で 95% 以上）は、仮の値。
5. **Windows**（段 7）。境界なしの運用を許容するか、Windows ネイティブの境界（CHG-0034 の候補 A〜C）を作るか。PowerShell が必須のプロジェクトで、WSL の `pis` から `powershell.exe` を呼ぶ形が、境界を突き抜けるかは未検証（CHG-0034 の候補 H）。
6. **オーケストレーションの上限の単位**（段 6）。費用、子の数、深さ、再試行、時間のどれを、どの粒度で持つか。

## 次の調査・実験

1. （段 1）ask と必須確認の、承認 / 拒否 / 時間切れの件数を、セッションログ（`~/.pi/agent/sessions/`）から集計する。手段は、`friction-review` スキルの集計スクリプト（`.agents/skills/friction-review/scripts/friction_scan.py`）を拡張するか、確認の結果を、ハーネスが、集計しやすい形で記録する。件数の下限（規則あたり 20 件）を決めておく。
2. （段 4）非同期の承認の、最小の形を、`git_commit` の退避の一般化として、設計する（`review` に見せる）。
3. （段 7）CHG-0034 の候補 H（WSL の interop）の検証手順を、`pis` の内側で、読むだけのコマンド（`Test-Path` など）で作る。

## 評価基準

**必須**: 境界が無い起動で、守りが、今より弱くならない（弱くなるなら、利用者がそれを選んだと明示する）。必須確認の取りこぼしが無い。

**望ましい**: 確認の件数が減り、承認率の低い（意味のある）確認だけが残る。時間切れで作業が止まらない。設定の単一ソース（`common.toml`）で管理できる。Windows でも同じ原則で説明できる。

結果を見て基準を変えたら、変えたこと自体を、「重要な更新」に残す。

## 実装・検証

未着手。先行実装として、原則に沿った次の 2 つが、[CHG-0053](0053-worktree-integration-gate.md) で配備済み。

- feature の linked worktree（`feature/*`）の `git_commit` の確認の省略（自由区）。実 git の表試験で、判定を確かめた。
- 保護ブランチへの統合コマンド（`git flow feature finish`、自由区の外の `git merge` など）の必須確認。配備後の実機で、確認の画面が出ることを確かめた。

各段の検証は、段ごとに、対象の試験と、全件（`mise run verify:all`）で行う。Windows 側は、実機でしか確かめられない（[AGENTS.md](../../AGENTS.md) の「Windows 実機での検証」）。
