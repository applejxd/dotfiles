# 手順

## A. 設計（項目 1〜8）

### 項目 1: repo の列挙

- **型:** `RepoSet` は順序つきの `(rel, kind)`。`rel="."` が親、子は相対パス。親が先、深いものが後。
- **rel の規則:** 各成分は `[A-Za-z0-9._-]+`。`..`・空成分・先頭 `-`・成分が `.git`・制御文字・200 字超は拒否する。空白や日本語のパスは v1 では拒否する（要望が出たら緩める）。`config.py` の `_resolve_data` と同じ流儀。

**探索（`repos.discover(root)`）:**

- `os.scandir`＋`follow_symlinks=False`。symlink は辿らず、「skipped: symlink」として報告する。
- ディレクトリ `X` の中に **実ディレクトリの** `.git` があれば、`X` を repo とする。`.git` の中へは入らず、`X` の下は続けて探す（孫 repo）。
- `.git` が**ファイル**（linked worktree・submodule）の場合は repo にしない。`.tmp/worktrees/*` はこれで自然に外れる。
- 除外名: `node_modules`・`.venv`・`venv`・`__pycache__`・`.tox`・`.nox`・`.mypy_cache`・`.pytest_cache`・`.ruff_cache`・`.cache`・`.tmp`・`.direnv`。
- ルートと `st_dev` が違うディレクトリ（mount。データセット）は入らない。許可表の `data_roots` と `DENY_*` に当たるパスも入らない。
- 上限: ルートからの深さ 5、repo の入れ子 3 段、走査エントリ 20 万件、repo 数は許可表の `max_repos`。超えたら**失敗**にし、「`repos` を宣言せよ」と出す。黙って打ち切らない。
- 各 repo の検査: `.git` の所有者が呼び出し元の uid、`realpath` がルート配下で、パスの途中に symlink が無い。親の `git ls-files -s -- <rel>` が mode 160000 なら submodule として拒否する（D14）。git の対象を変える継承環境変数（`GIT_DIR` など）は落として実行する。

**宣言（`kcage.toml` の `repos = ["src/foo", …]`）:**

- 省略は「探索の結果」。`repos = []` は「親だけ」。宣言があるときは宣言のとおりにし、探索はしない。
- 各パスは、探索と同じ検査を通る必要がある。実体が無い・`.git` が無い宣言は失敗にする。
- 宣言があるときの `doctor` だけは、予算内で探索し、宣言に無い `.git` を警告する。

**許可表の項目（締める方向だけ）:**

| 項目 | 意味 |
| --- | --- |
| `git = "shared"\|"clone"` | v1 は許可表だけで決める。`kcage.toml` の `git` は v1 では持たない。CLI と root helper で解釈がずれるのを避ける |
| `workdir = "auto"\|"host"` | D11 |
| `max_repos` | 既定 16、上限 64 |
| `seed_max_mib` | 全 repo の bundle の合計の上限。既定 4096 |
| `repo_allow = ["src/*", …]` | 省略は全て許可。あれば rel がどれかに一致するものだけ |

`kcage.toml` は、この範囲の部分集合しか選べない。

**信頼（A3）:**

- ホストの作業ツリーは信頼する。ただし `take develop` で箱が書いたファイルが入りうるので、`kcage.toml` は「要求」のまま扱い、**許可表 ∩ 探索 ∩ 宣言**で絞る。
- 箱から来るパス・名前は、列挙にも保存先にも使わない。`collect` や `view` が使う rel は、ホストの manifest の値を再検証したものだけ。
- 箱の側での再確認（seed 直後と `selftest`）:
  - `find <workdir> -name .git` の結果が、期待する集合（各 rel の `.git` が実ディレクトリ）と完全に一致すること。
  - 各 repo で `git rev-parse --absolute-git-dir` が `<workdir>/<rel>/.git` と等しいこと。
  - 余分な `.git` は、表示だけして警告する（箱の中で作った repo は同期の対象外）。

**`setup.sh` を解析しない根拠:**

1. 任意の shell なので、変数・分岐・ループ・環境依存を含み、静的に正しく読めない。
2. 実行するなら、ネットワーク・認証・任意コードが要る（A4）。
3. 箱が書き換えうるファイルをホストが設定として解釈すると、C4 の面が増える。
4. 正本は結果（実在する clone）だ。レシピは検証の対象にならない。

**代わりの検証（結果を見る）:**

- (i) manifest に seed 時の配置（rel と先頭 oid）を残し、`doctor` が現在の探索結果と比べる。新しい子が増えたら「再 seed が要る」と出す。
- (ii) 探索と宣言の差を `doctor` が警告する。
- (iii) seed 後に箱で配置を再確認する（上記）。
- (iv) 子のパスが親で未追跡または ignore であることを確認する。

### 項目 2: seed（ホスト→箱）

**どの枝を入れるか（repo ごと）:**

- `develop`・`main`・`master` のうち存在するもの。
- ホストで今チェックアウト中の枝（detached なら無し）。
- `--branch <名前>`（複数指定可）で追加した枝。
- 全枝は入れない（未統合の枝の分だけサイズが増える）。ホスト作成の feature 枝は、`feed --branch` か、`ws start` が既存の枝を見つけて attach する経路で渡す。
- 箱の主 clone は、`develop` があれば develop をチェックアウトする。無ければ main、master の順。

**事前検査（失敗なら何も作らない）:**

- 列挙結果・件数・`git count-objects -vH` から合計サイズの見積り。上限は `seed_max_mib`。
- 浅い clone（`git rev-parse --is-shallow-repository`）と partial clone は拒否する。bundle にできない見込み（一般知識・S0 で確認）。
- `.gitmodules` を持つ子は警告する（submodule は D14 で対象外）。
- `--dry-run` で、上記と所要時間の見積り（S0 で測るスループットを使う）を出す。

**手順（`kcage up` の最後に自動。`kcage seed` でも実行可）:**

1. repo ごとに、ホストで `git bundle create`（硬化した git。`core.hooksPath=/dev/null`・`GIT_CONFIG_GLOBAL=/dev/null` など。`apps/pr-viewer/git-view.ts:37-87` と同じ考え方）。
2. `kcage exec -- sh -c 'cat > ~/.kcage/seed/<nonce>/<n>.bundle'` で転送する。標準入力にファイルを渡す。`sha256sum` で照合する（転送の破損の検知。S0-T1）。
3. 箱の中で、親から順に次を行う。
   - `git init --template=` で空のテンプレート（サンプル hook なし）から作る。
   - `git fetch <bundle> '+refs/heads/*:refs/heads/*' --update-head-ok`。
   - `git checkout -f <枝>`。
   - remote は作らない。
4. 親の `.git/info/exclude` へ `/.tmp/` と子の rel（`/src/foo/`）を、各子の `.git/info/exclude` へ孫の rel（その子からの相対）を、生成して書く。
5. `user.name`・`user.email` を、ホストの各 repo の設定から箱の `.git/config` へ写す（無ければ飛ばす。identity の別 feature（`kcage-git-identity`）と整合を取る。未確認）。
6. 箱の `~/.kcage/layout.json` と、ホストの inbox manifest を書く。最後に完了印 `~/.kcage/seeded` を作る。

**親の `.git/info/exclude` について:**

- 箱の clone の `.git` は箱専用。`info/exclude` は bundle にも `take` にも載らない（refs と objects だけが運ばれる）ので、**ホストへ漏れない**。
- ホストの親の ignore の写しは不要（箱の clone に未追跡ファイルは無い）。
- 生成の目的は 2 つ。`git status` を静かにすることと、`git add -A` が子を gitlink として足すのを防ぐこと。

**順序と原子性:**

- 作業は `<workdir>` の中で直接行う（empty のはず）。`up` が `<workdir>` を空で作る前提。
- 開始時に `~/.kcage/seeding` を作り、完了印を最後に作る。失敗したら、`seeding` がある場合だけ `<workdir>` の中身を消して最初からやり直す。箱専用のデータだけを消す。
- 印が無いのに `<workdir>` が空でない場合は、他人のデータとみなして拒否する。
- 完了印があれば `up` は seed しない。再 seed は、`collect`・`take` の後に `kcage rm` → `kcage up`（C5: 元に戻せない操作を足さない）。

**サイズ・時間:**

- 概算は `T ≈ Σ(bundle 作成 + S_i/スループット + unbundle + checkout)`。`S_i` は各 repo の pack サイズで、全履歴を送る。
- N=3、各 200 MiB なら約 600 MiB。`incus exec` の標準入力のスループットは未測定（S0-T4 で測る）。目安は 5 分以内。
- 初回だけの費用。以降は `feed`・`collect` の差分 bundle で済む。

### 項目 3: collect / take / feed

**inbox の配置と命名:**

- `~/.local/share/kcage/inbox/<id>/<slug>-<hash8>.git`。bare repo で、`<hash8>` は rel の sha256 の先頭 8 桁。
- `<id>/manifest.json` はホストだけが書く。`rel`・`dir`・`known`（箱と共有済みの oid の一覧）・seed 時の先頭を持つ。
- inbox の config は固定: `transfer.fsckObjects=true`・`receive.fsckObjects=true`・`fetch.fsckObjects=true`・`gc.auto=0`・`core.hooksPath=/dev/null`。
- **alternates は使わない。** ホストの gc が借りているオブジェクトを消すと inbox が壊れるので、inbox は prerequisite となる commit を自前で持つ。初期化時と `collect` の前に、ホスト repo から inbox へ `refs/kcage/host/*` を fetch する（ホスト repo は信頼する側。パス指定の fetch）。

**collect（箱→inbox）:**

repo ごとに次を行う。

1. 箱の `git for-each-ref` で、manifest の `known` から変わった先頭だけを見る。変化が無ければ飛ばす。
2. `kcage exec -- git -C <workdir>/<rel> bundle create - 'refs/heads/feature/*' 'refs/heads/bugfix/*' 'refs/heads/box-wip/*' refs/heads/develop --not <known の oid…>`。標準出力をホストが一時ファイルに受ける（サイズ・時間の上限つき）。
3. `git bundle verify`、`git fetch`（硬化した環境、fsck あり）。
4. 走査（項目 7）を通した後で、inbox の ref を更新する。
5. `known` を更新する。

箱が rebase した枝でも inbox は常に追従する（inbox への更新は強制可。ホストへの取り込みで FF を検査する）。

**`kcage take <枝>`:**

- 許可する枝名は `^(feature|bugfix)/[A-Za-z0-9._-]+(/[A-Za-z0-9._-]+)*$`（`pr-review.ts:12` と同形）、`box-wip/<日時>`、`develop` の 3 種。`main`・`master` は取り込まない。
- 対象は manifest の全 repo（`--repo <rel>` を繰り返して絞れる。親は `.`）。
- 内部で `collect` を行い、**全 repo の事前検査を先に行う**。
  - 枝が無い repo は「-: 枝なし」で飛ばす。
  - 空の枝（`--not` で bundle が作れない）は飛ばす。
  - ホストに同名の枝があり FF でなければ「非 FF」で拒否。同じなら「最新」。
  - ホストで worktree にチェックアウト中の枝は拒否。
  - どれかが失敗したら、何も適用せず終了コード 3。`--partial` なら通った repo だけ適用する。
- 適用は repo ごとに `git update-ref refs/heads/<枝> <新> <旧>`（CAS）。ホストの `.git` はホストの物で、箱は触れない。`--as <名前>` は、衝突したときの別名での取り込み。
- 同じ処理を再実行すれば残りを続けられる（冪等）。

**`take develop` の規則（ホストの作業ツリーを守る）。PR ビューアの `advanceTarget`（`apps/pr-viewer/merge.ts:702-720`）と同じ規則:**

| 状況 | 動作 |
| --- | --- |
| develop をどの worktree もチェックアウトしていない | `update-ref` CAS |
| develop をチェックアウト中の worktree があり、追跡ファイルが clean | その worktree で `git merge --ff-only --no-overwrite-ignore --no-edit` |
| 同上で、追跡ファイルに変更あり | 拒否（終了コード 3）。変更ファイルを表示する |
| 未追跡のみ | git の `merge` に任せる（上書きされるなら git が拒否する） |
| 非 FF | 拒否。「`feed` してから箱で取り込む」と案内する |

- `merge --ff-only` は、箱が書いたファイルをホストの作業ツリーへ書く。C4(b) の限界になる。取り込む差分が `pi.json` の `risk_paths`（`common.toml.tmpl:1008-1025` に相当）に当たるときは、一覧を表示して `--accept-risk-paths` を要求する。
- **`kcage take develop|main` は `[pi.confirm]` の確認対象に足す**（`common.toml.tmpl:962-1000` の `commands`）。足さないと、AI が保護 ref を確認なしに進められる（CHG-0053 の不変条件に反する）。

**`kcage feed`（ホスト→箱）:**

- repo ごとに、develop・main（master）の差分 bundle を作る（`--not known`）。`--branch <名前>` でホスト作成の枝を渡す。
- 箱では `~/.kcage/feed/` へ置き、`kcage-box feed-apply` が `git fetch <bundle> '+refs/heads/develop:refs/kcage/host/develop'` で受ける。
- そのうえで、箱の develop がその祖先なら、チェックアウト中かつ clean は `merge --ff-only`、チェックアウトされていなければ `update-ref`。祖先でなければ `refs/kcage/host/develop` を残し、案内を出す（箱が develop を独自に進めている）。

### 項目 4: feature の運用（**確定設計**）

**前提（Q11）:** 同名枝を各 repo に切る。feature ごとに親子を揃えた作業ツリーが要り、複数 feature を並行する。

**箱の配置:**

```text
<workdir>/                        親の主 clone。常に develop（ここでは作業しない）
├─ src/foo/                       子の主 clone（develop）
└─ .tmp/worktrees/<名前>/         ← ワークスペース worktree（親の linked worktree。枝 feature/<名前>）
   └─ src/foo/                    ← 子の linked worktree（枝 feature/<名前>）。子の主 clone の .git/worktrees/ に属する
```

**比較と判断:**

| 案 | 並行 feature | 費用・整合 | 判断 |
| --- | --- | --- | --- |
| A. ワークスペース worktree（親＋子を揃える） | 可 | ディスクは worktree 分だけ。`.tmp/worktrees/<名>` の慣行と同じ。`git_commit` の `dir=<rel>` と自由区の判定（リンクされた worktree で `feature/*`。`pi-extensions.md:88,101`）に乗る | **採用** |
| B. 子は 1 つの clone を feature 枝へ切り替える | 不可（共有状態が混ざる） | 軽い | 要件に合わず不採用 |
| C. feature ごとに全 repo を別 clone | 可 | `.git` が重複。`take` の対象が増える | 不採用 |

**動詞（`kcage-box ws …`。ホストの `kcage ws …` は `kcage exec -- kcage-box ws …` の転送）:**

| 動詞 | 動作 |
| --- | --- |
| `ws start <名前> [--from <枝>] [--only <rel>,…]` | ワークスペースを作る（下の手順） |
| `ws ls` / `ws status [<名前>]` | 一覧、repo ごとの枝・ahead 数・dirty |
| `ws path <名前>` | ワークスペースの絶対パス。worker の `cwd` に使う |
| `ws update <名前>` | 各 worktree で `git merge develop`（現行の `cd <wt> && git merge develop` の束ね）。衝突で停止（終了コード 3、repo とファイル） |
| `ws merge <名前> <feature>…` | 各 repo で、その `feature/<f>` があるものだけを `--no-ff` で merge（feature 同士の取り込み・bundle 相当） |
| `ws finish <名前>` | 箱の中の finish（D3） |
| `ws rm <名前> [--force]` | 後片付け |
| `ws adopt <名前> <rel>` | detached の子に feature 枝を切る |

**`ws start` の手順（全 repo の事前検査 → 実行 → 失敗時は巻き戻し）:**

1. 名前は `^[a-z0-9][a-z0-9._-]{0,63}$`。
2. repo 一覧は `~/.kcage/layout.json`。箱の中で実在も再確認する。
3. 各 repo の基点は次の順で決める。
   - `--from F` なら、その repo に `refs/heads/F` があればそれ。
   - 無ければ `.gitflow` の `branch.feature.startPoint`、さらに無ければ develop → main → master。
4. 事前検査:
   - `<ws>` が存在しない。
   - `<ws>/<rel>` が空き（親が追跡している同名パスは衝突として拒否）。
   - 枝が他の worktree にチェックアウトされていない。
5. 実行は親から順に `git -C <主 clone> worktree add [-b feature/<名前>] <ws または ws/<rel>> <基点>`（`--no-track`）。
   - すでに `feature/<名前>` がある repo は、`-b` なしで attach する（ホストで始めた feature を箱へ持ち込める）。
   - `--only` に無い repo は `--detach` の worktree（基点で固定。枝を持たないので `take` の対象外）。
6. manifest は `<workdir>/.git/kcage-ws/<名前>.json`（箱専用）。
7. 失敗したら、この実行で作ったものだけを逆順に `worktree remove`、枝は `update-ref -d` の CAS（作ったばかりの空の枝）で消す。

**既定は「全 repo が参加」。** 変更の無い repo の枝は `take` が飛ばす（項目 3）。子が feature 枝を切らず develop で直接作業する場合は、`--only` から外す（detached）か、主 clone で直接 commit する。

**commit:** ワークスペースの根（親の worktree）で pi を���動し、子の commit は `git_commit` の `dir=<rel>` を使う。リンクされた worktree で `feature/*` なら自由区だが、箱の中で子に効くかは実機未確認。

**finish は 2 つの経路を持つ（D3）:**

- **経路 A（既定）**:
  1. 箱で commit する。
  2. `kcage take feature/x`（全 repo）。
  3. ホストで PR の要約と、PR ビューアでの統合を repo ごとに行う。
  4. `kcage feed`。
  5. 箱で `kcage-box ws rm <名前>`。
  - 統合は merge commit なので、`feed` 後は枝が develop の祖先になり、`git branch -d` が通る。
- **経路 B（箱の中で finish）**: `ws finish <名前>` は、深い repo（子）から親の順に、次のように動く。
  - 主 clone が develop で clean であることを事前検査する。
  - `git merge-tree --write-tree` で全 repo の衝突を事前検査する。1 つでも衝突なら何も変更しない。
  - 通れば `git merge --no-ff feature/<名前>` を適用し、worktree と枝を片付ける。
  - その後 `kcage take develop`（FF）で反映する。
  - 実行途中の失敗では、先に済んだ repo の merge が残る。reflog で戻せる（原子的ではない）。歯止めは箱の pi のフルガードの必須確認（D3）。`kcage-box ws finish` と `ws rm --force` は確認対象にする。

**`ws rm`:**

- 追跡ファイルの変更・未追跡があれば拒否する。
- 無視ファイルだけなら worktree ごと消す（`wt_clean.py` の規則と同じ考え方。`docs/spec/orchestration.md` の「worktree の掃除の規則」）。
- 枝は `git branch -d`。未統合は `--force` が無ければ残す。

**bundle（`feature/bundle-N`）:**

- 複数 repo では「ワークスペース `bundle-N` を作る → 各 repo で、その枝があるものだけ merge する」で表す。
  ```text
  kcage-box ws start bundle-1
  kcage-box ws merge bundle-1 a b
  ```
- 衝突は repo とファイルを出して停止する（終了コード 3）。worker が `<ws>/<rel>` で解消し、`git add -A` の後で `ws merge --continue bundle-1`。
- 検査は repo 固有の検査をワークスペースの根で回す（kcage は決めない）。
- `bundle.py` は流用しない。単一 repo 前提で worktree の場所が固定（`bundle.py:70-71`）のため。
- `take feature/bundle-1` は全 repo から取り込む。PR は repo ごとになる。
- **統合の順序**: ポインタが無いので、整合は人が守る。子 → 親の順で押す（`ws status` に表示）。

### 項目 5: wip（未コミットの作業）

- **`kcage feed --wip [--repo …]`**（ホスト→箱）:
  - repo ごとに、一時 index（`GIT_INDEX_FILE`）で次の順に作る。
    1. `read-tree HEAD`
    2. `git ls-files -z --cached --others --exclude-standard` と `--deleted` の結果から作る一覧を、`update-index --add --remove` で反映
    3. `write-tree`
    4. `commit-tree -p HEAD`
  - **入れ子の repo は一覧から外す。** `--others` は子を `path/` という行で出す（未確認。S0-T8）ので、末尾 `/` の行と、`rel` 配下のパスを落とす。`git add -A` を使わないのは、ignore されていない子が gitlink として入るのを避けるため。
  - 秘密検出（`cli.py:31` の `SECRET_VALUE` と同系統の正規表現・秘密らしいファイル名の拒否）、1 ファイル 5 MiB・合計 50 MiB・件数の上限を適用する。
  - 一時 ref `refs/kcage/wip/<日時>` で bundle にし、終了後に消す。
  - 箱には枝 `host-wip/<日時>` として入る。適用はしない。`ws start <名前> --from host-wip/<日時>` で使える。
- **`kcage collect --wip [--ws <名前>] [--repo …]`**（箱→ホスト）: 箱で同じ手順の固定スクリプト（`kcage-box snapshot`）を実行し、`box-wip/<日時>` を各 repo に切る（同じ日時）。変更の無い repo は飛ばす。ホストでは inbox に置くだけ。`take box-wip/<日時>` で取り込むが、適用はしない。
- **1 回の操作で全 repo を束ねる:** どちらも manifest の全 repo を順に処理し、結果を repo ごとの表で出す。

### 項目 6: view

- **目的と位置:** ホストの専用ディレクトリ `~/.local/share/kcage/view/<id>/<main|ws-名前>/`（読み取り専用の複製）。ホストの repo の外に置き、中に `.git` は作らない。
- **除外（どの深さでも、名前を casefold・末尾の空白とドットを除いて比較）:**
  - `.git`（ファイルでも）、`.hg`、`.svn`
  - `.vscode`・`.zed`・`.idea`・`.cursor`・`.devcontainer`・`.husky`・`.envrc`・`.direnv`・`.pre-commit-config.yaml`
  - `.claude`・`.pi`・`.codex`・`.agents`・`.mcp.json`
  - `mise.toml`・`.mise.toml`・`.tool-versions`
  - `.gitattributes`・`.gitmodules`
  - 大きな生成物（`node_modules`・`.venv` など。探索の除外名と共通）
- **根拠（実在する先例）:** `common.toml.tmpl:1008-1025` の `risk_paths` が、リスクのあるパスの例（agent 設定・pre-commit・mise・`.gitflow`・CI など）を持つ。D9 の一覧はこの拡張。
- **複製の展開（`view.py`）。箱が作った tar はホストでは信頼しない:**
  - Python の `tarfile`（`filter="data"` 相当）に、さらに独自の検査を重ねる。
  - 通常ファイルとディレクトリだけを許す（symlink・hardlink・デバイス・FIFO は拒否）。
  - 絶対パス・`..`・NUL・成分 255 字超・除外名の成分を拒否する。
  - モードは 0644/0755 に正規化する（setuid などを除く）。所有者は無視する。
  - `O_CREAT|O_EXCL|O_NOFOLLOW` で、新しく作った 0700 の一時ディレクトリの中にだけ書く。
  - 上限: 1 ファイル 10 MiB、総計 1 GiB、20 万件。超えた分は「skipped」として報告する。
  - 終わったら世代を入れ替える。消すのは、`.kcage-view` の印がある kcage 自身の生成物だけ。
- **同期（on-demand）:** v1 は**全量**（除外と上限の後、通常は数秒〜）。差分化は、実測を見て S2 以降で決める。差分化の案: 箱が `path size mtime` の一覧を返し、ホストが検証したうえで、変わったものだけの tar を要求する。
- **運用:** Orca・Zed では、この view をフォルダとして開く（Orca の folder workspace は git を呼ばない。`.tmp/keep/orca-capability/placement.md`）。ファイルは 0444 にする。編集は、箱の中で行うか `feed --wip` を使う（書き戻しは無い）。
- **限界（正直に）:** エディタの言語サーバーやビルドスクリプト（`build.rs`・tsserver の plugins など）が、箱のコードを実行しうる。除外名の一覧では防げない。view のフォルダは、エディタの restricted/untrusted モードで開く運用にする（エディタごとの設定は未確認）。

### 項目 7: doctor・selftest・安全

clone モードの `selftest` は `cli.py:322` の `selftest_commands` と、`cli.py:37` の `GIT_RO_PATHS` の検査を差し替える。

| 検査 | 内容 |
| --- | --- |
| (a) 箱にホストのパスが無い | `/proc/self/mountinfo` が、期待する集合（rootfs・`data` の ro・gpu の 2 つ）と一致する。`/mnt/c`・ホストのリポジトリのパスが存在しない。`workdir="host"` でも、その場所が rootfs 上（bind ではない）であることを `findmnt` で見る |
| (b) 箱専用の `.git` | 各 repo で `.git` が実ディレクトリ、`rev-parse --absolute-git-dir` が自身、`core.worktree` なし、`objects/info/alternates` なし、remote なし、`.git/config` にホストのパスなし |
| (c) 悪性 bundle の拒否 | `test/kcage/` の試験（実 git）と S0。`git hash-object -w -t tree --literally` で作った objects で、`.git`・`.GIT`・`.git `・`git~1` の tree entry、`.gitmodules` の symlink、gitlink、`..`・先頭 `-`・制御文字を含む ref 名、サイズ上限超え、prerequisite 欠け、壊れた pack を作る |
| (d) 親の bundle に紛れた入れ子の `.git` | 取り込みの走査に 3 層を置く（下記）。どの層で拒否したかを試験で記録する |

**(d) の 3 層:**

1. `fetch.fsckObjects` と `transfer.fsckObjects`（`.git` 名・`.gitmodules` の symlink を fsck が拒否する見込み。一般知識。bundle の fetch で効くかは S0-T7 で確認）。
2. 走査: `git rev-list --objects <新> --not <known>` のパス名と、`git log --raw -m --no-renames` の mode を見る。
   - `.git` 名の変種（`.git `・`git~1` など）を拒否する。
   - gitlink（160000）を拒否する。
   - **親の commit が子 repo の rel 配下に触れていれば拒否する**（子の作業ツリーへの書き込みと、gitlink によるポインタの混入を同時に防ぐ）。
   - ref 名は `git check-ref-format` と許可パターンで検査する。
3. 反映の段階: `merge --ff-only` の checkout も、git 本体が `.git` 成分を拒否する（`verify_path`。一般知識）。

**`kcage doctor`（clone 版）:** `cli.py:229` のホストの `.git` 検査を、次に差し替える。
- 列挙の診断（探索と宣言の差・配置の差）。

- inbox の config の検査。

# リスク

- **ワークスペースの入れ子（親の linked worktree の下に子の linked worktree）が git で崩れないか**は未検証（S0-T5）。崩れる場合は、ワークスペースを親だけにして子は主 clone を切り替える案（B）へ戻る。ただし並行 feature が成立しなくなるので、利用者の要件と衝突する。
- **`take develop` は箱が書いたファイルをホストの作業ツリーに入れる。** C4(b) の限界。確認と `risk_paths` の警告で緩和する。保護 ref の確認を `[pi.confirm]` に足さないと、AI が保護 ref を確認なしに進められる（S1g は必須）。
- **repo 間の整合は人が守る。** ポインタが無いので、親だけ統合された状態や、子だけ統合された状態が途中に生じる。`ws status` で見えるようにし、子 → 親の順を推奨する。
- **浅い clone・partial clone の子**は bundle にできない見込み。setup.sh の例（Q12）が来るまで未確定。
- **`kcage-box` の配布:** 箱が書き換えうる。ただしホストは出力に依存しない。ホスト側の取り込みは、箱の helper の出力ではなく、素の git の bundle を信頼せず検査する。箱に `python3` が無い場合は sh に変える。
- 箱の未回収の commit は、`kcage rm` や箱の破損で失われる。自動 collect で緩和する。
- `view` は、箱由来のファイルをホストのエディタが解釈する面を残す（項目 6 の限界）。
- 遅延: repo 数 × 数回の `sudo -n kcage-root exec`。測定は S0-T1。
- ホスト側の PR ビューアが、同名の枝を持つ複数 repo を扱えるか（`--repo` の複数指定）は未確認。

# 利用者に確認すべき点

推奨つき。未決の項目は、実装を止めずに推奨で進められる。

1. **Q12（`setup.sh` の例）。** 設計は `setup.sh` に依存しないが、次の 4 点で変わる。
   - 子が浅い／partial clone か（推奨: そうでない前提。そうなら seed は拒否する）。
   - repo 数と深さ（推奨: 16 以内・3 段以内。超えるなら `repos` を宣言する）。
   - 子が `.gitmodules` を持つか（推奨: 対象外のまま）。
   - 相対パスに空白・非 ASCII を使うか（推奨: v1 は拒否）。
2. **子が feature 枝を切らず develop で直接作業する場合の扱い。** 推奨: `ws start` の既定は全 repo 参加。直接作業する子は `--only` から外して detached で固定する。主 clone で直接 commit する運用も許す。
3. **`take develop` の既定。** 推奨: 追跡ファイルが clean なら `merge --ff-only`、`risk_paths` に当たる差分があれば `--accept-risk-paths` を要求する。代替案: develop がチェックアウト中なら常に拒否（安全だが、子が develop にいる通常の運用で使いにくい）。
4. **`ws finish`（経路 B）を v1 に含めるか。** 推奨: 含める。ただし既定は経路 A（PR ビューア経由）。
5. **D4（箱の git-flow-next）。** 推奨: S1 から外して S2 で判断（ワークスペースは `git worktree` で足りる）。
6. **`kcage.toml` の `git` キー。** 推奨: v1 は持たず、許可表だけで決める。
7. **`view` の置き場とエディタの運用。** 推奨: `~/.local/share/kcage/view/`。エディタは restricted モードで開く。
8. **箱の中で作った新しい子 repo。** 推奨: v1 は同期対象外（`doctor` が警告のみ）。新しい子は `setup.sh` でホストに作り、再 seed する。
9. **`take` の事前検査の失敗時。** 推奨: 既定は全 repo を適用しない（`--partial` で通った repo だけ）。
