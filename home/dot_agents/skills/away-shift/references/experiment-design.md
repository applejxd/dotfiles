# 1 サイクルの組み立て方

無人実行では、復帰時に読んで意味が分かる形で結果が残っていることが価値になる。
「たくさん試した」より「何が確かめられたか」を残す。

## 1 サイクル = 1 仮説

サイクルの先頭で次を書いてから手を動かす。

```text
仮説: <X をすると Y になるはず>
確かめ方: <実行するコマンド / 見るファイル>
成立の判定: <何が出れば成立か。何が出れば不成立か>
```

判定を先に書くのが肝心。後から書くと、出た結果に合わせて
「成立したことにする」方向へ引っ張られる。

## サイクルの長さ

子 1 つの実行は、既定で 30 分までに収める（`check` の `CHILD_TIMEOUT_MS`）。目安は 10〜20 分。
期限の少し前に、実行器が子へ「止まれ」と割り込む（`resume.md`）。割り込みは**実行中のコマンドの中には届かない**ので、
子のコマンドには `timeout` を付けさせる。

長くかかる処理（ビルド、学習、大きなテスト）を回すときは、
**投入と結果確認を別サイクルに分ける**（投入のサイクルでバックグラウンドへ出し、結果は次のサイクルの子が読む）。
投入したプロセスは、子が止められても残る。残したくないなら `timeout` で上限を付ける。

## 探索の順番

1. **再現**: 現状で何が起きるかを確認する。ここを飛ばさない
2. **切り分け**: 変数を 1 つだけ変える。同時に 2 つ変えない
3. **最小化**: 成立したら、余分な条件を削って最小の形にする
4. **確認**: 最小の形でもう一度再現する

3 サイクル連続で新しい情報が出なければ行き詰まり。方針を変えるか止める。

## コードを変えて検証するとき

子は**専用 worktree（枝つき）の中で、コードを直接変えてよい**。変えた結果は、枝のコミットとして残る
（親が `audit` で差分を確かめ、利用者が統合するか捨てる）。

- 変えるたびに、**変更と結果を対にして**コミットする。コミットの件名に、何を試したかが分かるようにする。
  失敗した試行も、戻さずに次のコミットで直すか、`cycle-<N>.md` に失敗として書く（`git reset --hard` などの履歴の破壊は拒否される）
- 依存が要るときは、worktree の中で `uv add`・`uv sync`・`uv run --with` を使う（`.venv` は worktree の中にできる）。
  グローバルな環境（`pip install`・`uv tool install`・`mise use -g` など）は拒否される
- worktree は**共有の履歴（`.git`）を持つ**。枝を作る・コミットする以外の操作（`git config`・`git worktree`・他の枝の更新・push）は、子にさせない
- worktree には、ignored の生成物・ローカル設定・秘密の疑いのあるファイルが入らない（枝は追跡ファイルだけ）。
  試験がそれを必要とするなら、実験をやらずにレポートに「入力が足りなかった」と書く
- 本体の作業ツリーは、親も子も変えない。停止時に `audit` が `HEAD` と `git status` で確かめる

## 記録に必ず含めるもの

- 実行したコマンド（そのまま貼れる形で）
- 出力の要点（長いものは末尾 20 行程度と、判断根拠になった行）
- 仮説が成立したか / しなかったか
- 次のサイクルでやること

**失敗も同じ粒度で記録する。** 復帰時に「これは試して駄目だった」と分かることが、
同じ道を辿らないために効く。

## 行き詰まったとき

ループを続けず、次のどれかへ切り替える。

| 状況 | 切り替え先 |
| --- | --- |
| 情報が足りない | 公式ドキュメント / ソースを読むサイクルに充てる |
| 前提が怪しい | 前提そのものを検証するサイクルを 1 つ入れる |
| 承認が要ると分かった | 止めてレポートに書く |
| 目標の定義が曖昧だった | 自分の解釈をレポートに明記して止める |

## レポートを意識する

各サイクルの記録は、そのままレポートの材料になるように書く。
記録を読み返して書き直す時間は無い前提でいる。
