# 提案のひな形（段 4 で使う）

方針は [ADR-0031](../../../../docs/adr/0031-evaluate-existing-extensions-first.md)（既存の評価が先。自作は最後の手段）。
段 4 の提案は、次の順で 1 回にまとめ、**承認を待つ**（承認なしに実装・導入へ進まない）。表と短い文で書く。
**悪くなる点を書けないときは、評価が足りない**（どんな機能も、利用者の操作や維持のどこかを変える）。

## 1. 要望の整理（段 1 の結果）

目的・使う場面・成功条件・やらないこと。

## 2. 探した結果（段 2 の記録）

[探し方と評価](public-research.md)の順序（pi 本体の標準・設定 → 入れている package → 公開 package → skill + CLI / MCP）で、
**何を・どこで探し、何が見つかったか**を、出典（URL・日付）つきで書く。見つからなかったときも、探した先と語を書く。
候補は評価の表で比べる（観点は [探し方と評価](public-research.md#評価の観点)）。確かめた事実と推測を分ける。

## 3. 案を出す（**「作らない案」を必ず含める**）

| 案 | 内容 | 維持費 | 撤去・やめ方 |
| --- | --- | --- | --- |
| A: 既存を導入する | 候補の package を版固定で入れる（`pi-stock-packages` に 1 行）。permission の方針も一緒に決める | package の更新に追従（版固定なので、更新は選んだときだけ） | 一覧から 1 行消す |
| B: 設定・スキル・MCP で代替する | pi の設定、スキル（skill + CLI）、既製の MCP サーバで足りる範囲にする | 設定とスキルの文書だけ | 設定・スキルを消す |
| C: 自作する（最小） | 薄く、公式の拡張点で、package の形で作る。ADR-0031 の自作の条件（a〜d）を満たす | 行数・追従が要る上流・試験・docs の全部 | 撤去条件を先に書く |

- **A と B で足りるなら C は出さない**（出すなら、足りない理由を書く）。「機能が足りなくなる点」は、**悪くなる点として明記する**。
- 案ごとに同じ項目を同じ順で埋め、**推奨する案とその理由**を 1 つ選ぶ。理由は、既存だけでは残る具体的な失敗、導入・自作で減る失敗、増える手間（確認・待ち・保守）を比べて書く。
- 供給網のリスク（導入する package は読み込み時に任意のコードを実行できる）は、案 A の「残るリスク」に必ず書く。対策: 版固定・権限（permission-system）・初回の試用。

## 4. 利用者の操作の変化を評価する

**今の操作と、変えたあとの操作を並べて**、良くなる点と悪くなる点を分けて書く。案ごとに差が出るところは、案を分ける。

| 観点 | 今 | 変えたあと | 良くなる / 悪くなる |
| --- | --- | --- | --- |
| 操作の回数・手間（入力、確認、待ち） | | | |
| 中断の頻度（承認や質問が出る回数） | | | |
| 見えるもの（表示、通知、エラーの分かりやすさ） | | | |
| 失敗したときの回復 | | | |
| 新しく覚えること（コマンド、設定） | | | |
| 既存の操作への影響（変わる・壊れるもの） | | | |

- 数えられるものは数える。数えられないものは、見込みと明記する
- 実機でしか分からないもの（TUI の見え方、モデルの実際の使い方）は未確認と書き、実機確認の項目として利用者へ渡す

## 5. 作るもの・触るもの・未確認

- 触るファイル（`pi-stock-packages`・`pi-permission-policy.json`・docs など）と、確かめ方
- 未確認として残る点、`chezmoi apply` が要るか
- **承認を待つ。** 承認の際に、案と、評価で悪くなる点への了承を、利用者に確かめる
