## 結論（3 行）
1. **追加は不要。最推しは「何も足さない」**（`pi-goal` ＋ `pi-subagents` の workflow ループ）。fresh context が本当に要る場面が出たら、次点は `@rahulmutt/pi-ralph@0.4.0`（小さい・同じプロセス内で `ctx.newSession()`・拡張がそのまま載る）。`@lnilluv/pi-ralph-loop` は子プロセスに拡張が載らず、permission-system と cc-safety-net を迂回するので除外。
2. 入れる場合（rahulmutt）: `pi-stock-packages` に `npm:@rahulmutt/pi-ralph@0.4.0`。permission の追記は `/ralph` がコマンドで、新規ツールは無いので不要。`.ralph/` を `.gitignore`（または global ignore）へ。
3. workflow による Ralph ループの例は末尾「4(b)」。

### 候補ごとの理由
- **tmustier**: 作者の README が「same Pi session の次の turn。fresh context ではない」と明言。利用者の目的（文脈の肥大を避ける）に合わず、`pi-goal` と機能が重なる。除外。
- **lnilluv**: 機能は最も豊富（独立した acceptance 再実行・無進捗検出・ログ出力）で、設計は「Ralph は `/goal` と別の層」と整理していて目的に最も近い。しかし**子プロセスは既定で `--no-extensions`**で、導入の前提である permission-system と cc-safety-net が子に効かない（README「Ralph runs each iteration in a child `pi --mode rpc`…disables normal Pi extension discovery」）。さらに `commands:` を拡張自身が spawn する。自前 guardrails は regex 止まりで deny の網の代わりにならない。拡張を載せる設定（`loadExtensions`）は、モデルが拡張由来の場合の内部経路で、利用者が常時有効にする手段は README から確認できなかった（`src/index.ts:2039` に settings 由来の値があるが、設定名・書き方は未確認）。権限境界を動かす変更なので、本格導入するなら ADR・review が先。**除外**（将来、`loadExtensions` を設定で常時有効にできると確認できれば再評価）。
- **rahulmutt**: 目的の「新しい文脈で、同じプロンプトを繰り返す」を最小の部品で満たす。拡張が全部載るので安全機構を迂回しない。弱点は、完了検出・無進捗検出・予算が無い（固定回数だけ）こと、`.ralph/` が作業ツリーを汚すこと、保守が止まっていること。離席中は ask で止まりうる（これは他の案も同じ）。`/ralph` が `newSession` で親から分岐するため、反復の途中の挙動は実機の確認が要る。**保留（次点）**。

## 4. 「何も足さない」案（比較の基準。必ず評価）

### (a) `pi-goal` だけ
- 得るもの: 予算・応答数上限・無進捗停止つきで目標まで続く。維持費ゼロ（追加なし）。
- 失うもの: 文脈が伸びる（70 万で圧縮）。完了は同じエージェントの自己申告（`goal_complete`）で独立していない。
- 離席: permission の ask で止まる点は他案と同じ。

### (b) `pi-subagents` の workflow で「毎回新しい子を起こす」ループ
根拠（`workflows.md`）: workflow はスクリプトで、ループ（`for`/`while`）も書ける（「Scripts are ordinary JavaScript statement bodies」、行 80-92）。`runs.run(key, {agent, task})` が子を起こし、子は新しい文脈。上限は `options.timeoutMs`・`toolBudget`・`usageBudget`（行 164-190）。sandbox にはファイル・shell が無い（行 92）ので、**進捗はファイルに書かせる役を子に任せ、親スクリプトは子の出力（output）だけで終了を判定**する。子ごとに `subagent_launch` が permission-system に見える（行 150）ので、**ask を 1 度 allow にしておかないと、子ごとに止まる**（離席中の止まる点。`subagent_launch` は利用者の設定で ask）。children に permission-system が載るかは未確認（`agents.md` の「Foreground children do not load ambient parent extensions」と `extensions:` 設定の記述から、明示設定が要ると読めるが、背景の children の既定は未確認）。**ここが最大の未確認で、載らないなら lnilluv と同じ迂回の問題になる。** 子の `permissions:` frontmatter（watchdog.md 行 168〜）で非 bash のルールは書ける。

例（短い版。検証は未実施。`subagent({ workflow: true, async: true, options: {...} })` の script 本体。キーは反復ごとに一意）:

```js workflow
// 1 反復 = 新しい worker 1 つ。進捗は PROGRESS.md（作業ツリー外の .tmp/ 推奨）に子が書く
const max = args.maxIterations ?? 8;
let last = null;
for (let i = 1; i <= max; i += 1) {
  const work = await runs.run("work-" + i, {
    agent: "worker",
    task: [
      "PLAN.md の未完了の項目を 1 つ進める。進捗と次の一手は PROGRESS.md に追記する。",
      "コミットはしない。git の状態を変えない。",
      "最後の行に STATUS: CONTINUE か STATUS: DONE か STATUS: BLOCKED を書く。"
    ].join("\n")
  });
  // 独立した判定: 別の reviewer が DONE の主張を確かめる（自己申告だけにしない）
  if (/STATUS: DONE/.test(work.output)) {
    const check = await runs.run("verify-" + i, {
      agent: "reviewer",
      task: "PLAN.md の全項目が満たされ、検査コマンド（" + args.verify + "）が通るか確かめ、PASS か FAIL と理由を書く。"
    });
    if (/\bPASS\b/.test(check.output)) return { done: true, iterations: i };
    last = check.output;
  } else if (/STATUS: BLOCKED/.test(work.output)) {
    return { done: false, blocked: true, iterations: i, why: work.output.slice(-500) };
  }
}
return { done: false, iterations: max, lastCheck: last };
```

呼び出し側（親）: `options: { timeoutMs: 3600000, usageBudget: { tokens: { soft: 2000000, hard: 3000000 } }, toolBudget: {soft: 80, hard: 120} }`。止める手段: 親から workflow の stop（`subagent` の control）。無進捗の検出は書いていない（必要なら `PROGRESS.md` の更新有無を verify 側に判定させる）。

- 維持費: 自前のスクリプト 1 本（package 追加なし）。`pi-subagents` の更新で API が変わる可能性（0.87.0 に版固定済み）。
- 失うもの: 専用 UI（`/ralph-status` 相当）・ログ export は無い（`status.json` と receipt はある）。
- 注意: `worker` は git を触らない約束を task に書く（強制ではない）。worktree 内で回す前提。反復の間に作業ツリーが壊れても、次の子が壊れた状態を見て直す（劣化は検出されない）。

## 判断した点
- 「fresh context」を最優先の軸とし、tmustier はそれを満たさないので除外した。
- 「利用者の安全機構を迂回しない」を、機能の豊富さより優先した（lnilluv を除外）。
- 依頼文は Windows/WSL/Ubuntu 横断を求めるが、`pi` の拡張としては OS 依存を示すコードを確認していない（lnilluv は Windows の Git Bash の解決を含む）。
