# レビュー役サブエージェントへ渡すプロンプト

`code-review` サブエージェントは呼び出し側のコンテクストを引き継がない。
必要な情報はすべてプロンプトに書く。書き漏らすと、レビュー役は
「規約を知らない外部の人」として当たり前の指摘を返してくる。

## 雛形

```text
このリポジトリの <変更 | 指定範囲の現状> をレビューしてください。

## 対象
比較基準は <base>（初回に固定したコミット）です。

<差分レビューのとき（対象は変更そのもの）>
作業ツリーの現在の状態を、次のコマンドで確認してください
（コミットされていない修正を含みます）。
  <例: git diff <base> -- src/parser/>
未追跡の新規ファイル（差分に出ないので、内容を直接読んでください）:
  <例: git ls-files --others --exclude-standard -- src/parser/ の出力>

<現状レビューのとき（対象はパス・ファイル・機能・プロジェクト全体）>
次のファイルの現在の内容全体をレビューしてください。変更の有無は問いません。
  - <path>: <役割>
参考（レビュー対象ではなく、ループ中に何を直したかの履歴）:
  <例: git diff <base> -- src/parser/>

関係するファイル:
  - <path>: <役割>

## プロジェクト固有の規約
<AGENTS.md / CLAUDE.md から、この変更に関係する箇所だけを抜粋>

## 累積の指摘台帳
| ID | 指摘 | 状態 | 対応 |
| -- | ---- | ---- | ---- |
| 1-1 | <指摘内容> | 未解決（修正した） | <どう直したか> |
| 1-2 | <指摘内容> | 未解決（見送り） | <理由> |
| 1-3 | <指摘内容> | 誤検知 / リスク受容 | <理由> |

「修正した」「見送り」の項目は、現在の作業ツリーで実際に解消しているかを
確認し、解消していれば「解消を確認」と書いてください。未解消なら再掲してください。
誤検知・リスク受容の理由が妥当なら再掲は不要です。妥当でないと考える場合は、
理由への反論を添えて再掲してください。

## 出力形式
指摘ごとに次を書いてください。

- ID: R<N>-<連番>
- 重大度: BLOCKER / MAJOR / MINOR / NIT
- 位置: <ファイル>:<行>
- 内容: 何が問題か
- 根拠: なぜ問題か（再現手順・規約・仕様のどれか）
- 提案: どう直すか（任意）

台帳の各 ID について「解消を確認 / 未解消」を併記してください。
新規の指摘が無く、台帳の項目もすべて確認できた場合は「新規指摘なし」と書いてください。
```

## 重大度の目安

レビュー役に判断を丸投げすると重大度がぶれる。定義を毎回渡す。

| 重大度 | 目安 |
| --- | --- |
| BLOCKER | 実行時に壊れる / データを失う / 秘密が漏れる / 明確な脆弱性 |
| MAJOR | 仕様の取りこぼし、エッジケース、設計上の無理、テストの欠落 |
| MINOR | 可読性、命名、重複、コメントの不足 |
| NIT | 好みの範囲。スタイル、語順 |

## 渡してはいけないもの

- **自分の修正意図の説明**。「ここはこう直したので問題ないはず」と書くと、
  レビュー役がそれを前提に読んでしまい、独立した目線が失われる
- **前ラウンドで自分が下した重大度の判断**。指摘の内容と対応だけを渡す
- **秘密情報**。トークン・パスワード・鍵は差分からも除く

## ラウンド数が増えたとき

3 ラウンド目以降は、レビュー役に「収束しているか」も尋ねる。

```text
## 補足
これは R3 です。R1 では 5 件、R2 では 3 件の指摘がありました。
今回の指摘が R2 までと実質同じ内容なら、その旨を明記してください。
```

同じ指摘が返ってきたら、修正方針が間違っているか、レビュー役が
文脈を取り違えている。どちらかを切り分けてからループを続ける。
