# 全体設計の独立 review（2026-11）

別系統のモデルによる独立 review（2026-11-05）の記録。対象は、3 層モデル（pi・アプリ・人の統合）、実行経路、統合の人手、再現性。コードは実行せず、文書とソースの読み取りだけの review。

## 結論

1. 3 層モデルは説明として妥当だが、権限の境界ではない。「統合は人のボタンだから見込みの実装は安全」は言い過ぎ。
2. 当面は親 pi → worker を標準にし、ジョブ・起票・一体化への追加投資を止める。実行方式の全面統一は早い。
3. すべての統合を人が押す現状は合理的。`risk_paths` による自動統合を理想形とはしない。
4. 先に直すのは、公開前の秘密検出の切れ目・子の終了と成果の合格の混同・所有と停止確認の不統一・運用スクリプトの再現性。
5. 残す中心は「並列 worker・共通の検査・小さいレビュー画面・人の統合器」。未使用機能を育ててオーケストレーター製品にしない。

## 点ごとの評価

| 論点 | 評価 | 判断 |
| --- | --- | --- |
| 層の分け方 | 良い／要改善 | 機能の層と信頼境界は別の図にする |
| 実行経路の二重化 | 要改善 | 起動方式より、所有・成果判定・検査証拠を共通化する |
| 段階ゲート（自動統合） | 保留が妥当 | 現在の検査・権限・記録のままでは実現できない |
| 費用と便益 | 要改善 | 統合画面は実利用が支える。ジョブ・起票の便益は未立証 |
| 再現性・可搬性 | 要改善 | 共通ランチャー + 機械ごとの設定 + 任意の常駐定義 |
| 規約と強制 | 要改善 | 起動時の所有取得などは機械化。全操作への規約ゲートの復活は勧めない |
| 根本的な弱点 | 要改善 | 人の押下に品質保証を背負わせすぎ。公開前の検査が分離されていない |
| 理想形 | 縮小を推奨 | 使っている経路を整え、需要が実測されたものだけ足す |

## 採った対応

- 保証の文言の訂正: 統合前の変更は元に戻せる。ただし、作業領域（共有 `.git` は書き込める）・試験や hook の実行・ホストへの影響は統合の前に起こりうる。ガードは「うっかり防止」で、敵対的な迂回への防御は保証しない（[ガード総覧](../../spec/guard/index.md#目的と保証の範囲)）。
- 案件 CHG-0062 の段 B・C を「実運用の結果で再判断」に変更。
- X3-a の食い違いの訂正（実測済み・実運用の利用は未）と、レビュー記録の ref の保存の注意（[PR ビューア仕様](../../spec/pr-viewer.md)）。
- 別の feature で実施中: 公開前の秘密検出（pre-push に gitleaks）、ジョブの停止確認の fail closed と lock の残骸の自動引き継ぎ廃止、子の終了を合格としない（ToDo を done にせず確認待ち）。

## 保留（利用者の決定待ち。既定は現状維持）

- ジョブ・起票・「送ると同時にジョブ」の一体化の扱い（追加開発の停止か、撤去か、限定使用で測るか）。
- ビューアの稼働版の固定（配備物から起動し、作業ツリーの変更と切り離す）。

## 採らなかった提案

- すべての統合の自動化。`risk_paths` は確認画面に印を付けるためのもので、一致しない変更が低リスクとは定義されていない。将来は shadow mode（判定だけ記録し、人の判断との食い違いを測る）を経る。
