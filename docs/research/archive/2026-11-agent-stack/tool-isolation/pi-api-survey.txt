## 結論

実現可能。公式の API は 7 ツールすべてに `operations` を用意している。ただし grep は `operations` で検索エンジン自体を差し替えられないので、自作の `execute` が要る（gondolin もそうしている）。

難所は次の 4 つ。

1. grep の自作
2. bash の中断と、箱の中の子プロセスの後始末
3. `tool_call` を通らない `!` コマンド（`user_bash`）の経路
4. 自作の `guarded_*` ツールはホストで動くこと

## 事実

**1. 差し替えの仕組み**

`create*Tool(cwd, { operations })` に渡す。型は `types/*.d.ts` にある。

| ツール | operations の型 | 行 |
|---|---|---|
| bash | `exec(command, cwd, {onData(Buffer), signal?, timeout?(秒), env?}) → {exitCode: number\|null}` | `bash.d.ts:35-48` |
| read | `readFile(abs) → Buffer`、`access(abs)`（読めなければ throw）、任意の `detectImageMimeType(abs)` | `read.d.ts:36-42` |
| write | `writeFile(abs, content: string)`、`mkdir(dir)` | `write.d.ts:17-21` |
| edit | `readFile`、`writeFile(string)`、`access` | `edit.d.ts:29-35` |
| ls | `exists`、`stat → {isDirectory()}`、`readdir → string[]` | `ls.d.ts:22-32` |
| find | `exists`、`glob(pattern, cwd, {ignore, limit}) → string[]`（相対でも絶対でも可） | `find.d.ts:26-34` |
| grep | `isDirectory`、`readFile → string`（コンテキスト行用）のみ | `grep.d.ts:28-33` |

- bash の注意点: シグナルで終了したときは 128+n で返す。`null` は失敗扱い（`bash.d.ts:41-42`）。
- write と edit は文字列を受け取るので、書き込みはテキストのみ。read は Buffer を返す。
- grep の `GrepToolOptions` には「Default: local filesystem plus ripgrep」とある（`grep.d.ts:35`）。`operations` では検索の実行先を変えられない。
- `user_bash`: `!` と `!!` はこのイベントで受ける。戻り値は `{operations}` か `{result}`（`extensions.md:1078-1106`）。`tool_call` は通らない。
- `user_bash` が受け取る `env` と `cwd` の仕様は文書にない（未確認）。

**2. ssh.ts**

- 差し替えるのは read、write、edit、bash の 4 つだけ（`ssh.ts:128,142,156,170`）。grep、find、ls は差し替えず、ホスト実行のまま。
- 実行時にその都度 `create*Tool(localCwd, {operations})` を作る（`:133`）。
- パスの変換は `p.replace(localCwd, remoteCwd)`（`:48,65,82`）。先頭を固定しない単純な置換。
- シェルへの渡し方は `JSON.stringify` でクオートした文字列連結（`:50,86`）。シェルに対しては安全でない。
- bash は `cd <cwd> && <command>` を ssh に渡す。stdin は `ignore`、pty なし、stdout と stderr は混ぜて `onData` に流す（`:86-87,96-97`）。
- 環境変数は `env` を受け取らない（`:84`）。リモートの環境がそのまま使われる。
- タイムアウトは `setTimeout` で `child.kill()`。中断は `signal` の abort で `child.kill()`（`:89-93,101-102`）。killされるのはローカルの ssh だけ。
- エラーは `Error("aborted")` と `Error("timeout:N")` を reject する（`:106-107`）。終了コードは `code` をそのまま返すので、シグナル終了では `null` になりうる（`:108`）。
- 読み出しは `cat` で全量を Buffer に載せる。上限なし（`:50`）。
- 書き込みは base64 を argv に載せる（`:68-69`）。引数長の上限で、大きいファイルは書けない。
- 画像判定はリモートの `file --mime-type`（`:54`）。
- `user_bash`（`:203-206`）と `before_agent_start`（`:210-216`）で、システムプロンプトの cwd 行をリモートのパスに書き換える。

**3. gondolin**

- ホストの cwd を `/workspace` に `RealFSProvider` でマウントする（`index.ts:385`）。書き込みはホストに反映される（`:3-5`）。
- 7 ツールすべてを差し替える（`:443-514`）。ファイル系はシェルを使わず `vm.fs` を使う（`:86-134`）。
- ツールは guest の cwd で作る（`:447`）。`toGuestPath` はホスト側のパスを guest のパスに変換し、外のパスはそのまま通す（`:74-80`）。
- find は `walkGuestFiles` による JS の自前走査。`.git` と `node_modules` を除外し（`:151`）、`options.ignore` は使わない（`:192-204`）。
- grep は `operations` を使わず `execute` ごと自作（`:239-313,509-514`）。結果の形は `GrepToolDetails` に合わせている。
- 画像判定は拡張子だけ（`:90-97`）。
- bash は `vm.exec([shell,"-lc",command], {cwd, env, signal})`（`:343-345`）で、argv を配列で渡す。timeout と abort は `AbortController` で扱う（`:328-358`）。
- 環境変数は `sanitizeEnv` が文字列でない値を落とすだけ（`:315-322`）。`env` はそのまま渡る。文書の「host process environment を継承」（`containerization.md:157`）の根拠はこの `:345`。
- `env` に何が入っているかは、文書の記述に基づく（`extensions.md:2421-2425`）。bash.ts の実装は資料に無く、未確認。

**4. 差し替えのレベルと順序**

- 同名で `registerTool` すると、組み込みを警告なしで置き換える（`extensions.md:2344`）。
- `operations` は、置き換えた `execute` の中で差し込む（`ssh.ts:128-141`）。
- 順序は `tool_call`（拒否・入力の書き換え）が先で、そのあとに `execute`（`operations`）、最後に `tool_result` の順（`extensions.md:362-367,973`）。拒否された呼び出しは実行されない。
- `tool_call` が見るのはモデルが渡した入力で、`operations` に届く前のもの。変換後のパスではない。
- `ctx.executeTool` による入れ子の呼び出しも `tool_call` を通る（`:2774`）。
- `user_bash` は別経路。ハンドラは拡張の読み込み順に動き、最初に `operations` か `result` を返したものが勝って、以降には伝わらない（`:414,1106`）。
- 拡張が登録した別ツールはホストで動く。委譲するかどうかは各ツールの作り次第（`containerization.md:16,26,183`）。
- 置き換えたツールは `details` の形を保つこと（`extensions.md:2363`）。`promptSnippet` と `promptGuidelines` は継承されない（`:2361`）。`create*ToolDefinition()` の使用が勧められている（`:2401`）。

**5. 公式が述べる限界**

- ホストの pi 本体と、隔離を使わない拡張ツールは制約されない（`containerization.md:26,16`）。
- 環境変数は箱の中に見える。そのため認証の境界としては使えない（`:157`）。
- 書き込み可能なマウントはホストを書き換える（`:21`）。`~/.pi/agent` をマウントすると認証・設定・セッションが露出する（`:22`）。
- 環境変数のほかに、`PI_SESSION_FILE` などのセッション情報がコマンドに渡る。`exposeSessionEnvironment: false` で止められる（`extensions.md:2421-2425`）。

**6. 私たちの実行先（kcage exec）への見立てと落とし穴**

- 子プロセスは argv 配列で起こし、シェル文字列は連結しない。改行やクオートの問題が消える（ssh.ts は連結で脆い）。
- cwd は、固定の小さな `sh -c 'cd "$1" && exec bash -c "$2"' sh <cwd> <cmd>` のように位置引数で渡す。
- ホストと箱でプロジェクトのパスを同一にできれば、変換が不要になる。変換が要るなら、先頭を固定した前置きの付け替えにする。システムプロンプトの cwd 行も合わせる。
- ファイルの read と write は、stdin/stdout で `cat` を使えば、バイナリも改行もそのまま通せる。ssh.ts の base64 を argv に載せる方式は不要で、引数長の上限も避けられる。write は一時ファイルに書いて `mv` すると安全。
- 環境変数は `env` を無視して渡さない。`PI_*` も箱には出さない。
- 長時間のコマンドは timeout と abort で、ローカルの `kcage exec` プロセスを kill する。箱の中の子プロセスまで止まるかは要実測。ssh.ts と同じく、止まらない恐れがある。
- pty が無いので、対話的なコマンドは動かない。
