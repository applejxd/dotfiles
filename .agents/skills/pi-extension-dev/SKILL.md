# pi-extension-dev

pi の機能を足す・変えるときは、**既存の拡張・設定の評価が先で、自作は最後の手段**（[ADR-0031](../../../docs/adr/0031-evaluate-existing-extensions-first.md)。
旧 [ADR-0016](../../../docs/adr/0016-pi-extensions-own-first.md)「自作を基本」を置き換えた）。
このスキルは、足す・直すときの**進め方と調べ方**だけを持つ。仕組みの正本は `docs/` にある。

## 原則

1. **作る前に探す。** 順序は、① pi 本体の標準機能・設定 → ② すでに入れている package の設定・機能 → ③ 公開の package を探して評価・導入 → ④ skill + CLI / MCP（既製のサーバを含む）→ ⑤ 自作。**探した記録なしに自作を提案しない**
2. **pi 本体の理解が先。** 作る前も直す前も、入れている版に合う一次の情報（文書・型定義・ソース）で確かめる。思い込みで作らない
3. **導入は評価して、固定して、囲う。** 保守・利用実績・権限の範囲を評価し、版を固定し（`npm:<名前>@<版>`）、permission の方針と一緒に入れ、初回は使い捨ての場所で試す
4. **自作は例外。** ①〜④で満たせない理由・維持費の見込みと撤去条件を記録し、最小にし（薄く、公式の拡張点で、package の形）、**利用者が明示的に承認**したときだけ
5. **提案には「作らない案」を必ず含める。** 「堅牢に作るには」と聞かれても、使用頻度と維持費を評価に入れ、例外を網羅する設計へ進まない（AI は進みやすい。[ADR-0031](../../../docs/adr/0031-evaluate-existing-extensions-first.md)）
6. **事実と推測を分ける。** 実機でしか分からないもの（TUI・実際のモデル・Windows）は、未確認と書く
7. **正本は `docs/`。** 知見は `docs/` へ記録し、修理で見つけた型だけをこのスキルへ戻す
8. **自作したときは、試験で固定する。** skip は通過ではない。skip 件数を必ず報告する

## 呼び出し

このスキルは作業先の `.agents/skills` から読まれる。明示して呼ぶなら `/skill:pi-extension-dev`。作業中に編集したら `/reload` で反映する。

## 全体の流れ

```text
段 0 pi 本体を理解する（共通・最初）
   ├─ 足す・変える: 段 1 要望 → 段 2 探して評価（順序 ①〜④）→ 足りる → 段 3 導入
   │                                                        └ 足りない → 段 4 提案（承認待ち）→ 段 5 自作（最小）
   └─ 直す:        修理の進め方（切り分け → 検索 → 再現 → 原因 → 修理）
   （仕様を調べるだけの依頼は、段 0 で報告して終わる）
終わるとき（共通）: 記録 → 還流
```

各段で、次へ進む前に結果を短く報告する。

## 段 0. pi 本体を理解する（共通）

[pi 本体の仕様を当たる方法](references/pi-spec-guide.md)に沿って、これから触る機能に関する**仕様を先に読む**。
順序は、版の確認 → 文書 → 型定義 → ソース → 同梱の例 → 変更履歴 → 上流の Issue → 実測。
話題から読む文書を選ぶ索引がある。公式に明示がある項目・無い項目の棚卸しは [pi-upstream.md](../../../docs/spec/pi-upstream.md) が正本で、
頼ろうとする挙動がそこに載っているかを先に見る。表の**該当する行の「確認した版」**を、入れている版と照合する（違うなら、インストール済みの文書・実装・試験で確かめ直す）。

**調べるだけの依頼**（「pi の仕様を調べて」）は、この段で終えてよい。確かめたこと・出典・未確認の点を報告し、段 1 以降や修理、ファイルの編集には進まない。

## 足すか、直すか

- **足す・変える**: 下の「進め方」の段 1〜5。
- **不具合を直す**: [修理の進め方](references/repair-guide.md)を読む（症状の切り分け → 先に広く検索 → 再現 → 原因の確定 → 修理）。
  stock の pi では、まず該当の package の Issue・更新・設定を確かめ、直せなければ版の変更・入れ替え・外すことを選択肢にする。
- 足すか直すか分からないとき（「この機能をこうしたい」と「これが動かない」が混ざっている）は、先に修理を済ませ、その後に機能を足す。

## 進め方（足す・変える）

**段 4 は利用者の承認を待つ**（承認なしに自作へ進まない。導入も、権限や挙動が変わるなら承認を取る）。

### 1. 要望を整理する

目的・使う場面・成功条件・やらないことを 1 つずつ書き出す。曖昧なら利用者に確認する。

### 2. 探して評価する

[既存の拡張の探し方と評価](references/public-research.md)の順序（①〜④）で、ハブを上から順に全部当たる（1 回の検索で済ませない）。
候補は評価の観点（保守・利用実績・権限の範囲・相性）で比べ、出典 URL・日付を付けて記録する。見つからなかったときも、探した先と語を報告する。
取得は**実行しない形**（読むだけ。`npm pack` の展開など）で行い、導入を決めるまで `install` はしない。

結論は 3 つのどれか。**足りる**（導入または設定）→ 段 3。**skill + CLI / MCP で足りる** → 段 4（その案）。**どれでも足りない** → 段 4（自作を含む案）。

### 3. 導入する

[導入するときの手順](references/public-research.md#導入するときの手順段-3)に沿う: 版固定で `pi-stock-packages` に 1 行 → permission の方針 → 初回の試用 → docs の記録 → 実機確認の項目を渡す。
権限の範囲が広い・第三者へデータが出る package は、導入の前に提案（段 4）で承認を取る。

### 4. 利用者へ提案する（承認を待つ）

[提案のひな形](references/proposal-template.md)に沿って、1 回にまとめて出し、**承認を待つ**。ひな形は、この段に入ったときに読む。

- 要望の整理（段 1）と、探した結果（段 2）
- **案 A: 既存を導入 / 案 B: 設定・スキル・MCP で代替 / 案 C: 自作（最小）** と、案ごとの維持費・撤去のやり方。**A・B で足りるなら C は出さない**
- 推奨とその理由、**利用者の操作の変化の評価**（良くなる点と悪くなる点）
- 供給網のリスク（導入する package は読み込み時に任意のコードを実行できる）と、その対策（版固定・権限・初回の試用）

### 5. 自作する（最小。例外）

[ADR-0031](../../../docs/adr/0031-evaluate-existing-extensions-first.md) の自作の条件（a〜d）を、着手前にもう一度確かめる。

- **最小にする**: 薄く、公式の拡張点で、pi の内部の挙動に頼らない。形は pi の package（公式 `docs/packages.md`。ローカルパスから読ませられる）
- **置き場と配備の細部は未決**（最初の自作のときに決め、`docs/spec/agent-config-generation.md` の「pi のプロファイル」へ書く。stock は自作の拡張ディレクトリを配らない）
- 試験は、公式の拡張点の範囲で自動化できるものを書く。skip は通過ではない。TUI の表示など自動で確かめられないものは、未確認として実機確認の項目へ足す
- ADR-0031 の「例外として残す自作の一覧」へ、理由・維持費の見込み・撤去の条件を足す
- 凍結した自作ハーネス（custom プロファイル）の拡張を触るときは [custom-harness.md](references/custom-harness.md)

## 終わるとき（共通）

1. **記録する。** 導入したら [stock の package の評価](../../../docs/research/agents/pi-stock-packages-evaluation-2026-11.md)（版・評価・決定）と `pi-stock-packages`。
   公式に明示が無い挙動を実測したら `pi-upstream.md` の表 B へ（原則は試験で固定。自動試験が組めないときは、再現の条件・手動で見た結果・未確認の範囲を残す）。自作したら ADR-0031 の例外の一覧
2. **還流する。** 修理で、既知のパターンに無い型を見つけたら、[修理の進め方](references/repair-guide.md)の表へ 1 行足す。
   このスキルの手順が実際と食い違っていたら、その場で直す（`skill-creator` の手順で）
3. **利用者へ伝える。** `chezmoi apply` が要るか、実機で確かめてほしい点、未確認として残る点
