# review-loop

レビューと修正を分業させ、**未解決の BLOCKER・MAJOR が無くなるか、それ以上良くならなくなるまで**
反復する（収束の定義は `references/convergence.md`、終了条件は手順 4）。レビューは毎回サブエージェントに任せ、修正は本エージェントが行う。

役割を分ける理由は、同じコンテクストで自作自演のレビューをすると
「直したつもり」を追認してしまうため。サブエージェントは対象の材料（差分または現在の内容）と前ラウンドの
指摘だけを渡された状態で読むので、思い込みが引き継がれない。

> **この skill は fork しない（`context: fork` を付けない）**
>
> この skill 自身がレビュー役のサブエージェントを起動するため、
> fork するとサブエージェントの入れ子になる。Claude Code は v2.1.172 より前で
> 入れ子を禁止しており、それ以降も既定は無効なので、レビュー役の起動が黙って
> 失敗して自作自演レビューに退化する。メインの会話で走らせること。

## 使わない場面

| 状況 | 代わりに使うもの |
| --- | --- |
| linter の機械的な指摘を直したいだけ | `fix` skill |
| 指摘一覧が欲しいだけ（修正は不要） | レビュー役のサブエージェント単体 |
| 脆弱性を探したい | Copilot CLI は `security-review` サブエージェント、Claude Code は `/security-review` コマンド、OpenCode は `review` に観点を指定して渡す |

## レビュー役のサブエージェント

CLI によって使える子が違う。

| CLI | レビュー役 | 差分の取り方 |
| --- | --- | --- |
| Copilot CLI | `code-review`（組み込み） | レビュー役に `git diff` などを実行させてよい |
| Claude Code | 組み込みに無い。`code-review` を定義していればそれを、無ければ `general-purpose` に「編集せず指摘だけを返す」と指示して使う | 同上 |
| OpenCode | `review` | `review` は shell を使えない（読むだけ）。差分・未追跡ファイルの一覧は親が実行し、出力を依頼文に貼る |

OpenCode に `code-review` / `security-review` は無い。作業先のリポジトリが同じ名前の子を
定義していても、`bypass` からは起動できない（起動できる子は許可リストで決まっている）。
テスト / lint の実行（手順 3-4）は、どの CLI でも本エージェントが行う。

## 手順

### 1. スコープと収束条件を決める

ユーザ指定が無ければこの順で対象を決め、**最初に見つかったもの**を使う。

1. ユーザが挙げたパス・ファイル・機能名・プロジェクト全体 → **現状レビュー**
2. `git diff` / `git diff --staged` に出る変更 → **差分レビュー**
3. 作業ブランチが既定ブランチと異なるとき、その分岐点からの変更 → **差分レビュー**

2 種類のレビューを区別する。

| 種別 | レビュー対象 | 毎ラウンドの材料 |
| --- | --- | --- |
| 差分レビュー | 変更そのもの | `git diff <base>` ＋ 対象内の未追跡ファイル |
| 現状レビュー | 指定範囲の現在の内容（変更の有無を問わない） | 対象ファイルの現在の内容（未追跡も含む）。`git diff <base>` は修正の履歴として補助的に渡す |

**比較基準 `<base>` を初回に 1 つ固定する**。ループ中は変えない。決め方は選択肢ごとに次のとおり。

- 1（現状レビュー）: 開始時点の `HEAD`。レビュー対象の範囲は `<base>` に依存しない。
  `<base>` はループ中の修正だけを示す履歴として使う
- 2（差分レビュー）: `HEAD`（staged / unstaged をまとめて `git diff HEAD` で見る）
- 3（差分レビュー）: `git merge-base <既定ブランチ> HEAD` のコミット

差分は `git diff <base>`（作業ツリーとの比較。未コミットの修正を含む）で取る。
`git diff <base>...HEAD` は未コミットの修正を含まないので使わない。
`git diff` だけでは未追跡の新規ファイルが出ないので、
`git ls-files --others --exclude-standard` で拾って内容を渡す。

現状レビューの対象ファイルは、パス・ファイルならそのまま、機能名なら `grep` 等で
関係ファイルを洗い出して宣言に列挙する。

対象が広すぎる（差分レビューで変更 50 ファイル超、または全体レビュー指定）ときは、
ディレクトリ単位・レイヤ単位に分割し、**分割した単位ごとにループを回す**。
1 ラウンドでレビュー役に渡す量は差分レビューなら差分、現状レビューなら対象ファイルの
内容で、概ね 1500 行までに抑える。

決めた内容を宣言してから始める。

```text
対象: <パス群> （差分レビュー | 現状レビュー、比較基準 <base>）
収束条件: references/convergence.md の定義どおり
上限: 5 ラウンド
```

### 2. 作業ディレクトリを用意する

ラウンドごとの記録を残す。前ラウンドの指摘を次ラウンドへ渡すために必要。
累積の指摘台帳は `ledger.md` に置く。

**実行ごとに専用のディレクトリを作る。** 使い回すと、前回の実行で残った
ラウンド記録を「前ラウンドの指摘」として読み込んでしまい、停滞判定が壊れる。

```bash
RUN_ID="$(date +%Y%m%d-%H%M%S)"
mkdir -p "./.tmp/review-loop/${RUN_ID}"
```

`./.tmp/` は使い捨ての置き場で、削除に承認は要らない（`redirect-tmp.py` が
`/tmp` の代わりに誘導する先）。ここに置いた記録は成果物ではないので、
最終レポートは会話に出す。

### 3. ラウンドを回す

各ラウンドで次を順に行う。

#### 3-1. レビュー（サブエージェント）

レビュー役のサブエージェント（「レビュー役のサブエージェント」の表）を起動する。**前ラウンドの指摘を必ず渡す**。
渡さないと、直したはずの指摘が再掲されて「収束していない」と誤判定する。

プロンプトに含めるもの:

- 対象のパスと、比較基準 `<base>`（手順 1 で固定）
  - 差分レビュー: 作業ツリーとの差分 `git diff <base> -- <パス>` と、対象内の未追跡ファイル
    （`git ls-files --others --exclude-standard -- <パス>`）の内容をレビューさせる
  - 現状レビュー: 対象ファイルの現在の内容全体をレビューさせる（変更が無いファイルも含む）。
    `git diff <base> -- <パス>` は「ループ中に何を直したか」の履歴として補助的に添える
- プロジェクト固有の規約（`AGENTS.md` / `CLAUDE.md` の該当箇所）
- 累積の指摘台帳（`ledger.md`）。各指摘の状態と、修正・見送りの内容
- 出力形式（次節の表）

誤検知・リスク受容の理由が妥当ならレビュー役は再掲しなくてよい。
一方、「修正した」「見送った」指摘は、作業ツリーで実際に解消したかを
レビュー役に確認させる（再掲されないことを解消の根拠にしない）。

#### 3-2. 指摘の分類

レビュー結果を重大度で分類し、
`./.tmp/review-loop/<run-id>/round-<N>.md` に残す。

| 重大度 | 意味 | 扱い |
| --- | --- | --- |
| BLOCKER | 壊れている・データを失う・脆弱 | 必ず直す |
| MAJOR | 仕様やエッジケースの取りこぼし、設計上の無理 | 直す。無理なら理由を記録し、未解決に残す |
| MINOR | 可読性・命名・重複 | 安全なら直す |
| NIT | 好みの範囲 | 直さない。記録だけ |

#### 3-3. 修正

BLOCKER → MAJOR → MINOR の順に直す。
1 ラウンドで直すのは**1 つの関心事まで**にする。無関係な改善を混ぜると、
次のラウンドで何が効いたか分からなくなる。

直さない判断をしたら、指摘 ID と理由を `round-<N>.md` に書き、台帳の状態を更新する。
ただの見送りは「未解決」のままで、収束判定では数える。「誤検知」「リスク受容」に
できるのは根拠と理由を記録したものだけ（リスク受容の BLOCKER・MAJOR はユーザの承認を得る）。
修正した指摘も、次のレビューで確認されるまでは「修正確認済み」にしない。

#### 3-4. 検証

リポジトリで定義されているテスト / lint / ビルドのうち、
**変更範囲をカバーする最小のもの**を実行する。
結果（コマンドと要約）を `round-<N>.md` に残す。

検証が落ちたらそのラウンド内で直す。直せなければループを止めて報告する。

### 4. 終了条件

次のいずれかに当たったら止める。**どれで止まったかを必ず報告する**。

| 条件 | 判定 |
| --- | --- |
| 収束 | `references/convergence.md` の「収束したと言える形」を満たす（正本。累積の未解決 BLOCKER・MAJOR がゼロ、最後の編集後の独立レビュー済み、など） |
| リスク受容で終了 | 未解決の BLOCKER・MAJOR が無いが、リスク受容にした BLOCKER・MAJOR が残る。「収束」とは呼ばない |
| 上限到達 | 5 ラウンド（ユーザ指定があればその値） |
| 停滞 | 2 ラウンド連続で、指摘の内容が実質同じ |
| 検証失敗 | テスト / lint が落ち、そのラウンドで直せない |
| 判断待ち | 設計方針の選択が必要で、勝手に決めると手戻りする |

**停滞の判定**は指摘の件数ではなく中身で行う。
件数が減っていても、同じ箇所に同じ趣旨の指摘が続いているなら停滞とみなす。
停滞したらループを続けず、対立点を整理して報告する
（レビュー役の指摘が的外れなのか、修正方針が間違っているのか）。

自動承認モード（autopilot）で走っている場合も、
**「判断待ち」で止まったら勝手に決めずに報告する**。

### 5. レポート

```text
## review-loop 実行結果

### 対象
<パス / 差分の指定>

### 終了理由
<収束 | リスク受容で終了 | 上限到達 | 停滞 | 検証失敗 | 判断待ち>（<N> ラウンド）

### ラウンドごとの推移
| R | BLOCKER | MAJOR | MINOR | 主な対応 |
| - | ------- | ----- | ----- | -------- |
| 1 | 2       | 3     | 4     | ...      |

### 修正した内容
- <ファイル:行> <指摘>: <対応>

### 未解決・見送り・リスク受容の指摘
- <ファイル:行> <指摘>（状態: 未解決 | リスク受容 | 誤検知、理由: ...）

### 検証
- <コマンド>: <結果>

### 残課題
- <判断が必要なもの / 次にやるべきこと>
```

詳細は `references/review-prompt.md`（レビュー役へ渡すプロンプトの雛形）と
`references/convergence.md`（停滞の見分け方）を参照する。

## 制約

- **レビューと修正を同一コンテクストで兼ねない**。レビューは必ずサブエージェント
- **1 ラウンド 1 関心事**。無関係な改善を混ぜない
- **前ラウンドの指摘を必ず引き継ぐ**。引き継がないと収束判定が壊れる
- **コミットしない**。コミットはユーザの承認事項なので、ループの外で行う。
  だから比較基準は初回に固定したコミットのままで、差分は各ラウンドで作業ツリーと比べる
  （現状レビューは差分ではなく現在の内容を読ませる）
- **検証を省かない**。「直したはず」ではなく実行結果を根拠にする
