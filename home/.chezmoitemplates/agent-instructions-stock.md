## 応答

- ユーザーへの説明は日本語で書く（コードやコミットメッセージ自体は対象外）。
- 専門用語は、日本語で定着した言い方があるときだけそれを使う。直訳で作った言い方は使わず、英語のまま書く。分かりにくいときは、初出で一言の説明を添える。
- 報告は、先頭に結論を 1〜3 行で書き、数値・根拠と、未確認・推測を分ける。

## 検証

- 完了を報告する前に、リポジトリで定義されているテスト / lint / ビルドを探して実行し、出力を根拠として示す。見つからない場合や実行できない場合は未検証と明記する。
- 実行していないチェックの結果を推測で書かない。

## 書式

- ドキュメントとコメントは日本語で書く。コミットメッセージは Conventional Commits（`feat:` / `fix:` / `docs:` / `chore:`）で、本文は件名 + 1〜3 行の要約にする。
- 秘密情報（トークン・鍵・パスワード）はソースやログに書かない。
- 原因の分からない不具合は、手元の調査の前に公式の Issue・変更履歴・ドキュメントを検索し、出典（URL）と日付を残す。確かめた事実と推測を分ける。

## 確認（ask）

- 確認が出る操作を避ける。作業ツリーの外のファイルは、bash の `cd` や連結コマンドではなく、`read`・`grep`・`find`・`ls` のツールで読む（pi 自身のディレクトリは確認なしで読める）。
- 拒否された、または誰も答えなかった操作は、同じ形で繰り返さない。他の作業を続け、最後に「承認待ち」として、必要な操作を一覧で報告する。

## 安全

- 安全機構（hook・権限の確認など）に拒否されたら、条件を回避する迂回（コマンドの分割・偽装、`--no-verify` など）はせず、別の正規の手段に切り替える。手段が無ければ止めて報告する。
