# 案件テンプレート

`docs/change/NNNN-kebab-case.md` の雛形。下のコードブロックの中身を写して使う。

- **目的ができた時点で作ってよい。** 実装の合意を待たない
- **実装前の期待動作（受入条件）を先に書く。** 実装後の説明にすると、
  結果を後から仕様として正当化する運用になり「仕様駆動」でなくなる
- `## 現在地` と `## 候補比較` を**現在の理解へ更新し続ける**。
  過去の観測は `research/` 側が持つので、ここでは上書きしてよい
- **未検証を不合格扱いせず、期待を確認済み扱いしない**

## 節の順序

**この順序を崩さない。** 読み手は上から読むので、読む頻度の高い順に並べる。

| ブロック | 節 | いつ読むか |
| --- | --- | --- |
| **いま** | 目的と非目的 → 実施計画 → 現在地 → 未解決点 → 次の調査・実験 | 毎回 |
| **判断** | 評価基準 → 候補比較 → 仕様への変更案 → 実装・検証 | 方針を疑うとき |
| **経緯** | 重要な更新 → 終了結果 | 遡るとき |

**`## 実施計画` を上の方に置くのは、そこが段ラベルの定義表でもあるため。**
`A1` `段 2` のようなラベルを本文で使うなら、**必ず計画表より後に書く**。
先に出てくると読み手は何の話か分からない（実例: CHG-0006 は計画表が
8 番目にあり、それ以前の節が `段 1.5` を説明なしに使っていた）。

案件固有の節（`### 軸について` など）を足すときは、**どのブロックに属するかで
位置を決める**。末尾に付け足さない。

## 上から読んで分かるように書く

**前方参照を作らない。** 最後まで読んで初めて前半が分かる形にしない。

- **使う前に定義する。** 段ラベル（`A1` / `段 2` / `4a`）は計画表より後で使う
- **独自の呼称・略号は初出で 1 行説明する。** `verify` ツール / `ocs` /
  `規則 3` / `B5` のような、他文書やこの案件の内部でしか通じない語が対象。
  リンクを張るだけでは足りない（読み手は飛ばずに読み進める）
- **「下記」「後述」で先送りしない。** どうしても先に触れるなら、
  **その場に 1 行の要約を添える**
  - 悪い: `| 4a | 少数の静的 allow | 見送り（下記） |`
  - 良い: `| 4a | 少数の静的 allow | 見送り（候補がほぼ全部、任意コード実行の経路だった） |`
- **参照は節名で書く。`上記` / `下記` を単独で使わない。**
  節を並べ替えると向きが黙って逆になる（実例: 2026-09-25 の並べ替えで
  CHG-0006 の「下記『まだ分からないこと』」が上を指すようになった）。
  `「現在地」の「まだ分からないこと」` のように名前で指せば壊れない
- **見出しの補足と計画表の状態を食い違わせない。**
  （実例: CHG-0002 は計画表が「完了」、見出しが「（着手中）」だった）
- **表の「理由」欄を参照で埋めない。** 表は一覧性のためにあるので、
  そこで飛ばされると一覧にならない
- **各段は「解決したいこと」から書く。** 名前と手段だけ書くと、
  読み手は「なぜこれが要るのか」を自力で再構成することになる

同じ語を言い換えない（`guide 規則` と `誘導規則` を混在させない）。
言い換えは読み手に「別物か？」と考えさせる。

- **状態**: Exploring
- **更新日**: YYYY-MM-DD
- **基準**: <比較の基準となる版・コミット・環境>

| 段 | 内容 | 状態 |
