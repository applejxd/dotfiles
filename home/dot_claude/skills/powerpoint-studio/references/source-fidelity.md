# Source Fidelity and Citation Rules

## Source ledger

原典を基にする資料では、スライドごとに次を記録する。

| Field | Meaning |
| --- | --- |
| claim | スライドが主張すること |
| source | URL、ファイル、該当見出し、可能なら行番号・ページ |
| support | direct / derived / illustrative / opinion |
| transformation | 要約、翻訳、再描画、集計など |
| caveat | 原典が示していないこと |

- `direct`: 原典が明示している。
- `derived`: 原典の値から計算・整理した。式や前提を残す。
- `illustrative`: 説明用の例。実測や原典の主張に見せない。
- `opinion`: 提案・解釈。引用や事実と視覚的に分ける。

コード識別子、状態名、制御フロー、API 名を等幅で見せる場合は原典の実装と一致させる。
簡略化する場合は「概念図」と明記し、実装名のように見せない。
日本語化するときは、コード識別子とその説明を分ける。`budget`等の訳語は
実装の単位・制限対象から選び、`fallback`が何をするかも原コードで確認する。
表示用の和訳と、原典のsection名・参照IDは別に管理する。詳細は
`japanese-wording.md` を参照する。

## Review decks must preserve source flow

原典のレビュー、輪読、教材紹介が目的の場合、一般論へ抽象化しすぎると、
内容が正しくても「何をレビューしているのか」が失われる。

`deck-plan.json` の `meta.source_review.enabled` を有効にし、次を定義する。

- `review_label`: 「2教材の実装順レビュー」のような資料の立場
- `works`: 原典ごとのID、タイトル、順序付きsections、最低レビュー枚数
- `omissions`: 扱わないsectionと、時間・対象読者・重複などの具体的理由
- `minimum_direct_slide_ratio`: 本文のうち原典へ直接対応するページの最低比率
- `max_sections_per_slide`: 一枚へ束ねる原典section数の上限

原典を扱う各ページには次を持たせる。

- `source_sections`: 原典IDとsection名
- `review_lens.builds`: そのsectionで実際に何を作るか
- `review_lens.why_next`: なぜ次のsectionへ進むか
- `review_lens.takeaway`: このsectionから持ち帰ること
- `review_lens.caveat`: 教材固有条件、未実装、適用限界

### Good compression

- 連続するsectionを、原典自身の共通テーマで3〜5個に束ねる。
- section名、技法名、入出力、構築順を残す。
- 「原典が何をしたか」と「発表者の一般化」を視覚的に分ける。
- ページ上部やフッターで現在の原典とsection範囲を示す。

### Over-summary

- 18パートを「検索を改善する」の一文だけへ変える。
- ツール、prompt、state、graph構築を「Agenticな制御」とだけ呼ぶ。
- 原典の順序を消し、発表者の理想アーキテクチャ順へ全面的に並べ替える。
- 具体的な実装や教材固有の工夫を落とし、汎用チェックリストだけを残す。

時間内に扱えない場合は黙って消さない。目次またはcoverage mapで全体を示し、
省略部分と理由を明記する。網羅性より、選択が追跡可能であることを優先する。

## Verbatim quotations

- 引用符内は原文と完全一致させる。要約・意訳を引用符で囲まない。
- 著者またはプロジェクト、文書名、URL、該当箇所を記録する。
- 翻訳引用は「原文からの翻訳」と明記し、原文を話者ノートか出典一覧へ残す。
- 省略は `…`、補足は角括弧などで明示し、意味を変えない。
- 強調や改行を変えた場合は、必要に応じてその旨を記す。
- 長い転載を避け、主張に必要な最小範囲だけ引用する。
- スライド上の引用と発表者の解釈・提案を、色・ラベル・配置で分離する。

## Figures, screenshots, and diagrams

- 作図前に、公式ドキュメント、標準、原著、元OSSに適切な図がないか調べる。
- 意味が一致し、読めて、利用条件を追跡できる公式図は、自作図より優先する。
- 図やスクリーンショットの出典、ライセンス、変更内容を記録する。
- 原図の文字が読めない場合、巨大な縮小画像を貼らず、必要領域をクロップするか
  原典に忠実なネイティブ図形へ再描画する。
- 再描画では原図にない矢印、順序、因果、閾値を追加しない。
- 公式図が全体の一部しか説明しない場合、公式部分とプロジェクト固有の補足を
  視覚的・台帳上で分離する。
- 原典の欠陥や機密情報を強調表示しない。

## Review

制作担当と別のレビュアーが、原典を開いて次を確認する。

1. 主張は source ledger の箇所で支持されるか。
2. `direct` と `derived` の境界が正しいか。
3. 実装名と制御フローが原コードに一致するか。
4. 原典が示していない性能、因果、推奨を追加していないか。
5. 引用、翻訳、図の変更が明示されているか。
6. レビュー資料では原典の順序、section名、具体的な構築物が追跡できるか。
7. 省略箇所と理由が明示され、抽象的な一般論へ置換されていないか。
