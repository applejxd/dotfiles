# docs を読み手別に整理し、利用者向けの入口を「今の作業計画」と「俯瞰」にする

- **ステータス**: Proposed（試作を利用者が見て決める。縮小版を先に作り、追い続けられるかを確かめる）
- **日付**: 2026-11-09
- **決定者**: applejxd
- **関係**: [ADR-0010](0010-exploratory-spec-driven-docs.md)（情報の役割で 4 種類に分ける）・[ADR-0011](0011-close-change-records-into-subdirectory.md)（終了案件は `closed/` へ）を**置き換えない。補う**。凍結の定義は ADR-0030。

## コンテキスト

- docs は役割で 4 種類（ADR・案件・調査・仕様）に分けてきたが、**誰が読むか**は決めていなかった。
- 凍結した自作基盤（ADR-0030。フルガード・`pis`・kcage・PR ビューア・作業台帳）の docs が、仕様の入口や案件の「活動中」に、継続している領域と同じ列で並んでいる。
- エージェントには「どの ADR が現行か」が見えない。廃止・置き換え・凍結された判断が積み上がり、古い判断に埋もれる。
- 利用者が「今の作業計画」を 1 か所で追えない。案件の「活動中」が長く、凍結・停滞した案件が混ざる。

## 検討した選択肢

- **A: 物理 archive**（凍結した docs を別ディレクトリへ移す）: 参照リンクの貼り直しが大きく、凍結の再開（ADR-0030 の再開の手引き）も遠くなる。
- **B: 案件を廃止**（change を無くす）: 利用者が「今の作業計画」を読む場所を失う。
- **C: ADR と README だけ整える**: エージェントの入口は良くなるが、利用者が読む案件・仕様の混在は残る。
- **D（採用）: 読み手別に入口を分ける**: 物理的な移動はせず、各入口（索引）で、読み手が要るものだけを先頭に出す。

B・C は、利用者が読む change と spec の入口を改善できない（B は失う）。A は費用に見合わない。D は索引の変更だけで済み、戻しやすい。

## 決定

**D を採る（試作の結果、追い続けられると利用者が判断したとき）。**

### 1. 4 種類の読み手

| 種類 | 主な読み手 | 役割 |
| --- | --- | --- |
| `docs/adr/` | **エージェント** | 過去の経緯を理解させる記録。廃止された判断も積み上がる。利用者は読まない（経緯を覚えている） |
| `docs/change/` | **利用者** | 「今の作業計画は何か」という利用者宛の記録 |
| `docs/research/` | **利用者** | エージェントが何を調べたかのレポート |
| `docs/spec/` | **利用者**（俯瞰） | エージェントが大量に実装した機能を、利用者が全体として見渡すための文書。必須 |

### 2. change は「今の作業計画」を見せる記録

- 案件は、利用者に今の作業計画を見せる記録とする。
- **コミットごとの自動更新はしない。** 更新する節目は、開始・方針の変更・完了・利用者の依頼だけ。
- この規則に合わせる**スキル（`sdd-docs` など）の修正は、この決定では行わない**。将来の変更として残す（下の「将来の変更」）。

### 3. 入口は 2 つ

- **活動中の 1 枚**: [案件の索引](../change/index.md)の先頭の「今の作業計画（活動中）」。成功条件は、**この 1 枚だけで利用者が今の作業計画を追える**こと。凍結・停滞した案件は載せない。
- **現行の決定の一覧**: [ADR の索引](index.md)の先頭の「現行の決定（エージェントの入口）」。置き換え・廃止・凍結された ADR を入れない。

### 4. 凍結した領域は入口で分けて表示する

物理的な移動はしない。仕様の索引（[spec](../spec/index.md)）は「継続する仕様」と「凍結した自作基盤の仕様」に分け、ドキュメント一覧（[docs/index.md](../index.md)）は凍結した領域の案内に「（凍結）」を付ける。調査の索引（[research](../research/index.md)）は、先頭の説明の 1 行にとどめる。

## 結果

- **得るもの**: 利用者が今の作業計画を 1 枚で追える。エージェントが現行の判断をすぐ見つける。凍結領域が継続領域と混ざらない。
- **失うもの・費用**: 現行の一覧と作業計画の表は手で保つ。更新を怠ると嘘になる（節目更新の規則で頻度を絞る）。
- **既存の決定との関係**: ADR-0010 の 4 種類の分割と、ADR-0011 の `closed/` は変えない。

## 将来の変更（この決定では行わない）

- `sdd-docs`・`feature-orchestration` など、案件を更新する手順を、2 の節目更新に合わせる。**利用者の決定（2026-11-09）**: 試作を統合して使ってみる。試用で「今の作業計画」の 1 枚で追えると確かめてから、**全リポジトリ共通のスキルを縮小する**（`commit` スキルの案件更新の自動呼び出しと、`sdd-docs` の索引の自動補完〔`docs_state.py` の scaffold〕を外す。明示して `sdd-docs` を呼んだときの整備は残す）。feature の統合のとき、1 枚を更新する手順を `feature-orchestration` に足す。
- 案件の物理的な整理（凍結案件の扱い）・research の全面の再分類は、試作の結果を見て決める。

## 見直しの条件

- 試作を見て、利用者が「今の作業計画」を追えないと判断したとき（別案へ戻す）。
- 現行の一覧が、手で保てず古くなったとき。
