# Git コミットスキル

> **fork しない（`context: fork` を付けない）。** 承認でユーザーとやり取りするため。

CLI 非依存。個別承認は既定で必要。ただし、適用されるリポジトリ規約が対象のローカルコミットについてメッセージの個別承認を省けると明示している場合は、手順 4 の例外に従う。ツールが確認なしで通るという理由だけでは承認を省かない。

**リポジトリの `AGENTS.md` に規約があるときはそれを優先する**（このリポジトリ: 本文は件名＋1〜3 行の要約・箇条書きなし。
feature の工程の `git add -A` は親が行う）。
以下の本文の書式・`git commit`・`git add` の記述は、リポジトリの規約が無い場合の既定。

## コンテキスト収集

補助スクリプトは使わず、以下のコマンドを直接実行する:

- `git status --short --branch` — 変更ファイルとブランチ
- `git diff HEAD` — HEAD からの差分の概観
- `git diff --cached` / `git diff` — index と作業ツリーの差分（別々に見る。手順 3）
- `git branch --show-current` — 現在のブランチ
- `git rev-parse --show-toplevel` — リポジトリのルート（承認時の提示に使う）
- `git log --oneline -10` — 直近コミット履歴

差分を論理単位に分け、ユーザーの変更や無関係な変更を混ぜない。

## コミット前の docs 反映

コミットを依頼されたら、差分を読ませる子エージェントを呼ぶ前に、作業の経緯を知る側（会話の当事者）が、`docs/change/` の活動中の案件へ経緯を反映する。リポジトリのルートに `docs/change/` が無いとき・メッセージ作成だけを依頼されたときなどは飛ばす。
判断・手順・飛ばす条件は `references/docs-sync.md` を読む。

## 実行

1. 上記コンテキストから **Conventional Commits** 形式のメッセージを作成する。
   詳細は `references/conventional-commits-spec.md` を参照する。
2. メッセージ作成だけを依頼された場合は、対象ファイルとメッセージを提示して終了する。
   差分を読む作業を子エージェントに任せ、対象とメッセージ全文の計画を受け取った側は、
   差分を読み直さない。手順 3 と 5 の確認は `git status --short`（部分ステージは状態の
   2 文字がどちらも空白でない行）と `git diff --cached --name-only` で行い、内容の確認は省く。ただし、個別承認を省く経路ではこの簡略手順を使わず、手順 3・5 の内容確認を行う。
   手順 4 の提示には受け取った全文をそのまま使う。
3. コミットを依頼された場合は、add の前に `git diff --cached` (index) と `git diff`
   (作業ツリー) の両方を確認する。次のいずれかなら、解除も add もせず止めて、
   利用者に対象を尋ねる（尋ねられない実行文脈では、その旨を呼び出し元に返して終了する）。
   尋ねるときは、選択肢ごとのコミット（対象とメッセージ全文）を
   [承認時の提示](#承認時の提示)の形で添え、選んだことが手順 4 の承認を兼ねるようにする。
   対象とメッセージを別々に尋ねて往復を増やさない。
   - 対象外のステージ済み変更、または対象外の変更が対象ファイルに混在している
   - 対象ファイルの index と作業ツリーの両方に差分がある（部分ステージ。
     ファイル単位の add は index の内容を作業ツリーで上書きして失う）

   `git diff HEAD` だけでは index の内容が見えないので、判断に使わない。
   問題なければ、対象ファイルをパスで明示してステージする。
   ステージは取り消せるので、この時点では承認を求めない。

   ```bash
   git add -- <対象ファイル...>
   ```

   誤ってステージしたものは `git restore --staged -- <パス>` で取り消す
   （環境の規則で拒否されたら、取り消さずに報告する）。

4. **コミット前の承認**: 適用されるリポジトリ規約が、対象のローカルコミットについてメッセージの個別承認を省けると明示している場合だけ、個別承認を求めず 5 へ進む。対象が規約の条件を満たすことを確認する。hook・ツールの確認は残し、統合・配備・push への許可にはならない。

   呼び出し元が `git commit` のツール確認を承認の場と定め、対象のコマンドで実際に確認が出ることを確かめられる場合は、チャットで承認を求めず確認付きの実行へ進む。確認が出ると保証できなければ、通常の提示・承認へ戻る。ツールの確認が拒否されたらコミットしない。

   それ以外では、ステージ内容とコミットメッセージ全文を
   [承認時の提示](#承認時の提示)の形で提示し、
   ユーザーの承認を得る。これが唯一の確認点で、目的はメッセージの確認である。
   提示済みの対象とメッセージ全文に対して利用者が「コミットして」「それで」などと
   答えたら、それを承認とみなし、提示し直さない（対象かメッセージを変えたら再提示する）。
   承認が得られない場合はコミットせず、指摘に沿ってメッセージや対象ファイルを
   直して再提示する。ステージは勝手に取り消さない。
   ユーザーと直接やり取りできない実行文脈では、コミットせずステージ内容と
   メッセージを呼び出し元に返して終了する。

   コミットを子エージェントなどへ任せるときは、任せる前にメッセージ全文を
   ユーザーに示して承認を得る。ただし、リポジトリ規約がそのコミットのメッセージの個別承認を省けると明示している場合は個別承認を求めない。確定した全文を渡し、受け取った側は一字も変えずに使う。
   pi では `subagent({ agent: "worker", task: "<承認済みの全文を含む指示>", cwd, async: true })`
   で任せる（同じ worktree に書き手を複数置かない）。
5. コミット直前に `git diff --cached --name-only` と `git diff --cached` が
   手順 3・4 で確定した対象・内容と一致することを確認する。個別承認を省く場合も、パス一覧だけでなく、ステージ内容を検証済みの差分と、監査が必要なら監査済みの差分に照合する。食い違えばコミットせず報告する。
   一致したらコミットする。`git add` と `&&` で連結せず、単独のコマンドとして
   実行する。環境側の確認機構が連結をどう扱うかは実装ごとに違い、連結すると
   コミット単体の確認が効かないことがあるため、環境を判別せずに常にこうする。
   stock の pi（`pi-permission-system`）は複合コマンドを分解して 1 つずつ照合する
   （docs の記述による。連結した `git commit` の実機確認はしていない）ので、
   連結しても確認は効く見込みだが、この規則は変えない。

   ```bash
   git commit -m '<件名>' -m '<本文>'
   ```

6. コミット後に `git status --short` と `git log -1 --oneline` を実行し、
   コミットと作業ツリーを確認する。

## スタイル規範

- **出力言語**: 次の順で決める。会話や依頼文の言語では決めない
  1. ユーザー（または呼び出し元）が言語を明示したらそれに従う
  2. リポジトリのルート直下の `README*`（`README.md` など）に、ひらがな・カタカナ・漢字が
     1 文字でも含まれていれば **日本語**。ファイル読み取りツールか grep ツールで確かめる
  3. それ以外（README が無い場合を含む）は **英語**
- **必要十分・非誇張**: 事実のみ（何を・なぜ・影響）。誇張・曖昧語を避ける
- 件名は命令形・**72文字以内**・文末ピリオドなし
- **定量主張の条件**:
  - 数値（例: `+30% speedup`）は**測定済みであること**が条件
  - 未測定の見込み・推定（例: `~30% expected`）は**禁止**
- **本文は短く、箇条書きにする**（リポジトリの規約が無い場合の既定。`AGENTS.md` が別に定めるなら従う。Git の慣習どおり、本文は「何を・なぜ」だけ。「どう」はコードと差分が語る）:
  - 件名の後に空行を 1 つ置き、本文は**箇条書きだけ**（段落の散文にしない）
  - 箇条書きは**最大 5 項目**、1 項目は**1 行（約 100 文字）まで**。本文全体は**約 120 語（日本語は 400 文字）以内**
  - 書くのは、変更の目的・主な変更・影響。経緯・実測・却下した案・レビューの指摘の一覧・試験の一覧は、案件や `docs/` が正本なので、**そこへの参照（案件の ID など）だけ**にする
  - 変更が大きく見えても、本文を延ばさず、コミットを論理単位に分ける
- **git flow で運用するリポジトリ**（`.gitflow` がある）: feature の worktree の中のコミットは、細かい作業の単位でよい（`finish` が develop へ 1 コミットに束ねる）。
  本文の上限と箇条書きの規約は、**束ねるときの squash のメッセージ**（利用者が git flow の feature finish で付けるもの）に適用する。feature の起票とクローズは利用者が行う。個別承認の有無は手順 4 に従う。feature ブランチであることだけでは承認を省かない。

## 出力フォーマット

```text
<type>(<scope>): <subject>

- Motivation: <why>
- Change: <what>
- Impact: <effect>  # 数値を書くのは測定済みのときのみ
```

## 承認時の提示

コミット 1 件につき 1 ブロック（リポジトリ・ブランチ・対象・メッセージ全文）を並べて提示する。リポジトリが 1 つでも省略しない。複数のリポジトリにまたがるときは、リポジトリごとにまとめ、先頭に `計 <N> コミット / <M> リポジトリ` の 1 行を置く。
形式の詳細は `references/approval-format.md` を読む。

## ポリシー

**禁止**:

- `--no-verify` などによる確認・検証機構の回避
- `git add .` / `git add -A` による無関係な変更の追加（リポジトリの規約が無い場合の既定。feature の工程では親が `git add -A` する）
- `git commit -a` / `git commit --all` による無関係な変更の追加
- 明示依頼のない `git commit --amend`
- 共同著者タグや生成ツールへのリンクの追加
- 未測定の数値主張

**要求**:

- 対象ファイルをパスで明示してステージする
- 手順 4 に従い、必要な承認を得る。承認が得られない、またはツールの確認が拒否された場合はコミットせず停止する
