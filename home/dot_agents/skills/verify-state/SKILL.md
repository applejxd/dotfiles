# 操作順で壊れる挙動を検証する

図を描くことではなく、利用者に約束する性質がどの順序で崩れるかを確かめよ。通常の回帰テストで十分なら、形式検証の基盤を新設しない。

1. 対象を一つのフローへ絞る。状態、イベント、そのイベントが成立する条件、利用者から観測できる結果を区別する。
2. 守る条件を一文にする。例: 読み込み後の編集を確認し直さない限り、古い画面から承認してはならない。モデルから外した事項と、探索の上限を記す。
3. 順序が少なければ、状態表と実コードを使うテストを優先する。順序が多ければ、既存のモデル検査・列挙テストなど、対象に合う手段を使う。環境の追加導入は勝手に行わない。
4. 検査に違反する既知の例、または意図的に壊した例を当て、検出できることを確かめる。反例は最短級の操作列で示す。実コードでの検査や反例の再現は、依頼と権限の範囲内で、副作用を確認したテスト環境に限る。実行できなければ未確認とし、実行して再現しないときはモデル・環境・実装のどこに差があるかを区別する。
5. 条件、検査の範囲、反例、実コードでの確認、残る不確実性を報告する。状態図が有効なら利用者から見える操作名で添える。モデルが通った結果を実装全体の合格に置き換えない。

繰り返し使う必要があり、依頼と権限の範囲内の場合だけ、モデルと実行コマンドを対象リポジトリに残す。初版では TLA+、TLC、Java などの依存や独自ドライバーを同梱しない。
