# Anthropic Sandbox Runtime（`srt`）を OpenCode に使えるか

> **調査日: 2026-09-22 / 対象: `@anthropic-ai/sandbox-runtime` v0.0.76（Ubuntu on WSL2）**
>
> [CHG-0004](../../../change/0004-opencode-sandbox.md) の前提調査。
> 「個別に穴を塞ぎ続ける」方針から「OS のアクセス制御を主役にする」方針へ
> 切り替えられるかを確かめた。

## 0. 結論

| # | 問い | 結果 |
| --- | --- | --- |
| 1 | `srt` は Claude Code 専用か | **汎用**。「任意のプロセスに境界をかぶせる」と自称 |
| 2 | 導入済みか | **済み**（seccomp のため mise で入れてあった） |
| 3 | ファイルの隔離は効くか | **効く**。ただし `denyRead` に**強い癖**がある（下記 3 章） |
| 4 | ドメイン制限は効くか | **効く**（`github.com` 200 / `example.com` 遮断） |
| 5 | 認証情報を落とせるか | **落とせる**。`git push` も `gh` も認証に失敗する |
| 6 | WSL2 の socket 脱出は塞がるか | **塞がる**（`cmd.exe` の起動が拒否された） |
| 7 | `chezmoi`（snap）は動くか | **動かない**。snap の阻却事由を実地で再現 |
| 8 | **実行主体ごと包めるか** | **包める**（`--standalone`。[19 節](#19-実行主体ごと包む案は成立するp0-1-の訂正)） |

**採用可能。`opencode --standalone` ごと包む構成を採る。**
`denyRead` の癖（3 章）と snap の解消が前提。

## 1. 起動方法（名前が衝突する）

`bin` は `srt` だが、**PATH の `srt` は Python の字幕処理ツール**だった。
mise 経由でも解決されないので、実体を直接叩く。

```sh
node ~/.local/share/mise/installs/npm-anthropic-ai-sandbox-runtime/latest\
/node_modules/@anthropic-ai/sandbox-runtime/dist/cli.js \
  -s <settings.json> -c '<command>'
```

`-d` で詳細ログが出る。**設定が無視されたときはここにしか出ない**（下記 3 章）。

## 2. Linux での実装

デバッグログで確認した。

```text
[SeccompFilter] Found apply-seccomp binary: .../vendor/seccomp/x64/apply-seccomp
[Sandbox Linux] Applying seccomp filter for Unix socket blocking
[Sandbox Linux] Wrapped command with bwrap (network, filesystem, seccomp(unix-block) restrictions)
```

bubblewrap + seccomp + **sandbox の外に置いたプロキシ**の 3 点構成。
ドメイン判定はプロキシが持つので、全サブプロセスに等しく効く。

## 3. `denyRead` は「許可領域の内側」にしか効かない

**最も重要な癖。** 許可領域の外に書いた `denyRead` は**黙って読み飛ばされる**。

```text
[Sandbox Linux] Skipping deny path not within allowed paths: …/.git/config
[Sandbox Linux] Skipping non-existent deny path not within allowed paths: …/.bashrc
```

実測は次のとおり。

| 設定 | `~/.ssh` | `~/.config/gh` | `~/.git-credentials` |
| --- | --- | --- | --- |
| `denyRead: ["~/.ssh", …]` | **読めた** | **読めた** | **読めた** |
| `denyRead: ["/home/applejxd/.ssh", …]`（絶対パス） | **読めた** | **読めた** | **読めた** |
| `denyRead: ["/home/applejxd"]` + `allowRead` で再許可 | 拒否 | 拒否 | 拒否 |

**`~` の展開の問題ではない。** 読み取りは既定で全面許可で、`denyRead` は
「広い領域を deny してから `allowRead` で戻す」形でしか機能しない。
README の Linux 向けレシピ（`denyRead: ["/home"], allowRead: ["."]`）が
唯一の正しい書き方で、**ピンポイントの deny は効かない**。

> 設定を書いても**エラーにならず黙って無視される**。これは今日踏んだ
> 「`~/` 始まりの read deny glob が一度も当たらない」件と同じ型の事故で、
> **設定した気になって開いたままになる**。導入時は必ず実地で確かめる。

### `allowWrite` が効く条件（規則を確定させた）

`denyRead` を広く掛けた下での `allowWrite` の挙動を、6 通りの組み合わせで
総当たりした。**「内側で書けるか」と「外に実体が残るか」を別々に測ること**が
要点で、これを分けないと結論を誤る。

| allowRead | allowWrite | 内側 | 実体 |
| --- | --- | --- | --- |
| WS | WS | OK | **残る** |
| WS | SUB | NG | 消える |
| WS, SUB | SUB | NG | 消える |
| WS | SUB, WS | OK | **残る** |
| (なし) | WS | OK | **残る** |
| SUB | SUB | OK | **root は消える** |

- **R1**: `allowWrite` のパスの**祖先**を `allowRead` に載せると、その
  `allowWrite` は無効化される（内側で `EROFS`）。読み取り専用の bind が
  入れ子の書き込み許可を覆うため。**完全一致なら問題ない**
- **R2**: `allowRead` にも `allowWrite` にも載っていない領域への書き込みは
  **成功したように見えて消える**。最も危険
- **R3**: `allowRead` に載っていれば、少なくとも `EROFS` で**気づける**

**実務上の指針**: 書きたい領域は**根ごと** `allowWrite` に載せ、その祖先を
`allowRead` に載せない。触りうる領域は必ずどちらかに載せる。

> 過去に 2 回踏んだ `EROFS` はすべて R1 が原因だった。
> **R2 は黙ってデータを失う**ので、設定を書いたら必ず実体を確認する。

### `denyWrite` は `allowWrite` の内側で効く

ディレクトリ単位で機能し、`allowWrite` より優先される。実測では保護対象
4 箇所すべてで新規ファイル作成が拒否され、**実体は 0 件**だった。

検証は**上書きではなく新規ファイル作成**で行うこと。効かなかった場合に
ソースを壊さないため。

### `$HOME` は差し替えられる

広い `denyRead` を掛けると、sandbox 内の `$HOME` が別の場所になる。
`$HOME` 直下への書き込みは**成功するが実ホームには現れない**。
「書けた」を境界の破れと誤読しないこと（実ホームを確認して無害と判定した）。

## 4. 効いたもの（実運用に近い設定）

`denyRead: ["/home/applejxd"]` + `allowRead` にワークスペース・mise・
`~/.cache`・`~/.local/bin` + `allowWrite` にワークスペース根・`~/.cache`・`/tmp`。

| 検査 | 結果 |
| --- | --- |
| `~/.ssh` / `~/.config/gh` / `~/.git-credentials` | **拒否** |
| ワークスペースの読み書き | 成功 |
| `git log` | 成功 |
| **`git push`** | **`fatal: could not read Username`** |
| **`gh auth status`** | **`You are not logged into any GitHub hosts`** |
| `curl https://github.com` | `200` |
| `curl https://example.com`（許可外） | **遮断**（`000`） |
| `cmd.exe /c echo`（WSL の脱出経路） | **拒否** |
| `mise --version` | 成功（ただし `mise.jdx.dev` が許可外で警告） |
| `uv --version` | 成功 |
| **`chezmoi --version`** | **snap の internal error** |

**認証情報を見せないだけで `git push` と `gh` の書き込みが止まる。**
コマンド文字列の判定は 1 つも要らない。

## 5. `chezmoi` が snap である限り成立しない

## 6. 許可リストに足りないもの

現在の `[sandbox] claude_network_allow` は Claude 向けに作られており、
`mise.jdx.dev` が入っていない（`mise-versions.jdx.dev` はある）。
OpenCode を包むなら実地で不足を洗う必要がある。

不足しても破綻はせず、接続が失敗するだけなので追記で回復できる。

## 7. 境界をまたぐ接続は成立しない（P0-1 の**部分的な**結論）

> **この節の結論を一般化してはいけない。** 「実行主体ごと包む案は不成立」と
> 読むのは誤り。当てはまるのは**境界をまたぐ構成だけ**。
> 成立する構成は [19 節](#19-実行主体ごと包む案は成立するp0-1-の訂正)。

OpenCode のサービスは **TCP `127.0.0.1` で待ち受け**、TUI がそこへ接続する。

```text
LISTEN 127.0.0.1:49374  users:(("opencode",pid=…))
```

Linux の `srt` は**ネットワーク名前空間を丸ごと除去する**（README）。
通信は unix socket 経由のプロキシだけになるため、内側で待ち受けても
外からは届かない。実測した。

| 位置 | 結果 |
| --- | --- |
| 内側で `bind 127.0.0.1:45671` | **成功** |
| 外側から接続 | **`TimeoutError`** |

`enableWeakerNetworkIsolation` は **macOS 専用**（trustd 向け）で、この件には
効かない。**サービスだけを包み TUI を外に置く構成は採れない。**

この性質は境界としては**利点**でもある。内側の OpenCode は
**外側の共有サービスへ到達できない**ので、「TUI だけ包んでも共有サーバへ
繋いでツールを外で実行する」抜け道が自動的に塞がる。

## 8. 実行ごとに包む案は成立する

plugin が `tool.execute.before` で **`e.input.command` を差し替えられる**。
計装で確認した。

```json
{"phase":"before","original":"echo REWRITE_ME","mutated":"echo REWRITTEN_BY_PLUGIN"}
{"phase":"after","output":"REWRITTEN_BY_PLUGIN\nCommand exited with code 0."}
```

モデルが受け取ったのは差し替え後の出力だった。よって
**shell の実行だけを `srt` で包む**構成が採れる。

### 引き換えに失うもの

**`read` / `edit` / `grep` / `glob` は境界の外に残る。** これらは shell を
経由しないため、包む対象にならない。permission の deny と既存の結果フィルタを
**捨てられない**。

### 故障時の振る舞い

plugin が死ぬと、包む処理と `allow` への引き上げが**同時に**死ぬ。
結果は「包まれないが確認は出る」= 現在の状態に縮退する。危険側へは倒れない。

## 9. プロジェクト単位の許可リストは効く

秘密を拒否したまま、chezmoi 管理下の非機密パスだけを開けられる。

| パス | 設定 | 結果 |
| --- | --- | --- |
| `~/.ssh` | 未許可 | **拒否** |
| `~/.config/gh` | 未許可 | **拒否** |
| `~/.config/opencode` | 未許可 | **拒否** |
| `~/.config/shell` | `allowRead` | **読める** |
| `~/.config/mise` | `allowRead` | **読める** |
| `~/.config` 自体の一覧 | — | 読める（子は個別に判定） |
| `. ~/.config/shell/shellenv.sh` | — | **読み込み成功** |

パス単位で粒度が出る。**ただし許可リストをプロジェクト側に置いてはいけない。**
敵対的なリポジトリが `~/.ssh` を自分で許可できてしまい、
[プロジェクト設定がグローバルに勝つ問題](gaps.md)と同じ穴になる。
`common.toml` にプロジェクトパスをキーとして持たせる。

## 10. 版は Claude Code と共有している（P0-3）

```toml
# home/dot_config/mise/config.toml.tmpl
"npm:@anthropic-ai/sandbox-runtime" = "latest"
```

`latest` の浮動指定で、Claude の `sandbox.seccomp.applyPath` も同じ `latest` を
指している。**片方の都合で上げると両方の挙動が変わる。** OpenCode でも使うなら
版を固定するか、壊れたときに両方を見る前提にする。

## 11. 固定費は 1 回あたり約 650 ms

CLI 経由で包むと、`echo` 1 回でも待たされる。

| 実行 | 所要 |
| --- | --- |
| 素の `echo` | **7 ms** |
| `srt` 包みの `echo` | **657 ms** |

CLI は毎回 node の起動とプロキシの初期化を行うため。**実行ごとに包む構成では
この固定費が全 shell 呼び出しに乗る。**

**回避策**: plugin は node（サービス）の中で動くので、CLI ではなく
**ライブラリ API** を使う。`SandboxManager.initialize()` を plugin のロード時に
1 回だけ呼び、コマンドごとには `wrapWithSandbox()`（文字列を返すだけ）を呼ぶ。
プロキシの起動を償却できる。**未計測**なので、実装時に測り直す。

参考として、確認を 1 回出すと人間の応答待ちで秒単位かかる。約 94% の
呼び出しが無確認になるなら、数百 ms の固定費は割に合う可能性が高い。

## 12. `--stdio` は行き止まり（P0-1 の再確認）

`opencode serve` に `--stdio` があるので、TCP を避けられれば
「サービスごと包む」案が復活する可能性を追った。**復活しない。**

TUI 側の接続手段は `--server <URL>`（HTTP）だけで、stdio で繋ぐ口が無い。
`--stdio` は別用途（ACP / MCP）のもの。

## 13. 組み込みツールは `execute.before` で止められる

反転案（shell で代替できるツールを禁止して境界の内側へ寄せる）の要。
`execute.before` で例外を投げると**ツールが失敗し、メッセージがモデルへ届く**。

```text
✗ Grep "Dotfiles" failed
Error: grep ツールは使えません。shell の `grep -rn` を使ってください。
```

モデルは理由をそのまま報告し、指示どおり代替手段を試さなかった。
誘導の `deny` と同じ挙動で、**向きだけが逆**になる。

| | いまの誘導 | 反転後 |
| --- | --- | --- |
| 目的 | permission の `deny` が効く経路へ寄せる | **OS の境界の内側へ寄せる** |
| 例 | `cat` → `read` ツール | `grep` ツール → shell の `grep -rn` |

## 14. 保護機構そのものが書き換えられる

`edit` の permission を実際に当てて確かめた。**全て書ける。**

```text
★書ける  home/dot_config/agents/common.toml.tmpl
★書ける  home/dot_config/opencode/guide-plugin/index.js
★書ける  scripts/agents/generate.py
★書ける  home/dot_config/mise/config.toml.tmpl
```

`chezmoi apply` を 1 回承認させれば保護が消える。**境界の内側で完結する経路**で、
外部レビュー（Astra）の指摘どおりだった。

`srt` の `denyWrite` は `allowWrite` より優先されるので、ワークスペース内でも
これらだけ書き込み禁止にできる。

## 15. ライブラリ API で固定費は 44 ms まで落ちる

CLI 経由の 657 ms は node の起動とプロキシ初期化を毎回やり直すため。
`SandboxManager.initialize()` を 1 回だけ呼び、コマンドごとには
`wrapWithSandbox()` を使うと解消する。

| 実行 | 素 | 包んだ | 上乗せ |
| --- | --- | --- | --- |
| `echo x` | 3 ms | 47 ms | **44 ms** |
| `grep -rn permission docs/` | 19 ms | 59 ms | **40 ms** |

`initialize()` は **426 ms**。plugin のロード時に 1 回だけ払う。

**plugin はサービス（node）の中で動くので、この構成が取れる。** CLI を
呼び出す実装にしてはいけない。

> **この 44 ms は楽観的だった。** あらかじめ包んだ文字列を実行するだけの
> 計測で、呼び出しごとに `wrapWithSandbox()` を通す実装では **91 ms**
> （試作で実測）。許容値には収まるが、**実装時の見積もりは 90 ms 前後**を
> 使うこと。

## 16. 移行後の自動化率（実履歴 1,128 呼び出し）

止まる要因を「承認待ち」と「失敗」に分けて数えた。**無人で進めたい場合、
失敗のほうが厄介**（止まったうえに理由が分かりにくい）。

| 区分 | 件数 | 割合 |
| --- | --- | --- |
| 自動で進む | 1,033 | **91.6%** |
| 承認で止まる | 15 | 1.3% |
| 失敗で止まる | 80 | **7.1%** |

加えて `grep` / `glob` ツール 36 件が shell へ移るので自動側に入る。

### 承認で残るもの

| 件数 | 内容 |
| --- | --- |
| 13 | `chezmoi apply` / `re-add` |
| 2 | `git push` |

### 失敗で止まるもの（対処可能）

| 件数 | 内容 | 対処 |
| --- | --- | --- |
| 50 | `opencode.ai` が許可外 | ドメイン許可リストへ追加 |
| 25 | `gh` / `git fetch` に認証情報が要る | 読み取り専用 PAT を境界内へ |
| 5 | `claude.ai` / `example.com` | 同上 |

対処後の見込みは **自動 98.7% / 承認 1.3% / 失敗ほぼ 0%**。

> **「自動」は「境界内で成功する」前提。** ワークスペース・`/tmp`・`~/.cache`
> 以外へ書くコマンドは失敗する。過去のリダイレクト先を見た限りほぼ無いが
> ゼロではない。実運用で洗い出す。

## 17. 包み方は `shell` 設定のラッパーしかない（**破棄。19 節を見ること**）

> **この節と次節は採用しなかった案（案 B）の記録。** 実行主体ごと包む
> [19 節](#19-実行主体ごと包む案は成立するp0-1-の訂正)が成立したので不要になった。
> 測定値と呼び出し規約は事実として有効だが、**この構成を実装してはいけない**。
> 外部レビューは「コマンド文字列で sandbox を解除する設計は採用すべきでない」
> と判定した（例外判定も bypass の目印も同じ穴）。

plugin による差し替えは権限評価を壊す（[hook の呼ばれ方](hook-order.md)）。
代わりに設定の `shell` へラッパーを指定する。

```text
argv[1]=-c
argv[2]=echo SHELLWRAP_OK     ← 原文のまま
```

`<ラッパー> -c "<原文>"` で呼ばれる。通常のシェルと同じ規約なので差し替えられ、
**権限評価は原文を見るので allow / deny が生き残る**。

### エージェント名はシェルへ届かない

`build` と `bypass` で環境が**完全に同一**だった。
届くのは `OPENCODE_CONFIG_DIR` / `OPENCODE_DB` / `OPENCODE_TERMINAL` のみ。

bypass は **plugin がコマンドへ目印を前置**して見分ける。
bypass は全 action が `allow` なので、**権限評価が狂っても損害が無い**
（差し替えが致命傷になるのは通常のエージェントだけ）。

### 固定費は 650 ms

ラッパーは毎回新しいプロセスなので `initialize()` を償却できない。

| 経路 | 固定費 |
| --- | --- |
| 素の `sh -c` | 5 ms |
| 常駐プロセス内のライブラリ API（償却あり） | 91 ms |
| **ラッパーが毎回 CLI を起動** | **650 ms** |

## 18. 遅延の最適化は急がない（外部レビューの判断）

4 案を検討し、**当面は最適化しない**と決めた。

| 案 | 判断 | 理由 |
| --- | --- | --- |
| 前置きのキャッシュ | **棄却** | 隔離設定は wrap 時に glob 展開され cwd にも依存する。使い回すと**隠すはずのファイルが見える**。文字列の切り貼りは引用を壊し、**一部が境界の外で評価されうる** |
| proxy だけ常駐して bwrap を自前生成 | **棄却** | proxy は隔離そのものではない（隔離は network namespace 側）。sandbox 実装を自分で保守することになる |
| node 起動の削減 | 低優先 | `initialize()` が支配的で、削減余地は 166〜224 ms が上限 |
| 常駐デーモン + IPC | **将来候補** | 公開 API だけで済むが「簡単」ではない（下記） |

> **「共通 497 文字」に意味を持たせてはいけない。** 2 回の出力比較では
> 「帰属以外が同一」を証明できない。ユーザー名が帰属キー・パスワードが
> 認証トークンという読み自体は upstream の実装と一致するが、
> それはキャッシュを正当化しない。

### 常駐デーモン案の落とし穴（着手するなら先に解く）

- srt の Linux 実装は **`process.cwd()` に依存**して保護対象を決める。
  デーモンとラッパーで cwd が違うと同じ隔離にならない
- `SandboxManager` は**モジュール内に状態を持つ**。1 インスタンスを共有して
  要求ごとに設定を切り替えると、**並行実行で混線する**
- 制御 socket の**完全性が重要**。偽のデーモンが返した文字列を外側のシェルで
  実行すれば、**隔離前のコード実行**になる。`0700` / `0600` は同一 UID の
  sandbox 内プロセスに対する境界にはならない

### 費用の比較

| 方式 | 1,128 コマンドの総計 |
| --- | --- |
| ラッパー（650 ms） | 約 12.2 分 |
| 常駐（91 ms） | 約 1.7 分 |
| **削減余地** | 約 10.5 分（IPC の費用を除く） |

対して承認は **98.7% → 1.3%** になる。承認待ちは**人が戻るまで止まる**ので、
自動で進む 650 ms とは性質が違う。**まず B の安定性を優先する。**

### 版を固定する

公開 API も research preview。更新時は「正常なコマンドが通る」ではなく
**「拒否すべきものが拒否される」**ことを検証する（deny・直接通信・
Unix socket・cwd 違い・並行実行）。

## 19. 実行主体ごと包む案は成立する（P0-1 の訂正）

**[7 節](#7-境界をまたぐ接続は成立しないp0-1-の部分的な結論)の一般化は誤りだった。**
`opencode --standalone` は **TUI とサーバが同一プロセス**なので、
これごと包めば境界をまたぐ接続が発生しない。7 節の不成立条件に当たらない。

```sh
srt -s <config> -c "opencode --standalone"
```

### 実測（Ubuntu / WSL、`opencode` v2.0.12）

| 確認 | 結果 |
| --- | --- |
| 非対話（`opencode run --standalone`） | 動いた |
| **対話 TUI** | **動いた**（起動・描画・入力・終了、異常なし） |
| モデルへの到達 | proxy 経由で正常 |
| shell ツール | 動いた |
| 内側から `~/.ssh` | **不可視** |
| 内側から `~/.git-credentials` | **読めない** |
| ワークスペースへの書き込み | **実体が残る**（外側から確認） |
| ホーム直下への書き込み | **消える**（[R2](#3-denyread-は許可領域の内側にしか効かない)の実地再現） |

`bwrap --new-session` は `setsid` するが、**TUI の動作に支障は出なかった**。

### この構成で消えるもの

| 案 B（`shell` ラッパー）の要素 | 状態 |
| --- | --- |
| `shell` 設定のラッパー | 不要 |
| 目印による bypass 判定 | 不要 |
| `chezmoi apply` の例外 | 不要 |
| コマンドごとの固定費 650 ms | 消滅（隔離は起動時 1 回） |
| 「shell しか守れない」制約 | 解消（`read` / `edit`・plugin・LSP も境界内） |

コマンド文字列に触れないので、**permission の allow / deny がそのまま生きる**
（[案 A が失敗した理由](hook-order.md)に当たらない）。

### 保護設定のソースと実体が自然に分離する

| 対象 | 置き場 | 内側から |
| --- | --- | --- |
| **有効な設定** | `~/.config/opencode/` | `allowRead` のみ → **書けない** |
| そのソース | dotfiles リポジトリ（chezmoi source state） | `allowWrite` → 編集できる |

この構成では自動的にそうなる**わけではない**（条件は
[22 節](#22-ソースと実体の分離は自動では完成しない)）。ただし置き場を正しく
選べば、AI はソースを提案できても**自分で有効化できない**。
`chezmoi apply` を例外として通す必要は消える。

## 20. 境界はエージェントから見えない（誤診の原因）

内側のモデルに `ls ~/.ssh` を実行させると `ENOENT` が返る。モデルはこれを
**「存在しない」と解釈し、`ssh-keygen` での作成を提案した**。

実行していれば、鍵は[書いても消える領域](#3-denyread-は許可領域の内側にしか効かない)へ
書かれ、黙って失われていた。

**隠すことと存在しないことをエージェントは区別できない。** 対策は
「隠す」ではなく「読めるが書けない」（`EROFS` で気づかせる）か、
境界の存在を明示的に伝えるか。秘密そのものには前者を使えない。

## 21. 境界の外に残る経路（実測で 2 件塞いだ）

外部レビューの指摘を受けて内側から測った。**2 件が本当に開いていた。**

| 経路 | 素の設定 | 対処後 |
| --- | --- | --- |
| seccomp | `Seccomp:2`（filter。**効いている**） | — |
| **`/mnt/c`（WSL）** | **見える。`/mnt/c/Users` まで読めた** | `denyRead` に `/mnt` を追加 → 不可視 |
| Windows interop（`cmd.exe` 等） | PATH に無く実行不可 | — |
| **ホストの `/tmp`** | **共有されていた** | `denyRead` に `/tmp` を追加 → 専用の空 tmpfs になる |
| 外側の共有サービス（TCP） | 到達できない | — |

**`denyRead: /home/<user>` は Windows 側を守らない。** `srt` の読み取りは
既定で許可なので、WSL では `/mnt` を明示的に塞ぐ必要がある。

`/tmp` は `denyRead` に入れると**空の書き込み可能な tmpfs で覆われる**。
内側から書けるので道具は壊れず、ホストとは双方向に分離される。
`allowWrite` から `/tmp` を外しても問題ない（実測：内側で書けて外に漏れない）。

`/var/tmp` と `/dev/shm` も同じ理由で塞いだ。

この設定でも `opencode --standalone` は正常に動く（実測）。

> **`Seccomp` の値は起動時に確認すること。** 上流仕様では seccomp が
> 使えないと Unix socket の制限が**警告だけで無効化される**。
> その状態で起動を続けてはいけない（fail-closed）。

### 「外側へ到達できない」と言い切れる範囲

TCP の loopback 直結は塞がる（実測）。**これを「外側への実行委譲が全て
不可能」と読んではいけない。** proxy 経由の到達先、ファイルシステム上の
Unix socket、継承した FD、リモート MCP の実行権限は別に成立させる必要がある。

## 22. 「ソースと実体の分離」は自動では完成しない

[19 節](#19-実行主体ごと包む案は成立するp0-1-の訂正)で「自動的に分離される」と
書いたのは**言い過ぎだった**。成立には条件が要る（外部レビューの指摘）。

| 条件 | 内容 |
| --- | --- |
| 別実体であること | 有効な設定が、書ける側への symlink / hardlink / 別名マウントでないこと |
| **ランチャーの置き場** | **ワークスペースに置いてはいけない。** 書き換えられ、次回**外側で**実行されると境界の前にコードが走る |
| `srt` の設定 | 同上。読み取り専用側へ置く |
| 外側の自動読み込み | 外側のサービスが内側で変えたファイルを自動で読まないこと |

主張できるのはここまで。

> AI は、ホストへ展開済みの保護設定を**直接**更新できない。
> ただし**ソース・コード・次回外側で使う成果物は変更できる**。

`chezmoi apply` も「内側では実行できない」ではなく、**保護された展開先へ
反映できない**が正確。スクリプトが一部走ってから失敗することはありうる。

**外側での `chezmoi apply` は単なるファイル複製ではない。**
変更されたコードをホスト権限へ移す操作なので、有効化の対象には設定だけでなく
**実行されるコード**（`.chezmoiscripts/`・mise タスク・シェル起動設定・
Git hooks・ランチャー）が含まれる。

## 23. 境界内に入る資格情報は `read:user` だけだった

deny を緩める前に、境界内から読める資格情報で**何ができるか**を確定させた。

| 項目 | 実測 |
| --- | --- |
| 置き場 | DB の `credential` テーブル（1 行） |
| 種別 | `github-copilot` の OAuth。接頭辞 `gho_`、refresh トークンあり |
| **GitHub での権限** | **`read:user` のみ**（`X-OAuth-Scopes`） |

`gho_` は GitHub の OAuth トークンなので「モデル専用だから他に使えない」とは
**推定できない**。実際に `api.github.com` へ当てて範囲を確かめた結果が上記。

**リポジトリの読み書きも `git push` もできない。** 残るリスクは
モデル推論の実行（課金・枠）とプロフィールの読み取りに限られる。

> 前提が変わったら測り直す。provider を替えれば別のトークンが入る。

## 24. 隔離用の DB は分ける

`--standalone` は専用サーバを意味するが**専用 DB は意味しない**。
共有すると他プロジェクトの会話が境界内へ入る。`OPENCODE_DB` で分ける。

作り方は「実 DB を複製 → 資格情報と `migration` 以外を消す → `vacuum`」。

| 残すテーブル | 理由 |
| --- | --- |
| `credential` / `account` / `account_state` / `control_account` | モデルへ繋ぐのに要る |
| **`migration`** | **スキーマ管理の記録。消すと壊れる** |

実測：2,907 行を削除し 240 KiB まで縮んだ。削除した会話の断片が
ファイル内に残っていないことを確認した（`vacuum` が効いている）。
この DB で `opencode --standalone` は正常に動く。

## 25. `/mnt` 配下は狙い撃ちで許可でき、symlink 越しでも届く

データ処理で `/mnt/d` の対象を扱う場合の確認。

```json
"denyRead": ["/mnt", …],
"allowRead": ["/mnt/d/<対象>", …]
```

| 確認 | 結果 |
| --- | --- |
| 許可したパスを直接読む | **読める** |
| **ワークスペース内の symlink 経由で読む** | **読める** |
| 許可していない `/mnt/d/repos` | 見えない |
| 許可していない `/mnt/c/Users` | 見えない |
| 許可したパスへ書く | **`Read-only file system`**（[R3](#3-denyread-は許可領域の内側にしか効かない)。気づける） |

**symlink を張り替える運用で問題ない。** 直接アクセスに切り替える必要はない。
書き込みが要るなら `allowWrite` に載せる（[R1](#3-denyread-は許可領域の内側にしか効かない) に注意）。

## 26. 実装時に踏んだ癖（配備して初めて出たもの）

設計と単体の検証では出ず、**実際にランチャーを走らせて初めて**出たもの。

### mise の shim を経由すると止まる

`~/.local/share/mise/shims/node` は **`mise` 本体への symlink**。呼ぶたびに
版解決が走り、ネットワーク確認（`packslip` の警告）で停止することがある。

```text
mise WARN  packslip:github.com/jdx/usage: skipping 6.11.0: …
（ここで止まる）
```

**境界を張る前に mise を経由してはいけない。** 停止するだけでなく、mise は
ワークスペース内の設定を読むので**可変な入力に依存する**ことになる。
実体（`installs/node/<版>/bin/node`）を直接指す。

### proxy は境界の生成直後には待ち受けていない

最初の要求が失敗する。同じホストへの再試行は通る。

```text
github.com   rc=7   Failed to connect to localhost port 3128 after 0 ms
github.com   rc=0   200
```

起動直後にネットワークを判定するなら**待つ**。待たずに「到達しない」と
判定すると、**穴が開いていても合格になる**。

### モデル提供元のドメインは別に要る

`web.allow_domains` には入っていない。入れ忘れると proxy が CONNECT を
**403 で落とす**ので、症状は「モデルの応答が来ない」になり原因が見えにくい。

```text
api.githubcopilot.com   rc=56   CONNECT tunnel failed, response 403
```

### 名前解決は内側で効かない（正常）

すべての通信が proxy 経由になるため、`getent hosts` は許可済みドメインでも
失敗する。**これを不通の証拠にしてはいけない。**
