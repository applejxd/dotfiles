# Narrative Balance for Technical Tutorials

技術入門では、モチベーションだけでなく「どう作るか」を時間として確保する。

## Narrative layers

各スライドを次のいずれかへ分類する。

- `why`: 問題、必要性、失敗の影響
- `what`: 用語、全体像、概念
- `how`: 責務、データ構造、処理順、インターフェース、設定
- `proof`: 評価、比較、根拠、検証方法
- `operate`: 可観測性、権限、コスト、障害対応、改善ループ
- `action`: 実装順、判断、次の一歩、まとめ

## Default balance

開発者向けの実装入門では、予定時間を次の目安で配分する。

- `how + operate`: **45%以上**
- `why`: 25%以下
- `proof`: 10%以上
- `action`: 少なくとも1枚

タイトル、目次、まとめを含めた全体で計算する。briefが概念紹介や経営説明の場合は
policyを変更してよいが、変更理由を記録する。

## What counts as How

部品名を列挙するだけではHowではない。次のうち複数を説明する。

- 各コンポーネントの責務
- 入出力データと保持するmetadata
- オフライン／オンライン処理の順序
- 条件分岐、上限、fallback
- 失敗症状から修正対象を特定する方法
- 最小構成からの実装順
- 本番化で追加する境界

## Full-deck revalidation

局所的なフィードバックでページを追加・置換した後は、必ず全体を再分類する。

- Whyが重複していないか
- Howの前提が前ページで説明されているか
- 同じHowを複数図で繰り返していないか
- ProofがHowの後に接続されているか
- Actionが実装可能な順序になっているか
