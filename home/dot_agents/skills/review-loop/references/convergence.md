# 収束と停滞の見分け方

ループを止める判断は件数では行わない。件数は簡単に減るし、簡単に増える。

## 指摘の台帳と状態

指摘は `./.tmp/review-loop/<run-id>/ledger.md` に累積し、ID ごとに状態を持たせる。
レビュー役が再掲しないことと解決したことは別物なので、判定は台帳で行う。

| 状態 | 意味 |
| --- | --- |
| 未解決 | 未修正。見送っただけのもの、修正したが再レビュー前のものを含む |
| 修正確認済み | 修正後の状態を、レビュー役が独立に確認した |
| 誤検知 | レビュー役が根拠を確認したうえで指摘を取り下げた |
| リスク受容 | 直さないと決め、理由を記録した（ユーザの判断が要るものはユーザ承認） |

## 収束したと言える形（正本）

次の 4 つが揃ってはじめて収束。

- 累積の未解決 BLOCKER・MAJOR がゼロ（今ラウンドの新規指摘だけでなく台帳全体で数える）
- 最後の編集の後に、レビュー役が作業ツリーの現在の状態を独立にレビューし、その結果が台帳に反映されている
- 残っているのが MINOR / NIT だけで、直さない理由を説明できる
- 変更範囲をカバーする検証が通っている

リスク受容の BLOCKER・MAJOR が残ったまま止める場合は「収束」と呼ばない。
終了理由を「リスク受容で終了」とし、対象の指摘と理由を報告に列挙する。
単なる見送りは未解決のままなので、収束にも「リスク受容」にもならない。

## 原因クラスと面の種別

指摘は件数でなく**原因クラス**で数える。レビュー役が各指摘に 1 つ付ける（`cause_class`）。

| クラス | 意味 |
| --- | --- |
| `spec` | 契約・仕様の不備 |
| `principle` | 原理の誤り |
| `scope` | 範囲が広すぎる |
| `premise` | 前提・旧挙動の理解の誤り |
| `impl` | 実装ミス |
| `surface-open` | 保証したい面が閉じていない（config・hook・環境変数など、全状態を列挙しないと保証を言えない） |

`introduced_by_fix` は、前ラウンドの修正を直接の原因として出た新しい指摘かを示す。
「面の種別」は `surface-open` をさす: これが出たら、範囲を狭めるか撤去するかを先に検討する（T7）。

## `rounds.jsonl`（判定用の記録）

1 行 1 ラウンド。`fingerprint` は「同じ箇所・同趣旨」を同定する短い文字列（例: `gate:bypass-env`）。

```jsonl
{"round": 1, "cost_usd": 0.8, "findings": [{"id": "R1-1", "severity": "BLOCKER", "cause_class": "impl",
 "fingerprint": "gate:bypass-env", "status": "open", "introduced_by_fix": false}]}
{"stepback": {"at": "2026-11-06 10:00", "decision": "範囲を狭める"}}
```

- `status`: `open`（未修正）・`fixed`（修正済み・独立レビュー前）・`verified`（独立レビューで確認）・`accepted`（リスク受容）
- 同じ `id` を後のラウンドで書くと状態の更新。初出のラウンドが「新しい指摘」
- `{"stepback": {...}}` 行で区間が切れ、判定は最後の step back より後だけを見る

## 停滞のパターン

### 1. 同じ指摘が名前を変えて戻る

R1「エラー処理が無い」→ 修正 → R2「例外が握りつぶされている」。
表現は違うが同じ箇所の同じ設計上の問題を指している。
これは**修正が対症療法になっている**サイン。
指摘の表面ではなく、指摘が生まれる構造を直す。

### 2. 修正が新しい指摘を生む

R1 で 3 件直したら R2 で 4 件出た、が 2 回続く。
**変更の範囲が広すぎる**か、設計が要求に合っていない。
ループを止め、設計の選択肢を整理してユーザに報告する。

### 3. レビュー役が文脈を取り違えている

同じ指摘が返るが、こちらの誤検知・リスク受容の理由に反論が無い。
プロンプトで規約や意図の抜粋が足りていない可能性が高い。
**1 回だけ**プロンプトを補強して再試行し、それでも同じなら報告する。

### 4. 指摘が NIT に痩せていく

BLOCKER / MAJOR がゼロになった後も回し続けると、
レビュー役は何か言おうとして NIT を出し続ける。
これは停滞ではなく、収束の条件を満たしていれば**収束済み**。すぐ止める。

### 5. 同じ原因クラスが再発する・異なるクラスの BLOCKER が毎ラウンド出る

指摘の箇所や趣旨は変わっているのに、原因クラスが同じ（T1）、あるいは BLOCKER が毎ラウンド別のクラスで出続ける（T2）。
穴を塗いでも次の穴が出るのは、範囲・原理・責任の置き場所が合っていないサイン。同様に、直した結果の新しい BLOCKER（T3）、
未解決の BLOCKER がラウンド 3 以降に複数残る（T6）、`surface-open`（T7）、累計の件数・費用の超過（T5）も同じ扱い。
**パッチを当て続けず、`stepback.md` の手順へ移る。**

## 判定の手順

各ラウンドの終わりに `scripts/converge.py check` を実行する（T1〜T7 の定義は `converge.py explain`）。手で確かめるときは次。

各ラウンドの終わりに次を確認する。

1. 今回の指摘のうち、前回と同じ箇所・同じ趣旨のものはどれか
2. それが指摘全体の半分以上なら停滞候補
3. 停滞候補が 2 ラウンド続いたら step back（T4）

比較は `./.tmp/review-loop/<run-id>/round-<N>.md` に残した指摘一覧で行う。
記録を残していないと、この判定はできない。

## step back したあとにやること

停滞・トリガーで止めたときは、**`stepback.md` の手順**（原因クラスで分類 → 12 の問い → 転換の型から案を比べる → 決定ログ → 新しい run-id で現状レビュー）を行う。
利用者の承認が要るもの（権限・元に戻せない操作・全廃）と、step back を 2 回行っても収束しないときは、
次の一手が分かる形で報告して止まる。

- 対立している論点は何か（レビュー役の主張 / こちらの主張）
- どちらを採るかで何が変わるか
- 判断に必要な情報は何か

「収束しませんでした」だけで終えない。
