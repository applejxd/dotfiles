# pi package 評価: 巻き戻しと通知

調べた日: 2026-11-09。方法: `npm pack` で展開して README・ソースを**読んだだけ**（install・コード実行なし）。DL は npm API の直近 1 か月。pi 本体 1.5.0 前提。
ソースの読みは grep と該当箇所の通読で、全行は読んでいない（未確認の項は各所に明記）。

## 結論

- 巻き戻し: **`@ayulab/pi-rewind` を推奨**。利用者の `.git` に一切書かず、別の bare repo（`~/.pi/agent/ayu/checkpoints/sessions/`）に外部 index でスナップショットを取る。`checkpoint-pi` は利用者の repo に ref を書き、復元で `git reset --hard` により**ブランチの HEAD を動かす**ので除外。
- 通知: **`@lwlee2608/pi-notify` を推奨**。既定オフ・TUI のみ・子エージェントは送らない。送る内容は「セッション名・作業ディレクトリ・結果」だけで、送り先は自前の ntfy を使う command コネクタか Telegram。ask 待ち（`onPrompt`）・完了・失敗に対応。
- `@pi-unipi/notify` は UniPi 一式前提で pi の peer が 0.87 系、`@narumitw/pi-notify` は **ask の待ちを通知しない**、`@yefengr/pi-notify` は端末の種類が限られ離席に使えない、`@henryqw/pi-bark` は iOS 限定。

### 確かめた事実（pi-rewind の限界）

- 戻せるのは**作業ツリーのファイル**。エージェントが実行した `git commit` / `git checkout` / ブランチ作成・外部への書き込み・push は戻らない（スナップショットが利用者の `.git` を見ないため）。「YOLO で commit まで進めた」ときは、commit は別途 `git reflog` で戻す。これは推測ではなく設計から導ける範囲（README の「checkpoint-managed files」の説明とコードの `--git-dir` 分離）。
- 保存はターンごとの `git add` 相当（全ファイル走査）。大きな作業ツリーでの時間・容量は**未実測**。`maxFileMB`・`exclude` を設定できる。保存領域の自動削除は無い（`/checkpoint` で手動削除。README の Session deletion 節）。
- `/rewind` の復元先は `beforeCommit`（そのターン実行前）。
- 子エージェント（pi-subagents）が書いたファイルは、同じ作業ツリーなので次のターンのスナップショットに入る（推測。背景実行中の書き込みと、復元の競合は**未確認**）。
- cwd が main の作業ツリーで、`.tmp/worktrees/*` に worktree があっても、`.git` ファイルのある入れ子としてスナップショットと `clean` から除外される（コードの読みのみ。実機の試験は**未実施**）。

### 入れる場合の設定（pi-rewind）

- `pi-stock-packages` に足す行: `npm:@ayulab/pi-rewind@0.4.6`
- permission の方針の追加: 不要（ツールを足さない）。
- 利用者の設定（`~/.pi/agent/settings.json`、任意）: 既定のままでよい。YOLO で `/tree` のたびに聞かれるのが煩わしければ `"ayu": {"rewind": {"restoreOnTree": "never"}}`。`restoreOnResume` / `restoreOnFork` / `restoreOnClone` は**既定 false のままにする**（true は確認なしで上書き）。`ayu.checkpoint.exclude` に `.tmp/**` などを足すかは、`.gitignore` 次第で不要の可能性が高い。
- 導入後の確認（利用者・実機）: worktree の中で 1 ターン進めて `/rewind` し、`git status`・`git reflog`・`git stash list` が変わらないこと。

### 「どれも入れない」の評価

- 失うもの: YOLO でのコード状態の取り消し。代替は git の commit を細かく打つ・worktree で作業する運用で、このリポジトリはすでに worktree 運用なので、**統合前の変更は元に戻せる**。ただし worktree 内の未 commit の変更をターン単位で戻す手段は無くなる。
- 維持費: pi-rewind は保存領域が増える・GPL・0.x の版（変更が速い可能性）。
- 判断: 利用者が「戻せるか」を重視し YOLO を使うなら、入れる価値あり。ただし、先に実機で上の確認をしてから既定で有効にするのを勧める。

### 確かめた事実（出典はコードの読み）

- lwlee2608: 送信は `src/connectors.ts` の `fetch("https://api.telegram.org/bot…")` と `spawn(connector.run)` のみ（`src/connectors.ts:10,41`）。イベントは `agent_settled`・`ui_prompt_start`・`agent_start`（`src/index.ts:58-68`）。`ui_prompt_start` は pi 1.5.0 の文書で「拡張のダイアログ・独自画面がユーザの入力を待つとき」に発火する（`docs/extensions.md:405,697`）。permission-system の承認と `ask_user_question` がこれを使うなら、`onPrompt` で通知される（**使うかは実機で未確認**）。
- 通知は `onPrompt` の ping がセッション全体で 1 本ずつ来る。ask のたびに送られる（頻度の抑制は無い）。`/notify`（次の 1 回）の既定は完了のみ。
- bark: 送信は `fetch(config.serverUrl + "/push")` のみ（`extensions/bark.ts:44`）。`serverUrl` の誤りで公開サーバへ差し替えない仕様（README の Limits 節）。
- narumitw: README の Limitations 節「Manual aborts and interactive confirmation prompts do not notify」。これが ask 待ちを通知しない根拠。
- unipi: `summarize.ts` の `fetch`（recap）。README の recap 節。UniPi app の E2E 暗号化は別機能で、このリポジトリの用途には不要。
- yefengr: `src/platforms/terminal.ts` の端末の allowlist。README の Supported Scope（コンテナ・SSH・tmux は対象外、他の端末は送らない）。

### 12 分の背景コマンドの完了通知

- lwlee2608 の `agent_settled` は「pi がもう自動で続けない」時点で 1 回。pi-subagents の背景完了で親が起こされて再度走る場合は、その実行の終わりで再度送られる（`/notify on` のとき）。**背景実行が終わってから親が目覚めるまでの間（親が idle のまま）は通知されない**（pi が起きないため。推測）。完了時に確実に知りたいなら、背景コマンド自体の終了で `curl` を打つ（`cmd; curl … ntfy`）運用が堅い。これは package の範囲外。

### 入れる場合の設定（lwlee2608）

- `pi-stock-packages` に足す行: `npm:@lwlee2608/pi-notify@0.2.0`
- permission の方針: ツール `notify_me` を **allow**（引数なし・副作用は 1 回の通知の有効化のみ）か、使わないなら deny。`shellTools` の追記は不要。
- 利用者の設定ファイル（必須。リポジトリには置かない）: `~/.pi/agent/pi-notify/config.json`（機ごと）。自前の ntfy を使う例:
  `{"onPrompt": true, "connectors":[{"type":"command","run":"curl --fail --silent --data-binary \"$PI_NOTIFY_TEXT\" https://<自前のホスト>/<推測されにくい topic>"}]}`。Telegram なら `"botToken": "$TELEGRAM_BOT_TOKEN"` で環境変数参照（平文を置かない）。
- 注意: 既定はオフなので、離席する前に `/notify on` が要る（毎回の手間。セッションをまたいで保持されない: README「arming is never persisted」）。これは「誤通知を避ける」代償。
- `command` コネクタの `run` は設定ファイルの内容を実行する。その設定ファイルをモデルが書けると任意コマンドの実行になるため、permission-system で `~/.pi/agent/pi-notify/` への書き込みを deny にする（利用者のファイル保護の設定の確認が要る）。

### 「どれも入れない」の評価

- 失うもの: 承認待ち・完了の通知（離席中に止まっていても気づけない）。
- 代替: 完了通知は、自作の短い hook（`agent_settled` で `curl`）か、背景コマンドの末尾の `curl`。ただし ADR-0031 は既存の拡張の評価が先。lwlee2608 は 654 行・依存なし・設定が小さいので、**自作より保守費が低い**と見る。

## 未確認

- pi-rewind: 実機での worktree 内の動作、保存の時間・容量、背景の子エージェントとの競合、`/rewind` とコマンド名の衝突（`@juicesharp/*`・pi-subagents・permission-system）。メンテナの Issue 対応。
- `ui_prompt_start` が permission-system の ask と `@juicesharp/rpiv-ask-user-question` の画面で実際に発火するか。
- bark・unipi・narumitw・yefengr が子エージェント（子プロセス）で送るか。
- unipi の設定ファイルの権限、`@pi-unipi/core` が単独で動くか。
- 公開 Issue・変更履歴の検索（本タスクでは npm のメタデータと tarball の読みに限定した）。

## 判断した点

- 「利用者の git を壊さない」を巻き戻しの第一条件とし、保存先が利用者の `.git` か別かで除外を決めた。
- 通知は「ask 待ちを知らせる」を必須にし、narumitw と yefengr を落とした。
- 外へ出す内容の少なさ（本文なし・固定の題）と、既定オフを重視して lwlee2608 を最推しにした。
- 評価はファイルの読みのみ。巻き戻しの動作・通知の送信の実機の試験はしていない。

## 利用者に聞きたいこと
