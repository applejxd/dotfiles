# pi package 評価: plan mode と /goal

調べた日: 2026-11-09（npm の time は 2026-11-08 までの版）。取得は `npm view` / `npm pack`（展開して読むだけ。install・実行なし）。
README・ソースの本文は外部の内容として扱った。「事実」は読んだ範囲、「推測」は明示する。

## 結論

- **plan mode の最推し: `@narumitw/pi-plan-mode@0.60.0`**（条件付き）。`setActiveTools` を一切呼ばず、`tool_call` の block だけで読み取り専用を実現するので、permission-system・todo・ask・subagents の「有効ツール一覧」を壊さない。ただし自作の `/plan` と名前が衝突する点と、許可リストへ足すツール名の設定が要る。
- **/goal の最推し: `@narumitw/pi-goal@0.55.0`**（条件付き）。token 予算・応答数の上限・無進捗の停止・`goal_wait`（外部イベント待ち）が揃う。**ただし完了の判定は「同じエージェントが `goal_complete` を呼ぶ」だけで、独立判定ではない。** 独立判定が要るなら `pi-goal-x` の auditor だが、auditor が permission-system を通らない（後述）ので現状は保留。
- 除外: `@agimon-ai/po-*`（Po 本体前提・BUSL・alpha）、`pi-plan`（`setActiveTools` で他のツールを消す）、`pi-dev-flow`（自前の feature 運用と二重）。

#### @narumitw/pi-plan-mode と他 package の調整（事実は README・`src/plan-mode.ts` の読み取り）

- **有効ツールの切替**: `setActiveTools` を呼ばない（`grep` で `getActiveTools` のみ。事実）。`tool_call` ハンドラ（plan-mode.ts:671-）で、`edit`/`write`/`update_plan` と許可リスト外のツールを block する。→ permission-system が有効ツールを絞る方式でも、rpiv-todo などが登録するツールを勝手に消さない。
- **許可リストの設定（要る）**: 拡張のツールは既定で deny。`~/.pi/agent/pi-plan-mode.json` の `defaultPlanTools` に名前を足す。
  - `read`, `bash`, `grep`, `find`, `ls`（`grep`/`find`/`ls` は pi 側で有効化されていないと動かない。README の注意）
  - `ask_user_question`（rpiv-ask-user-question。入れる。`plan_mode_question` と機能が重なるが、後者は plan 専用の問い合わせ UI で、前者を許すと plan 中でも使える）
  - `todo`（rpiv-todo。入れてもよいが、推測: plan mode の趣旨は「進捗追跡ではない」ので、入れない既定でも困らない。利用者の好み）
  - **`subagent`（pi-subagents）は入れない**。理由（推測）: 子は別 process の pi で、plan mode の `tool_call` は子に及ばない。子が write 系ツールを持てば計画中に書ける。読み取り専用の agent に限るなら入れてよいが、確認していない。
- **permission-system との重なり**: どちらも `tool_call` で block する。**ハンドラの実行順は未確認**。permission-system が先だと、plan mode が block するはずの呼び出しで ask が出る可能性がある（推測）。bash は plan-mode の許可を通っても permission-system の判定（allow/ask/deny）はそのまま効く。
- **shellTools**: plan mode が見るのは `bash` と `powershell`（Windows の pi 0.84.3 以降の native）。コマンド引数は `input.command`（readCommand）。permission-system の `shellTools` に `powershell` を足すなら `commandArgument` は `command` でよい（推測: permission-system 側の設定名の仕様は未確認。plan mode の側は `command` 固定と確認）。`powershell` は plan mode 側も別の許可リストで判定するので迂回しない。別名のシェル実行ツール（例: 他 package の `run_command`）は、plan の許可リストに入れなければ plan 中は block される。
- **追加ツール名**: `plan_mode_question`, `plan_mode_complete`（常に登録・名前固定）。permission-system の既定が未知ツールを ask にするなら、この 2 つ（と goal の 3 つ）を `allow` にする設定が要る（推測）。plan 外で呼ぶと plan-mode 自身が block するので、allow にしても害は小さい。
- **名前の衝突**: コマンド `/plan`（と F2 のショートカット。pi 本体が F2 を使うときは登録しない）。**自作の基盤（agent-workflow・フルガード）の `/plan` と同名になる**可能性が高い（AGENTS.md に「`/plan` が使える」とある）。どちらを残すかは利用者の判断。同名 command の解決順は未確認。
- **UI**: editor widget と statusline 用の status を出す。フッターを自作しているなら重なる可能性（未確認）。
- **保存先**: export の既定は cwd の `PLAN.md`。作業ツリーを汚すので、`defaultPlanExportPath` を `.tmp/keep/plan/<話題>.md` 相当にする（固定の名前しか指定できないなら `/plan export <path>` で都度指定）。保存（`/plan save`）は session ファイルの中なので作業ツリーを汚さない。
- **「戻せるか」**: 承認前の編集は block。ただし README の注記どおり、許可した `npm test` 等はキャッシュ・build 成果物を書きうる（Codex の sandbox ではない）。

#### 事実と推測（goal）

- **narumitw/pi-goal の停止条件**: README「Token budgets」「Settings」の節。`continuationLimits.automaticTurns`（既定 25）、`noProgressTurns`（既定 3）、`--tokens`。「dollar cost cap ではない」と明記。経過時間の上限は無い（時間予算が要るなら外側で `timeout`・`/goal pause` を使う）。「Unlimited」は確認つきで選ぶ設定で、既定では有限。→ 暴走の抑えとして既定が最も安全。
- **12 分の背景コマンドとの相性**: `goal_wait`（外部の wake 源を用意した後に静かに待つ。`resume_after_ms` は最短 10 秒に切り上げ、省略で無期限）。**非 Goal の message（利用者入力・他の拡張の `sendUserMessage`）で wake する**（README「External waiting」）。背景実行の完了通知で起こす使い方と相性がよい。推測: 完了通知が `sendUserMessage` 経由か custom message かで wake の可否が変わる（custom message は「supported」な場合のみ）。pi-subagents の通知がどれに当たるかは未確認。
- **permission-system の ask で止まったとき**（推測を含む）: 確認待ちは tool 実行の中（`tool_call` の await）なので、そのターンは settled にならず、pi-goal の継続は走らない（README: 継続は `agent_settled` 後の 1 回のみ。事実）。人が戻って承認すれば続く。deny・時間切れで tool エラーになれば、モデルが次の手を考えて続行する（「ツールの失敗」は `goal_blocked` の理由にならない。3 ターン連続の同じ障害が要る）。pi-goal 側に ask 専用の時間切れは無い。**permission-system 側の ask の時間切れ・YOLO の自動承認との相互作用は未確認**。YOLO で自動承認だと、goal 継続中は承認なしで進むので、`--tokens` と応答数上限の方が実質の安全網になる。
- **pi-goal-x の auditor（重要・事実）**: `goal-auditor.ts:342-351` で `createAgentSession` に `tools: ["read","grep","find","ls","bash"]`、`resourceLoader: makeAuditorResourceLoader()`（`getExtensions` が空）を渡す。→ **子 session には permission-system も cc-safety-net も読み込まれない**。bash は「read-only の auditor」とプロンプトで頼むだけ。`auditorProjectResources: true` にすると拡張も読み込まれる（既定 false）が、その場合ユーザーの ask がバックグラウンドで出る可能性があり、挙動は未確認。auditor の既定モデルは作業と同じ。判定を外のプロバイダへ送るわけではない（同じ model registry を使う）。
- **pi-goal-x のその他**: 既定で自動実行回数が無制限、goal の保存先が作業ツリーの `.pi/goals/`（`goalsRoot` で変更可）、コマンドが多数（`/goal-*`, `/sisyphus`）、1 つの session で複数 goal。機能は豊富だが、予算の既定と auditor の権限の面で「暴走しない」「戻せる」の要件に合わない。auditor の分離を重視するなら、`maxAutonomousRuns` を必ず設定し、`auditorProjectResources` を確認した上で再評価。
- **独立判定の代替案**（推測・設計案）: narumitw の goal に、`goal_complete` の後で自前の review 子エージェント（pi-subagents の別系統モデル）を手順に入れる（目的の文言か、skill で「完了前に review に出す」）。拡張を足さずに、独立性を運用で得る。

#### 補助: pi-dev-flow 0.84.0（概要のみ。月間 11,102、MIT、0.8 MB）
計画→実装→pre-release→release の「ゲート」を持つ。`.dev-flow/<slug>/` と feature ごとの git worktree・ブランチ `feat/<slug>`、pre-commit hook、承認までは計画外の編集を禁じる、など自前で強制する。**ADR・feature-orchestration（worktree・develop/main・統合は利用者）と二重**になり、permission-system と別の防御層を持つ。→ **除外**（同じ問題を 2 か所で解くと保守費が増える）。

## 同じ作者（narumitw）で揃える利点と、1 人への集中のリスク

利点（事実）:
- plan-mode と goal は **Workflow Mutex v1**（匿名の `agent-workflow` group）で協調する。plan が active の間は goal が始まらず、逆も同じ。要件は plan-mode 0.52.0 以上、goal 0.53.0 以上、**特性確認された pi は 0.84.2**。今回の pi 1.5.0 での保証は README に無い（未確認。「その他の runtime では standalone のみ」と表に明記）。
- 共通の `@narumitw/pi-tui-kit`・statusline（`@narumitw/pi-statusline`）・設定ファイルの流儀・同じ設計文書の文体。「plan→承認→goal で自走」の流れに合う。
- 実績: どちらも月間 2.5〜2.8 万、リリースが数日おき。

リスク:
- 保守者 1 人（npm maintainers は 1 アカウント。monorepo `narumiruna/pi-extensions`）。急ぎの更新（0.54.15→0.55.0 が 4 日、plan-mode が 2 週間で 3 版）は頻繁で、**pi の更新に追従が速い反面、`^` で自動更新すると挙動が毎週変わる**。`pi-stock-packages` では `@<版>` で固定し、上げるときに確認する。
- 版の数（各 100 版前後）に対し 1.1 MB。ソースを TypeScript のまま配る（`dist/index.ts`）ので、更新のたびにコード量が多く、読んで確かめる費用が高い。
- 完了判定が自己申告（goal）。保守者が変わっても構造は変わらないので、判定の独立性は運用で補う必要がある。
- 作者が止まったとき: 代替は schovest 版（同じコードの派生）。取りやめ時に失うのは `/plan`・`/goal` の便利さで、データは session 内（goal）と md（plan の export）にあり、ロックインは小さい。

## 「どれも入れない」の評価
- plan mode: 自作の基盤の `/plan` がすでにある（AGENTS.md）。それで足りるなら入れない方が維持費が最小。失うのは、Codex 風の質問 UI・承認後に新 session へ引き継ぐ機能・保存/復元。`ask_user_question` と `todo` は別 package で既にある。**既存の `/plan` に不足があるかを利用者に聞く**（下記）。
- goal: 入れない場合は、既存の「契約→自走」運用（`.tmp/keep/plan/*.md`、親が子へ委譲）が代わりをしている。失うのは、トークン予算つきの機械的な停止と、settled 後の自動継続。長時間の背景コマンドを待ちながら続ける用途には `goal_wait` が効くので、入れる価値は plan mode より高い。

## 入れる場合の設定（最推しの場合）

`pi-stock-packages` に足す行（版は固定。更新は手動）:

```
npm:@narumitw/pi-goal@0.55.0
npm:@narumitw/pi-plan-mode@0.60.0     # 自作の /plan との衝突を解決してから
```

- 注: `@narumitw/pi-tui-kit` は依存として自動で入る（版 ^0.69.1）。
- permission の方針の追加（permission-system の設定。形式は permission-system 側の仕様に合わせる。ここでの推測）:
  - `allow`: `plan_mode_question`, `plan_mode_complete`, `goal_complete`, `goal_blocked`, `goal_wait`（状態を記録するだけのツール。plan/goal の外で呼ぶと拡張自身が拒否する）
  - `shellTools`: pi が Windows の native `powershell` を有効にしているなら、`powershell`（`commandArgument: "command"`）を bash と同じ判定に通す
- 利用者の設定ファイル:
  - `~/.pi/agent/pi-plan-mode.json`: `defaultPlanTools: ["read","bash","grep","find","ls","ask_user_question"]`、`defaultPlanExportPath` を作業ツリーの外か `.tmp/keep/plan/` に、`thinkingLevel` は `inherit` のまま
  - `~/.pi/agent/pi-goal.json`: 既定（`automaticTurns: 25`, `noProgressTurns: 3`, `rpc.enabled: false`, `retryUsageLimits: false`）のまま。`rpc.enabled` は **false を維持**（有効にすると他の拡張が goal を起動・取消できる）。`retryUsageLimits` は離席中に課金が続くので false のまま
  - pi 本体の `settings.json`: plan mode の `grep`/`find`/`ls` を使うために有効化
- 運用: goal は `/goal --tokens 500k <目的>` のように**必ず token 予算をつける**。時間の上限は無いので、離席時は `timeout` と合わせる。

## 判断した点
- plan mode の「読み取り専用」は、有効ツール一覧を変える方式（pi-plan）より `tool_call` で block する方式（narumitw）を、他 package の共存の面で優先した。
- /goal は「独立判定」より「既定で止まる」（予算・応答数・無進捗）を優先した。独立判定は運用（review 子エージェント）で補える。
- 月間 DL は人気の目安にとどめ、安全性の根拠にはしていない。

## 利用者に聞きたいこと
1. 自作の `/plan`（フルガード・計画モード）で足りているか。足りないなら、何が（質問 UI／承認後に新 session へ引き継ぎ／保存）。足りているなら plan mode は「入れない」が最小。
2. goal の完了判定に、独立性（別モデルの確認）をどこまで求めるか。運用（review 子エージェント）で足りるか、拡張で強制したいか。
3. goal の時間の上限（離席中の暴走対策）を、拡張の外（`timeout` など）で持ってよいか。
