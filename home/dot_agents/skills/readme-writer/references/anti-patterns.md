# README のよくある失敗と、見つけ方

根拠の強さ: **【検査】**=スクリプトが見つける / **【手順】**=手順で防ぐ / **【推測】**=一次の研究は無く、
先行スキルの記述や実務の見立て(research 0007)。

| 失敗 | 何が起きるか | 防ぎ方 |
| --- | --- | --- |
| 実在しないコマンド・タスク・パス | 最初の一歩で詰まる。信頼を失う | 【検査】`command-missing` / `path-missing`。台帳から書く |
| 切れたリンク・アンカー | 読者が迷う | 【検査】`link-missing` / `anchor-missing` / `image-missing` |
| 別のパッケージ管理ツールを書く(npm と pnpm、pip と uv の取り違え) | インストールで失敗する | 【手順】lockfile は実ファイルで確かめ、scripts は台帳を見る。【推測】先行スキルの失敗報告(readme-wizard) |
| 存在しない機能・連絡先・SNS を作る | 虚偽になる | 【手順】根拠の無い主張を書かない。【推測】先行スキルの失敗報告 |
| 幻覚されたパッケージ名の install 手順 | 悪意あるパッケージを入れさせうる(slopsquatting) | 【手順】名前は manifest から取る |
| `TODO`・テンプレの穴が残る | 未完成が公開される | 【検査】`placeholder-todo` / `placeholder-hole` |
| license の食い違い・無言 | 利用条件が曖昧になる | 【検査】`license-*` |
| 概要の羅列(コードの言い換え) | 長くなるだけで読者に効かない | 【手順】読者の仕事に効くものだけ。AGENTS.md の研究(arXiv 2602.11988) |
| 誇大な言い回し・飾りのバッジ | 信用されない | 【検査】`hype-words` / `badges-many`(警告) |
| 手で作った出力例 | 実際と違う | 【手順】実行した本物の出力を貼る |
| README が古くなる | 約束が嘘になる | 【検査】再実行できる(`check_readme.py` を CI に入れてもよい)。LLM に陳腐化を検知させるのは精度が低い(arXiv 2603.00489) |
| 全部入りの README | 入口として読めない | 【検査】`too-long`(警告)。詳細は docs/ へ |
