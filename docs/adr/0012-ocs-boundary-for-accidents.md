# ocs の境界の目的を「エージェントのうっかりを防ぐ」に絞る

- **ステータス**: Accepted
- **日付**: 2026-09-29
- **決定者**: applejxd

> **ステータスの変更（2026-09-29）**: Proposed → Accepted。利用者が内容を確認して同意した。
> 実装は [CHG-0009](../change/closed/0009-ocs-simplify-for-accidents.md) で進める。

## コンテキスト

`ocs` は、OpenCode を `srt`（`@anthropic-ai/sandbox-runtime`。bubblewrap・seccomp・
通信の proxy で OS の境界を張る道具）で包んで起動するランチャー。
[CHG-0004](../change/closed/0004-opencode-sandbox.md) で作り、仕様は
[opencode-sandbox](../spec/opencode-sandbox.md) にある。

これまでの設計は、**ワークスペースの中身そのものを疑う**前提に立っていた。
境界の内側から書けるもの（リポジトリのファイル、設定、`.git` の設定が指す
スクリプト）が、ホストで動く処理を騙しうる、という脅威モデルである。
そのため、境界そのもの以外に次のような処理を積み上げてきた。

- 境界を張る前にホストで動く道具（`srt` 自身、退避の `git`、`rg`、管理操作の
  `opencode`）へ渡す環境変数・PATH・設定を 1 つずつ固める
- ワークスペースごとに隔離用 DB を持ち、他のプロジェクトの会話を境界に入れない。
  その代わりに `--handoff` / `--list-sessions` で行き来する
- `.opencode/sandbox.toml`（リポジトリが境界を広げる要求）を、ハッシュ付きで承認させる
- 全部 allow の子エージェント `bypass-worker` を、プロンプトインジェクションで
  普通のエージェントから呼ばされないよう、生成時に各エージェントの設定へ
  deny を差し込む

2026-09-28〜29 の review-loop（外部レビューと修正を繰り返す作業。記録は
リポジトリに入れていない）で、この前提の限界が見えた。

| 観測 | 内容 |
| --- | --- |
| 収束しない | 4 ラウンドとも、前の修正のすぐ隣に新しい穴が見つかった。ホストの `git` を固めると引用形式のファイル名で外のファイルを読む穴が、管理操作の PATH を固めるとプロジェクト設定の plugin を読む穴が出た |
| 修正で増える | 「危ない動きを列挙して塞ぐ」形なので、修正のたびにコードが増える。`generate.py` はこの期間に 300 行以上増え、前回の生成結果から保護の状態を推測する処理まで入った |
| 使い勝手 | 履歴が通常起動と分かれる、他のディレクトリを読めない、起動時に承認や検査で待つ・断られる |

利用者の実際の使い方は次のとおりで、上の脅威モデルとずれていた。

- 開くリポジトリは自分で精査している。精査していないリポジトリを境界で安全に
  開くことまでは求めていない
- 境界に期待しているのは、**エージェントのうっかり**（外部への誤送信、
  ワークスペース外の破壊、秘密の誤読）を止めること
- ここまで利便性を落とす意図は無かった

制約として、`srt` 0.0.76 の Linux 版では、**`~/.ssh` のような一部だけを拒否する
`denyRead` は黙って無視される**。効くのは「広く拒否して `allowRead` で開け直す」
形だけである（[sandbox-runtime の調査](../research/opencode/permission/sandbox-runtime.md)
の 3 章）。広く開けた中の一部を塞ぎ直すこともできない。

## 検討した選択肢

### 選択肢 1: 今の前提のまま、穴を塞ぎ続ける

- **利点**: 精査していないリポジトリを開いたときの耐性が最も高い
- **欠点**: 4 ラウンドで収束しなかった。上流（`srt` / OpenCode / git）の挙動が
  変わるたびに、ホストで動く道具の新しい経路を追う必要がある。使い勝手は戻らない

### 選択肢 2: 目的を「うっかりの防止」に絞り、上乗せを外す

境界そのもの（プロセス全体を包む・書き込みを限る・通信先を限る）は残し、
悪意あるワークスペースを前提にした上乗せを外す。

- **利点**: 使い勝手が戻る。ホストで動く道具を追いかける作業が消える。
  レビューの終わりの条件を有限の項目で決められる
- **欠点**: 精査していないリポジトリを開くと、ホストで仕込まれたものが動きうる

### 選択肢 3: `srt` をやめ、OpenCode の permission だけに戻す

- **利点**: 最も単純
- **欠点**: OpenCode はプロジェクト設定・plugin・MCP から permission を上書きできるので、
  ツール層だけではうっかりも止められない（[CHG-0004](../change/closed/0004-opencode-sandbox.md)
  の発端）。境界の利点まで捨てることになる

## 決定事項

**選択肢 2 を採用する。**

理由: 利用者が求めているのはうっかりの防止で、それには境界そのものが効く。
悪意あるワークスペースへの耐性は、求められていないのに保守の費用の大半を占め、
しかも収束しなかった。選択肢 3 はうっかりすら止められない。

### 保証するもの

- **書き込み**: 起動ディレクトリ・`~/.cache`・worktree の共有 `.git`（`hooks` と
  `config` を除く）、と OpenCode の永続状態に必要な例外だけ
- **通信**: 許可したドメインだけ
- **秘密**: `~/.ssh` などの秘密を含む場所は読めない
- **この dotfiles の制御ファイル**（permission・境界・ランチャーの単一ソース）と配備済みの
  ランチャー・設定は、境界の内側から書けない。ただし効く範囲は条件付き: source state は
  起動ディレクトリとその Git の根から相対で解く保護対象として守り、配備先は重なる場所での起動と
  重なる `write` の拒否で守る。精査していない `.opencode/sandbox.toml` の `write` で Git の根の外の
  別の場所を開けた場合、そこにある source state は対象外
  （[制御ファイルの保護が効く範囲](../spec/opencode-sandbox.md#制御ファイルの保護が効く範囲)）
- **起動前の退避**: うっかりで壊した未コミットの変更を戻せる（Git リポジトリの中で起動したとき。
  [起動前の退避](../spec/opencode-sandbox.md#起動前の退避)）
- **境界を張れないときは起動しない**

### 保証しないもの（非目的）

- 精査していないワークスペースが、境界を張る前にホストで動く処理（`srt`・`git`・
  `opencode` の管理操作）を騙すこと
- プロンプトインジェクションへの耐性
- プロジェクト間の会話の隔離
- 利用者自身の明示的な上書き（例: エージェント個別の `task = "allow"` で
  `bypass-worker` を呼べるようにすること）の後始末

### 項目ごとの扱い

| 項目 | 扱い |
| --- | --- |
| プロセス全体を `srt` で包む・通信先の許可リスト・書き込みの制限 | 残す |
| 起動ディレクトリの制限（`~` などで起動しない） | 残す。読み取りの方針を変えても、書き込みの範囲が広がりすぎないことを独立に守る |
| 制御ファイルの `denyWrite` | 残す。対象を際限なく増やさない |
| 読み取り | `denyRead: ~` の形は `srt` の制約上そのまま。**秘密を含まない作業用の親ディレクトリを `allowRead` で広めに開ける** |
| 隔離用 DB と `--handoff` / `--list-sessions` | ホストの DB の共有を第一候補にする。同時書き込み・snapshot の置き場・版の違いを実機で確かめ、駄目なら隔離用 DB を残して外で再開するコマンドだけにする。どちらにしても、今の隔離セッションを移してから機能を消す |
| `.opencode/sandbox.toml` の承認 | 記録をやめ、追加する書き込み先・通信先を表示するだけにする |
| 境界チェック | `ocs --check` で手動実行する。自動にするなら、境界の定義か `srt` が変わったときだけ |
| 起動前の退避 | 一時 index を使う素直な `git add -A` / `git archive` に戻す。コミットが無いリポジトリへの対応と大きさの上限は残す |
| ホストへ渡す環境の固め | 外す。ただし誤動作の防止に効く次は残す: `rg --no-config`、`srt` と `node` の実体の選び方、内側へ渡す認証の環境変数（`GH_TOKEN` など）の除去、`GIT_DIR` などで対象のリポジトリがずれることへの対処 |
| `bypass-worker` の保護 | 全体の deny と guide plugin の起動元の検査だけにする。各エージェントへの deny の差し込み・V1 → V2 の変換・保護を外したときの取り除きはやめる |
| guide plugin が `rules.json` を読めないとき | 節ごとに失敗を閉じ込め、他の節を巻き込まない。子エージェントを全部止めるのはやめ、警告にする |

## 決定の確認方法

- [ ] 秘密の目印（無害なファイル）を `~/.ssh` 相当の場所に置き、境界の内側から読めない
- [ ] 許可していないドメインへ出られない
- [ ] 起動ディレクトリの外（許可した例外を除く）へ永続的に書けない
- [ ] 普段の作業（別のリポジトリや資料を読む、worktree で commit する）ができる
- [ ] 境界の内側で作ったセッションを、境界の外で再開でき、snapshot から戻せる
- [ ] 以後の外部レビューは、上の項目と「保証しないもの」を渡して行い、
  「保証しないもの」に入る指摘は docs への記載で閉じる

## 結果

### ポジティブな結果

- 履歴の行き来・承認・起動前の検査の待ちが減り、Claude Code の sandbox に近い使い勝手になる
- ホストで動く道具の挙動を追いかける作業が消え、`ocs` と `generate.py` のコードが減る
- レビューを、有限の項目で終えられる

### ネガティブな結果

- 精査していないリポジトリ（clone 直後の OSS など）を `ocs` で開いても、ホスト側の安全は保証されない。
  そうしたリポジトリは、ホストの処理が触らない場所（コンテナなど）で開く
- ホストの DB を共有する場合、エージェントのうっかりで DB を壊すと全部の履歴に響く
- 読み取りを広げた分だけ、開けたディレクトリに紛れた秘密は読める

### 中立的な結果

- モデルの資格情報が境界の内側にあることは、今と変わらない（CHG-0004 で受け入れた例外）
- 実装は別の案件で進める。この ADR は実装の進捗を持たない
