# 統合は利用者が PR ビューアで押し、アプリが同期で実行する（保留と非同期承認を置き換える）

- **ステータス**: Accepted
- **日付**: 2026-11-03
- **決定者**: applejxd

## コンテキスト

[ADR-0023](0023-pending-approval.md) は、承認が取れない操作を保留として保存し、利用者が pi の `/pending approve` で後から承認して実行する形を選んだ。実機で次の摩擦が出た（[CHG-0062](../change/0062-pr-hub-simplify.md) §2）。

- 承認の記録が、承認する対象（枝の先頭）と別の永続物になり、古い保留がごみとして残る。
- 決定的な実行（squash）が、LLM を載せた TUI の中にあり、モデルの実行中は承認できない。スマホでは統合まで閉じられない。
- squash は元のコミットとの祖先関係を断つので、積み重ね（A の上に B）で衝突する。
- 保留・承認・受信箱の部品群に、独立 review の指摘が集中した。

## 検討した選択肢

### 選択肢 1: 保留を残して自動化する

巡回・一括承認・受信箱で、承認の操作を減らす。

- **欠点**: 保守する部品群が残り、スマホで統合を閉じられない。

### 選択肢 2: 統合を、人が操作するアプリへ移す

利用者が PR ビューアの「統合する」を押し、アプリが merge commit で同期統合する。保留・鍵・排他ロックは作らない。

- **利点**: 承認の記録が要らない。積み重ねで順序の問題が消える。pi を通常のコーディングエージェントへ戻せる。
- **欠点**: アプリが Fence の外で git を実行する（実行権限の移動）。

### 選択肢 3: GitHub の本物の PR・merge queue

- **欠点**: 公開リポジトリで作業中の枝が公開され、エージェントに push・merge の権限を渡すことになる。

## 決定事項

選択肢 2 を採る。AI は `git_commit` と `guarded_pr_summary` までを行い、統合は利用者の押下で行う。`git flow feature finish`・`git merge` を AI が実行するときは、素の pi の必須確認のまま。

理由: 承認の対象と記録を別物にしない形が最も単純で、実機の摩擦の原因（R1〜R5）をまとめて消せる。

## 決定の確認方法

- 統合器と API の試験（実 git。[ローカル PR ビューアの設計](../spec/pr-viewer.md)）。
- 運用では、積み重ねの統合が衝突せず通ること、残骸の ref が増えないことを見る。
- 実装の進捗は、ここに書かない（CHG-0062）。
