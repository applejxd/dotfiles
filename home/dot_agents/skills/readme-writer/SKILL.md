# readme-writer

README を、**リポジトリで確かめられる事実だけ**で作る・直す・点検する。
README は、初めて来た人が「何か・誰のためか・入れ方・最初の成功」を数分で掴む入口。
書いてあるコマンドやパスが実在しないと、一度で信頼を失う。だから事実はスクリプトで集め、書いたものもスクリプトで突き合わせ、
動かせるものは動かして、本物の出力を載せる。長く網羅的に書くことは目的ではない(読者に効かない節は、書かない方がよい)。

根拠と受け入れ条件は、スキルを作ったリポジトリ(skill-lab)の `docs/research/0007`・`docs/spec/0005` にある(配布した先では参照できない。手順は、この SKILL.md だけで足りる)。

## 守ること

- 対象は、頼まれた README(`README.md`・`README.ja.md`・サブディレクトリの README)。翻訳版は依頼の言語で書き、元と内容を揃える
- README に書く値(名前・版・コマンド・要件・license)は、事実台帳か実ファイルから取る。根拠が無いものは書かない
  (`TODO` や架空の値で埋めない)。**依頼されても根拠が無い項目**(速度・対応 OS・配布・動作保証など)は、書かずに、
  理由と「何があれば書けるか」を応答に 1 行ずつ書く
- **既存の README は、利用者が書き換えてよいと言っていなければ**、差分(または案)を見せて許可を得てから書き換える。
  「直して」「書き換えて構わない」と言われたときは、そのまま直してよい
- 検査スクリプトは読むだけ(ネットワークに出ない・README のコマンドを実行しない・リポジトリへ書かない・外を指すリンクや symlink は読まない)
- 秘密・個人のパス・手元の環境の値を README に写さない

## 手順

`SCRIPTS` は、この SKILL.md と同じディレクトリの `scripts/`(手順書を読んだパスから組み立てる。対象のリポジトリへ `cd` しない)。

1. **モードを決める。** Generate(README が無い・作り直し)/ Repair(古い・弱い節を直す)/ Audit(「見て」「点検して」。書き換えない)
2. **事実台帳を作る。** `python3 SCRIPTS/collect_facts.py <リポジトリ>` で、name・版・要件・コマンド/タスク・CI・LICENSE・既存 README の言語が
   `ファイル:行` つきで出る。台帳に出ない事実(何をするものか、誰のためか)はソース・テスト・既存の docs から読む。
   リポジトリから分からない**意図だけ**を利用者に聞く(聞けないなら、分かる範囲で最小の README にして、足りない点を報告する)
3. **読者の仕事で章立てを選ぶ。** 固定のひな形に埋めない。種類ごとの選び方と、載せない節の判断は [references/anatomy.md](references/anatomy.md)
4. **書く。**
   - 題名の直後に、何のためのものかを 1〜2 文。最初の成功への最短の道(前提 → インストール → 最小の使い方と期待する出力)を早く置く
   - コマンドはコピペで動く形で、台帳のとおりに書く(パッケージ管理ツール・名前・版を取り違えない)。**パッケージ名・コマンド名・import 名が違うときは、違いを明記する**
   - コードから自明な概要の羅列、飾りのバッジ・画像、依頼されていない節(Contributing・Roadmap・FAQ など)は足さない。
     限界・前提・未対応は正直に書く。数値・比較・実績は出典か実測があるときだけ
   - 詳細は別の文書へリンクする。LICENSE などの専用ファイルがあれば、節を作らずリンクだけにする。ただし前提条件と重大な注意はリンクの先に隠さない。
     **リポジトリに無い外部 URL**(外部ツールの公式文書・SNS・配布ページなど)は足さない。リンクは、リポジトリの中のファイルと、manifest・既存の README にある URL だけ
   - README は読者向けの文書にする。作業の経過(「この README を書いた時点では未実行」「検査済み」など)は書かず、応答で伝える。
     読者に必要な前提(「インストールは未確認」など、読者の判断に効くもの)だけ、使う場所のそばに書く
   - 言語は既存の README に合わせる(翻訳の依頼なら依頼の言語)。`AGENTS.md` / `CLAUDE.md` は別物で、README に混ぜない
   - 版の食い違い(manifest と `__version__` など)や、古い docs を見つけたら、README に誤った版を書かず、応答で知らせる
5. **検査する。** `python3 SCRIPTS/check_readme.py <README> --repo <リポジトリ>`。Generate / Repair では error を 0 にする
   (warning は基準で、残すなら理由を応答に書く。`path-missing` は実行時に作られるファイルなら無視してよい)。Audit では見つかった error をそのまま報告する。
   スクリプトが見ないもの: CLI のオプションの実在、出力例の正しさ → 次の手順で確かめる。`markdownlint-cli2` / `lychee` / `textlint` があれば追加で使ってよい
6. **動かして確かめる。** 次の条件を**すべて**満たすコマンド(テスト・`--help`・README の最小の使い方)は、**許可を求めずに実行**して、
   出力例を本物にする: 作業ツリーの中だけで完結する / ネットワークに出ない / 何もインストールしない / 秘密を使わない / 削除・上書きなど戻せない操作をしない。
   生成された一時ファイル(`__pycache__` など)は片づける。条件を満たさないもの(インストール・デプロイ・外への書き込み)は実行せず、
   「書いただけ(未実行)」と応答に書く。出力例は、実行した本物の出力だけを載せる(手で作らない)
7. **報告する**(次の節)。

## 報告(利用者への最終応答)

利用者に読まれる文章として書く。ツール名・内部の用語(「台帳」「Generate / Audit モード」など)・検査の件数だけの記述は出さない。
先頭に結論を 1〜2 文(何をしたか、できなかったこと)。続けて、**あるものだけ**:

- 確かめたこと: 実行したコマンドと結果、リンク・パスの実在確認の結果(1〜3 行)
- 確かめていないこと(未実行のコマンド・外部リンクなど)と、その理由
- 依頼されたが書かなかった項目と、その理由・何があれば書けるか
- 気づいた問題(版の食い違い・古い docs など。直していないもの)
- 利用者に決めてほしいこと(許可・質問)。あれば最後に

点検(Audit)の指摘は、重要な順に、README の行番号(**README を開いて確かめた行**。スクリプトの出力を写さない)・根拠のファイル・直し方を添える。
点検は指摘が本題なので、修正案の全文・言語の議論・書き換えの許可の確認で膨らませない(直してほしいときは言ってもらう、と 1 行で足りる)。
空のディレクトリなど、書ける事実が無いときは、書かない理由と、聞きたいことだけを短く書く。

## 中断する条件

- 対象が README の範囲外(サイト・API リファレンス全体)なら、その旨を伝えて止まる
- 利用者への確認が要る操作(既存 README の上書き・条件外のコマンドの実行)は、同じ形で繰り返さず、応答の「決めてほしいこと」に回す
