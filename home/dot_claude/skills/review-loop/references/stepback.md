# step back の手順

レビュー→修正が収束しないとき、パッチを当て続けず、**保証したい範囲・原理・責任の置き場**へ戻って設計から見直す手順。
正本の実例は、このリポジトリの 14 事例（非公開の調査記録）。判定は `scripts/converge.py check` が行う（トリガーの意味は `converge.py explain`）。

## ① いつ step back するか

ラウンドの終わりごとに `converge.py check <run-dir>/rounds.jsonl` を実行し、`verdict` が `stepback` なら本手順へ移る。
既定のトリガー（引数で変えられる）:

| 印 | 条件 | 実例 |
| --- | --- | --- |
| T1 | 同じ原因クラスの BLOCKER が累計 2 回再発（3 ラウンドで出現） | フルガード再設計の「緩和」クラス 3 回 |
| T2 | 異なる原因クラスの BLOCKER が 3 ラウンド連続で出る | `git_push` の 5 回の review |
| T3 | 直した結果の新しい BLOCKER が 2 ラウンド続く | `git_push` の v3 → v3.1 → v3.2 |
| T4 | 同じ fingerprint の BLOCKER/MAJOR が 2 ラウンド連続で open | 従来の「停滞」 |
| T5 | BLOCKER+MAJOR の累計が約 15 件、または累計費用が $6 超 | 非同期承認系の指摘 43 件 |
| T6 | ラウンド 3 以降で未解決の BLOCKER が 2 件以上 | 利用者の指定 |
| T7 | `surface-open`（保証したい面が閉じていない）が 1 件でも出る | `git_push`（config・hook・ref が面） |

利用者が「step back して」と言ったときは、トリガーを待たずに始める。

## ② 手順

1. **止める**。次の修正・レビューに進まない（パッチを当てない）。`rounds.jsonl` に `{"stepback": {...}}` の行を足す準備をする。
2. **指摘を原因クラスで分類する**（`spec`・`principle`・`scope`・`premise`・`impl`・`surface-open`）。件数でなく分類で数える。
3. **12 の問い**に答える（成功例で実際に行われた順）:
   1. 原因クラスは同じか、毎回違うか
   2. 原理が間違っているか、実装が間違っているか
   3. 面は閉じているか（環境の全状態を列挙せずに、保証したいことを言えるか）
   4. 範囲が広すぎないか（白名簿・厳密一致・1 形式・役割限定で閉じるか）
   5. 責任の置き場は正しいか（決定的な処理を LLM の中に置いていないか。非 LLM の部品か人の押下へ移せるか）
   6. **サンクコストを除いて、いま最初から作るならどうするか**
   7. やらない選択肢は何か（全廃・縮小・現状維持。全廃で失うものも書く）
   8. 実使用の証拠はあるか（0 件なら撤去を選択肢に入れる）
   9. 律速は何か（測ったか）
   10. 元に戻せるか（可逆なら強制をやめて指示にする。撤去は 1 feature で戻せる形、取り下げは退避ブランチへ）
   11. 旧実装を oracle（基準）にできるか（差分を数えられるか）
   12. 撤退条件を先に書いたか
4. **転換の型から 2〜3 案を表にして比べる**。各案が、いま出ている BLOCKER のクラスを**構造的に消せるか**を必ず書く（消せない案は穴を塞ぐだけ）。

   | 型 | 内容 | 向く条件 |
   | --- | --- | --- |
   | T1 撤去・取り下げ | 作らない・消す（YAGNI） | 便益が利便にとどまる。実使用 0。面が開いている |
   | T2 責任の移譲 | 決定的な処理を非 LLM の部品か人の押下へ | LLM の中に排他・停止確認が要る処理がある |
   | T3 範囲を狭める | 厳密一致・白名簿・役割限定 | **面が閉じている**とき。開いていると毎回別の穴が出る |
   | T4 原理の置換 | 「最大」を「現行を写した段の表」へ、など | 新原理を baseline で測れる |
   | T5 旧実装を oracle にする | 差分だけを台帳で 1 件ずつ承認 | 差を数えられる |
   | T6 分割・段階導入 | 既定は挙動不変・無効で先に入れる | 未接続の段は review の影響外にできる |
   | T7 実測してから決める | 実測で打ち切る | 評価・実装の費用が大きい |
   | T8 強制から指示へ戻す | 機械の強制をやめる | 操作が可逆で、強制の副作用が大きい |

5. **推奨を決めて決定ログに残す**（日時・決めたこと・理由・既定との差。契約ファイルがあればその末尾）。
6. **新しい run-id で、現状レビュー（差分レビューでなく）をやり直す**。旧ラウンドの台帳は引き継がず、`rounds.jsonl` には
   `{"stepback": {...}}` を足して区間を切る（以降の判定は最後の step back より後だけを見る）。

## ③ 実例（14 事例から）

| 事例 | 兆候 | 転換 | 結果 |
| --- | --- | --- | --- |
| `git_push` の取り下げ | 5 回の review で毎回別の穴（約 $8.4）。穴は repo 内の細工構成が前提 | T1 撤去（実装は退避ブランチへ） | 3 回目で止めれば約 $3〜5。教訓を docs に残した |
| 非同期承認系の置換 | 指摘 43 件、3 案件を積んだ後。保留の 91/92 が承認 0 | T2 責任を非 LLM の部品と人の押下へ | 107 ファイル −14,403 行で撤去。統合は押下だけに |
| ビューアのジョブ撤去 | 起動の無許可実使用 0。build 後約 1 日 | T1 撤去（依頼はチャットへ一本化） | −8,617 行。回復・排他の保守が消えた |
| `worktree remove` の例外 | 許可 → 単純トークン → 厳密一致 → 直接実行だけ | T3 範囲を狭める（面が閉じる） | 3〜4 手で収束（成功例） |
| フルガード再設計 | 12 BLOCKER・約 $11.8。「緩和」クラスが 3 回再発 | T4 原理の置換 + T5 旧実装を oracle | 1 つの BLOCKER は消えたが別の層で継続し**未収束** |
| 並列度の改善 | 子の上限を上げても同時数は平均約 1.7 | 律速を測り直し、待ちの回数を減らす | 効いたのは bundle のみ（親の手順が律速だった） |
| steer の重ね | 差分を重ねるたびに回答が作り直され、本体が失われた（約 $2.7） | 完全版を 1 回で依頼 | 差分を重ねず、1 回の依頼で完結させる |
| gitflow の強制 | 状態を読めない場所で bypass でも外れない（約 3,900 行の保守） | T8 強制から指示へ縮小 | 全廃は残す価値のある部分を失うので退けた |

- **効いた条件**: 実使用の証拠が 0 または乏しい／面が閉じている（T3）／可逆な形で退避した／旧実装を baseline にできた。
- **効かなかった条件**: 面が開いたまま範囲を狭めた（`git_push` v3）／原理を替えても旧の暗黙の拒否が緩和になるクラスが残った／
  保留系は有効化の約 33 時間後に置換され、段階導入が置換を防げなかった。

## ④ アンチパターン

- 毎回違う穴を塞ぐ（`git_push` の 5 回）。
- 症状だけ直す。旧実装の暗黙の挙動（再解釈による拒否）を見落とす。
- review を増やして安心する。review は指摘を分類するが、「その系統を作る前提」は問わない。
- 上に積む（保留 → 巡回 → 一括 → 受信箱）。
- 摩擦のたびに機構を足し、実使用を測らない。
- 差分を重ねて全体を失う（steer の重ね）。
- 検証を自己申告に頼る（台帳の class を自己申告にして承認者検査を外せた）。
- 保証を言い過ぎる（「人のボタンだから安全」）。

## ⑤ 利用者に止めて聞くもの

step back の結論を実行する前に、次に当たるときは止めて報告し、選択肢と推奨を示して判断を仰ぐ。

- 権限・安全の境界を動かす案、既定で有効になる権限の拡大
- 元に戻せない操作（push・公開・リポジトリ外の削除）
- 機能の**全廃**（縮小や退避ブランチへの取り下げで足りるかを先に示す）
- step back を 2 回行っても収束しない（`verdict: stop`）。撤退・縮小・撤去を提案して止まる

それ以外（範囲を狭める・原理の置換・分割）は推奨案で進め、決定ログに残して最終報告に一覧する。
