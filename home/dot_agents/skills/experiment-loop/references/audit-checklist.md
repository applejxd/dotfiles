# 監査の依頼の雛形（停滞したときにレビュー役の子エージェントへ渡す）

スコアが伸びない、または採否の判断に自信がないときに、独立した相談役（レビュー役の子エージェント。pi では `reviewer`）に、判断を見直させる。
下の `<…>` を埋めて渡す。会話の転写ではなく、**数字と判断の一覧**を渡す。暫定の結論は最後に「疑う対象」と添える。

---

## 依頼文

**目的**: <改善したい指標（`primary`）と向き、現在の値、目標>

**制約**: <時間・計算資源・変えてはいけないもの・調整用と検証用の分割>

**見てほしいこと**（`.exp/decisions.md`・`exp log`・`exp best` の出力を添える）:

1. **直近の判断の一覧**: <採用・却下した変更を、新しい順に 5〜10 件。各行に、何を・なぜ・結果>
2. **各判断の根拠**: <判断ごとの `exp compare` の出力（n・差・95% 区間・p 値・判定）>。根拠が単一の試行や、n < 5 の群だけの判断はないか
3. **採否の統計**: 採用した変更のうち、区間が 0 を含むもの・p ≥ 0.05 のものはないか。却下した変更のうち、「判断できない」を「効果なし」と読み違えたものはないか
4. **未検証の仮説**: <挙げたが測っていない仮説の一覧と、期待する効果の大きさ>。優先順位は妥当か
5. **自分で入れた計測・デバッグのコードの残り**: <入れた箇所の一覧>。測定の前に外したか。外した状態で測り直したか（`git diff` で確認）
6. **分割の予算**: <`val` の使用回数と `max_runs`>。`val` を見て調整していないか。`--allow-overrun` を使ったか（`overrun` の行）
7. **ばらつきの見積もり**: <同じ構成を複数 seed で回した標準偏差>。採用した変更の効果は、それより大きいか。計算資源の競合・熱・実行順の偏りはないか
8. **見落とし**: 上に無い、見落としている原因・前提・測定の偏りはないか。プロファイル（計測）を先に取ったか。同時に複数を変えていないか

**答えてほしい形**: 項目ごとに「問題なし／問題あり（根拠）／情報が足りない」。続けて、次の 1〜3 手の提案（優先順位つき）。

**疑う対象**: <暫定の結論（例: 「ボトルネックは X」「変更 Y が効いた」）>
