# 修理の進め方（既存の拡張・設定・起動の不具合）

> **pi（公式の既定＋人気の package）では、まず該当の package の Issue・変更履歴・設定を確かめ、直らないときは版の変更・入れ替え・外すことを選択肢にする**（[ADR-0031](../../../../docs/adr/0031-evaluate-existing-extensions-first.md)）。
> 自作ハーネス（旧 custom プロファイル）は 2026-11-12 に撤去した（[ADR-0037](../../../../docs/adr/0037-retire-custom-profile-and-other-harnesses.md)）。その修理の手順は、タグ `archive/custom-harness-2026-11-12` の同じファイルにある。

作る場合の段 1〜5 とは別の流れ。**直しが、防御の強さや利用者の操作（確認の回数・通知・拒否・表示）を変えるときだけ**、
[提案のひな形](proposal-template.md) の 3 案と操作の変化の評価を出して承認を待つ。挙動を変えない不具合の修正は、
原因・直し・固定を報告すれば足りる（ただし、変わる挙動は必ず報告する）。

## 進め方

### R1. 症状を切り分ける

次を 1 つずつ確かめて書き出す。

- 起動の違い: `pib`（囲い付き）か素の `pi` か。囲いの内か外か。`-ne` / `-nbt` / `--no-approve` で何が外れているか
- pi の版（`pi --version`）。pi-upstream.md の**該当する行の「確認した版」**（表全体ではなく）と比べ、違うときは変更履歴を先に読む
- **決定的か、ときどきか。** どの PC でも出るなら、環境や一時的な通信の問題より、**共通するもの（pi の版、設定、呼び出しの経路、モデル・認証の条件）を先に列挙する**。仮説を早く固定しない。
  環境ごとに違うなら、配置・PATH・プロキシ・囲いの見せる範囲の漏れを先に疑う
- 利用者の画面だけに出て、記録に残らないものは、まず全文を取れる形にする（通知・ログ）

### R2. 先に広く調べる

原因の分からない不具合は、手元の調査より前に、まず pi 本体の該当の仕様を読み（[読む順序](pi-spec-guide.md)。文書・型・ソース・変更履歴）、
公式の Issue・変更履歴・ドキュメントと、同じ症状の報告を検索する
（エラー文・症状・環境の語で。検索語と当てた先を報告に残す。反例も隠さない）。そのあとで、このリポジトリの既存の知見に当たる。

- pi の公式仕様と実測の棚卸し（表 B）: 公式に書かれていない挙動で、実測して頼っているもの
- 該当する package の評価（[stock の package の評価](../../../../docs/research/agents/pi-stock-packages-evaluation-2026-11.md)）

### R3. 原因を確定する

- **記録を読む**（どの症状でも最初）: セッション記録（`~/.pi/agent/sessions/**/*.jsonl`）には、圧縮の要約やツール結果の実データがある。事実の根拠になる
- 確かめた事実と推測を分ける。ソースにどう書かれているかは事実だが、**実行時にそうなるかは、実測するまで「読みからの推測」**と書く（[pi 本体の仕様を当たる方法](pi-spec-guide.md)）
- 候補が複数残るなら、**直す前に観測手段を足す**（失敗理由を全文で出す、頻度を数える）。費用の大きい再試行を、原因が分からないまま足さない
- 環境固有の症状は、使い捨ての agent 置き場で再現し、**本物の `~/.pi/agent` を汚さない**

### R4. 直して、固定する

- 小さく直す。同じ型の別の箇所がないかを探して、一緒に直す。直しで利用者の操作が変わるなら、先に評価して報告する
- **自動試験が組める修理は、試験を足し、直しを外すと落ちることを確かめる**（変異確認）。落ちない試験は、何も守っていない。
  見た目など、自動試験で捕まえられない症状は、再現の条件・直しの前後の観測結果・未確認の範囲を残す
- 仕様・実測は `docs/` を更新する（表 B など）。確認した版を書く
- 実行: 関連する試験（`test/test_pi_*.py`）と、`uv run pre-commit run --files <変更したファイル>`

### R5. 報告する

症状 → 原因（事実と推測を分けて）→ 直し → 固定したもの → **実機で確認したか**。原因が未確定なら、そう書き、次に何を見れば確定するかを残す。
節目ごと（原因の確定後、直しの後）に、**別系統モデルのレビューと、一歩引いた見直し（なぜ見逃したか、同型が他に無いか、やったことが必要十分か）**を入れる。

## 修理に入る前の確認

1. 版と、起動の違い（R1）を書いたか
2. 公式の Issue・変更履歴を検索したか（R2）
3. 表 B の該当項目と、固定している試験を回したか
4. 囲いの内側でだけ起きる症状なら、内側の環境を実測したか（環境変数、見える範囲、書き込み可否）
5. 手元で再現できない環境固有の事情（制約のある環境の機械など）を、再現できないと書いたか
