# CHG-0044: 強いモデルで計画し、既定のモデルで管理・実行する（`plan` 役の子と、`/plan` のモデル切り替え）

- **状態**: Exploring
- **更新日**: 2026-10-27
- **基準**: コミット 38fea41 以降、pi 1.4.0。モデルは Claude Sonnet 5.5 / Opus 5.5、GPT-6.1

## 目的と非目的

**目的**: 大きく複雑な変更や、曖昧な要件の設計（計画）の段だけ、**推論を深くした強いモデル**（`deep` 階層）の子に任せ、
親は**既定のモデルのまま**、管理・オーケストレーション・実行を続けられるようにする。親の文脈を、重い調査と設計の読み物で占めないことも狙う。

- 計画を作る系統（Claude）と、批評する系統（`review` の GPT）を分け、実装（`worker`、Claude）へつなぐ流れを作る
- [CHG-0026](0026-specialist-agents-with-skills.md) の「移行の調査役」は、この役に**統合する**（別の役を作らない）

**非目的**:

- 利用者と会話しながら詰める設計（分岐ごとに利用者の判断が要る）。これまでどおり、親が `ask` で進める
- 子（`plan` 役）が、親のモデルを切り替えること。子は別プロセスで、親のモデルは変えない（親のモデルの切り替えは、下の**既存の `/plan`** の拡張の話）
- 節目だけ強いモデルに相談する型（Claude Code の `advisor` 型）。相談先に会話の全体が渡る形は、会話を見ない子では作れない（[M4](../research/agents/subagent-model-assignment.md#記録-m4--2026-10-27強いモデルで計画し既定のモデルで管理実行する切り替えの実践)）

## 既存の `/plan`（計画モード）の確認（2026-10-27）

ハーネスには、**計画モードへの明示的な切り替えが、すでにある**（`home/dot_pi/agent/extensions/plan/index.ts`。仕様は `docs/spec/guard/pi-extensions.md` の `plan`）。

- 状態は `plan-mode` のエントリで、再開・分岐・圧縮のあとも保つ。フッターに `⏸ plan` を出す
- **モデルも推論の強さも切り替えない**（`setModel`・`setThinkingLevel` を呼ばない）。つまり、`opusplan` 型の「計画の間だけ強いモデル」は**無い**

### 2 つの仕組みの使い分け（案）

| 仕組み | 向く場面 | 強み | 弱み |
| --- | --- | --- | --- |
| **`/plan` で親のモデルも `deep` に切り替える**（`opusplan` 型） | 利用者と会話しながら、同じ文脈で計画する | **会話の文脈のまま**なので、子への別プロンプトへの転記で条件が落ちることは避けられる（ただし、圧縮や忘却で落ちることはありうる）。利用者が分岐ごとに答えられる | 計画の間、親の文脈の全体を強いモデルの単価で読む（費用）。親の文脈を、計画の調査が占める |

## 設計（案）

### 役の定義

- `[pi.agents.plan]`: `tier = "deep"`（階層の定義は変えない）、プロファイルは `reader`（bash なし。`read`・`grep`・`find`・`ls` だけ）。Git の履歴や差分が要るときは、親が取って依頼文に載せる
  - `explorer`（`git log`・`git diff` が読める）にしない理由: `explorer` は bash を持ち、共通の `skill_scripts` の許可（例: `away_guard.py` の `init`・`log`）が通る。「作業しない」を、指示だけでは強制できない（[CHG-0026 のレビュー R1-2](0026-specialist-agents-with-skills.md#レビューの反映)）
- `inherit_bypass` は付けない（読み取りだけなので不要）
- 階層の検査: 生成時の検査（[CHG-0043](0043-model-catalog.md)）が、`deep` の既定を、カタログの中の同じ系統の最新と照合する（Bedrock の Opus は、使える環境で確認するまで `verified = false` で、`enforce_verified = false` のため通る）

### 依頼文の標準形（親が書く）

子は会話を見ないので、親が次を**自己完結**で書く（`guarded_task` の `task`）。

1. 目的と、完了の定義
2. 前提（今の状態・分かっていること・確かめていないこと）。調査済みの事実は出典つき
3. **守る条件**（番号つき。変更してはならないもの・既存の約束・期限・費用など）
4. 対象のパスと、読んでよい範囲
5. 必要な Git の情報（差分・履歴の要点）
6. 返答の標準形（下）

### 返答の標準形（子が返す）

結論・手順・**守る条件の突き合わせ**・変更するファイル・リスク・検証の方法・**利用者に確認すべき点**・未確認・次の候補。

- 手順は、1 手順 = 1 つの変更と、その確認の方法。小さく直せる粒度にする（再計画は、変わった 1 手順だけを直せるように）
- **守る条件の突き合わせ**は、依頼文の番号ごとに「手順 n で満たす／満たさない／確認が要る」を書く。
  **検出は、構造化で行う（R1-4）**: 今の標準形の検査（`auditFormat`）は固定の見出しの有無しか見ないので、番号の欠落は検出できない。段 3 で、依頼の条件 ID を job に保存し、返答の ID の集合と照合する。欠落・重複・不明な ID・切り詰め・失敗・時間切れは、「未完了」として、親が回収するまで実行へ進めない。
  ID の一致は、条件を満たす証明ではない（内容の確認は、親に残る）
- 返答には、**取得した Git の情報の時点と、確かめていない範囲**を必ず書く（`reader` は差分を自分で確認できず、親が渡した情報が古い・不完全なことがある。R1-M2）
- 子は質問できないので、利用者の判断が要る点は、「利用者に確認すべき点」に、推奨つきで列挙する

### 親の運用

- 親は既定のモデルのまま、依頼文を作り、返答を受け、**守る条件の突き合わせを確かめ**、利用者に確認すべき点を `ask` で聞く
- 計画は、`review`（GPT）に見せてから、`worker`（Claude）か親が実行する（系統を分ける）
- 呼ぶ基準（親の判断。共通の指示に書く）: 影響が複数のファイルや層に及ぶ変更、要件が曖昧で設計の選択肢が多いもの、移行。**小さな変更には呼ばない**（往復の費用が見合わない）

### 移行スキルとの関係（CHG-0026 の統合）

移行スキルの調査の段（`references/` の読み込み・影響箇所の洗い出し・移行の計画）は、`plan` に任せる。実行・確認・利用者との対話は、親に残す（CHG-0026 の「なぜ実行は親に残すか」）。
スキルの `context: fork`・`agent: plan`（CHG-0026 の段 1c）で、`/skill:` から直接呼ぶ形は、その案件の対応後に検討する。

## 未解決点

- **`reader`（bash なし）で足りるか**: 計画に `git log` や `git diff` を、子が自分で確かめたい場面があるか。足りなければ、`explorer` にするか、読み取り専用の git だけを許す専用のプロファイルを作る
- **Copilot で `deep` が効くか**: モデルが既定と同じなので、効果は推論の強さ（`high`）だけ。測定（段 3）の結果しだいで、Copilot の `plan` は `worker` 階層に戻すか
- **Opus の費用**: 計画 1 回あたりの費用の見込みと、利用者への表示（結果の見出しに、モデルと effort を出す。CHG-0043）で足りるか
- **計画の粒度の限界**: 計画が長くなると、返答の 20000 文字の切り詰め（`docs/spec/guard/pi-subagents.md`）に当たる。切り詰められたら未完了と扱う規則を、標準形に入れるか
- **子の 15 分の上限**: 深い計画（`deep`）が、15 分で終わらない可能性

## 次の調査・実験

1. （段 1）設計を `review` に見せる。観点は、役の定義・標準形・階層の例外・`reader` で足りるか
2. （段 2）測定の課題を作る。候補: (a) 多ファイルにまたがるリファクタリングの計画、(b) 移行（CUDA・uv）の影響の洗い出し、(c) 曖昧な要件の設計。それぞれ、守る条件を番号つきで 3〜5 件持たせ、**外部の受入試験**（実装後の検証）を決めておく
3. 実験の条件: 同じ課題・同じ初期状態・同じ実装役（`worker`）・同じ検証で、「計画なし（親が直接）」「`explore` に `worker` 階層で計画を依頼」「`explore` に `deep` 階層で計画を依頼」を、複数の課題・反復で比べる。条件の順序は入れ替える。
   記録: 費用・トークン・所要時間・失敗／未完了・条件の遵守・範囲外の編集・やり直し。**少数の試行では優劣を断定せず、問題の発見と費用の見積もりに留める**（R1-5）
4. F（`/plan` の切り替え）は、別の実験として、`/plan` の現状と `deep` への切り替えを比べる（段 5 の前）

## 評価基準

**必須**:

- 子が、書き込み・実行をしない（`reader` で、判定器の試験: 編集・書き込み・bash が拒否される）
- 返答に標準形の見出しがそろい、守る条件の番号が欠けていない（欠けていれば親が検出できる）
- 親の文脈の増え方が、「親が直接調べて計画する」より小さい

**望ましい**:

- 守る条件の遵守率が、計画なしより高い（測定の課題で）
- 範囲外の編集・やり直しの回数が、計画なしより少ない
- `deep` 階層が `worker` 階層より、守る条件の遵守・設計の見落としで優れる。優れなければ、Copilot では `worker` 階層で足りる
