# 圧縮の失敗の調査（公式の報告・変更履歴・セッション記録）

- **日付**: 2026-11-02
- **対象**: pi 1.4.0（2026-10-21）。モデル `github-copilot/claude-sonnet-5.5`（context 1M・出力上限 128K。`pi --list-models` の表示）
- **状態**: **圧縮の最中の完了通知で失敗することを、実験で再現した**（2026-11-02）。圧縮を中断した直接の呼び出しは未特定。失敗の文言をセッションに残す観測も足す（末尾の「次」）
- **結論**: **手動 `/compact` の最中に完了通知が届くと、圧縮が中断される**ことは実験で再現した（下の「実験」。直接の中断元は未特定）。それ以外の失敗は、**セッションの記録には成功した圧縮しか残らず、文言が取れない**。公式の既知の不具合のうち、1.4.0 で直ったものが多い。残る候補は「大きな要求の一時的な失敗」「中断（Esc）」「モデル・認証の条件」で、記録がないので判別できない

## 問い

- 圧縮（`/compact` と自動）で「失敗が続く」のは、何が原因か
- 自作の圧縮（`session_before_compact`）が既定の圧縮に落ちた理由は、残っているか

## 実測した事実（pi 1.4.0 とこのリポジトリ）

- 本体の経路: 失敗や中断は、画面に `Compaction failed: …` / `Auto-compaction failed: …` と出る。セッションには**残らない**（成功した圧縮だけが `type: "compaction"` になる）
- 本体のイベント `session_compact_failed`: 理由（`manual`・`threshold`・`overflow`）・エラー文・中断か・再試行か・拡張由来かを、拡張へ渡す。**拡張が登録しないと、どこにも残らない**
- 自作の圧縮（`index.ts` の `session_before_compact`）: `compact()` が失敗したら、警告通知（`圧縮の指示を付けられなかったので既定の圧縮にする: <理由>`）と標準エラーに理由を出して、既定の圧縮に落とす。**理由は画面と標準エラーにしか残らなかった**
- 1.4.0 の変更履歴（修正済みのもの）:
  - 要約の出力上限（`reserveTokens` の 0.8 倍）を撤廃。要約はモデルの出力上限まで使える（#9512・#9075）
  - 分割ターンの先頭を要約するとき、`/compact <instructions>` の指示が無視される問題（#11058）
  - Copilot で、大きな要求本文が HTTP 413 になる問題（#11016）。圧縮して再試行する
  - 1.3.0: `The service is temporarily unavailable` で再試行が起きず、圧縮が 1 回目で失敗する問題（#10965）
- 自作の再試行: 「要約が出力上限で切れたら `reserveTokens` を倍にして 1 回やり直す」は、**1.4.0 では効かない**（`createSummarizationOptions` が `maxTokens` を渡さない）。害は無い

## 実験: 圧縮の最中の完了通知（2026-11-02）

### 実測した事実

| 項目 | 内容 |
| --- | --- |
| 手順 | 手動 `/compact` の実行中に、背景の子（explore）と背景ジョブを動かしておき、完了させた |
| 結果 | 圧縮の開始から約 53 秒後に子が完了 → 完了通知が新しい発言を始め、画面に `Warning: … Turn prefix summarization failed: This operation was aborted` と `Error: Compaction cancelled`。セッション記録に compaction エントリは残らない |
| 同型の失敗 | 同日の最初の失敗も、worker の完了通知の時刻と重なっていた（その時は観測が無く、推定） |
| 成功した圧縮 | 完了通知が無かった圧縮は成功した（文脈約 57 万トークンで約 4 分 53 秒）。背景の作業を 0 にしてから行った後の圧縮も成功した |
| ジョブ・子 | 圧縮の中断の影響を受けず、動き続けた（10 秒ごとの記録に途切れなし）。完了通知は、応答中ならキューに入り、応答が終わった後に届いた |
| 完了通知の送り方 | `pi.sendMessage(…, { triggerTurn: true, deliverAs: "followUp" })`（このリポジトリの harness と activity 拡張の 4 か所） |

### pi 1.4.0 の実装（読んで確かめた事実）

出典: `@earendil-works/pi-coding-agent` 1.4.0 の `dist/core/agent-session.js` と `dist/modes/interactive/interactive-mode.js`（行番号は 1.4.0 のもの）。

| 事実 | 場所 |
| --- | --- |
| 利用者の入力（`prompt()`）は、圧縮中だと「圧縮中は送れない」で拒否される | agent-session.js L1648 |
| `sendCustomMessage`（`pi.sendMessage` の実体）は、実行中でなく `triggerTurn: true` だと、圧縮の確認なしに新しい run を始める | 同 L1857〜1871 |
| `ctx.isIdle()` は圧縮の最中も false（`!_isAgentRunActive && !isCompacting`） | 同 L1073 |
| `session.abort()` は進行中の圧縮も中断する。発言中の Esc は `session.abort()` を呼ぶ | 同 L1976 ・ interactive-mode.js L3858 |
| 手動圧縮では、成功の `session_compact` が、圧縮の状態を解く**前**に届く。失敗の `session_compact_failed` は解いた**後** | agent-session.js L2300〜2350 |
| 自動圧縮は run の中で行われるので、`isStreaming` が true になり、通知は followUp のキューに入る（pi が圧縮の後に続行する）。**問題になるのは手動 `/compact`** | 同 L1068・L2610〜2614 |

### 推測（分かっていないこと）

- 圧縮を中断した**直接の呼び出し**は特定できていない。完了通知が始めた発言を、利用者が Esc で止めた可能性（上の `session.abort()`）が残る。どちらでも「圧縮の最中に発言を始めない」ことが対策になる
- 他の拡張・本体の別経路が圧縮を中断した可能性は、記録が無く判別できない

### 対策

- このリポジトリでは「圧縮の最中は完了通知を保留し、終わってから配信する」修正を取り込み中（仕様は `docs/spec/guard/pi-extensions.md` の小節「圧縮中の完了通知の保留」。取り込み前なのでリンクにしない）
- 配備した後に、同じ実験（圧縮の最中に子を完了させる）を繰り返し、中断されないことを確かめる（**未実施**）
- それまでの回避策: 圧縮の前に背景の作業を 0 にする（この後の圧縮は成功した）

## 候補（実験で再現したものと、まだ推測のものを分ける）

| 候補 | 状態 | 根拠 | 判別に要るもの |
| --- | --- | --- | --- |
| 圧縮の最中の完了通知が、新しい発言を始めて圧縮を中断する（手動 `/compact`） | **実験で再現した**（直接の中断元は未特定） | 上の実験。通知が無い・背景 0 の圧縮は成功 | 配備後の再実験 |
| 大きな要求の一時的な失敗（413・過負荷・切断・タイムアウト） | 推測 | 入力が約 46 万〜83 万トークンで、要約に数分かかる。本体の再試行は 3 回まで | エラー文の HTTP 状態 |
| 中断（Esc）の後の警告 | 推測（完了通知が始めた発言を Esc で止めた可能性は上の未特定部分） | `Operation aborted` が 17 件。圧縮の直前に中断している | `aborted: true` の記録 |
| モデル・認証の条件の 400・421 | 推測 | 公式の報告に前例。環境ごとに違う | エラー文 |
| 要約が出力上限で切れる | 推測（起きにくい） | 1.4.0 では上限が 128K で、要約は 4 万字前後（トークン数は未計測）。**起きにくい** | `token cap` の文言 |
| 自作の hook 自身の例外 | 推測 | `fileOps` の処理が、保護の外にある | 画面の `Extension error` |

## 限界と未確認

- 過去の失敗の文言は、利用者の画面にだけあった。**取得できていない**（実験の 1 件は画面の文言を確認した）
- 圧縮を中断した直接の呼び出し（完了通知の発言への Esc か、別経路か）は未特定
- 修正（完了通知の保留）の配備後の再実験は未実施。他の失敗（過去 11 回の記録に無い失敗）が全て同じ原因かは未確認
- 実モデルで、約 70 万トークンの要約を再現していない（費用が大きい）
- 本体の「分割ターンの前半の要約には、指示が入らない」（自作の圧縮の仕様の記述）が、1.4.0 の #11058 の修正で変わったかは**未確認**
- #3438・#2567 の現在の状態は未確認

## 次

- **観測を足す**: 失敗した圧縮の理由を、セッションの `custom` エントリとして残す（`harness-compact-fallback` = 自作の圧縮が既定に落ちたとき、`harness-compact-failed` = 本体の経路が失敗・中断したとき）。入ったあとで失敗したら、セッションの記録を読めば原因が分かる
- **配備後に再実験**: 圧縮の最中に子を完了させ、圧縮が中断されないこと・完了通知が圧縮の後に届くことを確かめる
- **`harness-compact-failed` の確認**（配備後）: 失敗した圧縮の理由が、セッションの `custom` エントリに残ることを確かめる
- 判別できたら、候補に合わせて直す。費用の大きい再試行を、原因が分からないまま足さない
- 陳腐化した `reserveTokens` の再試行の撤去と、分割ターンの指示の仕様の確認は、記録が溜まってから判断する
