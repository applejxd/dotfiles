# 承認が取れない操作を失わず保留し、利用者だけが後から承認して実行する

- **ステータス**: Superseded by ADR-0024
- **日付**: 2026-10-31
- **決定者**: applejxd

## コンテキスト

確認が時間内に取れない状況は、常態になっている。利用者は席を外し、複数のエージェントを並べ、場所によってホストも違う。確認の時間切れ（5 分）の扱いは、経路ごとに違う（[CHG-0046](../change/0046-guarded-action-timeout.md)）。

- `git_commit` だけは、時間切れ・不在・UI なしのとき、内容を `refs/pi/pending/` に退避して作業を続ける。ただし、承認して実行する手段は無い（一覧・表示・破棄だけ）。
- bash の必須確認・「ask」層・`ask` 拡張・`gh_issue_*` は、時間切れで拒否され、何も残らない。
- 子の UI 要求は、親が取り消し、親へは `not approved:` の文字列だけが届く。

[ADR-0022](0022-containment-first-minimal-approvals.md)（Proposed）は、確認を「人が判断を足せる操作」に絞る。残る確認は、人が不在でも失われず、後でまとめて承認できる形が要る（人の確認は、エージェントの数に比例してスケールしない）。

守る目的は「エージェントのうっかり」で、悪意への耐性までは求めない（[ADR-0012](0012-ocs-boundary-for-accidents.md)）。ただし、サンドボックス（Fence）は、人とモデルを区別しない。記録を git の ref に置けば、モデルも書ける。通知（BEL・OSC・ホストの `ask`）は、失われうる。

## 検討した選択肢

### 選択肢 1: 現状維持（`git_commit` だけ退避、ほかは拒否）

- **利点**: 変更が無い。
- **欠点**: 退避した内容を、承認して実行できない。時間切れのたびに、操作を作り直す。統合（`git flow feature finish`）と `chezmoi apply` が、離席のたびに失われる。

### 選択肢 2: 時間切れを延ばす・無期限にする

- **利点**: 実装が小さい。
- **欠点**: 離席が長ければ、結局止まる。複数のエージェントでは、全員が止まる。

### 選択肢 3: 任意の bash の必須確認を保留し、後で再実行する

- **利点**: 対象が広い。
- **欠点**: 前提（cwd・環境変数・ファイルの状態）を固定できない。承認した内容と、実行する内容が食い違う。

### 選択肢 4: 構造化した操作だけを保留し、利用者だけが後から承認する（提案）

- **利点**: 前提を型つきの値として固定でき、承認の時点で再検査できる。既存の退避と連続している。承認の入口を、利用者だけが呼べるコマンドに限れる。
- **欠点**: 操作ごとに、前提のアダプタが要る。任意の bash は救えない。記録は偽造されうるので、承認の時点の再検証が要る。

### 選択肢 5: 通知やホストの機能（BEL・OSC・Orca の `ask` など）を、保留の正本にする

- **利点**: ホストの機能を使える。
- **欠点**: 失えば、保留が消える。ホストごとに違い、ホスト非依存にならない。

## 決定事項

**選択肢 4 を、方向として採る**（実装は [CHG-0055](../change/closed/0055-async-approval.md) が持つ。段ごとに、実機と試験で確かめる）。具体的な原則は、次の 7 つ。

1. **保留は、構造化した操作の記録**（操作の ID・型つきの引数・前提・表示した内容）。承認が取れなかった理由（時間切れ・不在・UI なし・「あとで」）を問わず、同じ形で残す。
2. **承認できるのは、利用者だけ。** 利用者が打つコマンド（`/pending approve`）にし、モデルが呼べるツールにしない。子は承認できない。承認を、記録のフラグとして持たせない。
3. **承認は、検証済みの実行計画に対して行う。** 記録は信頼しない入力として読み、現在の設定・役割・実行先で再検証し、表示した記録の OID を排他的に取得してから実行する。実行計画は、操作の対象の識別子と期待値を持ち、反映は期待値の検証つきで行う。記録の中の値を、権限の根拠にしない。
4. **実行しない経路を保つ。** 時間切れ・不在・UI なし・「あとで」は、保存だけ。前提が食い違う・結果が不明なときは、自動で再実行しない。結果は `not_executed / success / failed_confirmed / unknown` の 4 値に分類し、証拠を添える。実行者と開始段階を記録し、実行中かもしれない試行は、人が `resolve` できない。
5. **品質ゲートを後退させない。** 承認後の実行は、通常の経路（hook と署名を通す）と同じ検査を受ける。hook を迂回する近道は採らない。
6. **通知は手段で、正本は git の ref。** 通知を全部失っても、一覧から状態を復元できる。
7. **範囲は、構造化した操作だけ。** 任意の bash の必須確認は保留せず、時間切れは拒否のまま。

理由: 前提を固定できない操作は、後から承認しても、承認した内容と実行する内容が一致しない。承認と実行の間の食い違いを、再検査で潰せるのは、型つきの引数を持つ操作だけ。承認の入口を人だけのコマンドにすれば、モデルが記録を偽造しても、承認までは偽造できない（うっかり防止の範囲では十分）。

**未決**（この ADR では決めない。CHG-0055 で扱う）: RPC（Orca・Zed の ACP）での有効化、別のセッションの要求元への通知、`chezmoi apply` の承認の形（承認の時点で差分を作る案）、子の要求の中継、Windows。

## 決定の確認方法

- 各段の試験で、承認が無いまま実行する経路が無いこと、偽造した記録では承認が要ること、前提の不一致・結果不明で自動の再実行が起きないこと、承認後の `git commit` が hook を通ることを確かめる。
- 運用では、時間切れで作業が止まる回数、保留が承認されるまでの時間、保留の滞留件数（多ければ、絞りが足りない）、「あとで」の使用率を追う。
- 実装の進捗は、ここに書かない（CHG-0055）。
