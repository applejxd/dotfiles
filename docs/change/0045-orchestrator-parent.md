# CHG-0045: 親をオーケストレーターに寄せる（実作業は子へ、親は対話・判断・委譲・承認）

- **状態**: Exploring
- **更新日**: 2026-10-28
- **基準**: コミット 146dd6e 以降、pi 1.4.0

## 目的と非目的

**目的**: 親エージェントを、**利用者との対話・判断・委譲・承認・ToDo の管理**に専念させ、調査・計画・実装・検証などの実作業は、子（`guarded_task`）へ任せる設計にする。
親の文脈を、重い読み物・実行の出力・ログで占めないことと、親のモデルを既定のまま保つことが狙い。今後のオーケストレーター設計（保留中の orchestrator ロール・待ち合わせ・DAG・予算。[調査 O1](../research/agents/pi-orchestrator-survey.md)）の**前段**に当たる。

- スキルは、**対話の段**（親）と**実行の段**（子）に分け、実行の段を、自己完結の依頼文で子へ渡す形にする
- 子が確認なしで動けるように、子の承認の経路・質問の中継・上限の扱いを整える
- 親の道具を絞る（作業のツールを持たせない）かどうかを、実測で決める

**非目的**:

- 利用者との対話そのもの（質問・承認・設計の詰め）を子に任せること。対話は親に残る
- 子から子を作る入れ子（今の基盤は不可。指揮役のスキルは親に残る）
- 公開の子エージェント拡張の導入（[ADR-0016](../adr/0016-pi-extensions-own-first.md)。自作を優先する）

## 現在地

- **利用者の方針**（2026-10-28）: 親で、あまりいろいろな作業をする設計にするのをやめたい。今後のオーケストレーション設計の前段にする
- **今の子の基盤**（[pi の子エージェント](../spec/guard/pi-subagents.md)）: 役割は `explore`・`review`・`plan`・`commit`・`worker`。並列は 4 本、1 往復の上限は役割ごと（既定 15 分、`plan` は 30 分）、背景の完了は通知で受ける。結果は要約で返る
- **スキルの調査**（2026-10-28。全 20 スキルを、子 4 本が本文から調べ、親が確かめた。[記録 F3](../research/agents/skill-fork-enforcement.md#記録-f3--2026-10-28スキルごとの-fork-と-allowed-tools-の調査)）:
  - `context: fork` を、そのまま付けられるスキルは `fix` だけ（5 条件。[基準](../spec/skill-frontmatter.md#context-fork-の基準)）
  - 多くのスキルは、**対話の段と実行の段が混ざっている**。全体を子へ渡せないが、実行の段だけなら渡せるものが多い（型 B・C）
  - 指揮役のスキル（`arxiv-paper-ja`・`review-loop`・`away-shift`・`powerpoint-studio`）は、子を使うので、親に残る（型 E）
- **子の側に足りないもの**:
  - 承認: `worker` は親が bypass のときだけ確認なしで動く。通常のモードでは、確認で止まる（子は承認できない）
  - 質問: 子は利用者に質問できない。中継（ask-user 段 2）は未実装
  - 入れ子: 子は子を作れない
  - 背景の子（Claude Code の `fork` の既定）は、使えるツールが狭く、確認を出せない（Claude 側の仕様）
- **`/plan` の穴は塞いだ**（[CHG-0044](0044-plan-agent.md) 段 4）。計画の間、書き込みの子は動かない。この仕組み（モードごとの子の制限）は、orchestrator ロールにも使える
- **CHG-0026 の段 1c**（`context: fork` をハーネスで解釈する）は、この案件に統合する。`/skill:` を子へ回す解釈よりも、**依頼文の雛形と子の基盤**を整えるほうが、方針に合う（解釈の実験は [F1](../research/agents/skill-fork-enforcement.md) に残っている）

## 未解決点

- 型 B・C で、**親が子へ渡す依頼文**の質（目的・前提・守る条件・対象のパス）をどう保つか。`plan` 役は、返答側の検査（守る条件の番号）を持つ。依頼側の雛形と検査が要る
- 子の承認の経路: (a) 親が bypass で起動する（既定を変える）、(b) 子が承認を要求し、親が利用者へ中継する（RPC の拡張 UI の中継）、(c) 役割ごとに、確認なしで通す操作を、設定で決める。範囲と副作用の評価が要る
- 質問の中継（ask-user 段 2）の設計: 子が質問して止まり、親が答えて続ける形。時間切れの扱い
- 親の道具を絞る（orchestrator ロール）と、利用者の小さな頼み（1 ファイルの修正など）が、遠回りになる。**どの大きさから委譲するか**の基準
- 子の結果の確認の負担: 子の「通った」を、親が確かめる原則（共通の指示）との兼ね合い
- 費用・待ち時間: 委譲の往復が増える。Copilot は費用が無制限だが、待ち時間が増える

## 次の調査・実験

1. （段 1）型の割り当てと、基盤の不足を、`review` に見せる
2. （段 2 の前）子の承認の経路の案を、実際の拒否の出方（`worker` が止まる条件）から整理する
3. （段 3）`fix` で、親が依頼文を作って `worker` へ渡し、結果を受ける流れを、実機で 1 回通す

## 評価基準

**必須**:

- 親の文脈の増え方が、親が直接作業するより小さい（実行の出力・ログ・読み物が、親に入らない）
- 利用者への質問・承認は、親が出す（子が黙って止まらない）
- 権限の境界を弱めない（子の権限は、今のプロファイルの範囲のまま。承認の経路を足すときは `review` に見せる）

**望ましい**:

- 小さな頼みで、遠回りにならない（委譲しない基準が明確）
- 型 A・B のスキルで、依頼文の雛形が再利用できる
