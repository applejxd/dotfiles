# 実物の振る舞いを検証する

ユーザーが使う経路と結果を確かめよ。ビルドの成功や内部関数だけのテストを、画面や CLI での成功に読み替えない。

## どの作業か決める

- **検証する:** 今回の依頼・差分が対象。検証手順の生成や設定の変更はしない。
- **手順を整える:** 利用者が再利用できる手順を求めた場合だけ。既存のテスト・タスク定義・文書を活かし、最初は代表機能一つに絞る。

## 既存の入口から検査を選ぶ

1. 依頼と差分から「前提 → 利用者の操作 → 観測できる変化」を一組書き出す。拒否時や副作用が重要なら、その観測も加える。
2. `AGENTS.md`、検証文書、タスク定義、既存の E2E・統合テストの順に探す。操作と結果を覆う検査があれば候補にする。別の仕組みは足さない。
3. 実行前に、許可されたローカル・テスト環境かを確かめる。対象の版、接続先、入力データ、出力先、副作用を確認する。作業用のデータと出力先は既存成果物から分ける。公開済み環境や利用者の実データは使わない。
4. 環境と権限を確かめてから、選んだ既存テストを実行するか、実際の UI・コマンド・API を操作する。ブラウザ操作、外部への書き込み、課金を伴う呼び出しをこの手順だけで許可しない。ファイル生成は、終了コードに加えて出力の中身や失敗時に出力が残らないことも見る。
5. 自分で起動したものだけを停止する。証拠は後片付けで消さない。依存が足りない、または権限がない場合は勝手に導入・変更せず、どこまで確かめたかを報告する。

## 再利用する手順を残す場合

起動、準備完了を見分ける方法、操作、合格条件、証拠の場所、片付けを記録せよ。次のセッションで迷わないコマンドと入力例を使う。既存の文書・タスクを優先し、別の検証スキルは必要が出るまで作らない。手順を一度も通せなければ草稿と明記する。

## 報告

実行したコマンドまたは操作、観測、合否、未確認点を分ける。ユニットテストの結果と実物の結果を区別する。画面や成果物を確認できていない場合は、そのまま書く。外部操作や承認はこの手順の範囲外。
