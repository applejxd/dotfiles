# worker の共通の約束

親の依頼文から参照される。依頼文の個別の指示（担当ファイル・作ること・合格条件）が、ここより優先する。

## 役割と境界

- 編集するのは、依頼文の**担当ファイルだけ**。**親は worker を `guarded_task` の `cwd` に担当の worktree を指定して起動する**（依頼文の絶対パスに加えて）。**編集は worktree の絶対パスだけで行う**（相対パスだと、本体のファイルを書き換えてしまうことがある。実際に起きた）。**`cwd` を指定して起動された worker は、edit / write で担当 worktree と明示した一時領域の外（本体・他の worktree を含む）を書けない（判定器が deny）。強制するのは edit / write だけで、shell・試験・hook からの書き込みは未強制。絶対パスで編集する約束は引き続き守る。**担当外のファイル・ほかの worktree・本体は、読み取りだけ（使い捨ては `$TMPDIR` に置いてよい。役割の system が正本）。
- git の状態を変える操作はしない（親が行う。役割の system が正本）。
- 1 worktree = 1 feature = 1 worker（同じ worktree に別の worker はいない）。隣の worktree の別の worker の途中状態で、試験が一時的に落ちることがある（自分の担当と関係がなければ無視し、最後に 1 回だけ再実行する）。
- 共有の docs（`docs/spec/pr-viewer.md`・`docs/change-history/*.md` 以外の索引・表、`common.toml.tmpl`・golden）は、依頼文に明示が無い限り触らない。案件の履歴は `docs/change-history/0062.md` の**末尾に 1 行だけ**足す（既存行を変えない。union merge で衝突しない）。
- 担当のコード以外にバグを見つけたら、直さず、再現のコマンドつきで報告する。

## ツール

- bash での読み書き・一行スクリプトは拒否される（役割の system が正本）。ファイルは `guarded_write` / `guarded_edit` で書き、読むのは `guarded_read`、探すのは `guarded_grep` / `guarded_find`。
- `guarded_edit`: 同じファイルへの編集は、1 回の呼び出しの `edits[]` にまとめる。`oldText` は一意にする。
- **整形 hook が、書き込み直後にファイルを書き換える**。続けて編集するときは、先に読み直す。
- 長いスクリプトは、ファイルに書いてから実行する。

## 検査

- 行長は 140（E501）。subprocess の `text=True` には `encoding="utf-8"` が要る。シェルスクリプトは先頭に `set -eu`。
- 重い検査（`mise run verify:all`）は回さない。**設定や生成物を変えたときは、その値を固定している既存の試験を `grep` で探して（キー名・値で `test/` 全体を検索）、同じファイル群を回す**。変更の意図どおり期待が変わる試験は、期待値をハードコードせず、単一ソースの値から取る形に直す。`uvx ruff check test scripts`、担当の試験、`uv run pre-commit run --files <ファイル>`（lint 系は `--files` で未追跡の新規ファイルも検査される。秘密検出（gitleaks）は `--staged` なので、新規ファイルは `git add` の後でないと見ない。ステージは親が行う）。
- 新しい試験ファイルを `scripts/verify.py` の `_PI_TESTS` に登録するのは、**依頼文が許したときだけ**。許されていなければ、親が登録するので、報告に「登録が必要」と書く。
- **広い範囲の試験（`test/agents/` 全体など）は、直列で回さない。** `pytest` は既定で直列で、`test/agents/` は約 31 分かかり、打ち切りの上限（約 30 分）に当たる（実測。全件検査は 8 並列で約 6.5 分）。広く回すときは `uv run --with pytest --with pyyaml --with pytest-xdist --no-project pytest <範囲> -q -n 4 --dist worksteal`（並列度 4。親や他の worker と同時に動くので、これより増やさない）。担当の数ファイルだけなら直列でよい。**時刻に依存する試験は、負荷で 1 度だけ落ちることがある**。落ちたら、その試験だけを単独で再実行して通るかを確かめ、報告に「負荷で揺れた」と落ちた出力を書く（親が原因を調べる）。

## 公開リポジトリ

- 公開リポジトリの規則（私物・勤務先の具体をどこまで書いてよいか、禁止する具体の例）は、`AGENTS.md` の公開の規則が正本。それに従う。
- docs は日本語。日付を書くときは `date '+%F %H:%M'` で確かめる。

## 時間と報告

- **約 30 分で打ち切られる**（24 分で「まとめに入れ」が届く。大きい担当は依頼文に書いた時間まで）。優先順位の高い順に作り、時間切れの前に報告する。
- **本体（担当の worktree 以外）のファイルは編集しない。** 同じ worktree の他の担当のファイルも触らない。lint が他の担当のファイルで落ちるときは、自分のファイルだけを個別に検査し、報告に書く。
- **自分の worktree の lock（`git worktree lock`。理由欄 `owner=worker …`）を解除しない。** 解除は親が `wt_owner.py release` で行う。
- 報告は**結論を先頭に 3 行以内**で書き、続けて: 変更・作成したファイルと公開した関数、各検査の出力（抜粋。「通った」は実行した出力を添える）、依頼や型と食い違った点、確かめられなかったこと、未完了の項目とその原因、判断に迷った点、**次の担当への申し送り**。親は先頭だけを読む。
