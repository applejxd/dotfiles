# 評価: オーケストレーション(1) pi-subagents 0.87.0 で利用者の運用が足りるか（調べた日 2026-11-09）

## 結論
- **ほぼ足りる。ただし「そのまま」ではなく、設定 2 点と agent 定義 3〜4 本で埋める前提**。足りない中心は (a) 前景の子に permission-system / cc-safety-net が**載らない**こと、(b) `worktree: true` が「使い捨て worktree + patch 回収」で、利用者の「名前つき feature worktree に 1 worker」と形が違うこと、(c) 子の同時数が「実行中の run 数」の上限で、「空きが出たら次を自動起動」は親（モデル）の指示に頼ること。
- 最小の補い: `config.json` に `forceTopLevelAsync: true`（前景の子を作らせず、全部背景＝ambient 拡張が載る）と `maxActiveAsyncRunsPerSession`、worker は `subagent({agent:"worker", cwd:"<feature worktree>"})` で既存 worktree を指す（`worktree:true` は使わない）。別の package は要らない。
- 根拠は下記。**実機の動作は未確認**（実行禁止。コード・docs を読んだだけ）。

## (1) 組み込み agent と役割の対応
出典: README「Builtin agents」、`agents/*.md`、docs/agents.md。

| 利用者の役割 | 組み込み | tools（frontmatter） | 判定 |
|---|---|---|---|
| 調査（コード） | `scout` | read, grep, find, ls, bash, write, contact_supervisor（output: context.md） | 使える。ただし **bash と write を持つ**ので「読み取り専用」ではない。上書きで絞る |
| 調査（Web） | `researcher` / `evidence-auditor` | web_search, fetch_content 等（**pi-web-access を子に載せる前提**） | 利用者の web-search スキル（CLI）運用と別系統。使うなら要件を満たす package が要る（未評価）。当面は不要 |
| 計画 | `oracle`（別名 advisor） | read, grep, find, ls, bash; `defaultContext: fork`（親の文脈を引き継ぐ） | 「計画の相談・方針の整合」役。利用者の `plan` 役（契約を書く）に近いが、**契約ファイルの書き出しは別**（write を持たない）。`plan` 用に別 agent を足す |
| 実装 | `worker`（別名 developer 等） | read, grep, find, ls, bash, edit, write, contact_supervisor; `acceptanceRole: writer`; 決めていない判断は `contact_supervisor` で親に聞いて止まる | **利用者の worker とほぼ同じ思想**（担当範囲で実装・未承認の判断は止まって報告）。使える |
| レビュー | `reviewer` | read, grep, find, ls, watchdog_diff, contact_supervisor（**bash なし**、`acceptanceRole: read-only`） | 読み取り専用で合う。試験は実行せず「親が実行すべきコマンド」を報告する点も利用者の運用と同じ |
| 汎用 | `delegate` | read, grep, find, ls, bash, edit, write, contact_supervisor | 不要 |

- 置き場（優先の低い順）: 組み込み → package の `package.json` の `pi-subagents.agents` → **ユーザー `~/.pi/agent/agents/**/*.md`** → **プロジェクト `.pi/agents/**/*.md`**（旧 `.agents/**/*.md` も読む）。同名は上書き（全置換で、省いた項目は継承されない）。
- 書式: Markdown + YAML frontmatter（`name`, `description`, `tools`, `excludeTools`, `extensions`, `subagentOnlyExtensions`, `model`, `thinking`, `systemPromptMode`, `inheritProjectContext`, `inheritGlobalContext`, `inheritSkills`, `skills`, `async`, `timeoutMs`, `acceptanceRole`, `allowedAgents`, `permission:` ほか）。本文がシステムプロンプト。
- 権限の指定は 2 層:
  - **見える tool**: `tools:`（厳格な許可リスト）/ `excludeTools:`。**拡張が追加する tool は、`tools` に名前を書き、かつ提供元の拡張を `extensions` / `subagentOnlyExtensions` で載せないと使えない**（docs/agents.md「Tool and extension selection」）。
  - **方針**: `permission:`（`write: allow` / `edit: ask` など。非 bash の tool のみ。**bash の規則は拒否される**）。`ask` は「子の watchdog が持つ 1 回限りの仲裁モデル」が approve/deny を決め、人には聞かない（watchdog.md「Native child tool permissions」）。watchdog 無効・モデル無し・タイムアウトは deny。→ 利用者の「ask を人に」とは別物。bash の方針は **permission-system に任せる**（下記 5）。
- 上書き: `~/.pi/agent/settings.json` の `subagents.agentOverrides.<name>`（`tools`, `model`, `description`, `disabled` 等）で、定義ファイルを丸ごと写さずに直せる。`subagents.disableBuiltins: true` で組み込み全部を無効化。
- 組み込みは**モデルを固定しない**（親の既定を継承）。`subagents.defaultModel` / `agentOverrides.<name>.model` で変える（docs/models.md、未精読）。

## (2) 並列の worker と worktree の隔離
出典: docs/workflows.md「Worktree isolation」、docs/configuration.md「worktreeBaseDir / worktreeProvider / worktreeSetupHook」、docs/tool-reference.md。
- `worktree: true`（workflow の各 child、または `subagent` の `worktree`）は、**クリーンな HEAD（または `baseRef`）から使い捨ての管理 worktree とブランチ（`pi-subagents/…`）を作り、終了時に patch と handoff manifest を取って、きれいに回収できたら worktree とブランチを消す**。作る場所は `worktreeBaseDir`（既定は専用ルート。`{root}/{プロジェクト名}/pi-worktree-{runId}-{index}`）。元の checkout は**クリーンであること**が条件で、そうでなければ分配前に拒否（隔離は黙って外さない）。
- 利用者の運用は「**名前つき feature worktree（`.tmp/worktrees/<名前>/`）に 1 worker、その worktree 上のブランチへ commit**」。上の仕組みは**形が違う**（patch を親が適用する形。ブランチ名・場所・commit の流れが合わない）。→ **推奨: `worktree: true` を使わず、親が feature worktree を先に作り、`subagent({agent:"worker", task, cwd:"<worktree の絶対パス>", async:true})` で起動する**。`cwd` は「作業ディレクトリの上書き」として docs にある（tool-reference.md の `cwd` 行）。1 worktree = 1 feature = 1 worker は、親が `cwd` を分ければ作れる。同じ worktree に 2 本の writer を立てないのは親の規律（`worker` のプロンプトも "single writer thread"）。
  - 未確認: `cwd` が**リポジトリ外の別 worktree**（`.tmp/worktrees/…` はリポジトリの内側だが別 checkout）のとき、project 設定の解決（`.pi/agents` の探索は「最も近い `.pi` / `.agents` を含む親」）や git root が期待どおりか。`git-root` 設定（configuration.md「Project root resolution」）の影響も未確認。
  - 未確認: 子の `bash` が worktree の `.git`（`.git` ファイル）で動くか。通常の `git worktree` なので動くはず（推測）。
- 補足: `worktree: true` は「同じファイルを触りうる並列の writer を隔離して、あとで patch を統合」する用途には良い。利用者は feature ごとに分けて衝突しない運用なので、**不要**。

## (3) 背景実行・完了通知・FleetView
- 背景: `async: true`（agent の frontmatter `async: true`、`asyncByDefault`、`forceTopLevelAsync: true` でも）。workflow は既定で背景。背景の子は**親と別の detached runner プロセス**内の session（README「How it works」）。
- 完了通知で**親が idle のとき起きる**: `src/runs/background/notify.js:494` が `pi.sendMessage(message, { triggerTurn })` で、失敗・paused は即時、成功は `completionBatch` で束ねる（`completionBatch`: 既定で有効、`maxWaitMs` 1000）。workflows.md:15「Native completion wakes the parent session, so the parent returns control instead of sleeping or polling」。→ 利用者の「子の完了は通知で親へ。親は応答を終えて待つ」と一致。**確かめたのはコードと docs まで。実機で idle の親が起きるかは未確認**（`sendMessage` の `triggerTurn` がアイドル中に新ターンを始めるかは pi 本体の挙動。pi-background の評価でも同じ未確認）。
- 通知は**起動した親 session にだけ**届く。親が終了していたら「次にその session を開いたとき」に届く（configuration.md「waitTool」）。
- `bg_wait`: 待つための tool。ブロック（`bg_wait({id})`。既定の窓 `waitTool.defaultTimeoutMs` 120000ms、`timeoutMs` で延長）と、`nonBlocking: true`（購読して完了で wake。UI のある対話 session のみ）。**普通の async の子は通知が自動で来るので `bg_wait` は不要**（docs/configuration.md）。「親が応答を終えて待つ」運用では `bg_wait` を使わない方針でよい。
- FleetView: 入力欄の下に常時表示（`fleetView`、既定 true、`fleetViewPlacement` で位置）、`/subagents-fleet` で一覧・transcript・steer・stop。他拡張（pi-background のウィジェット等）との枠の衝突は未確認。

## (4) 同時数・予算
出典: docs/configuration.md。
- `globalConcurrencyLimit`（既定 20）: **1 つの run の中**で同時に走る子の上限。超えた子は**キューに入り、空きが出たら開始**（`runs.all` / workflow の中の話）。
- `maxActiveAsyncRunsPerSession`（既定 0=無制限）: 親 session が持つ**トップレベルの背景 run**の同時数。1 を予約してから起動する。静的な chain / parallel は収まらないと**起動前に失敗**する。単独の起動が上限超過のときの挙動は docs に明記が薄い（キューではなく拒否と読めるが**未確認**）。→ 「空きが出たら次を起動」は、**親モデルが完了通知を見て次を起動する**運用になる。自動の待ち行列ではない。確実にしたいなら、1 つの workflow script（`runs.all` + `globalConcurrencyLimit`）にまとめて投げる手がある（キュー自動。ただし契約・worktree の準備は親が先にやる必要がある）。
- `maxSubagentSpawnsPerRun`（既定 64、run ツリーの累計）、`maxSubagentSpawnsPerSession`（既定は無制限、累計、`grant-spawn-budget` で追加）、`maxSubagentDepth`（既定 2。入れ子の深さ）、`parallel`（`maxTasks` 8 / `concurrency` 4。`tasks` 配列の並列）。全部 `~/.pi/agent/extensions/subagent/config.json`。
- 「全件検査は 1 本ずつ」: 専用の排他は**無い**（読んだ範囲）。受け入れ検証の `gate` / `acceptance.verify` はホストで実行され、結果は作業ツリーの状態で memoize される（tool-reference.md）が、複数 run の同時検査の排他は別。→ 利用者の全件検査の排他は、従来どおり親（または `mise run verify:all` 自体のロック）に任せる。

## (5) permission-system との連携（最重要）
事実（出典つき）:
1. **前景の子は親の ambient 拡張を載せない**（docs/agents.md「Tool and extension selection」: "Local foreground children ... never load the parent's ambient extensions"; `src/runs/shared/child-launch.js:203` `ambientExtensions = input.host === "runner" && ...`）。→ **前景の子には permission-system も cc-safety-net も載らない**。tool_call の網が丸ごと無い。`reviewer` は bash が無いので実害は小さいが、**前景の `worker` は bash/edit/write を無防備で持つ**。
2. **背景の子（detached runner）は ambient 拡張を載せる**（同上。`extensions` を省略したとき）。→ permission-system・cc-safety-net が子の session に載る（pi-stock-packages 由来で settings に載っていれば。載り方の実機は未確認）。
3. **背景の子の `PI_SUBAGENT_PARENT_SESSION`**: `src/runs/background/async-execution.js:553-555` が、runner 起動時の env にその起動の親 session id を入れる（`SUBAGENT_PARENT_SESSION_ENV`、コメント "Root parent session id the parent publishes for pi-permission-system ask forwarding"）。根の親プロセスでは、`src/extension/index.js:924` が子でない限りこの env を消す。→ permission-system v42（docs/subagent-integration.md「Out-of-process implementations」）の仕様では、**この env を持つ子は ask を親に転送**し、親が UI で draining（heartbeat 更新）中なら待つ（`forwardingTimeoutMs` 既定 600000ms）。親が応答していない / 終了なら約 2 秒で「承認不可」として deny。
   - 注意: permission-system v42 の docs の対応表は「nicobailon は parent-session 変数を設定しない」と書く（docs/subagent-integration.md の Conformance）が、**0.87.0 は設定している**（上のコード）。docs が古いか、版の差。実際の転送が動くかは**未確認**。
   - 利用者の「ask を待つ間は離席」: 転送された ask は親の UI に出て待つ（人が戻るまで）。親が idle でも heartbeat は更新される想定だが、**親がターン外のとき inbox を poll しているか**は未確認（要実機）。
4. **前景の子の ask**: `PI_SUBAGENT_PARENT_SESSION` は前景（同一プロセス内）には設定されない（watchdog.md:187「Root and in-process foreground hosts do not publish a global parent identity ... Environment-only permission extensions therefore cannot safely forward foreground `ask` requests; that path remains unsupported」）。そもそも前景には permission-system が載らないので、ask は出ず、規則の判定も無い。
5. `excludedExtensionPackages` は **`@gotgenes/pi-subagents`（別の package）の設定**で、nicobailon 版には**無い**（0.87.0 の docs とソースを grep、該当なし）。nicobailon 版で子に載せる拡張を絞る手段は、agent の `extensions:`（許可リスト。指定すると ambient を全て無効化して、列挙分だけ載る）/ `subagentOnlyExtensions:` / `subagents.defaultExtensions` / `defaultSubagentOnlyExtensions`（settings.json）/ `capabilityCeiling.denyExtensions`。**「ambient から特定のパッケージだけ外す」設定は無い**（読んだ範囲）。
6. 親側の判定: workflow の子の起動前に、**仮想 tool `subagent_launch`** の `tool_call` が出る（docs/workflows.md「Approving workflow children in permission extensions」）。permission-system が「規則の無い tool は ask」なら、workflow の子 1 つごとに 1 回 ask が出る（allow を足すと止まる）。入力に `cwd`・`commands`（受け入れ検証で走るシェルコマンド）が入るので、**`subagent_launch` を allow にすると、`gate` / `acceptance.verify` のコマンドは bash 規則を通らない**（docs「Commands are offered at launch ... An extension's bash rules don't apply to them on their own」）。通常の `subagent` 単独起動（`agent`+`task`）は `subagent_launch` を経由しない。
7. 子が `contact_supervisor` で親に聞く道（`need_decision`）は、**permission の ask とは別系統**で、親の `subagent_supervisor({action:"reply"})` で答える（native。pi-intercom 不要）。worker の「未承認の判断は止まって聞く」はこちら。利用者の `ask_user_question`（rpiv）は子には出ない（`tools` に書いて拡張を載せれば可能だが非推奨）。

→ 推奨: **`forceTopLevelAsync: true`**（depth 0 の single / parallel / chain を強制的に背景にする）にして、前景の子を作らせない。これで (a) 完了通知で idle の親が起きる、(b) permission-system / cc-safety-net が子に載る、(c) ask は親へ転送。**ただし `forceTopLevelAsync` は呼び出し側の `async:false` も上書きし、`clarify: false` も強制する**（configuration.md）。短い `scout` が背景になる分の遅延と、結果が通知で届く（`bg_wait` かターン待ち）ことは受け入れる。

## (6) 子が使うツール名（permission に allow を足すもの）
親（permission-system）が見る名前（ソースの `registerTool` / 定数で確認）:
- `subagent`（本体）、`subagents_enable`（前景のローダ。`toolActivation` が既定の新規 session で出る）、`bg_wait`、`subagent_supervisor`（親が子の質問に reply）、`subagent_launch`（workflow 子の起動前に出る仮想 tool。モデルには宣言されない）、`subagent_command`（bash コマンド制御用。明示選択時のみ）。
- 子側: `contact_supervisor`、`watchdog_diff`（reviewer）。子の bash / read / edit / write は子の session で permission-system（背景の子）が判定。
- 提案する方針（利用者が決める）: `subagent` は ask か allow（別の子を作る＝権限の拡大ではないが費用が出る）、`subagents_enable` / `bg_wait` / `subagent_supervisor` は allow、`subagent_launch` は **ask のまま**（上の 6 のとおり allow にすると検証コマンドが bash 規則を迂回する）。`bg_wait` は pi-background の `bg_*` と接頭辞が並ぶだけで名前は重ならない。`waitTool.name` で変更可。
- 重要: **`shellTools`（permission-system）に載せる必要のある、コマンド実行 tool は無い**（`subagent` の `task` は文字列のプロンプトで、シェルではない）。ただし `gate` / `acceptance.verify` / `runs.host`（run-ci は `npm test` / `npm run typecheck` 固定）は**ホストがシェルを実行する別経路**で、cc-safety-net は見ない（`bash` / `powershell` の tool 名だけを見る。pi-background の評価で確認済み）。→ 導入時の方針: **`gate` / `acceptance.verify` は使わない**（検査は親が bash で `mise run verify` を回す）。

## (8) 設定の置き場と chezmoi で配る案
- agent 定義: `~/.pi/agent/agents/*.md` → chezmoi の `home/dot_pi/agent/agents/<name>.md`（既に `home/dot_pi/agent/` がある。`pi-stock-packages` の配り方に合わせる）。プロジェクト固有は `.pi/agents/`（リポジトリ。ただし project 信頼（trust）を拒否すると無視される）。

## 「pi-subagents だけで足りるか」の結論
- **足りる（条件つき）。別の package は要らない。** 条件: (i) `forceTopLevelAsync: true` で前景の子を作らない、(ii) worker は `cwd` で feature worktree を指し `worktree:true` を使わない、(iii) agent 定義 3〜4 本、(iv) 「同時数の空きで次を起動」「全件検査は 1 本」は親の運用規則（スキル）で担保、(v) `gate` / `acceptance.verify` は使わない。
- **実機で確かめる 4 点（導入後すぐ）**: ①idle の親が完了通知で起きる、②背景の子の bash が permission-system と cc-safety-net に止められる（`/subagents-doctor` も）、③子の ask が親の UI に転送され、離席後に答えて続く（`PI_SUBAGENT_PARENT_SESSION` 経由。permission-system の docs は nicobailon 版を未対応と書いているので**ここが最大の不確実性**）、④`cwd` を別 worktree に向けた worker が正しく動く。③が不成立なら: 背景の worker の bash は `ask` を使わず allow / deny だけの規則にする（ask が無いので転送は要らない）か、permission-system 側に `PI_SUBAGENT_PARENT_SESSION` の対応状況を確認する（Issue 検索。未実施）。
- 補う最小の案: 上の config.json と agent 定義、スキルへの運用の節。コードの自作はしない。

## 判断した点
- worktree は pi-subagents の管理方式に合わせず、利用者の既存運用（名前つき feature worktree）に合わせた。理由: 運用の中核（ブランチ・commit・PR ビューア）が feature worktree 前提で、patch 回収方式に直すと移行費が大きい。
- `forceTopLevelAsync` を推奨とした理由: 前景の子が権限判定の網の外になるため。短い調査の遅延は小さい代償と判断。

## 利用者に聞きたいこと
1. 前景の子を禁止（`forceTopLevelAsync: true`）してよいか。推奨: はい。
2. 子の bash の ask を「人に転送」にするか、「子では ask を使わず allow / deny のみ」にするか。推奨: 最初は後者（転送の不確実性を避ける）、実機で転送が確認できたら前者。
3. `subagent_launch` を ask のままにするか（workflow を使わないなら出ない）。推奨: workflow は使わず、単独の `subagent` 起動に絞る。
