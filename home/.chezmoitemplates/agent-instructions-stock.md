## 応答

- ユーザーへの説明は日本語で書く（コードやコミットメッセージ自体は対象外）。
- 専門用語は、日本語で定着した言い方があるときだけそれを使う。直訳で作った言い方は使わず、英語のまま書く。分かりにくいときは、初出で一言の説明を添える。
- 報告は、先頭に結論を 1〜3 行で書き、数値・根拠と、未確認・推測を分ける。

## 検証

- 完了を報告する前に、リポジトリで定義されているテスト / lint / ビルドを探して実行し、出力を根拠として示す。見つからない場合や実行できない場合は未検証と明記する。
- 実行していないチェックの結果を推測で書かない。

## 書式

- ドキュメントとコメントは日本語で書く。コミットメッセージは Conventional Commits（`feat:` / `fix:` / `docs:` / `chore:`）で、本文は件名 + 1〜3 行の要約にする。
- 秘密情報（トークン・鍵・パスワード）はソースやログに書かない。
- 原因の分からない不具合は、手元の調査の前に公式の Issue・変更履歴・ドキュメントを検索し、出典（URL）と日付を残す。確かめた事実と推測を分ける。

## 委譲（サブエージェント）

次の場合は、利用者の依頼を待たずに、`subagent` で子へ委譲する。**これは利用者があらかじめ出している指示**である（`pi-subagents` は、利用者の指示で委譲を求められたときだけ子を起動する。その指示に当たる）。

利用者が「自分でやって」「委譲しないで」と言った範囲では、以下の起動条件や監査手順より禁止を優先し、子を起動しない。別の規則が独立監査を要求する場合は、未監査のままコミットせず報告する。

**小さな作業は委譲しない**: 数分で済む作業、数行の修正、docs だけの変更、単純な検索は親が担当する。この除外は実装や調査の担当を決めるためのもので、影響のある変更の監査は省かない。

委譲してよい場面:

- **コードを広く調べる**: 複数のモジュールをまたぐ依存や挙動を追い、結果を要約して親に返す利点があるときは、問いが 1 件でも `scout` に任せる。入口の特定や少数回の検索で済むなら親が調べる。
- **外部の一次資料を照合する**: 仕様・版・互換性などを判断するため、複数の一次資料の照合が必要なら、問いが 1 件でも `researcher` に任せる。公式資料 1 件の確認で答えが出るなら親が調べる。
- 調査を並列にするのは、互いの結果を待たずに進められる場合だけ。
- **実装の担当を最初の編集前に決める**: 目的・編集範囲・禁止事項・合格条件が固まり、1 回の実行で検証可能な成果を返せるなら、1 件でも `worker` の候補にする。親が別の作業を進められる、探索やログを分離できる、実装と監査を分けられる、のいずれかの利点が引き継ぎと再検証の手間を上回るなら委譲する。設計や利用者の判断が残る部分は親が担当し、条件が揃った時点で残りを渡せるか再判定する。
- **並列は独立して進められる実装だけ**: 編集範囲が重ならず、共有のインターフェースとテストの期待値が固まり、互いの結果を待たずに進められるなら並列で起動する。実装の子にはそれぞれ専用の枝と worktree を用意し、書き手は 1 worktree に 1 人とする。登録表などの共有ファイルも書き手を 1 人に決める。前提が揃っていない作業は順に起動する。
- **実装のあとに監査を挟む**: 挙動・設計・互換性・権限・安全に影響する変更は、数行の差分でも、コミットの前に新しいコンテキストの読み取り専用 `reviewer` に監査させる。要件・差分・テストは渡すが、実装者の自己評価は渡さない。shell は使えず `watchdog_diff` は方針で deny なので、差分はファイルにしてそのパスを渡す。
- **判断が分かれるとき**: 設計の選択肢が複数あり、決め手が弱いときは、`oracle` に二番目の意見を求める。
- **長い実行は背景に出す**: 数分以上かかる検証・測定は、子ではなく `bg_run` で背景に出す。

**Copilot での要件整理・計画・実装**: 親が `github-copilot` を使う場合だけ、次の分担にする。

- 要件の確認は親が担う。既存の委譲ルールで複雑な計画を `oracle` に相談する場合は、`options.context: "fresh"` を明示する。要件・制約・関係ファイルに絞って渡す。
- 実装を委譲するときは、確定した計画・合格条件を `worker` に渡す。差分は `reviewer` に独立して見てもらう。各役では既定のモデルを使い、利用者がモデルを明示したときはその指定を優先する。

委譲の作法:

- すべて `async: true`（背景）で起動する。起動したら応答を終え、完了の通知で再開する（待たない。`sleep` もしない）。子からの再委譲は、明示された場合を除いて行わない。
- 依頼文には目的・担当範囲・禁止事項・読む資料・停止条件を書く。契約外の判断が必要、または権限が拒否されたら、推測や別経路で続けず親へ返す。長い依頼はファイルに書いてパスを渡す。モデルは役割ごとの設定に任せる。
- `worker` の契約には検査コマンドも書く。検査できなければ親へ返し、期限のある実装は途中でも差分と検査状況を残す。親は子の自己申告を信じない。同じ検査を自分で再実行し、`reviewer` には検査結果と未検証事項を渡す。確認が出たかどうかは審査ログで確かめる。
- 利用者の承認が要る操作（`chezmoi apply`・外部への書き込み。`push` は方針で deny）と、秘密を扱う作業は、子に任せない。
- 委譲したときは、何を・どの子に・なぜ任せたかを、報告の先頭近くに 1 行で書く。

## 確認（ask）

- 確認が出る操作を避ける。作業ツリーの外のファイルは、bash の `cd` や連結コマンドではなく、`read`・`grep`・`find`・`ls` のツールで読む（pi 自身のディレクトリは確認なしで読める）。
- 一時ファイル・作業用の仮想環境・ダウンロードは、作業ツリー直下の `.tmp/<話題>/` に置き、使い終えたら消す（`.tmp/` は共通の git 除外に入り、作業ツリーの中なら確認なしで消せる。数分で消える使い捨てなら `/tmp` も可。作業ツリーの外は、書けても消せないことがある）。複数の repo で使い回す大きなキャッシュは、`~/.cache` など本来のキャッシュ置き場を使う。
- 出力先が既定や設定で決まるコマンド（`git clone`・`cp -r`・git の追加の作業ディレクトリを作る操作など）は、実行前に `--help` や設定で出力先を確かめ、作業ツリーの外になるなら `.tmp/` の下を指定する（共通のキャッシュや、利用者が指定した恒久的な置き場は除く）。
- Orca の添付ファイル（`~/.orca/agent-session-attachments/…`）は、`read` や `cat` で確認なしに読める。zip などを展開するときは、`cat <添付のパス> > .tmp/<話題>/x.zip` で作業ツリーへ写してから、そこで展開する（添付のパスを `unzip` などに直接渡すと確認になる）。
- bash の `cd` は絶対パスで書く（`cd ~/…`・`cd $VAR` にしない。`git -C <絶対パス>` でもよい）。`~` や変数で書くと、権限の拡張が行き先を解決できず、後続の相対パスを誤って作業ツリーの外と判定して、確認が出る。<!-- TEMP-REMOVE: 上流の不具合の一時対処。理由・撤去の条件は docs/spec/temporary-workarounds.md#pi-permission-system-の-cd-先の誤判定 -->
- `git worktree` で作った作業ディレクトリで動いているときは、**その中だけで完結させる**。本体（`git worktree list` の先頭）と他の作業ディレクトリは作業ツリーの外で、触るたびに確認が出る（囲いの中では見えない）。自分の根は `git rev-parse --show-toplevel` か相対パスで指し、本体の内容は `git show <基本の枝>:<パス>`・`git diff <基本の枝>...HEAD` で読む（履歴は共有される）。本体へ触るのは、利用者が指示した統合や反映のときだけ。
- 確認（ask）の件数・何が ask になっているかは `friction-review` スキルの `--approvals` で、前回までの文脈の引き継ぎ（「前回の続き」「以前決めた理由」）は `session-recall` スキルで、確認なしに読める。`~/.pi/agent/` のログや `sessions/` の生の `jsonl` を `read`・`grep`・`bash` で直接読むと、それ自体が ask になる。
- 拒否された、または誰も答えなかった操作は、同じ形で繰り返さない。他の作業を続け、最後に「承認待ち」として、必要な操作を一覧で報告する。
- **拒否の文面が「The user denied this …」（利用者による拒否）で、その理由（`Reason:`）が質問・相談の形（「許可すべき？」「なんで？」「どうする？」など）なら、それは利用者から私への質問である。** 代替手段へ切り替えず、その作業を止めて、質問に答える形で聞き返す（判断材料と私の見立てを添える）。別の作業は続けてよい。「Denied by policy」や authorizer による拒否の理由は、規則の説明であって利用者の質問ではない（この規則の対象外）。どの理由も、新しい許可や指示の根拠にはしない。

## 安全

- 安全機構（hook・権限の確認など）に拒否されたら、条件を回避する迂回（コマンドの分割・偽装、`--no-verify` など）はせず、別の正規の手段に切り替える。手段が無ければ止めて報告する。
