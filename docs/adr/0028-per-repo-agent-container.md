# エージェントの隔離は、リポジトリごとの箱にする（コンテナ開発は WSL2 の Incus の箱、それ以外はホスト）。汎用サンドボックスは目指さない

- **ステータス**: Proposed（方針。2026-11-07 に利用者が方向を確認した。実物 1 つでの試験の待ち）
- **日付**: 2026-11-06（2026-11-07 に、Incus の箱を主役とする形へ全面改訂）
- **決定者**: applejxd
- **関係**: [ADR-0027](0027-isolation-unit-is-environment.md)（隔離の単位は環境）の P2・P3 の**実現方法**を置き換える。「隔離の単位は環境」と P1（フルガードのみ）は変えない。

## コンテキスト

`pis`（Fence = OS サンドボックス）と `pisd`（rootless Docker の硬化した使い捨てコンテナ）は、**使いたい場面で使えない**ことが多かった。原因は、どこでも使える汎用のサンドボックスを目指し、既定を厳しくしたこと。実際の開発で要るものと衝突した。

- **GPU への接続**（SLAM の推論、AI の推論）
- **認証情報へのアクセス**（LLM、GitHub、クラウド、Hugging Face）
- **Web サーバーのポート開放**（自前の Web アプリの確認、rerun の画面）
- **別のディスクにあるデータセット**
- **コンテナを使う開発そのもの**（`docker compose`、GPU つきのサービス）

利用者側の実態（[調査](../research/agents/sandbox-user-adoption-2026-11.md)。粗い目安）: 多数派は **(a) ホストでそのまま動かす（YOLO）** と **(b) Docker・devcontainer の中で動かす**。OS のサンドボックス・VM・別の機械は少数。自作の隔離層は、保守の費用が大きい（Fence は 5.5 週で約 40 件の変更）。

## 脅威モデル（この方針が守るもの・守らないもの）

**守る（対象）**: エージェントの**正規の権限の範囲での被害**を、リポジトリ単位に絞る。

- T1 エージェント自身の誤動作（誤った削除・書き換え）
- T2 外部コード・依存の暴走（ビルドスクリプト、パッケージの実行）
- T3 外部の内容に仕込まれた指示（プロンプトインジェクション）で、エージェントの正規の権限が使われること
- T4 与えた資格情報の範囲での漏洩（範囲を絞る・中継で隠す）

**守らない（対象外）: ホスト側の脆弱性に由来するもの。** カーネル・GPU ドライバ・コンテナのランタイム・OS・ブラウザの脆弱性、コンテナからの脱出、ホストのブラウザ経由の `localhost` への攻撃など。別の脆弱性の悪用が前提で、コンテナの設計では防げない。個人の開発では、費用に見合わない。**ホストを最新に保つ**（OS・Windows・NVIDIA ドライバ・Incus・Docker）運用で対処し、この方針の設計には含めない。

境界の位置づけ: 箱は「誤動作と仕込まれた指示の被害の範囲」を絞る道具で、**悪意のある攻撃者に対する強い境界ではない**（ガードも、うっかり防止）。箱はカーネルをホスト（WSL の VM）と共有する。WSL2 のカーネルには AppArmor が無く、native より壁が 1 枚薄い。

## 決定事項

1. **汎用サンドボックスを目指さない。** `pis` の Fence（OS サンドボックス）と、`pisd` の硬化した起動器（`pisd.py`）は、縮小・撤去の方向にする。ホストの pi は、フルガードだけで使う（[ADR-0025](0025-dotfiles-dev-without-os-sandbox.md) の延長）。
2. **使い分けは「コンテナを使う開発か」で決める。**

   | リポジトリ | pi を動かす場所 | Docker の役割 |
   | --- | --- | --- |
   | コンテナを使わない（dotfiles・スクリプト・docs など） | **ホスト**（フルガードと確認だけ） | 関係なし |
   | コンテナを使う（SLAM・AI Web アプリなど。GPU・compose が要る） | **Incus の箱 1 つ**（リポジトリごと。pi は箱の中で直接動かす） | **箱の中で、リポジトリの既存の Dockerfile・compose をそのまま動かす** |
   | 箱に置けない例外 | ホスト（定義を書くだけ。起動は人。案 1） | 既存のまま |

   Docker 直起動の agent コンテナ（当初案の、pi を入れた compose）は、**主役ではなく退避先**にする。退避先は 3 つだけ: ① Incus が使えない機（macOS など。Incus のサーバーは Linux 専用）② WSL の Incus が不安定だったときの退避 ③ 他の人に渡す devcontainer。**今は作らない**（必要になったら、箱の定義から派生させる）。
3. **箱は、WSL2 の主ディストロの中の Incus の、非特権のシステムコンテナ**にする（`security.nesting=true`。特権にしない）。リポジトリごとに 1 つ（名前は `kcage-<リポジトリ>`、ラベル `kcage.*`）。箱の中で、pi と、リポジトリ自身のサービスの Docker を動かす。実機で T1〜T7 に合格した（[実機確認](../research/agents/incus-dev-environment.md#5-wsl2-での実機確認2026-11-07使い捨てディストロt1t7-すべて合格)）。
   - 箱ごとに別のネットワーク名前空間で、**箱から、主ディストロ・Windows の `127.0.0.1` に届かない**。
   - GPU: `/dev/dxg` を渡し、`/usr/lib/wsl/lib` と `/usr/lib/wsl/drivers` を**別々の読み取り専用 `disk`** で渡す。箱の中の Docker の GPU は **CDI 方式**（`docker run --device nvidia.com/gpu=all`）。従来の `--gpus all` は不可。
   - 要設定: 別ディストロの Docker の `FORWARD drop` に対する許可（再起動で消えるので永続化する）、`raw.idmap "both 1000 1000"` と `/etc/subuid`・`subgid`（`shift=true` が使えない）。
   - WSL の専用ディストロは採らない（全ディストロが VM とループバックを共有し、ネットワークを隔離できない）。native Ubuntu の Incus は、VM への GPU 専有などが要るときの追加手段として残す。
4. **箱の作り方**: 公式の `images:ubuntu/24.04` に、初期設定（docker・nvidia-container-toolkit と CDI・Node・pi・git・uid 1000 のユーザー）を入れ、`incus publish` で**手元のテンプレート**にする。箱は `incus copy` で作る（`dir` で 8〜9 秒）。**Incus 用のイメージは自作して配らない**（ghcr に載せられるのは OCI だけで、Incus は ghcr から Incus 形式を引けない）。ghcr の土台イメージは、今は作らない（2 の退避先が必要になったとき）。Ubuntu 標準の Incus は 6.0.0（LTS）で、OCI の直起動（6.3 以降）は使えない。
5. **リポジトリごとに、必要十分を宣言する**（`kcage.yaml`。箱を使うリポジトリだけに置く）: GPU の要否、公開するポート（**`127.0.0.1:` に限る**。`proxy` デバイス）、データセット（**読み取り専用で、必要なディレクトリだけ**）、認証の型（7）。リポジトリの Dockerfile・compose は**そのまま**（置き換えない）。Docker 構成が無いリポジトリ（apt や colcon で直接ビルド）は、箱の中へ直接入れる。
6. **作業ツリー（worktree）の運用を維持する。** **worktree の作成・管理はエージェント（箱の中）が行い、ADE（Orca など）では worktree を作らない・操作しない前提。** リポジトリのルートを、**ホストと同じ絶対パスで、書き込み可能で重ねる**。`.git` の共通ディレクトリと `.tmp/worktrees/*` が含まれるので、箱の中で `git worktree add` でき、ホストからも見える（[下の影響](#worktree-運用への影響)）。
7. **資格情報: 長期の認証情報は箱に入れない。** 箱に入るのは、ダミー、または短命で範囲を絞ったものだけ。本物は**ホスト側のブローカー**が持つ（`kcage up` で必要なものを起動する）。つなぎは Incus の `proxy` デバイス（ホストの Unix ソケット ⇄ 箱の中のソケットまたは `127.0.0.1` のポート。要実機確認）。型は 3 つ: `simple`（範囲を絞った認証を、読み取り専用で渡す）・`relay`（ホスト側のブローカーで中継）・`offline`（外向きなし）。防御は、認証情報そのものの範囲（PAT・ロール・トークンの権限）で作る。

   | ツール | 型 | 箱に入るもの | 備考 |
   | --- | --- | --- | --- |
   | gh | relay | ダミーの `GH_TOKEN` と `http_unix_socket` | 本物は**読み取り専用の fine-grained PAT**（ホストの Envoy が持つ。[broker](../spec/sandbox/broker.md) の流用）。**push の資格情報は渡さない**（push は人） |
   | aws | relay | 最大 1 時間の、専用ロールの認証情報（コンテナ認証情報エンドポイント） | 箱のロールは**読み取り専用**（Bedrock の使用状況・料金・AgentCore の一覧）。**キーの発行・IAM の変更は外（人）だけ**。AgentCore の gateway 設定は、コードは箱で書き、反映は外。Bedrock を使う鍵は、ホストが作る短期の API key（最大 12 時間） |
   | az | offline（必要になったら relay） | 短命のトークンだけ | refresh token は箱に入れない。実測は必要になってから |
   | hf | simple | 専用の fine-grained 読み取りトークン（`HF_TOKEN`） | キャッシュは箱ごとの領域 |
   | pi の LLM | 既存どおり | Copilot は pi 自前（長期トークンは `read:user` だけ）。Bedrock は短期キー | [CHG-0037](../change/0037-pis-usability-and-telemetry.md) の G8・G1 |

   **LLM ゲートウェイ（LiteLLM など）は使わない**（サプライチェーン事件が 2 回、仮想キーに DB が必須で長期キーが集まる。[調査記録 D4](../research/agents/agent-auth-delegation.md)）。開発中のアプリが複数のプロバイダーや予算の上限を要するときだけ、その repo の compose で再検討する。
8. **git のフックと設定**: `.git/hooks` と `.git/config` は**既定で読み取り専用**（フックの実行は妨げない。書き換えだけを防ぐ。ホストの git が、書き換えられたフックを実行するのを避ける）。必要なリポジトリは、オプションで書き込み可にできる（信頼するリポジトリ）。
9. **ソケットは渡さない。制御面は、root 所有の補助（`kcage-root`）を `sudo` で呼ぶ形に一本化する。** 箱へ、docker のソケットも **Incus のソケットも渡さない**。`incus-admin` は実質 root なので、**ホストの pi の実行主体を入れない**（入れると pi も箱を特権化できる）。`kcage` コマンドは `sudo kcage-root <動詞> <リポジトリ>` を呼ぶ薄い入口で、補助は root 所有の許可表（`/etc/kcage/policy.toml`）にある項目だけを**固定生成**する（呼び出し側はデバイスや設定を指定できない。`device_to_argv` が最後の関門）。`up`・`stop`・`exec`・`ls` はパスワードなし（登録済みの箱しか作れず、特権が増えない）、`register`・`rm`・`setup`・`template` はパスワード必須。**特権の箱は作らない**。フルガードは、`incus`・`kcage-root`・`kcage rm/register/setup`・ソケットや配備先への書き込み・`incus-admin` への追加を拒否する。箱の中の Docker は、箱の中に閉じる。根拠: Incus の制限つきプロジェクトと制限つき証明書は成立しなかった（GPU とブローカーに要る proxy・unix-char デバイスを許すと、利用者が proxy で Incus の管理ソケットを箱へ転送でき、箱から管理 API を使えた。[実測](../research/agents/incus-dev-environment.md#6-制限つきプロジェクトの実測t10と箱の結合試験e2e)）。前提: パスワードなしで何でも実行できる sudo（`NOPASSWD: ALL`）が無いこと（`kcage doctor` が検出する）。
10. **Orca は、ターミナル起動だけを使う**（構造化チャットは使わない）。画像のアップロード・通知・GitHub 連携は使う。
    - 画像: 貼り付け画像のフォルダを、読み取り専用の `disk` として重ねる（Windows の Temp 全体は渡さない）。
    - 通知: 箱の端末が通す BEL・OSC。
    - GitHub: Orca 側の連携はホストの認証で動く。エージェント側は 7 の型。
11. **スキル（このリポジトリが配る agent-box）が、`kcage.yaml` の雛形を作る。** 「GPU は？ポートは？データセットは？認証は？」と尋ねる。**いきなり汎用化せず、実物 1 つ（SLAM か AI Web アプリ）を手書きで作って 1 週間使い、うまくいった部分を抜き出す**。操作は `kcage` コマンド（`up`・`pi`・`stop`・`rm`・`ls`・`snap`・`doctor`）にまとめる（案。これから作る）。
12. **ツールだけを包む案は採らない**（ホストの pi がホストのファイルを読める面が残り、隔離にならない）。

## 箱の構成

```text
Windows 11
└ WSL2 VM（カーネル 1 つ。全ディストロが共有。GPU は /dev/dxg）
   └ 主ディストロ Ubuntu 24.04（systemd）… 人が使う。incus を叩けるのは人だけ
      ├ incusd ＋ incusbr0（DHCP・DNS・NAT）、ホスト側のブローカー（gh・aws・hf の中継）
      ├ 既存の Docker（FORWARD drop → incusbr0 の許可を足す）
      └ 箱 kcage-<repo>（非特権のシステムコンテナ。nesting あり）
          ├ pi（直接）と docker（overlayfs）＋ nvidia-ctk（CDI）
          ├ リポジトリ自身の compose のサービス群
          └ 重ね: リポジトリ（rw）・.git/hooks と config（ro）・データ（ro）・/usr/lib/wsl/{lib,drivers}（ro）・/dev/dxg
```

## worktree 運用への影響

「バカスカ worktree を立てる」運用は、次の条件で**維持できる見込み**（実機で一部確認済み。残りは実物で確かめる）。

| 論点 | 影響と対処 |
| --- | --- |
| 箱の数 | 1 リポジトリ = 1 箱。worktree が増えても、箱は増えない。子エージェント（`guarded_task`）は、同じ箱の中の別プロセス |
| worktree の `.git` | worktree の `.git` は、共通ディレクトリへの**絶対パス**を持つ。**ホストと同じパスで重ねれば**、そのまま動く |
| 場所 | worktree はエージェントだけが `.tmp/worktrees/*`（リポジトリの中）に作り、ADE は作らない・操作しない前提。ルートの重ねだけで足りる |
| ホスト側の操作（統合・掃除・PR ビューア） | 共有の重ねなので、これまでどおり動く。`guarded_pr_summary` が書く `refs/pi/review/*` も共有の `.git` に直接入る。ただし**箱とホストで同じパス**が条件 |
| 隔離の粒度 | 箱の境界は**リポジトリ単位**。同じ箱の中の worktree どうしは、隔離されない（1 worktree = 1 worker は、これまでどおり規約と所有の表明で守る） |
| 共有の履歴 | 共通の `.git` が書き込み可なので、エージェントは全ブランチの参照を書き換えられる。対処: push の資格情報を渡さない（リモートが退避先）、フルガードの deny、フックと設定は読み取り専用 |
| ファイルの所有者 | 実測済み: `raw.idmap "both 1000 1000"` で、箱の uid 1000 とホストの uid 1000 が対応し、箱で作ったファイルの所有者がホストでも uid 1000 になる。`shift=true` は使えない |
| `pre-commit` などの導入 | `.git/hooks` が読み取り専用だと、導入（`pre-commit install`）はホストで行う。実行は、箱の中でそのまま走る（実測済み） |

## 検討した選択肢

- **A. `pis`・`pisd` を改良して続ける**: GPU・認証・ポート・データセットの例外を、硬化した既定の上に積むことになり、保守が重い。
- **B. 開発単位の環境（専用 WSL ディストロ）を、すべてに使う**: ネットワークを隔離できず、作る手間も大きい。採らない。
- **C. microVM・OpenShell**: WSL2 で GPU と両立しない、または apt・compose を満たさない（[ADR-0027](0027-isolation-unit-is-environment.md)）。
- **D. ツールだけ包む**: ホストのファイルが読める面が残る（12）。
- **E. Docker 以外（Podman など）**: 箱の中の rootless でない Docker で足りる。移る利点が見当たらない。
- **F. Docker 直起動の agent コンテナ（pi を入れた compose。当初案）**: 主流（devcontainer）に沿うが、コンテナを使う開発では、箱と二重になる。**退避先に格下げした**（2）。
- **G. native Ubuntu の Incus を主にする**: データを native へ置く必要がある。WSL の Incus が実機で要件を満たしたので、追加手段にした。
- **H. LLM ゲートウェイ（LiteLLM など）**: 採らない（7）。
- **I. リポジトリごとの Incus の箱（採用）**: GPU・入れ子の Docker・ネットワーク隔離・重ねが、実機で通った。

## 費用と便益

- **便益**: 実際に要る機能（GPU・認証・ポート・データ・compose）が、宣言で足りる。リポジトリの Docker 構成はそのまま使える。自作の隔離層の保守が減る。worktree と Orca の運用を、ほぼ維持する。箱は `127.0.0.1` のサービス（PR ビューアなど）に届かない。
- **費用**: テンプレートの作成、`kcage` コマンド・ブローカー・スキルの整備、`FORWARD` の許可の永続化、ホストの最新化の運用。隔離は完全ではない（カーネル共有・AppArmor なし）。箱は常駐の systemd と dockerd を持つので、同時に多数立てると資源を使う。
- **廃止・凍結**: `pis` の Fence、`pisd.py` の硬化した起動器、`dev-*` の自動化（CHG-0064 の W2・C1）、native 側の Incus（N2・N3。追加手段として保留）、環境内ハーネスの台帳・PR ビューアとの統合。
- **流用**: `pisd` の Envoy の認証設定（gh のブローカー）、フルガード、台帳。`feature/pisd` と `feature/dev-env-front` の枝は、流用元として残す。

## 未確認と、確かめ方（小さな試験）

実機（WSL2）の T1〜T7 は合格した。残りは、SLAM か AI Web アプリのどちらか 1 リポジトリで、手書きの `kcage.yaml` と箱を作り、次を確かめる。

1. **T8 ブローカー**: `proxy` デバイスで、ホストの Unix ソケットを、箱のソケット・`127.0.0.1` のポートへつなげるか。箱の中から `gh api`・`aws sts get-caller-identity`・`hf download` が、本物の認証なしで通るか。箱の中に認証情報のファイルが無いか。
2. **永続化**: 再起動後に、`FORWARD` の許可・`raw.idmap`・箱が戻るか。
3. **compose の GPU**: 箱の中の compose で、CDI の `devices`（または `runtime: nvidia`）が通るか。
4. **Orca の 3 機能**: ターミナル起動（`kcage pi`）、画像の受け箱、通知。
5. **外向き通信の制限**: 当面は制限なし。許可リスト（Incus の ACL）で、ブローカーと必要なホストだけに絞れるか。
6. **Windows 側の `0.0.0.0` の待ち受けが、箱から見えるか**（ゲートウェイ経由。ホストの `0.0.0.0` の待ち受けは見える）。

追加で確認する点（決め切っていないもの）:

- **箱の中のフルガードの既定**（確認を維持するか、箱が境界なので bypass 既定＋deny・confirm のみにするか）。
- **OAuth トークンの更新**: 認証ファイルを読み取り専用で渡すと、更新できない可能性（`simple` の型）。
- **セッション履歴・設定・キャッシュの永続**: 箱の中に残る（`kcage rm` で消える）。残したいものの置き場。
- **未 push の枝の退避**: 共通の `.git` が壊されたときの、ホスト側の定期的な退避（`git bundle` など）。

## 見直しの条件

- 実物の試験で、worktree 運用・Orca の 3 機能・ブローカーのいずれかが、実用にならないと分かったとき。
- WSL の Incus が不安定（再起動後の復帰・ネットワークの干渉など）で、実用にならないとき（native の Incus、または Docker 直起動の退避先へ）。
- 外部の信頼できないコードを、頻繁に動かすことになり、ゆるい境界では足りなくなったとき（`pisd` の硬化した形を再び使う）。
- Incus が使えない機（macOS など）で、コンテナを使う開発をするとき（退避先の Docker 直起動を作る）。

## 決定の確認方法

- 1 つのリポジトリで、GPU・ポート・データセット・認証が、宣言どおりに使えること（実機）。
- worktree を複数立てて、並列の作業が、これまでと同じ手順で回ること。
- 箱の中から、ホストの秘密（`~/.ssh`・他のリポジトリ）と、ホストの `127.0.0.1` のサービスに届かないこと（否定試験。T4・T5 は合格）。
- 箱の中に、長期の認証情報（PAT・IAM のキー・refresh token）が無いこと。
