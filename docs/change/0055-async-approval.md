# CHG-0055: 承認つきの操作を、確認が取れなくても失わず、利用者が後から承認して実行できるようにする（非同期承認の実装）

- **状態**: Exploring
- **更新日**: 2026-10-31
- **基準**: コミット `9e979d8` 以降、pi 1.4.0。方針は [ADR-0023](../adr/0023-pending-approval.md)（Proposed）。上位は [CHG-0054](0054-containment-and-async-approval.md) の段 4。原型は [CHG-0046](0046-guarded-action-timeout.md)（`git_commit` の退避）

## 目的と非目的

**目的**: 構造化した操作（`guarded_action` の各操作と、これから作る統合 `git_integrate`・`chezmoi_apply`）の確認が、時間切れ・不在・UI なし・「あとで」のとき、**操作を実行せずに記録を残して作業を続け**、利用者が後で `/pending approve` で承認したときだけ、前提を再検査して実行する。利用者の最優先の要望（各種の確認の時間切れの根本的な解消）。最初に届かせたい先は、**統合（`git flow feature finish`）と `chezmoi apply` の時間切れ**。

- 承認が無いまま実行しない。時間切れ・不在・UI なし・「あとで」は、保存だけ（実行する経路を作らない）
- 承認できるのは利用者だけ（モデルが呼べるツールにしない。子は承認できない）
- 通知（BEL・フッター・モデルへのメッセージ）は手段で、保留・承認・結果の正本にしない。正本は git の ref

**非目的**:

- 任意の bash の必須確認の保留と再実行（前提を固定できない。時間切れは今までどおり拒否）
- 時間切れでの自動実行。悪意あるコードへの耐性（守るのは、うっかり。[ADR-0012](../adr/0012-ocs-boundary-for-accidents.md)）
- 初版で扱わないもの: RPC（Orca・Zed の ACP）での有効化、pi の外から使う CLI、子からの保留（段 P11 で設計）、別リポジトリの保留の横断一覧、承認画面の「編集して承認」（直すなら破棄して、モデルに再要求させる）

## 設計の契約

実装の前に決める。独立した `review` を 2 回（1 回目: 実装計画、2 回目: この契約）受け、指摘を反映した（MAJOR は 1 回目 7 件、2 回目 6 件）。

**3 つの層を分けて守る。** 保留 ref の CAS だけでは、承認した内容と実行する内容の一致は保証できない（2 回目の指摘）。

| 層 | 守るもの | 手段 | 限界 |
| --- | --- | --- | --- |
| 要求 | 同じ要求の二重承認、古い表示の承認 | 保留 ref の遷移を、表示した記録の OID で CAS する（契約 2・3） | 操作の対象が変わることは止めない |
| 対象 | 承認したものと違う内容の反映 | 実行計画が、対象の識別子と期待値（OID など）を持ち、反映を期待値の検証（git の CAS など）で保護する（契約 2・5） | 利用者の通常の操作や、任意の外部プロセスによる差し替えは、完全には防げない（うっかりの範囲） |
| 実行者 | 実行中の試行と、人の `resolve`・再実行が重なること | 実行所有権・開始段階・停止の確認（契約 3） | 別のホストや、確認できないプロセスは、手動の復旧が残る |

1. **保存と重複の抑止**: 記録は `refs/pi/pending/<id>` が指す commit（tree は `record.json` だけ）。種類は trailer `Pi-Pending-Kind` と構造の両方で検証し、trailer だけに頼らない。既存の退避（`git_commit` の tree とメッセージ）は、無変更でそのまま読む。状態は ref の名前空間（`refs/pi/pending|running|done/<id>`）で表す。id は既存の時刻ベース。**記録は信頼しない入力として読む**（スキーマ検証・未知のキーの拒否・symbolic ref の拒否）。Fence は人とモデルを区別しないので、記録は偽造できる前提で設計し、守るのは、偽造しても権限が上がらず、承認が要ること（契約 2）。
   - **重複の抑止**: digest は、保存された値を信用せず、検証済みの値から再計算する。正規化には版を付け、本文の空白などを勝手に直さない。対象が worktree に依存する操作は worktree の識別を、gh は接続先のホストを含める。作成時の判定は原子的にする（digest をキーにした ref の `create` で排他にする。具体は P2）。`pending`・`running`・未解決の `unknown` と同じ digest は、新しく作らず既存の id を返す。`done` の後の同じ要求は、新しい要求として作れる（決着すると鍵は外れる。`supersedes` で前の要求を示すのは、retry で作る要求だけ）。**digest は、承認済みの証明でも、永久のリプレイ防止のキーでもない。**
   - **大きさの上限**: JSON を読んだあとの検査だけにしない。ref の列挙数、commit メタデータ・tree・blob を読む量、総処理時間にも上限を置き、上限を超えたことを「保留なし」に見せない。直接 git を書けるモデルによる、意図的なディスクの消費までは防げない。
2. **承認の流れ（検証済みの実行計画）**: 記録から直接実行しない。(a) 記録を読み、操作の定義と引数を**現在の設定・役割・操作定義・キルスイッチ**で再検証して実行計画を作る。実行先は今の `ctx.cwd` と実体の共有 `.git` で決め、記録の `cwd` を権限の根拠にしない。**実行計画は、操作の対象の識別子（完全な ref 名と OID、結果の tree など）・期待値・許す副作用を持ち、実行時にブランチ名や記録から再算出しない。** (b) 前提を再検査する。(c) 利用者に、その計画を表示する（期限なし。`ctx.mode === "tui"` かつ `ctx.hasUI`。子には登録しない）。(d) 承認されたら `beginApproval(id, 表示した記録の OID)`（CAS）。(e) 実行の直前に、前提・現在の役割・設定・キルスイッチをもう一度検査する。(f) 反映は、対象の期待値の検証つきで行う（契約 5）。(g) 結果を記録する。不一致なら、実行せず `pending` に戻して理由を見せる。自動では再実行しない。
   - **初版の `/pending approve` は、モデルの実行中（`ctx.isIdle()` が偽）は断る。** pi は拡張のコマンドを、モデルの実行中でも即座に実行する。承認の実行が、モデルの作業（同じリポジトリの編集など）と重なるのを避けるため。理由と、止める・終わるのを待つ案内を出す。使ってみて不便なら見直す。
3. **ref の遷移と、実行の所有権**:
   - 遷移はすべて 1 回の `update-ref --stdin` のトランザクションにし、**各コマンドの前に** `option no-deref` を付け（option は次の 1 コマンドだけに効く）、期待 OID を指定する（読み出しと遷移の間に ref を symbolic ref へ差し替えられても、通常のブランチを巻き込まない）。`create running/<id>` は、既にあれば失敗する（排他になる。**Fence の内側から、実機で確かめた**）。
   - `running` は 2 段階にする。**予約**（`reserved`）と、**開始**（`started`。副作用を始める意図を、永続化した状態）。**開始を保存する前には、副作用のあるプロセスを起動しない。** 保存に失敗したら、起動せず `pending` に戻す。
   - `running` の記録は、試行の識別子（`attemptId`）と、実行者（owner: セッション ID・実行時の世代・プロセスの ID と起動時刻・ホスト）を持つ。`attemptId` と期待 OID は、古い試行の結果による上書きを防ぐだけで、実行者が生きているかの証明にはならない。
   - **`resolve` の規則**: 実行者が生きているかもしれないときは拒否する。PID だけ、または heartbeat の期限切れを「止まった」の証明にしない（同じホストで、PID が存在しない・起動時刻が違う、で確認する）。確認できないとき（別のホスト・確認の手段が無い OS）は、利用者が「実行者は止まっている」と明示して承認し、その旨を結果の証拠に残す。`reserved` で実行者が止まっていれば、安全に `pending` へ戻せる（未実行）。`started` で止まっていれば、証拠（下の契約 4）を見せて、人が決める。retry は、古い試行を消さず、**新しい要求として作り直して再承認させる**。
   - **セッションの終了・reload・切り替え**: 承認の待ち（未開始）は取り消す。開始済みの実行には中断の信号を送り、起動したプロセス群を止め、結果を保存する。結果を保存できなければ `running` を残し、未解決として一覧に出す（旧い実行時の許可を、持ち越さない）。
   - `finishApproval`・`returnToPending`・`resolve`・期限の削除も、同じ形のトランザクションにする。
4. **結果の 4 値と、結果の型**: 実行器は `not_executed / success / failed_confirmed / unknown` を返す。副作用の有無を確定できないもの（gh の応答の断、ref の更新後の失敗など）は `unknown`。結果は `outcome`・`phase`（どこまで進んだか）・`confirmedEffects`（成立したと確認できた副作用）・`remainingCleanup`（残った後片付け）・`evidence`（判断の材料）を必ず持つ。「統合は成立し、後片付けだけ失敗した」と「応答が失われ、成立したか分からない」は、人に渡す復旧の内容が違うため。
   - **結果の保存に失敗したら**、保存できない `unknown` を作ろうとせず、`running` を残して保存の失敗を表示する。復旧は、まず読み取りだけで git・gh の状態を検査し、判断の材料を作る（自動の再実行ではない）。
5. **品質ゲートを後退させない**:
   - **`git_commit`**: 承認後は、ブランチ・HEAD・現在のインデックスの tree が保留と一致するときだけ、通常の `git commit`（hook と署名を通す。pre-commit の秘密検出も効く）。不一致なら再要求する。保留した tree を `commit-tree` と CAS で作る方式は採らない（hook を迂回する）。hook が内容を変えた場合の保証は、通常の `git commit` と同じ（保証の対象外）。
   - **`git_integrate`**: ブランチの ref だけを `update-ref` で進めない（チェックアウト中のブランチの ref だけを進めると、作業ツリーとインデックスが古くなり、変更が消えたように見える）。統合先をチェックアウトしている worktree で、作業ツリーとインデックスも一緒に動く反映（`git merge --squash` と `git commit` に相当）を行い、**作業ツリーが clean でなければ断る**。squash 後のインデックスの tree が、承認した結果の tree と違えば、commit の前に止める。hook は通す。hook が内容を変えたときは、巻き戻さず、結果に印を付けて報告する（`success` と証拠）。統合先の ref の期待値は、この反映の中で検証する。方式の確定と試験は P7・P8。
6. **通知**: 正本は ref。通知を全部失っても、`/pending list` で状態を復元できる。モデルへの通知は、`content` に操作名・対象・要求 ID・試行・確定した結果を、**固定のテンプレート**で入れ（`details` はモデルに渡らない）、「これは実行の指示ではない」と添える。記録の中の自由な文を、指示として流さない。承認した側のセッションのモデルへ通知する。**別のセッション（feature の pi で要求し、本体の pi で承認する）の要求元へは、初版では通知しない**（要求元は `/pending list` で見られる。要求元が結果を知るには、利用者が伝える。要求元の軽いポーリングは後段）。
7. **範囲と、操作ごとの能力表**: 構造化した操作だけ（`guarded_action` の各操作と `git_integrate`・`chezmoi_apply`）。bash の必須確認・「ask」層・`ask` 拡張は、時間切れで拒否のまま。初版は TUI のみ（`modes = ["tui"]`。RPC は従来どおり）。
   - **アダプタ（前提の取得・再検査・実行）を登録した操作だけ**に、新しい保留・「あとで」・新形式の承認を出す。未登録の操作で「あとで」を出すと、後から実行できると誤解させる。
   - P9 の時点: `git_integrate` だけが新しい承認の対象。`git_commit` は今の退避のまま（一覧・表示・破棄だけ）。gh は、確認が取れなければ今までどおり拒否し、保存しない。UI とモデル向けの説明に、この対応表を出す。
   - **旧形式・新形式・不正な形式を判別する。** `reconcilePending`（旧形式の片付け）は、旧形式と確認できたものだけに適用する。不正な新形式を、旧形式として扱わない。
   - **`/pending` の登録を `registerTask` から分ける。** 今は `registerTask`（`task` を持つ役割だけ）の中にあるので、`task` を持たない親では使えない。保存できる親では、一覧・表示・破棄・復旧を常に出す。`[pi.pending] enabled = false` は、新しい保留と承認だけを止め、一覧・破棄・復旧は残し、bash の必須確認を弱めない。
8. **外部コードを動かさない算出と、git の runner の分離**（`git_integrate`）: 承認前の算出で使う git は、hook・署名・fsmonitor・外部の diff や textconv を無効にする。外部の merge driver を設定したリポジトリは、初版で断る。保存・一覧・状態遷移の git も、同じ許可の方針にする。承認後の、品質ゲートつきの実行（hook を通す）とは、runner を分ける。陰性試験（ダミーの印が作られない）を入れる。
9. **秘密の永続化**: gh の本文などは、git のオブジェクトとして保存される。通常の push とは別でも、mirror などの送信対象になりうる。保持期限と、ref の破棄ではオブジェクトがすぐには消えないこと（`git gc` まで残る）を、仕様に明記する。
10. **`chezmoi_apply` の承認**: 要求時の状態を承認するのではなく、**承認の時点で適用計画を作って見せ、その計画を実行する**形を候補にする。適用計画は、実際の source・宛先・対象の範囲・実効設定・ファイルの変更と削除・実行予定のスクリプトの内容と順序を含み、固定・照合できない部分は、未対応として断る。差分の表示と、別の `apply` の呼び出しを、同じ計画の実行とみなさない。一般の `chezmoi apply` で、これをどう固定できるかは**未確認**（段 P11 で `review`）。実行は境界の外だけ（`pis` の内側では `~/` が見えず無意味なので、承認を断って案内する）。

## 現在地

## 評価基準

**必須**: 承認が無いまま実行する経路が存在しない。偽造した記録で、権限が上がらず、承認も要る。前提の不一致・結果不明で、自動の再実行をしない。**承認した内容と違う内容を反映しない（対象の期待値を検証する）。実行中の試行と、`resolve`・再実行が重ならない。**品質ゲート（pre-commit の秘密検出）を後退させない。通知を全部失っても、一覧から状態を復元できる。既存の退避が無変更で動く。

**望ましい**: 時間切れで作業が止まらない。統合と `chezmoi apply` の承認の負担が減る。設定が単一ソース（`common.toml`）から生成される。
