# エージェントの隔離は、リポジトリごとの agent コンテナ（pi を入れた compose）にする。汎用サンドボックスは目指さない

- **ステータス**: Proposed（方針の草案。利用者の確認と、実物 1 つでの試験の待ち）
- **日付**: 2026-11-06
- **決定者**: applejxd
- **関係**: [ADR-0027](0027-isolation-unit-is-environment.md)（隔離の単位は環境）の P2・P3 の**実現方法**を置き換える。「隔離の単位は環境」と P1（フルガードのみ）は変えない。

## コンテキスト

`pis`（Fence = OS サンドボックス）と `pisd`（rootless Docker の硬化した使い捨てコンテナ）は、**使いたい場面で使えない**ことが多かった。原因は、どこでも使える汎用のサンドボックスを目指し、既定を厳しくしたこと。実際の開発で要るものと衝突した。

- **GPU への接続**（SLAM の推論、AI の推論）
- **認証情報へのアクセス**（LLM、GitHub、認証つきレジストリ）
- **Web サーバーのポート開放**（自前の Web アプリの確認、rerun の画面）
- **別のディスクにあるデータセット**

利用者側の実態（[調査](../research/agents/sandbox-user-adoption-2026-11.md)。粗い目安）: 多数派は **(a) ホストでそのまま動かす（YOLO）** と **(b) Docker・devcontainer の中で動かす**。OS のサンドボックス・VM・別の機械は少数。自作の隔離層は、保守の費用が大きい（Fence は 5.5 週で約 40 件の変更）。

## 脅威モデル（この方針が守るもの・守らないもの）

**守る（対象）**: エージェントの**正規の権限の範囲での被害**を、リポジトリ単位に絞る。

- T1 エージェント自身の誤動作（誤った削除・書き換え）
- T2 外部コード・依存の暴走（ビルドスクリプト、パッケージの実行）
- T3 外部の内容に仕込まれた指示（プロンプトインジェクション）で、エージェントの正規の権限が使われること
- T4 与えた資格情報の範囲での漏洩（範囲を絞る・中継で隠す）

**守らない（対象外）: ホスト側の脆弱性に由来するもの。** カーネル・GPU ドライバ・コンテナのランタイム・OS・ブラウザの脆弱性、コンテナからの脱出、ホストのブラウザ経由の `localhost` への攻撃など。別の脆弱性の悪用が前提で、コンテナの設計では防げない。個人の開発では、費用に見合わない。**ホストを最新に保つ**（OS・Windows・NVIDIA ドライバ・Docker）運用で対処し、この方針の設計には含めない。

境界の位置づけ: コンテナは「誤動作と仕込まれた指示の被害の範囲」を絞る道具で、**悪意のある攻撃者に対する強い境界ではない**（ガードも、うっかり防止）。

## 決定事項

1. **汎用サンドボックスを目指さない。** `pis` の Fence（OS サンドボックス）と、`pisd` の硬化した起動器（`pisd.py`）は、縮小・撤去の方向にする。ホストの pi は、フルガードだけで使う（[ADR-0025](0025-dotfiles-dev-without-os-sandbox.md) の延長）。
2. **リポジトリごとに agent コンテナを立てる。** 1 リポジトリ = 1 compose プロジェクト（名前は `<リポジトリ>-box`。専用のネットワーク・ラベル。`network_mode: host` は使わない）。**pi ごとコンテナの中で動かす**（ファイルの読み書きもコマンドも同じ境界の中。遠隔化の仕組みは要らない）。定義は devcontainer の形（`.devcontainer/`）に寄せる。
3. **土台のイメージを ghcr で配る。** dotfiles の `main` からだけ作る（公開。タグは `main` と日付）。各リポジトリは**ダイジェストで固定**する。中身は安定した部分（pi・ハーネス・拡張・生成済みの設定・mise・uv）だけで、秘密は入れない。更新が頻繁な設定は、マウントでもよい。
4. **リポジトリごとに、必要十分を宣言する。**
   - GPU の要否
   - 公開するポート（**`127.0.0.1:` に限る**）
   - データセット（**読み取り専用で、必要なディレクトリだけ**。ディスク丸ごとにしない）
   - 資格情報の型（下の 6）
   - compose のサービス（ROS・rerun・アプリなど）
5. **作業ツリー（worktree）の運用を維持する。** リポジトリのルートを、**ホストと同じ絶対パスで、書き込み可能でマウント**する。`.git` の共通ディレクトリと `.tmp/worktrees/*` が含まれるので、コンテナの中で `git worktree add` でき、ホストと Orca からも見える（[下の影響](#worktree-運用への影響)）。
6. **資格情報は、スキルが 3 つの型を持つ。**
   - `simple`: 範囲を絞った認証ファイルを、読み取り専用でマウント
   - `relay`: compose に Envoy の sidecar を足す。agent は内部ネットワークだけに置く（`pisd` で実機確認済みの形）
   - `offline`: 外向きなし

   GitHub は、中継か、範囲を絞ったトークン。**push の資格情報は渡さない**（push はホストで人が行う。リモートが、履歴の退避先になる）。
7. **git のフックと設定**: `.git/hooks` と `.git/config` は**既定で読み取り専用**（フックの実行は妨げない。書き換えだけを防ぐ。ホストの git が、書き換えられたフックを実行するのを避ける）。必要なリポジトリは、オプションで書き込み可にできる（信頼するリポジトリ）。
8. **docker のソケットは渡さない。** オプションで、信頼するリポジトリにだけ、rootless Docker のソケットを渡せる（隔離をほぼ無効にする、強い権限）。
9. **コンテナを操作する開発は、リポジトリの性質で分ける。**
   - 定義を書くだけ（Dockerfile・compose の編集）: エージェントはファイルを書き、ビルドと起動はホストの人が行う（ログは共有のフォルダ）。
   - コンテナの出し入れが開発の中心（SLAM の compose など）: **専用の環境**（WSL の専用ディストロなど、箱の中に docker がある形。[ADR-0027](0027-isolation-unit-is-environment.md) の P3）を使う。
   - 信頼するリポジトリ: 上の 8 のオプション。
   - 将来、不便が出たら、compose の定義を検証して限られた操作だけを受ける小さな中継を足す（今は作らない）。
10. **Orca は、ターミナル起動だけを使う**（構造化チャットは使わない）。画像のアップロード・通知・GitHub 連携は使う。
    - 画像: 貼り付け画像のフォルダを、読み取り専用の受け箱としてマウント（Windows の Temp 全体は渡さない）。
    - 通知: コンテナの端末が通す BEL・OSC。
    - GitHub: Orca 側の連携はホストの認証で動く。エージェント側は 6 の型。
11. **スキル（このリポジトリが配る agent-box）が、定義の雛形を作る。** 「GPU は？ポートは？データセットは？資格情報は？」と尋ね、土台のイメージから `.devcontainer/` と `compose.yaml` を出す。**いきなり汎用化せず、実物 1 つ（SLAM か AI Web アプリ）を手書きで作って 1 週間使い、うまくいった部分を抜き出す**。
12. **ツールだけを包む案は採らない**（ホストの pi がホストのファイルを読める面が残り、隔離にならない）。ただし、Orca との相性を優先したいリポジトリのために、同じ compose の定義のまま「pi はホスト、bash だけコンテナ」で起動する型を、スキルのオプションに残す。

## worktree 運用への影響

「バカスカ worktree を立てる」運用は、次の条件で**維持できる見込み**（未確認。実物で確かめる）。

| 論点 | 影響と対処 |
| --- | --- |
| コンテナの数 | 1 リポジトリ = 1 コンテナ。worktree が増えても、コンテナは増えない。子エージェント（`guarded_task`）は、同じコンテナの中の別プロセス |
| worktree の `.git` | worktree の `.git` は、共通ディレクトリへの**絶対パス**を持つ。**ホストと同じパスでマウント**すれば、そのまま動く（別のパスにするなら、git 2.48 以降の相対パス設定が要る） |
| 場所 | worktree が `.tmp/worktrees/*`（リポジトリの中）なら、ルートのマウントだけで足りる。Orca が、別の場所に worktree を作る場合は、その場所も、宣言に足す（未確認） |
| 隔離の粒度 | コンテナの境界は**リポジトリ単位**。同じコンテナの中の worktree どうしは、隔離されない（1 worktree = 1 worker は、これまでどおり規約と所有の表明で守る） |
| 共有の履歴 | 共通の `.git` が書き込み可なので、エージェントは全ブランチの参照を書き換えられる。対処: push の資格情報を渡さない（リモートが退避先）、フルガードの deny、フックと設定は読み取り専用 |
| ファイルの所有者 | rootless Docker では、コンテナの root がホストのユーザーに対応する。コンテナの中は root で動かすと、ホストのファイルの所有者が揃う（要確認） |
| `pre-commit` などの導入 | `.git/hooks` が読み取り専用だと、導入（`pre-commit install`）はホストで行う。実行は、コンテナの中でそのまま走る |

## 検討した選択肢

- **A. `pis`・`pisd` を改良して続ける**: GPU・認証・ポート・データセットの例外を、硬化した既定の上に積むことになり、保守が重い。
- **B. 開発単位の環境（専用 WSL ディストロ・Incus）を、すべてに使う**: コンテナの出し入れが開発の中心の場合には有効（9 に残す）。リポジトリごとに作る手間が大きい。
- **C. microVM・OpenShell**: WSL2 で GPU と両立しない、または apt・compose を満たさない（[ADR-0027](0027-isolation-unit-is-environment.md)）。
- **D. ツールだけ包む**: ホストのファイルが読める面が残る（12）。
- **E. Docker 以外（Podman など）**: rootless Docker と GPU は、すでに実機で動く。移る利点が見当たらない。
- **F. リポジトリごとの agent コンテナ（採用）**: 主流（devcontainer）に沿い、必要な機能を宣言で足せる。

## 費用と便益

- **便益**: 実際に要る機能（GPU・認証・ポート・データ）が、宣言で足りる。自作の隔離層の保守が減る。worktree と Orca の運用を、ほぼ維持する。
- **費用**: 土台のイメージの作成と公開（GitHub Actions）、スキルと雛形の整備、ホストの最新化の運用。隔離はゆるくなる（GPU・ポート・データを許すため）。完全な隔離ではない。
- **廃止・凍結**: `pis` の Fence、`pisd.py` の硬化した起動器、`dev-*` の自動化（CHG-0064 の W2・C1）、Incus と native 側（N1〜N3）、環境内ハーネスの台帳・PR ビューアとの統合。
- **流用**: `pisd` の Dockerfile（pi とハーネス入り）、Envoy の認証設定、squid の設定、フルガード、台帳。

## 未確認と、確かめ方（小さな試験）

SLAM か AI Web アプリのどちらか 1 リポジトリで、手書きの `compose.yaml` を作り、次を確かめる。

1. **worktree 運用**: 同じパスでのマウント、コンテナの中での `git worktree add`、ホストの Orca からの見え方、ファイルの所有者、フックの実行と書き換えの拒否。
2. **Orca の 3 機能**: ターミナル起動（`docker compose exec -it agent pi`）、画像の受け箱、通知。
3. **GPU**: rootless Docker と compose で GPU が使える。ホストの NVIDIA ドライバ（WSL2 では Windows 側）が最新であること。
4. **認証**: `relay` の型（Envoy）が、compose の内部ネットワークで動く（Copilot 系以外の認証は未対応）。

## 見直しの条件

- 実物の試験で、worktree 運用または Orca の 3 機能のいずれかが、実用にならないと分かったとき。
- 外部の信頼できないコードを、頻繁に動かすことになり、ゆるい境界では足りなくなったとき（`pisd` の硬化した形を再び使う）。
- コンテナを操作する開発の頻度が増え、9 の区分で回らなくなったとき。

## 決定の確認方法

- 1 つのリポジトリで、GPU・ポート・データセット・認証が、宣言どおりに使えること（実機）。
- worktree を複数立てて、並列の作業が、これまでと同じ手順で回ること。
- コンテナの中から、ホストの秘密（`~/.ssh`、他のリポジトリ）に届かないこと（否定試験）。
