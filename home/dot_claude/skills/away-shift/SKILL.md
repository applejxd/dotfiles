# away-shift

ユーザが席を外している間に、**承認が要らない操作だけ**で目標に向けた
検証・実験を反復し、戻ってきたときに読めるレポートを残す。

> **この skill は fork しない（`context: fork` を付けない）**
>
> 離席時間をまたいで動き続けることが要件なので、独立したサブエージェントでは
> 成立しない。
>
> - サブエージェントは 1 回走って要約を返して終わるため、`manage_schedule` で
>   自分を再開させる自己ペースループを維持できない
> - ユーザの復帰はメインの会話にメッセージとして届く。サブエージェントからは
>   観測できず、「復帰時に止まる」が効かない
> - レポートは要約に畳まれず、そのままユーザに見える必要がある

前提は **autopilot / 自動承認モードで動いていること**。
それでも「承認が要る操作」には手を出さない。理由は
`references/unattended.md` にまとめてある（要点: 無人では `ask` に誰も答えないので
自動拒否・スキップ・応答待ちのいずれかになり、どれもサイクルが無駄になる。
加えて、事前承認や `ask` 未登録のせいで**止まらない**破壊的操作も実在する）。

## 使わない場面

| 状況 | 理由 |
| --- | --- |
| ユーザが在席していて即答できる | 対話した方が速い |
| コミット / push / リリースが必要 | 承認事項。提案までに留める |
| パッケージのグローバルインストール、sudo | 環境を変える |
| 外部サービスへの書き込み（issue 作成、PR 作成など） | 取り消しにコストがかかる |

## 手順

### 1. 目標と停止条件を確定する

始める前に次を宣言する。曖昧なまま走らせない。

```text
目標: <達成したいことを 1 行で。検証可能な形にする>
成功の判定: <何が起きたら「できた」と言えるか>
停止時刻: <HH:MM>
作業範囲: ./.tmp/away-shift/<run-id>/work/
```

目標が検証可能でない（「良くしておいて」など）場合は、
**自分で検証可能な形に言い換えてから**始め、レポートに言い換えた旨を書く。

### 2. run を作る

```bash
uv run --no-project python ~/.claude/skills/away-shift/scripts/away_guard.py \
  init --goal "<目標>" --deadline "<復帰予定時刻>"
```

`--deadline` は `HH:MM`（次にその時刻になる瞬間）、`YYYY-MM-DD HH:MM`、
`8h`、`90m` のいずれか。出力された `run_id` を以降ずっと使う。

離席の形に合わせて使い分ける。

| 離席の形 | 指定例 |
| --- | --- |
| 夜に離席して翌朝戻る | `--deadline "07:30"` |
| 日中に出かけて夕方戻る | `--deadline "17:00"` |
| 戻る時刻が読めない | `--deadline "6h"`（長さで指定） |

ディレクトリの役割は分ける。

| パス | 用途 | 消してよいか |
| --- | --- | --- |
| `.tmp/away-shift/<run-id>/work/` | 試行錯誤の作業場 | 消してよい |
| `.tmp/away-shift/<run-id>/cycles/` | サイクルごとの記録 | **消さない** |
| `.tmp/away-shift/<run-id>/state.json` | 停止判定の状態 | **消さない** |
| `.tmp/away-shift/<run-id>/report.md` | 復帰時のレポート | **消さない** |

`./.tmp/` 配下の削除には承認が要らない。だからこそ、
**証跡を消さない**ことを自分で守る必要がある。

### 3. サイクルを回す

**各サイクルの最初に必ず `check` を実行する。** 期限や STOP ファイルの確認を
サイクルの終わりに回すと、長いサイクルを 1 つ跨いだだけで期限を超える。

```bash
uv run --no-project python ~/.claude/skills/away-shift/scripts/away_guard.py \
  check <run-id>
```

- 終了コード 0 → 継続。出力に残り時間、現在のサイクル番号、
  次のサイクルまで空ける秒数（`NEXT_WAKE_SECONDS`）が出る
- 終了コード 3 → **その場で止めて手順 4 へ**。理由が出力される

継続する場合、1 サイクルで次を行う。

1. **仮説を 1 つ立てる**。「何を確かめるか」「どうなれば成立か」を書く
2. **最小の実験**をする。作業は `work/` 配下。既存ファイルは読むだけ
3. **結果を記録する**

#### 実行前に必ず事前判定する

無人実行で最悪なのは、**承認プロンプトが出たまま誰も答えず離席時間を丸ごと
失う**こと。プロンプトはコマンドを実行する**前**に出るので、タイムアウトでは
救えない。実行してから困るのではなく、実行する前に同じ判定器へ問い合わせる。

判断に迷うコマンドは、まず次を通す。

```bash
uv run --no-project python ~/.claude/skills/away-shift/scripts/preflight.py \
  "<実行しようとしているコマンド>"
```

- `ALLOW`（終了コード 0）→ 実行してよい
- `ASK` / `DENY`（終了コード 3）→ **実行しない**。`work/` で代替する方法を
  探すか、レポートに書いて次の仮説へ移る

判定には PreToolUse hook 本体を使うので、予測と実際がずれない。
`uv sync` のような日常的なコマンドまで毎回通す必要はないが、
**環境やリポジトリの状態を変えるものは必ず通す**。

```bash
uv run --no-project python ~/.claude/skills/away-shift/scripts/away_guard.py \
  log <run-id> --text "$(cat <<'EOF'
### 仮説
...
### やったこと
...
### 結果
...
### 次にやること
...
EOF
)"
```

### 3-1. 離席時間いっぱい使う（重要）

1 サイクルは実時間で数分しかかからない。何もしないと、離席直後に
全サイクルを使い切って手が空き、「戻るまでかけて検証する」前提が崩れる。

**サイクルの終わりに `manage_schedule` で自分を再開させる。**
`check` が出した `NEXT_WAKE_SECONDS` をそのまま `delaySeconds` に渡す。

```text
manage_schedule(action="wakeup", id=<自己ペースループの id>,
                delaySeconds=<NEXT_WAKE_SECONDS>,
                reason="away-shift <run-id> cycle <N+1>")
```

自己ペースループとして起動されていない場合は、最初のサイクルで
`manage_schedule(action="create", interval="<NEXT_WAKE_SECONDS>s", prompt=...)`
を作り、prompt に **run_id と「SKILL の手順 3 から再開する」旨**を書く。
prompt にはコンテクストが残らないので、run_id を書き忘れると再開できない。

停止したら（`check` が終了コード 3）、必ず
`manage_schedule(action="stop", id=...)` でスケジュールを止める。
止め忘れると、レポートを出した後も起こされ続ける。

1 サイクルの実作業は 15〜30 分を目安にする。長くなりそうなら分割する。
`check` はサイクルの先頭でしか走らないので、サイクルが長いほど
停止が遅れる。

### 4. 停止したら

`check` が停止を返したら、**新しい実験を始めない**。
残り時間をレポート作成に使う。
`manage_schedule(action="stop", ...)` で再開スケジュールも止める。

`report.md` を書いて会話にも同じ内容を出す。

```markdown
# away-shift レポート (<run-id>)

## 目標
<宣言した目標と成功の判定>

## 結論
<できた / 一部できた / できなかった>。<1〜3 行で要点>

## 分かったこと
- <根拠になるコマンド出力・ファイルとともに>

## 分からなかったこと・詰まった点
- <何が障害だったか。承認が必要で進めなかったものはここに書く>

## 次にやるべきこと（ユーザの判断が要るもの）
- <承認が要る操作。コミット、インストール、外部への書き込みなど>

## 成果物
- <path>: <内容>

## 停止理由
<期限 / STOP ファイル / 最大サイクル / 目標達成 / 行き詰まり>
（<N> サイクル実行）
```

### 5. ユーザが戻ってきたら

ユーザからメッセージが来た時点で **その場でサイクルを打ち切る**。
`manage_schedule(action="stop", ...)` で再開スケジュールを止めてから、
中断したサイクルの状態を 1 行で伝え、レポートを提示する。

## 停止条件

| 条件 | 検出 |
| --- | --- |
| 期限 | `check` が `--deadline` を過ぎたと判定 |
| 予備時間 | 残りが 15 分未満（レポート作成分を確保する） |
| STOP ファイル | `.tmp/away-shift/<run-id>/STOP` または リポジトリ直下の `STOP` |
| 最大サイクル | 既定 20（`init --max-cycles` で変更） |
| 目標達成 | 成功の判定を満たした |
| 行き詰まり | 3 サイクル連続で新しい情報が出ない |
| 承認が必要 | 目標に到達するには、不可逆・外部・環境変更のいずれかが要ると分かった |

ユーザは `touch STOP` だけで止められる。run_id を覚えていなくてよいよう、
リポジトリ直下の `STOP` も見る。

## 制約

- **承認の有無に関わらず、次の性質を持つ操作をしない**。
  「不可逆」「外部に見える」「環境を変える」のどれかに当たるもの
  （コミット、push、`work/` 外の削除、sudo、`docker run --privileged`、
  グローバルインストール、依存の追加、外部サービスへの書き込み）。
  承認が要るかどうかで判断しない。**止められていない = やってよい、ではない**。
  必要になったらレポートに書いて止める
- **リポジトリ本体のファイルを書き換えない**。変更案は `work/` 配下に
  パッチやコピーとして置き、レポートで提示する
- **証跡を消さない**。消してよいのは `work/` 配下だけ
- **秘密情報をログに出さない**。トークン・鍵・パスワードは記録しない
- **`check` をサイクルの先頭で必ず実行する**。省略しない
- **環境やリポジトリを変えるコマンドは `preflight.py` を通してから実行する**。
  `ASK` / `DENY` が返ったものは実行しない
- **再開スケジュールを止め忘れない**。停止条件に当たったら
  `manage_schedule(action="stop", ...)` を必ず呼ぶ
- **行き詰まりを隠さない**。「できなかった」も成果として書く

詳細は `references/unattended.md`（無人実行で避けること）と
`references/experiment-design.md`（1 サイクルの組み立て方）を参照する。
