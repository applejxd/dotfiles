# CHG-0024: 編集直後の診断フィードバック（LSP・linter・型検査）を足す

- **状態**: Planned
- **更新日**: 2026-10-20
- **基準**: コミット 47a5755、pi 1.3.0

## 目的と非目的

**目的**: エージェントが、ファイルを編集した直後に、その言語の診断（型・linter のエラーや警告）を得て、自分で直せるようにする。
今は編集後の整形（ruff・markdownlint）の結果を返すだけで、型検査や言語サーバの診断は無い。

**非目的**:

- 公開拡張の導入（[ADR-0016](../adr/0016-pi-extensions-own-first.md)）。参考にするのは設計だけ
- 補完・ホバー・定義へのジャンプなど、診断以外の言語サーバの機能（診断が働いてから別に判断する）
- 全言語への対応（まず、このリポジトリで使う言語に絞る）

## 動機

[調査記録 P1](../research/agents/pi-public-extensions-survey.md) で、使えないことの不利益が「中」と評価した 4 点の 1 つ。

- `pi-lens`（月間 88k 前後）は、書くたびに LSP・linter・型検査の結果を返し、影響範囲の診断も出す（README の主張。未検証）
- `@narumitw/pi-lsp` は、言語に依存しない LSP のツールを共有の実行器で出す
- 自作側は、`rules.json` の `post_edit` で、整形と markdownlint の違反を、編集の結果の末尾へ足す仕組みがある（`index.ts` の `formatAfterEdit`）

## 受入条件（実装前の期待動作）

1. `guarded_edit` / `guarded_write` の直後に、**編集したファイルの診断の要約**が、結果の末尾に付く（markdownlint の警告と同じ形）
2. 診断の道具は、言語ごとに宣言する（`common.toml` の `post_edit` の延長。例: ruff・pyright・tsc・shellcheck）
3. 1 回の編集あたりの**時間の上限**を持つ（超えたら診断を打ち切り、編集は成功のまま返す）
4. 診断の失敗・道具の不在は、編集の成否に影響しない
5. サンドボックスの中で動き（ネットワークを要さない）、道具の起動は判定器を通る
6. 長い出力は、件数と先頭の数件に縮約する（文脈を占めすぎない）
7. 診断が**増えたかどうか**が分かる（編集前後の差。既存の違反と、今回の違反を区別できる）

## 候補

| 案 | 内容 | 規模 | 備考 |
| --- | --- | --- | --- |
| A | `post_edit` の延長。CLI の linter・型検査を編集後に実行して要約を返す | 小 | 既存の仕組みと同じ。言語サーバは使わない |
| B | LSP クライアントの拡張。言語サーバを常駐させ、診断を受け取る | 大 | 常駐プロセスとガード・サンドボックスの関係を設計する必要がある |
| C | skill + CLI。モデルが必要なときに実行する | 最小 | 取りこぼす（実行を忘れる） |

**段階案**: まず A で、型検査まで広げる。それで足りなければ B を別案件にする。

## 未解決

- どの言語・道具まで対応するか（Python: pyright、TypeScript: tsc、シェル: shellcheck など）
- 型検査は、プロジェクト全体を見るので遅い。編集 1 回ごとに回すか、ターンの終わりにまとめるか
- 診断のノイズ（既存の違反が多いプロジェクトでの扱い）
- B にするなら、言語サーバの起動を、拡張が子プロセスとして行う。読み込み時のコードは囲えない（[ADR-0016](../adr/0016-pi-extensions-own-first.md) と同じ論点）。サンドボックスの内側で動かせるか
- Windows の素の `pi`（フルガードなし）での扱い
