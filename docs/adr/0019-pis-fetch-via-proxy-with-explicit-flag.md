# pis の内側のページ取得は、専用フラグでプロキシ越しにし、事前の名前解決を省く

- **ステータス**: Accepted
- **日付**: 2026-10-25
- **決定者**: applejxd

## コンテキスト

`pis`（サンドボックスの内側で動く pi）の内側では、DNS を引けない。一方、環境変数 `HTTPS_PROXY`（`http://127.0.0.1:3128`、Fence のプロキシ）経由の通信は通り、
許可ドメインの外はプロキシが `403 Forbidden` を返す（[記録 S2](../research/agents/pis-sandbox-field-test.md#記録-s2--2026-10-25内側のネットワークページ取得クリップボード)）。

ページ取得の 2 経路（`websearch.py fetch` と imozuru の `fetch.py` / `watch.py`）は、接続の前に自分で名前を引き、全ての IP が公開アドレスかを検査して、その IP に接続を固定する（SSRF と DNS rebinding への対策）。
内側では名前を引けないので、プロキシに届く前にこの事前検査で必ず失敗し、調査系のスキルの原文取得が全滅していた。

守る目的は、[ADR-0012](0012-ocs-boundary-for-accidents.md) のとおり「エージェントのうっかり」を止めること。ただし取得先の URL は、検索結果やページを書いた他人が決める。
環境変数は、境界の証明にならない（[ADR-0018](0018-pis-sandbox-default-relax-only-when-proven.md) の「自己申告にしない」と同じ）。

## 検討した選択肢

### 選択肢 1: ブローカーに `/fetch` を足す

Envoy のブローカーに、任意の公開 URL を取る経路を足す。

- **利点**: 検査をホスト側へ集約できる
- **欠点**: Envoy はホスト固定のルートなので、任意の URL を取るには Python の中継を新設することになり、攻撃面と実装が大きい。プロキシが既に許可ドメインを強制していて `curl` が通るので、不要

### 選択肢 2: サンドボックスの DNS を開ける

- **利点**: 取得側の変更が要らない
- **欠点**: 境界を広げ、許可の強制がプロキシ任せでなくなる

### 選択肢 3: 既存の環境変数の組み合わせで、プロキシ越しに切り替える

`PI_HARNESS_BOUNDARY=1` と、ループバックの `HTTPS_PROXY` が揃ったら、事前の名前解決を省く。

- **利点**: `pis` 側の変更が要らない
- **欠点**: 境界の外でも、利用者が自分でプロキシを設定しただけで満たせる。偶然の既存の設定で、従来は拒否していた内部宛先名の検査が省かれる（独立レビューの BLOCKER）

### 選択肢 4: `pis` だけが付ける専用フラグ + ループバックのプロキシ + https 限定（採用）

`pis` の `inner_env` が `PIS_FETCH_VIA_PROXY=1` を付ける（ホスト側の同名の値は落とす）。このフラグと、ループバックの `HTTPS_PROXY`（認証情報なし）が揃い、`no_proxy` に当たらない https の URL だけ、事前の名前解決を省き、プロキシへ `CONNECT` する。

- **利点**: 境界の外の既定の動作が変わらない。ブローカーに中継を足さずに済む。実装が小さい
- **欠点**: 環境変数は境界の証明にならない（環境を操作できる相手は、すでにコード実行の権限を持つ、という想定に依る）。内部名への防御が、ツール内の IP 検査から、プロキシの許可リストへ移る

## 決定事項

選択肢 4 を採用する。

- 有効にする条件は、(1) `PIS_FETCH_VIA_PROXY=1`、(2) `HTTPS_PROXY`（urllib が実際に使う値）が `http://127.0.0.1:<port>` の形、(3) https の URL、(4) `no_proxy` に当たらない（imozuru は urllib の判定関数と同じ値を見る）。http と、http への転送は従来の経路
- プロキシモードでは、ホスト名の形を厳格に見る（ASCII のドット区切りの名前だけ。最後の部分は英字で始める。IP の直指定・10 進/16 進/省略形の IP・`localhost` と内部の接尾辞・末尾のドット・`@`・`%`・非 ASCII を拒否）。リダイレクトのたびに同じ検査をし、本文の上限と型の制限は変えない
- プロキシが `CONNECT` を拒否したときは、ページの 403 と区別して「プロキシが接続を拒否した」と伝える
- 内部アドレスに解決される名前への防御は、プロキシの許可リストに任せる（許可リストに内部名を足さない限り届かない）

理由: 取得の失敗の原因は、ツールの作りと内側の環境の食い違いで、プロキシは設計どおり動いている。専用フラグは、既存のプロキシ設定が偶然に条件を満たす事故を避けつつ、境界の外を変えない。
選択肢 3 は、独立レビュー（`review`）が BLOCKER とした。選択肢 1・2 は、小さい解決があるのに境界や攻撃面を広げる。

## 決定の確認方法

- [x] `pis -p` の内側で、許可ドメイン（arxiv・raw.githubusercontent.com）の取得が通り、許可外は「プロキシが接続を拒否した」で止まる（[記録 S2](../research/agents/pis-sandbox-field-test.md#記録-s2--2026-10-25内側のネットワークページ取得クリップボード)）
- [x] 有効条件・ホストの形・名前を引かないこと・http の経路・リダイレクトを、試験が固定している（`test_websearch.py`、`test_imozuru.py`）
- [ ] 内部名（`*.internal` など）へプロキシが 403 を返すこと（未確認）

## 結果

### ポジティブな結果

- 調査系のスキル（`web-search`・imozuru）が、`pis` の内側で原文を取れる
- 境界の外の挙動は変わらない

### ネガティブな結果

- 防御の位置がプロキシの許可リストへ移り、許可リストに内部名を足すと内部宛先へ届く
- `websearch.py` と imozuru の `imozuru_net.py` に、同じホスト検査を 2 か所持つ（試験が正規表現の一致を固定する）
- imozuru は上流の vendor で、`fetch.py` と `watch.py` に各 4 行の差分を足した

### 中立的な結果

- 許可ドメインの外の原文を取るには、許可リストを足すか、`pis --no-sandbox` が要る（従来と同じ）
- **更新 (2026-10-26)**: `[pis.network] mode = "denylist"` では、許可リストを足さなくても拒否リスト以外の公開宛先へ届く。
  このとき「内部名への防御」は、プロキシの許可リストではなく、**中継が名前解決後のアドレスを検査すること**（公開アドレス以外は 403）に移る。
  内側は DNS を引けないままなので、この ADR の専用フラグとローカルのプロキシは引き続き必要。詳細は
  [pi-sandbox.md](../spec/guard/pi-sandbox.md#拒否リスト型の通信)
