# 読者の仕事ごとの章立て

固定のひな形に埋めず、読者が最初にしたい仕事から節を選ぶ。**迷ったら節を足さず、削る**。
README は入口で、詳しいことは別の文書へ(合意された原則。research 0007)。

## 種類別の節の選び方

| 種類 | 読者の最初の仕事 | 先に置くもの | 足すもの |
| --- | --- | --- | --- |
| ライブラリ・SDK | 自分の問題に合うか判断し、使い始める | 説明 → インストール → 最小の使用例と出力 | 対応する版・主な機能・API 文書へのリンク |
| CLI | 入れて最初のコマンドを打つ | インストール → 最初のコマンドと出力 | 主なオプション(全部は書かず `--help` へ) |
| アプリ・サービス | 手元で起動する・運用する | 前提 → 起動手順 → 動作確認 | 設定(環境変数の名前だけ。値は書かない)・運用・依存するサービス |
| monorepo | どのパッケージが何かを知る | パッケージの一覧表(名前・役割・場所) | 共通の開発手順 |
| 研究・データ | 結果を再現する・引用する | 何を示すか → 再現手順 → 結果の場所 | 引用の形式・データの出所と版・license |
| 社内・個人の道具 | 新しい人が最初に動かす | 目的 → 環境構築 → よく使う作業 | 担当・連絡先・runbook へのリンク |
| ワークスペース(スキル集など) | 全体の構造と作業の入口を知る | 何のための場か → 最初に打つコマンド | ディレクトリ構成・検証の方法 |

## どの種類にも要るもの

- 題名と、何のためのものかの 1〜2 文
- 最初の成功へ至る道(前提 → 入れ方 → 最小の使い方)。ここが長くなるなら、何かが重すぎる
- license(LICENSE ファイルへのリンク)。ファイルが無いなら無いと報告する
- 重大な前提・注意(破壊的な操作、必要な権限、対応 OS)は、使う場所のそばに置く

## 節ごとの判断

| 節 | 載せる条件 | 載せない・縮める |
| --- | --- | --- |
| 特長・機能一覧 | 選ぶ判断に効くとき | コードから自明な羅列。実績・性能は出典か実測がある場合だけ |
| バッジ | 保守されている意味のある指標(CI・版・license) | 6 個を超える、飾り |
| スクリーンショット・GIF | UI・CLI の結果・構成図が理解を助けるとき | 装飾。古くなるものは、いつの版かを添える |
| 目次 | 100 行を超えるとき(GitHub も見出しから自動で出す) | 短い README |
| コントリビュート | 受け入れているとき。CONTRIBUTING があればリンクだけ | 受け入れていないなら、その旨を 1 行 |
| 開発・テスト | コントリビュータが最初に打つコマンド(CI と一致させる) | 内部の設計(docs/ へ) |
| 変更履歴・ロードマップ | 書かない。CHANGELOG・Issue へリンク | 腐りやすい |

## 置き場所と表示

GitHub は `.github/`、ルート、`docs/` の順に README を表示し、500 KiB を超えた分は表示しない。
サブディレクトリの README は、そのディレクトリを開いたときに表示される。相対リンクが使える。
複数言語は `README.ja.md` のように別ファイルにし、先頭で相互にリンクする(既存の慣習に合わせる)。
