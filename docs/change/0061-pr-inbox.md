- 「pi との結合度を高めるため、メッセージングやキューなど、非同期にやり取りする仕組みを入れたい。俯瞰して計画し直してほしい」

## 2. 目的と非目的

| 区分 | 内容 |
| --- | --- |
| 目的 | アプリで送ったレビュー・承認が、**pi の入力を待たずに**届く（キュー）。承認のみを 1 操作で送れる。最終的に、承認をアプリで閉じる（レビュー → 承認 → 統合） |
| 目的 | 待ち時間に人が張り付かず、非同期に往復できる（長期方針「本質的な確認だけを人に求める構成」の一部） |
| 非目的 | 常駐の監督プロセス・外部のメッセージブローカー（Redis など）・汎用スケジューラー |
| 非目的 | アプリが統合の実行器を持つこと（実行は窓口の pi。[CHG-0060](0060-local-pr-viewer.md) の決定のまま） |

## 3. 現状（事実）

| 項目 | 内容 |
| --- | --- |
| 輸送 | git の ref `refs/pi/review/<prKey>`（PR ごとに 1 本の追記専用ログ）。通信の口（TCP・ソケット）は無い。**ログ自体が耐久キュー** |
| 配送 | pull だけ。pi は `before_agent_start` で、利用者の入力のときだけ、自分宛の未受領の batch を注入する（`collectInjection`）。**push（通知・自動配信）は無い** |
| 受領 | 注入の**前**に、前提条件つきで `receipt` を追記する。つまり配送は**高々 1 回 + 利用者の手動再送**（「少なくとも 1 回」ではない。受領後に落ちた分は自動では回収されない） |
| 注入の範囲 | 全 PR の、宛先が自分の未受領の batch を、**承認（`items=[]`）も含めて**文章として消費する |
| 段 4・5 | ペアリング・制御ポート・承認の指示は、設計だけで未実装（[spec §7・§8](../spec/pr-viewer.md)） |
| ref の偽造 | モデルの bash による `git update-ref refs/pi/…` は、判定器が**常に必須確認**にする（`gitintegration.ts`）。残る経路は、アプリの UI ポートへ curl で POST（判定器での拒否は未実装） |

## 4. 決定（2026-11-03）

| # | 決めること | 決定 |
| --- | --- | --- |
| D1 | 承認の最終形 | **アプリで閉じる**（[CHG-0060](0060-local-pr-viewer.md) の決定の維持）。実装は 2 段: 2a（承認のみを送れる。統合は `/pending approve`）→ 2b（統合まで、アプリの承認で閉じる） |
| D2 | 2b の通信と「共有の秘密」 | **ref だけで輸送する**。ペアリングの共有の秘密・制御ポート・long-poll・Fence の `local_ports` の変更は採らない（CHG-0060 の「制御の通信路」「承認の指示に共有の秘密」の決定を置き換える）。偽造は、ref 書き込みの必須確認と、判定器でのアプリのポートへの curl 拒否（前提・未実装）で防ぐ |
| D3 | 自動配送 | **実行中の pi への `queue` と、アイドルの pi の自動起動（`auto`）を、どちらも opt-in で作る**。既定は「通知だけ」 |
| D4 | 窓口が複数あるとき | **利用者が窓口の pi を 1 つ選ぶ**（`/pr inbox on`）。先着の取り合いに任せない |

- 変わらないもの: アプリでの追加認証は置かない（遠隔の通信路は tailnet が保証する。[CHG-0060](0060-local-pr-viewer.md)）。実行は窓口の pi。アプリは `refs/pi/pending` を書かない。

## 5. 構成: 2 つのトラック

### 5.1 トラック 1: 配送（「キューに積まれない」の解消）

pi の拡張（**親だけ**。子には登録しない）に、**受信箱**（新ファイル `pr-inbox.ts`）を足す。

| 項目 | 内容 |
| --- | --- |
| 動き | `session_start` から約 5 秒間隔で、`git for-each-ref refs/pi/review/` を 1 回実行し、前回から oid が変わった PR だけ読む。未処理の候補は、oid の記憶とは別に持つ（oid が変わらなくても、確認画面の終了・実行中の解消・モード変更で再評価する） |
| 寿命 | タイマーは `session_start` から始め、`session_shutdown` で冪等に閉じる（pi の規約）。タイマーは `unref`。重なり防止の実行中フラグと**世代**を持ち、遅れて完了した処理が副作用を持たないよう、受領・配送の直前に世代・停止・モード・対話の状態を再検査する |
| 既存の注入 | 残す（受信箱が無い環境でも「次の入力で届く」が成り立つ）。注入・take・受信箱は、**共通の dispatcher**（候補の読み取り・種類別の処理・受領の記録を分ける）を通す |
| 宛先 | `worktreeId` が自分の batch だけ。**窓口に選んだセッションだけ**が受け取る（D4） |

| モード | 動き | 既定 |
| --- | --- | --- |
| `notify` | 読み取りと通知だけ（フッター `📨 レビュー N 件`・BEL）。モデルへの配送も保留の保存もしない。`/pr inbox take`（利用者専用）か次の入力で取り込む | **既定** |
| `queue` | 実行中なら `followUp` で pi のキューに積む。アイドルのときは `notify` と同じ | opt-in |
| `auto` | 実行中は `followUp`、アイドルなら起こす（`triggerTurn`） | opt-in |
| `off` | 受信箱を止める | — |

| 状況 | `notify` | `queue` | `auto` |
| --- | --- | --- | --- |
| アイドル | 通知 + バッジ | 通知 + バッジ | 起こす（歯止めを満たすとき） |
| 実行中 | 通知 + バッジ | `followUp` で積む | `followUp` で積む |
| 圧縮中 | 通知のみ | 保留して圧縮の後に（再検査して）積む | 同左 |
| 承認の確認画面・巡回の最中 | 通知のみ | 積まない（画面の後に再評価） | 起こさない（画面の後に再評価） |

`queue`・`auto` の歯止め（すべて満たすときだけ配送）: セッション単位の opt-in・頻度と件数の上限（busy にも効く）・確認画面中でない・圧縮中でない・`ctx.isIdle()` の再確認・`/pr inbox off`（利用者専用。モデルは呼べない）。

### 5.2 トラック 2: 承認をアプリで閉じる（決定 D1。2 段）

| 段 | 内容 | 前提 |
| --- | --- | --- |
| 2a | 承認のみ（`submit` の `kind: approve`・`items=[]`）を送れる。pi には承認のデータとして届き、統合は今までどおり `/pending approve` | 画面は実装済み（「承認して送る…」） |
| 2b | アプリの承認 = `merge_request`（ref の追記）。窓口の pi の受信箱が `requestApproval` → `planApproval` → `executeApproval` で、TUI の画面を経ずに実行する。**ref だけで輸送**（D2） | 下の §6 の前提・§9 の合格条件。実装の前後に独立 review（外せない） |

### 5.3 S2 の実装（`notify` + `take` + `off`。実装済み・未配備）

| 項目 | 内容 |
| --- | --- |
| 操作 | `/pr inbox on`・`off`・`status`・`take`。**既定は off**。on はそのセッションだけ（プロセスのメモリ。`/reload` で戻る）。TUI でないときは on にできない（`take`・`status` は使える） |
| 見張り | 約 5 秒ごとに `git for-each-ref` を 1 回。oid が変わったキーだけ読み直す。**ref は一切書かない**（受領を書かない）。読めなかったキーは「読んだ」と覚えず次の tick で再試行する |
| 通知 | 未受領の件数が**増えたとき**だけ、トースト・BEL（TUI のとき）。バッジは件数に合わせて更新し、0 で消す。開始のたびにバッジは出し直すが、**通知済みの件数は再開始（`new_session` の二重の `session_start`）では保つ**。`off` → `on` は新たに知らせる |
| `take` | 受領してから文面を `sendMessage`（customType `pr-review`）で渡す。アイドルなら `triggerTurn`、実行中なら `followUp`。圧縮中は保留する。文面が無ければ通知だけ。受領後の送信が失敗したら、アプリの「再送」を案内する |
| 寿命・無効化 | 開始は冪等。世代を各 tick が握り、`await` の後に再確認する（旧世代は共有の状態も書かない）。`session_shutdown` では、進行中の `take` も無効にする（新たな受領・通知・送信をしない）。`off` は進行中の `take` を取り消さない（利用者が打った操作は続ける）。古い `ctx` の例外は握って静かに止める |
| 試験 | `test/agents/test_pi_pr_inbox.py`（偽の時計・タイマー・git・UI。実際の ref で確かめる）と、配線の試験（`test_pi_harness.py`。実際の pi の RPC） |

実機（TUI の表示・BEL・Windows・Fence の内側）は未確認。

## 6. 脅威の分析（外部入力でモデルや保留を動かす面）

追加認証は置かない（決定）。歯止めは、種別・宛先・頻度・状況・利用者専用の停止で作る。

| # | 書ける者 | 経路 | 起きうること | 歯止め | 残るリスク |
| --- | --- | --- | --- | --- | --- |
| T1 | 利用者本人（スマホ） | アプリの POST → `submit` | 誤入力・誤タップで承認・変更依頼が届く | `vs`・`expect` の照合（古い版で書かない）。2a は統合しない | 誤ったコメントの注入。再送・追記で直す |
| T2 | tailnet 内の他の端末（乗っ取りを含む） | アプリの POST（`X-PRV`・Host 検査を満たす非ブラウザ） | 偽の `submit`。`queue`・`auto` を有効にした窓口なら、本文つきでモデルを動かせる。2b なら統合の指示も | 既定は `notify`。`queue`・`auto` は opt-in・上限つき。2b は、判定器の curl 拒否が入るまで有効にしない | `queue`・`auto` の間は、囲まれた引用データに従わされうる（プロンプト注入の完全な防止は無い）。tailnet の信頼は決定どおり |
| T3 | 差分・コメント本文の中の命令文 | 注入の文面 | モデルが引用内の指示に従う | 既存の囲み・固定の案内・「データ」の明示（`pr-review.ts`） | 今の注入と同じ |
| T4 | モデル自身 | UI ポートへ curl で偽の `submit` を POST | 自分を起こす。2b なら自己承認 | **判定器でアプリのポートへの curl の変更系を拒否（2b の前提・未実装）**。`git update-ref refs/pi/…` は必須確認（実装済み）。起動回数の上限 | 判定器が入る前の `queue`・`auto`・2b は、素の pi（Fence なし）では防げない。ガードは「うっかり防止」で境界ではない |
| T5 | 同じマシンの他のプロセス | ref の直接の書き込み | 偽の batch | ファイル権限（Fence の外では守れない） | 私物の機の前提 |
| T6 | 古い承認の再生 | `submit` の再利用 | 進んだ source を承認したことにする | 元の `submit` の `vs` と現在の OID を照合。後続の変更依頼で失効。違えば保存・実行せず通知のみ | 同じ OID への再承認は有効（意図どおり） |

## 7. 守る条件

| # | 条件 |
| --- | --- |
| I1 | 公開リポジトリ。私物・勤務先の具体を書かない（例は架空） |
| I2 | ガードは境界ではなく「うっかり防止」。**過剰を避ける**（各部品は、具体的な失敗か要望で正当化する）。追加認証は置かない |
| I3 | 常駐の監督プロセスを作らない。タイマーは `session_start` から始め、`session_shutdown` で冪等に閉じる |
| I4 | 外部入力でモデルを動かす面（`queue`・`auto`）は、opt-in・頻度と件数の上限・利用者専用の停止つき。§6 の脅威の分析を保つ |
| I5 | 圧縮中は起こさない（`compact-defer` と同じ口。圧縮後の配送の直前にも再検査する） |
| I6 | `/pending approve` の隙間を食わない（確認画面・巡回の最中は起こさない） |
| I7 | 受信・注入は親の pi だけ（子には届けない） |
| I8 | ref のスキーマは後方互換（追記専用）。**新しいイベント種別を足さない**（古い読み手は未知の種別を拒否する）。任意キーの追加だけ。上限（本文 16 KB・events.jsonl 512 KB・2000 件・末尾 32 KB は終端記録の予約）の中で動く |
| I9 | アプリが import してよい harness ファイルは `review-log.ts` と `review-git.ts` だけ（試験で固定） |
| I10 | Fence の内側から届く経路は、作業ツリーの中の git の ref だけ。`local_ports` を変えない |
| I11 | 試験は反例を先に書く。タイマーは時計を注入する（実時間に頼らない） |
| I12 | pi の文書化された API だけを使う。文書にない挙動は S0 で確かめる |
| I13 | Windows でも動く（`fs.watch`・unix ソケットに頼らない。ポーリングの間隔と上限を明示） |
| I14 | 規模: 利用者 1 人・pi 数本・PR 数十本。idle の 1 tick は git の起動 1 回 |
| I15 | 配送保証は正直に書く: **高々 1 回 + 手動再送**。保留の保存は、受領と対応付けを持つ（再起動後に「保留なしで消費済み」を作らない） |

## 9. 実装の合格条件（独立 review の指摘から）

| 項目 | 条件 |
| --- | --- |
| 配送保証 | 「高々 1 回 + 手動再送」と書く。保留の保存は、受領と同じ commit にまとめる、または batch ID と保留の対応付けを持つ |
| 既存の注入との競合 | 注入・take・受信箱が、同じ batch を二重に消費しない。承認のみがモデルに文章で流れない（2b で決定的に処理するとき） |
| 承認対象の固定 | 元の `submit` の `vs`・対応する summary を固定し、source・target の ref 名と OID・base・message・cleanup を capture の結果と照合する。後続の変更依頼で失効する。`mergeMessage` の長さ（summary 側と統合側）が一致する |
| 停止・遅延 | 各 await の途中に off・shutdown・新セッションが来ても、旧 tick が受領・配送・保存しない（世代）。圧縮後に保留した処理も再検査する |
| 未処理候補 | oid が変わらなくても、確認画面の終了・実行中の解消・モード変更・容量回復・一時失敗で再評価する。失敗した読み取りを「読んだ」として覚えない |
| 可視化 | 保存の成功・拒否・実行・結果の記録の失敗が、アプリの GET 応答と画面で見える。結果まで扱わないなら「保存済み・結果は未連携」と明示する |
| 画面の更新 | 入力・返信・送信シートの状態、宛先、フォーカス、表示版を、定期取得で失わない |
| 文言 | 「保留は期限なし」ではなく「確認画面は期限なし。保留の保持は既存設定（既定 30 日）」 |

## 10. 実験（S0。実機・実 pi で確かめる）

**結果**: [調査記録](../research/agents/pi-message-queue-experiments.md)。E1〜E3・E5〜E8 は実施済み（偉のモデル・RPC）。E4・E9・E11・E12 と、TUI・実モデルで確かめる分（E3 の編集欄、E5 の LLM 呼び出しの最中）は未実施。E13〜E18 は、受信箱の実装の試験（S2 以降）で確かめる。

| # | 確かめること |

| E2 | 実行中の `followUp` と `steer`（いつ届くか、そのときの `before_agent_start` の `messageType`、利用者の入力が積まれているときの順序） |

| E4 | 承認の確認画面（`/pending approve`）の間の `isIdle()` と、その間の `triggerTurn` の効果（承認が断られるか） |

## 11. 却下・見送り

| 案 | 理由 |
| --- | --- |
| 制御ポート・long-poll・ペアリングの共有の秘密（D2） | ref の追記と pi 内の受信箱で足りる。Fence の `local_ports`（境界）を動かさずに済む。実機で 5 秒の遅延が問題になったら、別に起票して再検討する |
| 心拍・対応中の `ack`・`seq` | 今回の失敗の解決に必須ではない（処理中か停止中かは、時間経過の目安で足りる） |
| 保留フッターの他セッション同期 | レビュー配送とは独立した改善（[CHG-0055](0055-async-approval.md) の既知の制限）。混ぜると試験の範囲が増える |
| 外部のメッセージブローカー・SQLite・git notes・常駐の監督プロセス | 要望に対して過剰 |
| TOML の細かい設定 | 間隔・上限は少数の定数と注入の時計で足りる。実需が出てから設定にする |
| 「`mergeMessage` が無いとき、黙ってモデルに任せる」 | 決定的な処理という説明を崩す。通知して、利用者の take に戻す |

## 12. 未決・リスク

| 項目 | 内容 |
| --- | --- |
| 2b の偽造防止 | ペアリングの秘密を捨てるので（D2）、判定器でのアプリのポートへの curl 拒否が**前提**。素の `pi`（Fence なし）では、判定器も境界ではない |
| `queue`・`auto` | 実行中の別作業へ Web 由来の文を混ぜる面（T2・T4）。S0 の E16 と、運用の実績で見直す |
| 窓口の選択の操作 | `/pr inbox on` の具体（複数ウィンドウ・Orca・Zed でのスラッシュコマンドの扱い）は S2 で決める |
| `cleanup` の既定 | 2b で `git_integrate` を作るときの `cleanup`（`none`・`branch`・`branch_and_worktree`）。保守的な `none` を候補とし、`feature finish` の運用との整合は実機で見る |
| Windows | ポーリングの git 起動コストは未測定（E12） |
