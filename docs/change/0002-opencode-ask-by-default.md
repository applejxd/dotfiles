# CHG-0002: OpenCode の permission を既定 ask にする

- **状態**: In progress
- **更新日**: 2026-09-22
- **基準**: OpenCode V2（`v2.0.12`）

## 目的と非目的

**目的**: OpenCode の permission から「未掲載＝無条件許可」を無くし、
既定を `ask` にする。そのうえで**秘密へのアクセス経路を機構で塞ぐ**。

**非目的**:

- Claude Code / Copilot CLI の設計変更。対象は OpenCode V2 のみ
- 確認画面の情報量を増やすこと。それは
  [CHG-0003](closed/0003-ask-command-description.md) が扱う

**発端**: 従来の設計は「未掲載は LLM classifier に委ねる」前提だったが、
**OpenCode に classifier は無い**。未掲載が「無条件許可」へ静かに退化し、
`curl` / `docker run` / `python3` / `chmod` / `dd` / `base64` が全て
無確認で実行できていた。

### 段階 1: 既定を ask にする（完了）

`[bash]` に触らず `[opencode.shell] allow` を新設し、permissions の先頭へ
`{shell, *, ask}` を置いた。`[bash]` は 3 CLI 共通なので、そこを削ると
効果の切り分けができなくなるため。

```toml
[opencode.shell]
allow = ["git log", "wc", "grep -n", "uv pip list", "docker ps"]
```

allow の基準は副作用なし・冪等・**任意コード実行を含まない**こと。
当初あった `git diff` / `git status` は監査で基準を満たさないと判明し
外した（[制約の総覧](../research/opencode/permission/constraints.md)）。

結果は 224 → 225 rules、他 CLI の生成物はバイト単位で無差分。

### 段階 2: 読み取り経路の保護（完了）

**sandbox を採用しない以上、ここが唯一の防御層になる。**

穴はどれも permission の `read` / `edit` を **shell 経由で迂回**すること
に起因する。3 つの手を打った。

| 手 | やったこと | 効き目 |
| --- | --- | --- |
| 誘導 | `cd` / `cat`・`head`・`tail` / `sed -n` を `deny` し `read` ツールと `workdir` へ寄せる | **deny が効く経路へ移る** |
| 結果フィルタ | `grep` / `glob` の結果から保護パスを落とす | 濾せる |
| 伏字化 | shell 出力を `execute.after` で書き換える | 安全網 |

**誘導は確認削減の施策ではなく保護の一部。** 実装の詳細は
[エージェントの権限設定](../spec/agent-permissions.md)が正本。

#### 成果（実履歴 1,031 呼び出し）

| 測ったこと | 結果 |
| --- | --- |
| 秘密へ触れた（触れうる）呼び出し | 15 件（1.5%） |
| そのうち 3 層が受け止める割合 | **15 / 15 件** |
| `read` ツールへ移った割合 | 108 件（10.5%） |
| 誘導後も確認が出る割合 | 901 件（87%） |
| 伏字化の誤爆 | 3 件（0.3%） |

得たものは「`deny` の効かない経路から効く経路へ 10.5% を移したこと」
（[段階 2 の被覆率](../research/opencode/permission/stage2-coverage.md)）。

### 段階 3: 確認 1 回あたりの負担を下げる（着手中）

#### 問題

確認の**回数**ではなく**1 回あたりの量**が負担の本体だと分かった。

| 指標 | 値 |
| --- | --- |
| コマンドの長さ 中央値 | **245 字** |
| 複数行 | 53.8% |
| 500 字超 | 28.1% |
| **ヒアドキュメント（`<<`）を含む** | **178 件（19%）** |

この長さを毎回読むのは不可能で、**読めない長文を形式的に承認している**。
確認が多いことより悪い。

#### やること: ヒアドキュメントを `write` ツールへ誘導する

```text
python3 - <<'PY' … 40 行 …        → deny
  「スクリプトは write ツールでファイルに書いてから実行してください」
write .tmp/x.py  →  python3 .tmp/x.py   ← 確認するのはこの 1 行
```

段階 2 と同じ構図で、得られるものが 3 つある。

| # | 得るもの |
| --- | --- |
| 1 | 読む量が激減する（19% が 1 行の確認になる） |
| 2 | 中身が diff で見える。流し読みより実質的な審査になる |
| 3 | **`edit` の deny が効く経路へ移る**。`python3 - <<PY` で書く経路には一切効かない |

3 番目が段階 2 の思想そのもの。誘導は確認削減ではなく経路の移動。

#### 承知している弱点

**`edit` は既定 `allow`**（`*` 規則が無い＝未掲載は許可）。ファイルへ書く
行為自体は無審査になり、**審査の実質が下がる危険がある**。

それでも移す。現状の 245 字を読めていない以上、形式的な承認が実質的な
審査に変わるとは言えないため。ただし **diff を見る保証はない**ので、
ここは弱点として残る。

#### 完了条件

- ヒアドキュメントを含む shell 呼び出しが `deny` され、代替案が返る
- パイプの途中など `write` で代替できない形は**誘導しない**
- 実履歴へ当てて誤爆を数え、記録する

#### 結果

実履歴 1,049 件への当てで**取りこぼし 0 件・誤爆 1 件（0.1%）**。
誤爆は過去の検査スクリプトが `"cat <<EOF"` という**テスト用の文字列**を
持っていたもので、伏字化で踏んだのと同じ型。

実地でも 3 本すべて deny を確認した。

| 試したもの | 結果 |
| --- | --- |
| `cat > .tmp/probe.txt <<'EOF'` | deny（write ツールへ誘導） |
| `python3 - <<'PY'` | deny（ファイルに書いてから実行へ誘導） |
| `head -1 README.md`（段階 2-A の規則） | deny |
| `grep -c "" README.md` / `wc -l` / `git log` | 素通り（誤爆なし） |

**配備の確認方法を 2 つ誤っていた**（`stat -c %Y /proc/<pid>` と
`pgrep -f`）。そのため誘導が一度も効いていない状態を「配備済み」と
記録していた。手順は
[hook の呼ばれ方](../research/opencode/permission/hook-order.md)に記録した。

### 段階 4: 少数の静的 allow + `always` の運用

#### 静的 allow

安全に足せるのは `git status` / `git log` / `git diff` / `ls` / `wc` /
`find` 程度で、**約 8%**。費用も小さいので入れるが、**網羅を狙わない**。

上位ルールの中身は `grep` 114 / `rm` 86 / `python3` 53 / `cat >` 30 件で、
これらを allow にするのは**任意コード実行と削除の恒久許可**にあたる。

#### `always`（承認の永続化）

OpenCode の確認ダイアログには `once` / `always` / `reject` があり、
`always` はパターンを SQLite の `permission` テーブルへ永続化する
（プロジェクト単位・wildcard 照合）。**現在 0 件で未使用。**

**主軸には据えない。** 完全一致で 2 回以上出たコマンドは
**20 種・延べ 62 件（6.6%）**しかなく、溜まるものが少ない。
狭いパターンでだけ使い、インタープリタや任意スクリプト実行へ広がる
許可には使わない。

### 段階 5: `verify` ツール

`AGENTS.md` の検証コマンド表を
`verify(target: "all" | "agents" | "templates" | "docs" | "shell")` の
ツール 1 個に畳む（5 個作るのとコンテキストコストが 3 倍違う）。
`codemode` は既定のままにして固定費を 0 にできる
（[ツールのコンテキストコスト](../research/opencode/tool-context-cost.md)）。

**自動承認はしない。** `verify(target:"all")` は
`.pre-commit-config.yaml` の local hook を起動するため、設定を書き換えれば
任意コマンドが動く。ゲートは `tool.execute.before` で自作する。

### 段階 6: 残りへの手当（決着）

**「何もしない」で決着。** 誘導後も確認が出る 901 件のうち、状態を変えない
ものは 103 件（11.4%）しかない。段階 4 で拾う分を除けば残りは
ヒアドキュメント付きの長いスクリプトか書き込みを含むもので、
**allow へ移せる余地が無い**。

#### 既定を `allow` に戻さない理由

| 理由 | 内容 |
| --- | --- |
| 得るものが無い | 対話では確認が要るものばかりが残っている |
| 故障時に危険側へ倒れる | 設定が読まれない事故は実在した（Orca overlay）。基準 4 に反する |
| 元の状態への回帰 | 既定を変えても shell deny 85 件は残る。実態は「その 85 件以外は無条件」＝この案件が最初に否定した状態 |

## 評価基準

**必須:**

1. Claude / Copilot / Codex / Gemini の生成物に diff が出ないこと
   （テストで固定）
2. **自動実行のまま**、保護対象のファイルを `cat` / `grep` / `head` で
   読んだ内容がモデルへ渡らないこと。素直な形で実測して判定する
3. 任意コード実行を含むコマンドが allow に 1 件も無いこと
4. plugin がロードに失敗しても、危険側（無条件許可）に倒れないこと

**基準 2 に「難読化した形でも遮断」は求めない。** 符号化されるとすり抜ける
ため達成不能。伏字化は事故と素朴なプロンプトインジェクションへの
安全網であって、意図的な持ち出しへの境界ではない。

## 設計の前提

**すべての判断は実測から出ている。根拠は
[制約の総覧](../research/opencode/permission/constraints.md)が持つ。**
計画に効いている要点だけ挙げる。

- **境界は無い。** permission も plugin も安全網。sandbox は成立を確かめた
  うえで**採用しない**（利点がほぼ否定された）
- **設定で入れる保護は設定で外せる。** プロジェクト設定がグローバルの
  deny に勝つ。`**/.opencode/opencode.json` の write deny で緩和するのみ
  （**訂正 2026-09-23**: `v2.0.12` では勝たなくなった。
  [permission の穴 §5](../research/opencode/permission/gaps.md#5-プロジェクト設定とグローバル設定の優劣2026-09-23-再測)。
  ただし機構を特定できておらず寄りかからない。write deny は残す）
- **自動実行では `allow` と `ask` が等価。** ただし**対話では等価でない**。
  この案件は当初この区別を誤っており、2026-09-22 に訂正した
- **静的 deny は代替案を返せない**（hook を呼ばないため）。誘導は既定 ask の
  まま plugin が `deny` へ変える。故障時は ask に縮退して安全側へ倒れる

## 候補比較

検討して見送った手段と、保留中のもの。

| 候補 | 支持する根拠 | 不利な点・反証 | 扱い |
| --- | --- | --- | --- |
| **LLM classifier（`ask` → `allow`）** | 対話では `allow` と `ask` は等価でないので、当初の見送り理由は崩れた。機構は実証済み（1 回 $0.0006 / 1.1 秒） | 長いスクリプト・間接呼び出し・実行時の状態まで判断が要る。**権限昇格を任せるほど信頼できない**。誤許可は誰も見ないまま走る | **見送り**（理由を差し替え） |
| **LLM classifier（`ask` → `deny`）** | **deny だけが自動実行で意味を持つ**。静的パターンが破られる穴を意味で補える。誤検知は安全側 | 遅延が全コマンドに乗る。入力は攻撃者に操作されうる | **未評価** |
| LLM による**承認の補助** | 要約は既に動いている（CHG-0003）。次点は**前回承認との差分提示** | — | **次点** |
| sandbox（プロセスごと隔離） | 唯一の境界。難読化した持ち出しを止められる | 利点がほぼ否定された（[制約の総覧](../research/opencode/permission/constraints.md)） | **見送り** |
| 誘導を `bypass` にも効かせる | `cd` のような作法だけの規則は代替が必ずある | **誤爆したときの逃げ道が消える。** `bypass` は「秘密を読むために一時的に全部外す」用途も兼ねる | **見送り** |
| `always` を主軸に据える | 標準機構で費用ゼロ。使いながら溜まる | **完全一致の繰り返しが 6.6% しかない**。溜まるものが少ない | **段階 4 で限定採用** |
| session スコープの事前宣言 | セッション内で完結し永続化しない | **`ctx.permission.rules` が存在しない**（公式ドキュメントには記載あり） | **保留** |
| `check_bash.py` への bridge | 既存の判定資産（4,913 行・1,782 テスト）を再利用できる | 承認エンジンにはせず、既知の危険の拒否・誘導のみに使う | **未評価** |

## 重要な更新

**2026-09-22 — 配備の確認方法が誤っていた。**
`stat -c %Y /proc/<pid>` を起動時刻として使い、`pgrep -f` が自分自身の
シェルに当たっていたため、**誘導が一度も効いていない状態を「配備済み」と
3 回記録していた**。`execute.after` の層は別経路で再読み込みされて動いて
おり、それが誤りを覆い隠した。正しい確認は `ps -C opencode -o lstart` と、
配備済み規則を 1 つ叩くこと。

**2026-09-22 — 「確認回数は目的でない」を訂正した。**
「自動実行では `allow` と `ask` が等価」を根拠に確認削減を非目的としていたが、
**実際には対話で使っており等価ではない**。負担の本体は回数ではなく
**1 回あたり 245 字・複数行 53.8%** という量だと分かり、段階 3 を新設した。
外部レビュー（Astra）の指摘と実測による。

**2026-09-22 — 段階 2 が完了し、実履歴で被覆率を測った。**
秘密へ触れた 15 件を 3 層が全件受け止める。内容の形による判定とパス判定は
**両方要る**（`/proc/…/environ` はパス判定で捕まらない）。

**2026-09-22 — sandbox を検討し、採用しないと決めた。**
成立は実測したが利点がほぼ否定された。これにより**境界を持たない前提**に
統一し、評価基準から「難読化耐性」を外した。

**2026-09-21 — 確認回数の測定単位が誤っていた。**
計画はセグメント数で数えていたが、permission は**呼び出し 1 回につき
1 判定**。正しく測り直すと誘導全体でも 8%（39 件 / 466 呼び出し）で、
当初の評価基準「6 割削減」は達成不能だった。

**2026-09-21 — allow の選定基準を既存リスト自身が満たしていなかった。**
「任意コード実行を含まない」を基準にしながら、残した `git diff` /
`git status` が**どちらも任意コード実行の経路を持っていた**。
