# 提案のひな形（段 4 で使う）

段 4 の提案は、次の順で 1 回にまとめる。長くなるので、表と短い文で書く。
**悪くなる点を書けないときは、評価が足りない**（どんな機能も、利用者の操作のどこかを変える）。

## 0. 前提

- 脅威モデルの既定は「エージェントのうっかり操作を防ぐ」。悪意のあるリポジトリ・攻撃者は既定の対象外
  （[ADR-0012](../../../../docs/adr/0012-ocs-boundary-for-accidents.md)、
  [ADR-0018](../../../../docs/adr/0018-pis-sandbox-default-relax-only-when-proven.md)）
- 防御と使い勝手は、片方を上げるともう片方が下がることが多い。**どちらかだけで決めない**。
  防御を足すと確認や制限が増えて、承認の疲れから確認を読まずに通すようになり、結局安全が下がることもある
- 既存の仕組み（サンドボックス・判定器・確認）が同じ脅威をすでに防いでいるなら、重ねて足さない。
  二重の防御は、使い勝手の費用だけを増やす

## 1. 要望の整理（段 1 の結果）

目的・使う場面・成功条件・やらないこと。

## 2. 方式の比較

調べた公開拡張の方式を、出典つきで比べる。確かめた事実と推測を分ける。

## 3. 実装案を 3 つ出す（防御の強さで分ける）

同じ要望を、防御の強さの違う 3 案で書く。**案ごとに同じ項目を埋める**。
3 案が実質同じになるなら、その理由を書く（無理に作り分けない）。

| 案 | 想定する脅威 | 考え方 |
| --- | --- | --- |
| 堅牢案 | 悪意のある入力（プロンプト注入、悪意のあるリポジトリ・外部の内容、敵対的な子）まで | 信頼の境界を越えるものは、すべて検査・確認・隔離する |
| 標準案 | エージェントのうっかり操作（この機能で起こり得る誤った読み取り・送信・書き込み・状態変更） | 取り返しのつかない操作と、意図しない範囲への影響を塞ぐ。**推奨を考える出発点であって、既定の採用ではない** |
| 体験案 | 既存のサンドボックスと判定器に任せ、新たな制限を足さない | 利用者の操作の少なさと分かりやすさを最優先にする |

案ごとに書くこと（**案どうしを対比できるよう、同じ項目を同じ順で埋める**）:

- 追加する機構と、既存の機構（サンドボックス・判定器・確認）に任せる範囲
- 何を作る・触るか（ファイル、規則、設定）
- 塞ぐもの と **塞がずに残るリスク**（残るリスクを正直に書く）
- 利用者の操作・中断の差（次の 4 の評価）。通知の出し方や確認の有無のように、**防御と関係なく利用者が選べる軸**も、案の違いとして書く
- 費用（実装の大きさ、試験、保守、実機でしか確かめられない点）

3 案が実質同じになるなら、無理に作り分けず、**同じになる軸と、それでも利用者が選べる別の軸**を書く。

**推奨する案とその理由**を 1 つ選ぶ。選ぶときは、案ごとに次を比べる。

- 既存の対策だけでは残る、**具体的な失敗**
- 追加の対策で**減る失敗**
- 追加の対策で**増える**確認・待ち・回復の手間

増える手間が、減る失敗に見合うかで決め、防御と使い勝手の両方を理由に挙げる。
信頼の境界を越える機能（外部の通信、永続する状態、他のプロセスへの指示、秘密に触れるもの）は、標準案で足りるかを
とくに疑う。逆に、利用者の手元だけで完結する機能に堅牢案を当てると、使い勝手の費用が見合わないことが多い。

## 4. 利用者の操作の変化を評価する

**今の操作と、新機能のあとの操作を並べて**、良くなる点と悪くなる点を分けて書く。案ごとに差が出るところは、案を分ける。

| 観点 | 今 | 新機能のあと | 良くなる / 悪くなる |
| --- | --- | --- | --- |
| 操作の回数・手間（入力、確認、待ち） | | | |
| 中断の頻度（承認や質問が出る回数。1 作業あたりの増減の目安） | | | |
| 見えるもの（表示、通知、エラーの分かりやすさ） | | | |
| 失敗したときの回復（原因の分かりやすさ、取り消し、やり直し） | | | |
| 新しく覚えること（コマンド、約束、設定） | | | |
| 既存の操作への影響（変わる・壊れるもの） | | | |

- 数えられるものは数える（確認が何回増えるか、追加の入力は何か）。数えられないものは、見込みと明記する
- 「安全のために不便になる」点は、**悪くなる点として書き、利用者の承認を求める**。黙って不便を入れない
- 実機でしか分からないもの（TUI の見え方、モデルの実際の使い方）は未確認と書き、段 5 の実機確認の項目へ足す

## 5. 作るもの・試験・未確認

- 触るファイルと、試験の方針（偽のモデル・実機）
- 未確認として残る点
- `chezmoi apply` が要るか
- **承認を待つ**（承認なしに実装へ進まない）。承認の際に、案（堅牢・標準・体験）と、操作の変化の評価で悪くなる点への了承を、利用者に確かめる
