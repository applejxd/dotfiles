# skill-creator

スキルを作り、試して、直す。流れと原則は Anthropic の公開実装
（[anthropics/skills の skill-creator](https://github.com/anthropics/skills/tree/main/skills/skill-creator)）と
Agent Skills の仕様（<https://agentskills.io/specification>）に従う。
**このスキルは手順だけを持ち、実行用のスクリプトは同梱しない**（外部のコードを審査せずに持ち込まない）。

> **fork しない（`context: fork` を付けない）。** 利用者へ質問して確認しながら進めるため。

## 進め方

利用者が今どの段にいるかを見て、その段から入る。すでに草稿があれば、試験と改善の段へ進んでよい。
「評価は要らない、一緒に作ろう」と言われたら、試験を省いてよい。

1. 意図を捉える
2. 聞き取りと調査
3. SKILL.md を書く
4. 試験の依頼文を作って試す
5. 結果を見て直す（4 と 5 を繰り返す）
6. description を仕上げる

### 1. 意図を捉える

会話にすでに手順があれば（「これをスキルにして」）、まず会話から拾う。使ったツール、手順の順序、利用者の訂正、
入出力の形。足りない所だけ利用者に聞き、進む前に確認する。

- 何をできるようにするか
- どんな発話・場面で発動させるか
- 出力の形
- 試験を用意するか（ファイル変換・抽出・固定の手順は向く。文体や見た目のように主観で決まるものは、たいてい要らない）

### 2. 聞き取りと調査

境界の場合、入出力の形、サンプル、成功の基準、依存を、書く前に聞く。調べられることは先に調べる
（既存のスキル、公式の文書、同種の公開実装）。**同種のスキルが既にあるなら、新しく作らず、拡張か統合を先に考える**。

### 3. SKILL.md を書く

構成:

```text
skill-name/
├── SKILL.md      (必須。frontmatter と本文)
├── scripts/      (決まりきった処理。実行するだけで読み込まなくてよい)
├── references/   (必要なときだけ読む資料)
└── assets/       (出力に使うひな形など)
```

#### frontmatter

- `name`: 小文字・数字・ハイフンだけ。**ディレクトリ名と一致させる**（連続・先頭・末尾のハイフンは不可、64 字まで）
- `description`: **何をするか**と**いつ使うか**の両方を書く（1024 字まで）。発動の判断はここだけで決まるので、
  「いつ使うか」は本文ではなくここへ書く。モデルは発動させなさすぎる傾向があるので、
  関連する発話や場面を具体的に挙げて、やや積極的に書く
- `:` や `#` を含む description は二重引用符で囲む（囲まないと読み込みに失敗して**黙って読み飛ばされる**）

#### 段階的な読み込み

3 段で読み込まれる。

1. 名前と description: 常にコンテキストにある
2. SKILL.md の本文: 発動したときに読む。**500 行以内**を目安にする
3. 同梱の資料: 必要なときだけ読む。SKILL.md から、いつ読むかを添えて指す。300 行を超える資料には目次を付ける

複数の領域や変種を扱うなら、領域ごとに資料を分け、SKILL.md には選び方だけを書く。

#### 書き方

- 命令形で書く。「〜しなければならない」を並べず、**なぜそうするかを説明する**（モデルは理由が分かれば一般化できる）
- 特定の例に狭く合わせず、一般的に書く。まず草稿を書き、頭を切り替えて読み直して直す
- 出力の形が決まっているなら、ひな形を示す。例は入力と出力の対で示すと効く
- マルウェア・不正アクセス・情報の持ち出し・利用者を欺く内容は書かない。**スキルの中身は、説明された意図から驚くものであってはならない**

### 4. 試験の依頼文を作って試す

草稿ができたら、本物の利用者が言いそうな依頼文を 2〜3 個作り、利用者に見せて確認する。

- 同じ依頼を、**スキルありとスキルなし**（改善のときは直す前の版）で、同じタイミングに走らせる。
  後から基準を取り直すより、同時のほうが条件が揃う
- 結果は `<スキル名>-workspace/iteration-<N>/` のように、版ごと・依頼ごとに分けて置く（スキルの隣に作る。リポジトリへは入れない）
- 走らせている間に、客観的に確かめられる観点（出力に含まれるべきもの、守るべき手順）を決める。
  主観で決まるものを無理に点数化しない。利用者が実物を見て判断する
- サブエージェントが使えるなら、各実行をサブエージェントに任せる。使えなければ、順に自分で試す

### 5. 結果を見て直す

利用者の指摘と、実行の記録（最終出力だけでなく、途中で何をしたか）を読んで直す。

1. **指摘から一般化する。** 数個の例に合わせて過剰に直さない。同じ指摘が別の依頼でも起きるかを考える
2. **軽く保つ。** 効いていない記述は消す。記録を見て、スキルのせいで無駄な作業をしていたら、その部分を削る
3. **理由を書く。** 利用者の指摘が短くても、なぜそう言ったかを理解して、理由ごとスキルに反映する
4. **繰り返される作業を見つけたら同梱する。** どの実行でも同じ補助スクリプトを書いていたら、`scripts/` へ 1 回だけ書いて持たせる

直したら、新しい版の番号で試験をやり直す。利用者が満足するか、指摘がなくなるか、進歩が止まるまで繰り返す。

### 6. description を仕上げる

発動しない・発動しすぎる場合は、description を直す。

- 発動すべき依頼文と、発動すべきでない依頼文（**似ているが別の用途のもの**を含める）を、それぞれ数個ずつ作る
- 発動すべきものは、いつも発動するか。発動すべきでないものは、発動しないか。見て、description の言葉を直す
- 最後に、本物の依頼文で試して確かめる

## このリポジトリでの約束

- **置き場所**
  - 全プロジェクトで使う: `home/dot_claude/skills/<名前>/SKILL.md`（`chezmoi apply` で配る）
  - このリポジトリでだけ使う: `.agents/skills/<名前>/SKILL.md`（`pis` が作業先の分を `--skill` で足す。
    `docs/spec/pi-guard.md` の「起動」）
- **frontmatter の検証**: `uv run pre-commit run --files <SKILL.md>`（`name` とディレクトリ名の一致、`description` の長さ、
  引用符を確かめる。`.agents/skills` も対象。`scripts/agents/validate_skills.py` の `SKILL_ROOTS`）。読み込めるかは `pis` の `/reload` でも確かめる
- **`pis` の下で呼ぶ**: フルガードがスキルの一覧をシステムプロンプトへ足すので、description で自動に発動する。
  明示して呼ぶなら `/skill:<名前>`、編集したら `/reload` で再読み込みする
- **コメントと docs**: 仕組み・判断・経緯は `docs/` を正本にし、スキルからは参照先を示す。同じ説明を両方に書かない
  （リポジトリの `AGENTS.md`）
- **外部のスキルは取り込まない**: 参考にするのは設計だけで、コードやスクリプトは写さない（審査していないコードを持ち込まない）
