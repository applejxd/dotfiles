# CHG-0041: コミットを bypass のとき確認なしで実行できるようにする（確認の場を push 前へ移す）

- **状態**: Exploring
- **更新日**: 2026-10-27
- **基準**: pi 1.4.0、コミット `0f7efea`（`guarded_action` は CHG-0038 段 G11）。判定の表は 2026-10-27 に `test/agents/test_pi_confirm.py` の `_judge`（TS 版の判定器）で実測した。承認の実装は `harness/actions.ts` を読んで確かめた（実機の TUI は未確認）。gitleaks は 8.28.0、pre-commit のフックの経路は使い捨てのリポジトリで実測した

## 目的と非目的

**目的**: `git commit` の承認で、作業が止まるのを減らす。今は `git commit` が、1 回の承認（`guarded_action` の `git_commit`）を毎回要求する。確認が時間内に無く拒否された例が、1 回の長い作業の中で 2 回あった（再試行しない規則のため、そのたびに利用者の指示待ちになる）。コミットはローカルの操作で、それだけでは何も公開されない。そこで、**bypass のときは、コミットの確認を省き、確認の機会と検査を push 前へ移す**。ただし、**省くのは、push 前の検査（段 3 の pre-push フック）が、そのリポジトリで有効であると、ハーネスが確かめられたときだけ**（U10）。入っていないリポジトリでは、bypass でも今までどおり確認する。

**前提の置き方**: 「push は deny なので、エージェントは公開できない」は、この案件の根拠にしない。ガードは「うっかり防止」で、強制の境界ではない（Python や `curl` を経由する迂回を、既存の仕様が認めている。`docs/spec/guard/pi-extensions.md#guarded_action承認つきの外部操作`。GitHub の API 経由の書き込みも、CHG-0038 が push 相当の経路として記録している）。実際の公開の境界は、**認証の権限・ブローカー・ネットワークの許可**である。この案件の主張は、「**自動のコミットは、公開の経路を新しく増やさない**（コミットはローカルで、公開には push かそれ相当の送信が要る）」と、「**人間が端末で push するときに、内容を見る機会と、機械の検査を置く**」だけ。確認の操作は、**見たことの証明ではなく、見る機会を与えるもの**で、強制ではない。

**適用範囲（限界）**: push 前の確認・検査は、**git の pre-push フックを通る push にだけ**働く。`git push --no-verify`、フックが入っていないリポジトリ、フックを通らない送信（GitHub の API など）には掛からない。**人間が見る機会は、端末のある対話の push に限る**（端末が無い push は、検査だけで、機会は補償しない）。

**非目的**:

- `git push` をエージェントに許すこと（deny のまま）
- `git commit --amend`・`rebase`・`reset --hard` などの履歴の書き換えを自由にすること（今は deny。push 前かどうかの状態を調べる検査が要るので、この案件では扱わない）
- 通常モード（bypass オフ）の承認を省くこと
- issue のコメント・編集（`gh_issue_*`）の確認を省くこと（外部へ見える操作なので、bypass でも確認する）
- 子エージェントの権限を変えること（`action` ツールは、子に登録されない。実行側も子を拒否する）
- 検査した内容と、コミットされる内容が、絶対に同じであることの保証、別のプロセスのコミットとの競合の保証（残余のリスクは U9）
- フックを通らない送信の検査

## 現在地

**確かめた事実**（ファイル・行番号は 2026-10-27 時点）:

- **承認は `git_commit` のツール自身が取る**。判定器は `action` を役割の許可だけで通し、ask を出さない（`judge/decide.ts:289-292`）。承認は `executeAction` の `select`（承認して実行・編集して承認・拒否）の 1 回で、`bypass` を見る分岐は今ない（`harness/actions.ts:255-262`）。確認画面は、メッセージの全文と、ブランチ・HEAD・ステージ済みの `--stat` を出す。承認の後、HEAD・ブランチ・index を照合してから実行する（`actions.ts:125-132,201-203,271-273,284-291`）。外部コマンドの実行は、30 秒・64 MiB の上限を持つ（`actions.ts:122-128`）。既存の `dialogInOrder` が直列にするのは、確認の対話だけ（`harness/index.ts:151-155`）
- **UI が無い（print モード）・子エージェントでは、承認できないので実行しない**（`not approved`。`actions.ts:190-191`）。`action` ツールは、子には登録されない（`harness/index.ts:421-424`）。`action` を持つ役割は、今は implementer だけ
- **bypass** は、判定器の「ask を確認なしで通す」で、`mustConfirm` の ask（外部への送信・公開）は通さない（`judge/decide.ts:312-313`）。値は可変で、`/bypass` で起動後に切り替わる（`index.ts:42-43,245-274`）。`pis`（サンドボックスの中）の既定はオン、`--no-sandbox` と素の pi はオフ。明示の `--bypass` と対話中の `/bypass on` でもオンにできる。したがって、省かれる範囲は、「**bypass がオンの親の対話セッション**」で、サンドボックスの有無では限定されない
- **現行の仕様**は「`guarded_action` の確認は、bypass でも省けない」（CHG-0038 段 G11）。省けないのは、「事前に `ask` を取ると、承認が 2 回になる・抜け道ができる」ためで、**承認を 1 か所に集める**設計だった。今回は、その 1 か所の承認を、条件つきで省く
- 生成器は、`[[pi.actions]]` のキーを明示的に組み直して出力し、未知のキーを拒否する（`scripts/agents/generate.py:1861,1975-1984,2043-2049`）。判定器（TS・Python）は、`id`・`replaces`・`fields` だけを読み、他のキーを無視する。ハーネスは、`rules.json` の `judge.common.pi.actions` を `loadActions` で読む
- `git_commit` の `argv` は `git commit -F <メッセージファイル>` で固定で、`--no-verify` を引数から足せない。メッセージは最大 8000 文字（`text` の検査は空白だけのメッセージを通す）。空のステージは拒否する。hook の実行中の変更までは、同一性の照合に含まれない

**実測した pre-commit・git の挙動**（2026-10-27、使い捨てのリポジトリ。`.tmp/exp_prepush.py`・`.tmp/exp_prepush2.py`・`.tmp/exp_gitleaks.py`）:

- **pre-commit の pre-push のフックは、標準入力を受け取らない**（空で、端末ではない）。環境変数は 1 組の `PRE_COMMIT_FROM_REF` / `PRE_COMMIT_TO_REF` だけで、**新規ブランチの push では、どちらも設定されない**。ブランチとタグを同時に push しても、標準入力の 2 行ではなく、1 組の値だけになる。したがって、pre-commit のフックでは、実際に送る範囲を求められない
- **`pre-commit install` は、既存の `.git/hooks/pre-push` を `.git/hooks/pre-push.legacy` に移し、pre-commit のスクリプト（shim）が、最初にそれを、git が渡した引数（リモート名・URL）と標準入力（`<local ref> <local sha> <remote ref> <remote sha>` の行）のまま呼ぶ**（ブランチとタグの同時の push で、2 行とも届いた）。**legacy が `exit 1` すると、push は止まる**
- 端末（`/dev/tty`）は、この実験の環境（端末なし）では開けなかった。**pre-commit 経由のフックで開けるかは、未確認**。legacy のフックは、shim が直接呼ぶシェルのスクリプトなので、端末のある環境では開けると推測する（**未確認**。段 3 の手動の確認項目）
- **pre-push の第 2 引数は、実際の push 先の URL**（`pushurl` を設定しても、`url.<base>.pushInsteadOf` で書き換えても、URL を直接指定しても、書き換え後の push 先になった。第 1 引数は、リモート名または指定した URL）。取得用の URL（`remote.<name>.url`）とは別になる（`.tmp/exp_pushurl.py`）。**第 2 引数と `ls-remote` の認証・URL 書き換えが同じ接続になるかは、実際のリモートでは未確認**
- **経路のプローブが成り立つ**（`.tmp/exp_probe.py`）: pre-commit の shim（先頭の 2 行目が識別行 `# File generated by pre-commit: https://pre-commit.com`）を、**直接**、環境変数・合成した引数・標準入力つきで実行すると、環境変数と引数が legacy のスタブに届く。スタブが終了コード 1 で終わると、shim も 1 で終わり、**pre-commit の本来のフックは走らない**。所要は約 0.2 秒。つまり、プローブは、ネットワークにも検査にも触れずに、shim → legacy のスタブの経路を、実行時に確かめられる
- **gitleaks 8.28.0**:
  - `gitleaks git --pre-commit --staged --redact --no-banner` が、現行のフック（`.pre-commit-config.yaml:12-16`）と同じ形で使える。`--log-opts` に `git log` の範囲（`A..B`、`<sha> --not --remotes=<name>`）を渡せる。**後続のコミットで消された秘密も、範囲の指定で検出した**
  - **`gitleaks git` は、コミットのメッセージを検査しない**（メッセージに秘密のあるコミットで、終了コード 0）。メッセージのファイルは、`gitleaks dir <ファイル>` で検出できた
  - **`--max-target-megabytes` を超える大きいファイルは、警告も出さず、「no leaks found」（終了コード 0）で、検査されずに通る**（上限 5 MiB・6 MiB のファイルで確認。上限を上げると検出した）。つまり、成功の終了コードは、「全部検査した」の証拠にならない
- ガードの現行の pre-push は、テンプレートの検査・Raspberry Pi の判定の試験・`verify-stamp`（警告のみ。範囲が不明なときは `None`、検査できなくても成功を返す）。**`verify-stamp` の範囲の決め方は、この案件の根拠にしない**。「未 push のコミットの一覧」を見せるフックも無い。他のリポジトリには、このリポジトリの pre-commit・pre-push の設定が無い

**実測した判定**（`pis` と同じ境界つき、`通常 / bypass`）:

| コマンド | implementer | worker | committer | explorer |
| --- | --- | --- | --- | --- |
| `git commit`（`--amend` を含む） | deny / deny | deny / deny | deny / deny | deny / deny |
| `git reset --hard`・`rebase`・`filter-branch`・`stash drop` | deny / deny | deny / deny | deny / deny | deny / deny |
| `git reset`（`--soft` / `--mixed`） | **ask / allow** | deny / deny | deny / deny | deny / deny |
| `git push`（`--force` を含む） | deny / deny | deny / deny | deny / deny | deny / deny |
| `git branch -D`・`git clean -fd` | ask / **allow** | ask / **allow** | ask / **allow** | ask / **allow** |
| `git checkout` / `switch` | allow / allow | deny | deny | deny |
| `git tag -d` | allow / allow | allow / allow | deny | deny |

読み取れること:

- bash の `git commit` は、全役割・全モードで deny。コミットは `guarded_action` を通るしかない（今回の変更でも変えない）
- `--amend` は、bash でも、`git_commit` の操作でも、できない。push 前にコミットを直す手段は、`git reset --soft`（implementer で bypass のとき allow）でコミットを戻し、再度コミットすること
- **別件**: bypass のとき、`git branch -D`・`git clean -fd`・`git tag -d` が、`explorer`・`committer` を含む全役割で allow になる（`inherit_bypass` で子に bypass が継がれるため。実測）

## 評価基準

**必須**:

- bypass オフでは、今までどおり承認を求める
- bypass オンでも、確認を省くのは、`confirm_in_bypass=false` の操作（`git_commit` だけ）で、**push の検査が有効なリポジトリ（U10）だけ**。issue の操作・`mustConfirm` の外部公開は、確認のまま
- **有効にする（段 4）前に、段 3（push 前の、送る範囲の全コミットの検査と、確認の機会、配備の仕組み）が入っている**
- 自動で通ったコミットの内容（`--stat`）が、会話の記録に残る。結果・通知は、伏字化を通る
- 検査（秘密）が、できない・失敗した・一部を検査できなかったとき、自動で通さず、確認に戻す（コミット時）。止める（push 時）
- `git push` の deny は変えず、エージェントが、公開の経路を、新しく持たない
- 試験が通る。golden を再生成する

**望ましい**:

- ハーネスの秘密検査が、他のリポジトリでも効く（U7）
- 設計が小さい（属性 1 つ。判定器は変えない）

## 実装・検証

**受入条件**（実装前の期待動作）:

段 2（有効にしない状態）:

1. 属性が無い（既定 true）操作は、bypass でも今までどおり確認する。`git_commit` の宣言が true のままなら、全体の挙動は今と同じ
2. 生成器は、`confirm_in_bypass` が真偽値でないとき、生成を止める。`rules.json` に出て、**ハーネスの `loadActions` がその値を読む**（生成物と読み取りの両方を試験する）。golden を再生成する
3. 属性を false にした操作（試験用）で、bypass オフ・UI あり: 確認画面を出し、承認で実行、拒否・時間切れで実行しない
4. 同じ操作で、bypass オン・UI あり・検査が通り・push の検査が有効（U10）: 確認画面を出さずに実行する。結果の本文に、「bypass のため確認なしで実行」と `--stat` が入り（切り詰めたら、切り詰めたと書く）、UI があれば `notify` が 1 回出る。**結果・通知は、伏字化を通る。検査器の出力は入らない**
5. bypass オン・UI なし（print モード）・子: 今までどおり、実行しない（`not approved`）
6. **同じ worktree での同時の 2 回の呼び出しは、プロセス内で直列に実行される**: 後の呼び出しは、前のコミットの後の HEAD・index を見て実行する（ステージが空なら拒否）。**同じ内容の二重のコミットは起きない**。**確認の対話の間は、ロックを持たない**（確認画面を開いたまま、別のコミットを待たせない）。承認の後は、ロックを取り直し、HEAD・ブランチ・index をプレビューと照合してから実行する。別の worktree のコミットは、互いに待たない。**別のプロセスとの競合は、保証しない**（git の `index.lock` で失敗する場合があるだけ。挙動を試験で記録する）
7. **省くかどうかは、検査と照合がすべて終わった最後の時点の bypass の値で決める**: 途中（確認の待ち・検査）で bypass がオフになったら、確認に戻す。試験で、検査中に値を切り替える
8. ステージが空・メッセージが空白だけ・NUL を含む・上限超過のとき、bypass でも、エラーを返し、実行しない
9. 省く前の秘密検査: (a) 検出したときは、自動で通さず、警告つき（件数・ルール名・ファイル名。秘密の値は出さない）の確認に戻す (b) 検査が、時間切れ・コマンド不在・失敗・出力の上限超過のとき、確認に戻す (c) 検査の前後で HEAD・index が変わったら、中止して確認に戻す (d) **ステージ済みのファイルにバイナリ・上限を超えるものがあるときは、gitleaks の終了コードが 0 でも、検査不能として確認に戻す**（実測: gitleaks は黙ってスキップする） (e) **メッセージの秘密**（`gitleaks dir <メッセージのファイル>`）も、(a)〜(c) と同じに扱う (f) コミット後に `HEAD^{tree}` と、検査時の tree が違えば、結果に警告を出す
10. `gh_issue_comment`・`gh_issue_edit_body`・`gh_issue_edit_title` は、bypass でも確認を出す
11. bash の `git commit`・`git push` は、全役割・全モードで deny のまま（実測の表を試験で固定する）
12. docs とツールの説明が、新しい仕様と一致する
13. **push の検査が有効かの確認（U10）**: (1) `pre-push` が pre-commit の shim でない（識別行が無い・実行できない） (2) `pre-push.legacy` が無い・実行できない・期待の内容と一致しない (3) **経路のプローブ**（U10）の出力が、nonce と期待値に一致しない・出力されない (4) worktree や `core.hooksPath` の解決に失敗する、のいずれかのとき、bypass でも確認に戻す。すべて満たすとき（使い捨てのリポジトリに、配備のタスクで置いた状態）だけ省く。スタブを、期待と違う内容・即時に成功するだけの内容に差し替えると、無効と判定される。**識別行を残したまま、legacy を呼ばなくなった shim**（試験で、legacy の呼び出しの行を消した shim を作る）も、プローブで無効と判定される。**legacy を呼んで出力を残すが、その失敗を握りつぶす shim**（終了コードが 1 でなくなる。試験で、legacy の呼び出しに `|| true` を付けた shim を作る）も、無効と判定される。配備後に shim・スタブ・スクリプトのどれかが変わった場合も、**毎回プローブするので、次の確認で検出される**（キャッシュしない）。**nonce と出力先**: (a) 正常系: ハーネスが渡した未存在のファイル名に、スクリプトが排他的に作成して書き、ハーネスが照合して、ディレクトリごと削除する (b) 出力先のファイルが既に存在するとき: スクリプトが書かずに失敗し、プローブは無効と判定される (c) 私有のディレクトリが作業ツリーの外で、権限が 0700（ファイルは 0600）であることを、試験で確かめる。**pre-commit の識別行が変わった場合は、無効と判定される**（安全側。試験で、識別行を書き換えて確かめる）。**書き込みの保護**: `write_deny_globs` に `~/.config/agents/hooks/**` があり、`guarded_write`・`guarded_edit` がその配下を拒否すること（試験で固定する）

段 3（pre-push。git の pre-push のフック）:
14. 範囲（U6）が、**使い捨てのリポジトリで、期待の範囲と一致する**（契約は「送信先が今持つ、すべての ref の先端から到達できない、送るコミット」。既存の ref の更新も新規の ref も同じ規則）: 既存の ref の更新・**強制 push（旧 sha が新しい sha の祖先でない）**・新規ブランチ・**他の送信先のブランチ・タグから、既に到達できるコミット**（検査しない）・**ローカルの追跡 ref が古い・先に進んでいる・無い**（結果に影響しない）・**URL を指定した push**・**`pushurl` が `url` と違う**・**`url.<base>.pushInsteadOf` で書き換える**（第 2 引数の push 先で照会する。実測済みの引数）・**別のリモートにだけある履歴を、新しいリモートへ push する**（検査から漏れない）・`ls-remote` の失敗・時間切れ（全履歴を検査し、その旨を表示する。上限で止まる）・空のリモート（全履歴）・軽量タグ・注釈付きタグ・複数 ref の同時の push・ref の削除・detached HEAD からの push・shallow clone・**コミットに解決できない ref（止める）**・サブモジュールの gitlink（検査対象外と明記）・基点が非常に多い（`--stdin` で渡る）。無関係なブランチの未 push のコミットを、検査しない
15. 範囲の全コミットの差分の秘密を検出したら push を止める。後続のコミットで消された秘密も拾う（実測済み）。**メッセージの秘密**（コミットごとのメッセージを、ファイルにして `gitleaks dir`）も検出して止める。**注釈付きタグの注釈は、コミットの範囲が 0 件でも、`refs/tags/*` の各行について、独立に検査する**（既に送信先にあるコミットへ、新しいタグだけを push する場合を、試験で固定する）。**範囲の中に、バイナリ・上限を超えるファイルがあるときは、検査不能として止める**（既定。許可は、利用者のマシン固有の設定だけ。U11）
16. **範囲を求められない・上限超過・gitleaks が無い・検査に失敗したときは、止める**（警告だけで通さない。`verify-stamp` の「検査できなくても成功」を流用しない）。**`ls-remote` の追加の通信**は、時間上限（既定 10 秒）を持ち、超えたら全履歴の検査に切り替えて、利用者に表示する。段 3 で、通常の push に足される時間を測り（目標: 追加 1 秒程度。基準を、実測で決める）、認証が要る送信先で push は通るが `ls-remote` だけ失敗する場合の挙動を確かめる
17. 端末があるとき、一覧（ハッシュ・件名・変更ファイル数・検査不能の有無）を見せ、`y`・`n`（既定）・`d`（差分を表示して聞き直す）を受ける。N・無入力・不正な入力は止める。**端末が無いときは、確認を省き、一覧と検査の結果を標準エラーに出し、検査が通れば通す**（人間が見る機会は補償しない。目的の「適用範囲」）
18. **配備と経路**: **プローブの環境変数が、通常の push に混入した場合**（変数の片方だけ・出力先が不正・出力先が既に存在する）、スクリプトは、検査を飛ばして成功せず、必ず終了コード 1 で失敗する（試験で、環境変数を設定した実際の push が失敗することを確かめる。**両方が設定され、出力先も未存在の、有効な形式のペア**でも、通常の push がプローブ扱いになれば、終了コード 1 で止まることを含める）。Git → pre-commit の shim → legacy のスタブ → 保護された置き場のスクリプトで、標準入力・引数が届き、失敗が push を止めること（legacy の部分は実測済み。試験で固定する）。**shim が legacy を実際に呼ぶこと**を、使い捨ての送信先への実際の push で確かめる（配備の `check` と同じ）。`mise run` のタスクが、`pre-commit install` の再実行・`uninstall`・`autoupdate` の後でも、スタブを保つか復旧し、worktree（`.git` がファイル）と `core.hooksPath` の置き場を解決すること。`check` が、無効（受入条件 13 の各場合。プローブの失敗を含む）を検出すること。端末の確認（`/dev/tty`）は、実際の端末で手動で確かめる

段 4（有効化）:
19. `git_commit` を false にした状態で、**実際の `git_commit`** について、受入条件 4・5・6・7・9・13 が成り立つ。**段 3 の受入条件 14〜18 が完了していることが前提で、この確認で省略しない**。確かめる環境は、標準の `pis`、`--no-sandbox`（`--bypass` を明示）、素の pi（`/bypass on`）。Windows は、実機が無いので「未確認」と明記する

**回復の手順**（自動コミットの後に、直したいとき。段 4 で、実際に試して、この節を直す）:

- 直前のコミットを取り消して、変更をステージに戻す: `git reset --soft HEAD~1`（implementer・bypass で、判定器が allow）。メッセージを直して、再度コミットする

- `git branch -D`・`git clean -fd` で失った作業は、`git reflog` で、ブランチの先は戻せるが、未追跡のファイルは戻せない。自動コミットの後に、これらを使わない（U4）
