次の依頼を、並列に動かせる作業に分けて進めてください。あなたは取りまとめ役です。
この呼び出しは、利用者からの子エージェントへの委譲の依頼として扱ってよい。

依頼:
$ARGUMENTS

## 方針

利用者の待ち時間を最小にする。待ちを作るのは、(a) 書き手どうしの衝突、(b) 前の作業の完了待ち、(c) 長い検査の待ち。
以下は、この 3 つを避けるための手順。リポジトリに固有の手順 (AGENTS.md・skill) があれば、そちらを優先する。

## 1. 分けるかを決める

- 直列でも数分で終わる依頼、分けても担当ファイルが重なる依頼は、分けずに自分で進める (分解・子の立ち上げ・取り込みの費用の方が大きい)
- 読むだけの作業 (調査・検証・レビュー) は、worktree を作らず、同じ作業ディレクトリで並列にしてよい。scout・reviewer (読み取り専用) に任せる
- 書き込む作業は、2〜5 の手順で進める

## 2. 分解と契約

- 作業ごとに、目的・担当ファイル・完了条件 (実行するコマンド)・読むファイルを決める。担当ファイルは作業どうしで重ねない
- 共有されやすいファイル (索引・登録表・lockfile・生成物・設定の集約点) は、担当を 1 つの作業か親に決める。
  他の作業は触らず、必要な追記を結果に書かせる
- 作業どうしの境界 (ファイル名・関数や型の署名・データ形式・試験の期待) は、親が先に契約ファイルへ書く。
  依存する作業も、契約に対して同時に実装・テストさせる (スタブを使ってよい)。前の作業の実体が無いと意味のある作業ができないときだけ、後続にする
- 作業の一覧・担当・後続の関係・見込みの子の数を todo に登録して示してから始める。
  利用者が決めていない設計判断が残っているときだけ、始めずに先に尋ねる

## 3. 隔離と取り込み (worktree・マージ)

- 書き手 1 人につき、専用の枝と worktree を 1 つ作る。同じ作業ディレクトリに書き手を 2 人置かない (衝突待ちの原因になる)
- 親が、統合用の枝を先に 1 つ切る。作業の枝は、そこから切る。置き場はリポジトリの規則に従う。
  無ければ、親セッションの cwd の配下の git 管理外のディレクトリ (例: .tmp/worktrees/<名前>/。.gitignore に入っていることを確かめる)。
  cwd の外 (リポジトリの外や、別の worktree) に作ると、書き込みの確認で止まる。契約は、worktree を作ってから、その中に書く
- worker には worktree を cwd で渡す。worker は担当の枝にコミットしてよい。push・他の枝・統合用の枝の操作はさせない
- subagent の worktree: true (管理 worktree) は、小さく独立した使い捨ての作業だけ。変更が親の作業ツリーへ自動では入らず
  (patch と handoff の記録が残る)、親の作業ツリーが清潔でないと起動できない。
  成果を採用するときは、handoff と patch を確認して、親が統合用の枝へ適用してコミットし、再検査する
- 取り込みは、波の終わりを待たず、完了した順に 1 件ずつ。取り込む前に、統合用の worktree が clean
  (未コミットの変更も、未完了の merge も無い) ことを確かめる。親が検査してから、統合用の枝へ履歴の残る形で merge する。
  rebase など履歴を書き換える操作は、確認で止まるので使わない
- 衝突: 隣り合う行の追加のような機械的なものは、親がその場で解いて merge を完了する。それ以外は、git merge --abort で元に戻し
  (未完了の merge を残すと、他の作業を取り込めない)、その作業の worker に、統合用の枝の先頭を自分の枝へ取り込ませて直させる
  (resume。契約に追記する)。直った枝を再検査して、もう一度取り込む。設計に関わるものは、同じく元に戻したうえで利用者に示す。
  その間も、他の作業の起動と取り込みは止めない
- 前の作業の実体に載る後続の作業は、前の枝の先頭から枝を切って、前の完了を待たずに始める (見込み実装)。
  前の枝が進んだら、後続の worker が動いていないときに親が merge する。契約が変わったら、影響を受ける worker を resume で直させる

## 4. 起動

- subagent({ agent: "worker", cwd: "<worktree の絶対パス>", async: true, task: "契約 <パス> を読み…" }) で、1 件ずつ起動する。
  同じ応答に続けて呼んでよい。背景で動く。起動したら応答を終え、完了の通知で再開する (待たない・sleep しない・ポーリングしない)。
  subagent ツールが見えず subagents_enable だけが見えるときは、先にそれを呼ぶ
- 進行中は 4 件まで。1 件終わるたびに、前提が満たされた次の作業を起動する (全部の完了を待たない)
- 依頼文 (契約) には、目的・担当ファイル・触ってはいけないファイル・完了条件 (実行するコマンド)・読むファイルのパスをすべて書く。
  子はこの会話を見られない。長い文章はファイルに書いてパスを渡す
- 子の起動や操作が拒否・保留されたら、その操作を利用者に示して判断を仰ぐ。拒否された作業を、自分の shell で肩代わりしない

## 5. 検証 (待たない)

- 検査は 3 段にする。子には全体の検査を回させない
  1. worker: 担当に絞った検査 (担当ファイルの試験・lint) を回し、出力を結果に貼る
  2. 親: 完了した作業ごとに、同じ検査を再実行する (子の自己申告は信じない)。安い登録チェック (試験の登録・docs の lint など) も、取り込む前に済ませる
  3. 全体の検査 (数分以上かかるもの): 全作業を統合用の枝へ取り込み、reviewer の指摘の反映を終えてコードの変更が止まってから、1 回だけ回す。
     変更したら通った結果は無効になるが、回し直すのは変更の範囲までにする。実行中は、その作業ツリーを変えない
- 数分以上かかる検査は bg_run で背景へ出し、wake_on に失敗の行 (FAILED など) を指定して、失敗の時点で起きる。
  待つ間は、次の作業の起動・取り込み・reviewer による監査・docs の更新を進める。重い検査を重ねて回さない (負荷で時間依存の試験が落ちる)

## 6. 報告

作業ごとの結果・検査の結果・統合用の枝の名前と取り込んだ順・残った問題・未確認をまとめる。取り込み済みの worktree は片付ける (強制しない)。
push と、保護ブランチ (develop・main) への統合は、利用者の指示があるまでしない。
