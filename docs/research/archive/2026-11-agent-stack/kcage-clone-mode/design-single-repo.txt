# 結論

**推奨: M1（1 リポジトリ 1 箱＋箱専用の clone）。ホストとは `git bundle` で feature の枝だけを交換する。**
- 許可表に新項目 `git = "clone"` を足し、既定は `shared`（現行 M0）のままにする。M0 は撤退先として残す。
- M2（1 feature = 1 箱）は、条件が揃ったときだけ足す追加手段にする。
- M3（作業ツリーだけ共有）は採らない。

**利用者の質問への答え**
1. **1 リポジトリ 1 箱で、git の運用は足りる。** feature どうしの隔離は今と同じで、箱の中の worktree と規約で守る。M0 でも同じ箱の中の worktree どうしは隔離されない（`docs/adr/0028-per-repo-agent-container.md:97`）。M1 でそこが弱まることはない。
2. **1 feature = 1 箱は必須ではない。** 要るのは次のときだけ。
   - (a) 同時に動かす feature が compose のポートや DB を取り合う。公開ポートはホストの `127.0.0.1` で一意（`scripts/kcage/plan.py:51-80`）。
   - (b) feature ごとに通信モード・`data`・ブローカーを変えたい。
   - (c) 信頼できない依存を試す実験を、他の feature から切り離したい。
   - VRAM は箱どうしでも共有されるので、GPU は M2 の理由にならない。
   - M2 の費用: 許可表の行を feature ごとに足す、`kcage register`（パスワード）が要る、Docker イメージが箱ごとに重複する（`docs/spec/sandbox/incus-box.md:236`）。
3. **今の feature 開発は、段の担当を移せば成立する。** 起票・実装・commit・feature 同士の merge・bundle・検査は箱の中で行う。PR サマリー・確認・統合・掃除はホストで、取り込んだ枝に対して今までどおり行う。
   - 変わるのは 3 点: ホストから見える box の worktree が無くなる、箱では `git flow` が使えず素の git になる、`pr_summary` はホストでしか使えない。
   - 検査は、箱のコードに対しては箱で回す（C4 のため）。

# 手順（1 手順 = 1 つの変更と確認の方法）

## 設計の要点（S1 の仕様）
- **clone の置き場（Q1）**: 箱の rootfs の `/home/ubuntu/work/<repo-id>` に置く。ホストのユーザーは到達できず、デバイスの関門（`plan.py:140` の `device_to_argv`）も変えずに済む。
  - 永続のためには Incus の custom volume が使える（S4。`disk` デバイスの関門を広げるので `review` が要る）。
  - ホストの root 専用ディレクトリを bind する案（M1b）は、将来そこをホストの git が読む危険が残るので採らない。
- **seed（箱が clone を持つまで）**
  1. ホストのユーザー権限で `git bundle create <tmp> develop main` を作る。
  2. `kcage exec`（stdin 経由）で `~/.kcage/inbox/host.bundle` へ送る。
  3. 箱の中で `git clone host.bundle <work>` を実行する。
  - 箱のネットワークが nat・proxy-only・offline のどれでも動く（外へ出ない）。
- **collect（箱→ホスト）**
  1. `kcage exec -- git -C <work> bundle create - 'refs/heads/feature/*' 'refs/heads/bugfix/*' ^develop` の標準出力を、ホストのユーザー権限で一時ファイルに受ける（サイズ上限・時間制限つき）。
  2. ホスト専用の **inbox bare repo**（`~/.local/share/kcage/inbox/<id>.git`）に `git bundle verify` と fetch で入れる。refspec は feature・bugfix だけ。develop と main は取り込まない。
  3. `git fsck --strict` をかける。
  - ホストの git 呼び出しは `pr-review.ts:16` や `apps/pr-viewer/git-view.ts:37-87` と同じ硬化にする。
    - 固定の先頭引数: hooksPath と fsmonitor を無効化、`diff.external` を空、`protocol.ext.allow=never`。
    - 環境: `GIT_CONFIG_GLOBAL=/dev/null`、`GIT_CONFIG_NOSYSTEM=1`、`GIT_NO_LAZY_FETCH=1`。
    - inbox の config に `transfer.fsckObjects=true` と `gc.auto=0` を固定する。
- **take（inbox→本体）**: `git fetch <inbox> refs/heads/feature/x:refs/heads/feature/x`。`+` なし・FF のみ。同名の衝突は拒否し、`--as <名前>` で別名にできる。
  - inbox の config はホストの git だけが書く。
  - 宛先が保護 ref（main・develop）のときは判定器が必須確認にする（`docs/spec/guard/pi-decide.md:121`）。feature 宛は通常の操作。
- **feed（ホスト→箱）**: ホストが develop（と main）を bundle にして送り、箱の中で `git fetch ... develop:develop`（FF のみ）。ホスト作成の枝（人が書いた `feature/h1` など）を箱へ渡すのも同じ経路。**箱からホストへ書く経路は無い**。
- **許可表の項目（案）**
  - `git = "shared" | "clone"`（既定 `shared`）。
  - `seed_refs`（既定 `develop`・`main`）。
  - `kcage.toml` の `git = "clone"` は「締める方向だけ」として、shared→clone のみ有効にする。
  - 箱内のパスはコード固定。変更案は Q2 で確認する。
- **kcage-root のコードの変更は最小**。collect・take・feed は、ユーザー権限の CLI から既存の passwordless 動詞 `exec`（`root_helper.py:31-32`）経由で行うので、新しい sudoers 行も新しい権限も要らない。
- **ホスト側の規則（docs に書く）**
  - ホストの git・pi・エディタ・Orca は、箱の clone を開かない。clone は到達不能な場所に置く。
  - Orca には箱のパスを登録しない。
  - 箱が書いた `.gitmodules` で `git submodule update` をしない。
  - box 由来の枝を host で merge・commit・checkout するときは `core.hooksPath=/dev/null` を付ける。
  - box 由来のコードに対して host で `bundle.py verify` や試験を回さない。

## 運用手順（利用者が実行する形。名前は案）
- 新しい repo: `kcage register ...`（人。許可表に `git = "clone"`）→ `kcage up`（seed まで行う）→ `kcage selftest`
- 日常: `kcage pi`（箱の中で起票・worker・commit。終了時に自動で collect）→ `kcage collect` → `kcage take feature/x` → ホストで `guarded_pr_summary` と PR ビューア（今までどおり）
- 統合後: `kcage feed` → `python3 scripts/wt_clean.py x`（host に枝がある名前だけ）→ 箱の中で `git worktree remove ...` と `git branch -d feature/x`（`kcage exec -- ...`）
- 箱の中の起票: `git worktree add -b feature/x .tmp/worktrees/x develop`。依存する feature は `cd <絶対パス> && git merge feature/B`。bundle は箱で `feature/bundle-N` を作って merge する。
- 失敗時: 箱の clone が壊れたら `kcage rm` → `kcage up`（再 seed）→ `kcage feed --from-inbox`（inbox の枝を箱へ戻す）。`collect` は、最後の collect 以降の箱の commit を保護しない。
- 複数 repo: repo ごとに箱と inbox が別。`--repo <id>` で指定する。

# リスク
- **同じ枝名を host と箱が別々に進める**と、`take` が非 FF で拒否される。`wt_owner` の lock は片側からしか見えない。運用規則で防ぐ（枝は片側が持つ）。
- **箱の未回収 commit は、箱が壊れると失う**。`collect` を `kcage pi` 終了時と `stop` 前に自動で走らせて緩和する。`kcage snap` はパスワード動詞。
- **ホストの人が箱のコードを直接編集できなくなる**。代替は viewer・`.git` なしの閲覧・箱の端末。必要なら M0 を使う。
- **LFS・submodule を使う repo**は箱の clone で別手当てが要る（Q6）。
- **host で box 由来の枝を merge・commit・checkout する**と、host の hooks（pre-commit など）が箱の設定を実行しうる。hooks 無効を既定にする（上の規則）。
- **`wt_clean.py x` に箱だけの枝名を渡すと拒否される**（「枝も worktree も無い」。`wt_clean.py:127-189`）。害はないが、host に存在する枝だけを渡す。
- **未取り込みの pin**（`kcage-git-pin`）は、M0 を残す間は必要。取り込み前に S3 の判断が来ると、pin が無駄になる。
- 箱の clone に対する `kcage snap` と `kcage template` の相互作用は未確認。
