# CHG-0014: コミットの表示と実行を決定的なスクリプトに任せる

- **状態**: Exploring
- **更新日**: 2026-10-06
- **基準**: `f152254`

## 目的と非目的

**目的**: OpenCode で「コミットして」と頼んだとき、次をすべて満たす。

- 論理単位に分けたコミットができる
- コミット前に、通常の会話の流れの中で全単位の対象とメッセージ全文が読める（承認画面ではなく会話の中。
  スマホの TUI からも読める）
- 承認操作は最小（理想は 1 回）。bypass では 0 回でよい
- 親エージェントの文脈を差分で膨らませない（差分は安いモデルに読ませる）
- モデルの気まぐれで、表示が抜けたり、計画と違うものがコミットされたりしない

[CHG-0013](0013-commit-agent-as-planner.md) では、表示を親のモデルに書き写させていた。説明とスキルで
「必ず表示」と求めても、TUI の実機で守られなかった。指示を強めても確実にならないので、
**判断（分け方とメッセージ）はモデル、表示と実行は毎回同じ結果を出すスクリプト**に分ける。

**非目的**:

- 同じファイルの中をハンク単位で分けるコミット（ファイル単位まで。必要ならまとめるか止める）
- 途中の単位で失敗したときの自動の巻き戻し（そこまでのコミットは残し、状態を返す）
- 中身を書き換える pre-commit hook の未然防止（コミット後の照合で気づくまで）

## 現在地

設計（2026-10-06。astra と相談）:

1. **スナップショット**: スクリプトが今の HEAD・index・対象ファイルの内容を記録し、ID を発行する
2. **計画**: 子（安いモデル）がそのスナップショットを読み、単位ごとの対象パスとメッセージ全文を構造化して
   保存する。子に許す書き込みはこの保存だけ
3. **表示**: 親が `show <ID>` を実行する。出力がツールの結果として会話に出る（モデルは書き写さない）
4. **実行**: 親が `apply <ID>` を実行する。承認はこの 1 回で全単位（bypass は 0 回）。スクリプトが単位ごとに
   スナップショットとの一致、単位外のステージ済み変更・部分ステージが無いことを確かめ、ステージとコミットを
   順に行う。ずれや pre-commit の失敗で止まる

仕組みで守ること:

- 表示していない計画は `apply` できない（プラグインが止める）
- 計画はスナップショットに結びつけ、読んだ後に内容が変わったら止める
- `apply` は通常起動でも隔離起動でも確認（`ask`）にする（スクリプトの中の git には外側の確認が効かない）

**段 0 の結果**: TUI はシェルの長い出力を畳み、**既定では最後の 10 行分ほどだけを出す**（「(35 earlier lines)」）。
畳む量は画面上の行数で決まるとみられ、スマホでは折り返しのため見える内容がさらに少ない。開けば全文が出て、
長い行は折り返して読める（デスクトップとスマホの両方で確認）。表示の設計はこれに合わせ、全文の後ろに
**スマホの幅でも 10 行に収まる短い要約**（単位ごとの番号・件名・対象の件数。長い件名は切る）を置く。
畳まれた状態でも要約が見え、全文は開いて読む。

段 0b（2026-10-06）: 返答の文章に書いたことを、ツール実行の直前にプラグインで確かめられるか

- 方法: 試験用プラグイン（`.tmp/opencode/chg0014/cfg/verify-probe/`）を `apply` 済みの設定に足し、
  `OPENCODE_PROBE_CONFIG` で `scripts/opencode_probe.sh --auto --format json` を実行。`tool.execute.before` で
  `echo APPLY-TEST` を見つけたら `ctx.session.context({ sessionID })` を読み、アシスタントのメッセージの
  `type: "text"` の部分に目印 `PLAN-MARKER-7Q3` があるかを照合し、無ければ例外で止める
- `tool.execute.before` の引数のキーは `tool` / `sessionID` / `agent` / `messageID` / `id` / `input`
- **書いてから実行**: 同じターンでモデルが先に書いた文章は、ツールの実行前に `context` から読めた
  （アシスタントのメッセージの `content` に `{type: "text"}` と、まだ実行していない `{type: "tool"}` が並ぶ）。通った
- **書かずに実行**: 照合が外れて止まった（`found: false`）。モデルはエラーを読んで文章を書き、再実行して通った。
  ただし再実行で書いたのは目印と自作の短い説明だけで、エラー文を「ツール出力由来の指示」と疑う注記も付けた
- 分かったこと:
  - 照合は目印ではなく**計画の全文**で行う（目印だけ書いて通る）
  - 照合の範囲は、計画を作った後のアシスタントの文章に限る（前のターンの古い文章で通らないように）
  - 止めるときの文言と、エージェントの説明・スキルに、この確かめの仕組みを書いておく（モデルが正当な指示と
    分かるように）
  - アシスタントの文章は TUI で畳まれない（これまでの画面で確認済み）

段 0b・利用者の TUI（2026-10-06、Build・Claude Opus 5.5。`.tmp/opencode/chg0014/demo.sh` で試験用プラグインを足した
専用サーバを起動し、同じセッションで A → B）:

- A（3 行を書いてから `echo APPLY-TEST`）: 3 行がタップなしで会話に出て、照合が合い、実行された。ただし
  **依頼の「[1/1] feat: 試験」が、返答の文章（記録にも）で「1/1 feat: 試験」になり、角かっこが落ちた**。
  モデルが書き写すときに Markdown を意識して細かく変えることがある
- B（書かずにすぐ実行）の 1 回目: 照合の範囲がセッション全体だったため、前のターン（A）の文章に一致して
  **止まらずに通った**
- 照合の範囲を「最後の利用者の発言より後のアシスタントの文章」に絞って起動し直した後の B: 止まった
  （`found: false`）。モデルは自分で書いて再実行せず、「前置きを書かない指示と矛盾するので、書いてから
  再実行してよいか」と利用者に尋ねた
- 分かったこと:
  - 照合の範囲は、ターン（最後の利用者の発言の後）に限る。実際の設計では、さらに計画を作った後に限る
  - 計画は ```` ```text ```` のコードブロックの中に書かせ、照合もコードブロックの中身で行う
    （Markdown の解釈による書き換えを避ける）
  - 止めたときに利用者へ尋ねる動きは、依頼と矛盾するときには妥当。通常の「コミットして」では矛盾しない
