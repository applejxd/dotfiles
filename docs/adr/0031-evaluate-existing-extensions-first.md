# pi の機能は、既存の拡張・設定の評価を先にし、自作は最後の手段にする

- **ステータス**: Accepted
- **日付**: 2026-11-09
- **決定者**: applejxd
- **関係**: [ADR-0016](0016-pi-extensions-own-first.md)（自作を基本）を**置き換える**。[ADR-0030](0030-freeze-agent-stack-return-to-stock-pi.md)（自作基盤の凍結）の方針を、今後の作り方の規則にする。

## コンテキスト

- [ADR-0016](0016-pi-extensions-own-first.md) は「拡張は自作を基本とし、外部の拡張は条件を満たす例外だけ」と決めた。その ADR 自身が、前提となった「拡張を足さない」構成は **AI が提案し、利用者が十分に理解しないまま承認したもの**で、利用者が決めた方針ではないと書いている。「自作を基本にする」への移行も、AI が「堅牢に作るには」に答える形で進み、利用者が選んだものではなかった。
- スキル `pi-extension-dev` は「自作が基本。公開されている拡張は設計の参考として読むだけで、導入しない」と定め、**新しい機能を頼むたびに、既存の拡張を探して導入せず自作する手順が自動で繰り返される**構成だった。
- 結果は [ADR-0030](0030-freeze-agent-stack-return-to-stock-pi.md) の凍結に至った基盤である（約 1,400 ファイル。ハーネスの本体 1 ファイルだけで約 115 KB。フルガード・`pis`・隔離環境・PR ビューアなど）。保守が仕事の中心になり、本来の開発を圧迫した。2026-11-05 の独立 review（[記録](../research/agents/arch-review-2026-11.md)）も、追加投資の停止と使う経路への縮小を勧めていた。
- 外部の AI との相談（2026-11-09。[原文](../research/archive/2026-11-agent-stack/consult/own-first-review.txt)。外部の意見として扱い、鵜呑みにしない）の指摘のうち、リポジトリの記録と一致するもの:
  1. 「第三者のコードを使わないこと」と「安全に運用すること」は**別の評価軸**で、ほぼ同じ方向の目標として扱っていた。自作のコードにも、自分のバグと脆弱性がある。
  2. 自作の費用（上流の追従・実装・試験・docs の維持、小さな変更の波及）が過小評価されていた。
  3. AI は「堅牢に作るには」と聞かれると、使用頻度や維持費より、例外とリスクを網羅する設計へ進みやすい。個々の提案が合理的でも、全体では使いにくい仕組みになる。
  4. 目標は最も堅牢な pi を作ることではなく、**pi の開発に時間を取られず、pi を使って本来の開発をすること**。
- 供給網のリスクは実在する。拡張は読み込み時に任意のコードを実行できる。ただし、版の固定・権限の確認・実行時の網（permission-system・cc-safety-net）・初回の隔離試用で下げられる。

## 検討した選択肢

### 案 1: ADR-0016 のまま（自作を基本）

- **欠点**: 実績が示すとおり、維持が仕事の中心になる。AI が自作へ誘導し続ける。却下。

### 案 2: 既存の拡張を無審査で自由に導入する

- **欠点**: 供給網のリスクを評価せずに受け入れる。却下。

### 案 3（採用）: 既存の評価を原則にし、自作は最後の手段にする

- **利点**: 維持するコードが減る。pi 本体と package の更新に追従するだけで済む。AI の誘導が逆向きになる。
- **欠点**: 供給網のリスクを受け入れる（下の対策で下げる）。既製品が目的に完全には合わない妥協が出る。

## 決定

**案 3 を採る。**

### 1. 機能が要るときの順序

次の順に探し、**探した記録なしに自作しない**（人も AI も）。

1. pi 本体の標準機能・設定（文書・設定項目・キーバインド・テーマ・組み込みの MCP など）。
2. すでに入れている package の設定・機能。
3. **公開の package（拡張・スキル）を探し、評価して導入する。**
4. skill + CLI、または MCP（既製のサーバを含む）で足りるか。
5. 自作（最小。下の 3）。

### 2. 導入するときの評価と手順

- **評価の観点**: 目的に合う・保守が続いている（最終更新・Issue への対応）・利用実績（月間ダウンロード）・権限の範囲（ネットワーク・ファイル・子プロセス・環境変数・鍵）・ライセンス・依存の量。出典（URL・日付）を残す。
- **版の固定**: `npm:<名前>@<版>` で固定し、更新は変更履歴を読んでから。一覧は `home/.chezmoitemplates/pi-stock-packages`。
- **初回の試用**: 使い捨ての作業ディレクトリ・ダミーの鍵で試してから、実際の環境に入れる。
- **権限**: permission-system の方針（ask・allow・deny）を、導入と一緒に決める。
- 手順の詳細は、スキル `pi-extension-dev`（この決定に合わせて作り直した）。

### 3. 自作の条件（例外）

次の**全て**を満たすときだけ自作してよい。

- (a) 1〜4 で満たせない理由を記録した。
- (b) 維持費の見込み（行数・追従が要る上流・試験）と、**撤去の条件**を記録した。
- (c) **最小**にする（薄く、公式の拡張点で、pi の内部の挙動に頼らない。形は pi の package の形で、リポジトリ内のローカルパスから読ませる）。
- (d) **利用者が明示的に承認した。**

### 4. 凍結の維持

[ADR-0030](0030-freeze-agent-stack-return-to-stock-pi.md) の凍結（フルガード・`pis`・kcage・PR ビューアなど）は、この ADR でも解かない。再開するときは、ADR-0030 の条件に加えて、1 の順序での評価を先に行う。

### 5. AI への指示

- 機能の提案には、**「作らない案」（既存の導入・設定・スキルで足りる案）を必ず含める**。
- 「堅牢にするには」の問いでも、使用頻度と維持費を評価に入れ、例外を網羅する設計へ進まない。
- スキル `pi-extension-dev` を、この順序（既存の評価が先）に作り直す。共通の指示（`AGENTS.md`）にも 1 行足す。

## 結果

### ポジティブな結果

- 維持する自作のコードが減り、pi 本体と package の更新に追従するだけになる。
- 「作る前に探す」が既定になり、AI が自作へ誘導する構造が逆向きになる。
- 自作は、理由・維持費・撤去条件・承認の記録つきの例外になる。

### ネガティブな結果・トレードオフ

- 導入する拡張は読み込み時に任意のコードを実行でき、囲えない。**残る危険は、版の固定・権限の確認・初回の試用・実行時の網で下げるだけ**で、受け入れる。
- 既製品が目的に完全には合わない妥協が出る。
- package の更新で挙動が変わりうる。版を固定するので、更新は利用者が選んだときだけ。

### 今後の見直し条件

- 導入した package で、実際の事故または事故の寸前が起きたとき。
- 例外の自作が 3 件を超えたとき（置き換えられるものがないか再評価する）。
