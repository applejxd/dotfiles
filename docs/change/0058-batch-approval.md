# CHG-0058: 保留の巡回承認と一括承認（複数の保留を、見ずに承認することなく、少ない操作で承認する）

- **状態**: Exploring
- **実装の前提**: 独立 `review` は反映済み（v2）。**段 1（巡回）は §5.1 の条件つきで先行**。段 2（一括）は **§5.2 の再設計と再審査のあと**
- **更新日**: 2026-11-01
- **基準**: pi 1.4.0、[CHG-0055](0055-async-approval.md)（非同期承認・`/pending approve`）・[保留](../spec/guard/pi-pending.md)の上。方針は [ADR-0023](../adr/0023-pending-approval.md)

## 1. 要約と状態

`/pending` の承認は、**1 件ずつ**（一覧から選ぶ → 承認画面 → 実行）。並列実装で保留が 5〜7 件たまると、毎回 `/pending` を開き直して選ぶ手間が大きい（実機: 1 日で 7 件を 1 件ずつ承認した）。
以前は「一括承認は、需要を実測するまで見送る」（[CHG-0056](0056-orchestrator.md) §6）としていた。**その実測の条件は満たした**。

- **段 1 巡回**: 1 件の処理の後に、**次の承認待ちの画面を自動で開く**。ただし、**「外側のループだけ」では済まない**（結果の通知・取消・初期選択・構造化した結果が要る。§5.1）
- **段 2 一括**: 選択 → まとめの画面 → 1 回の承認 → 1 件ずつ実行。**初版の設計（ファイル集合の部分集合・OID の連鎖）では、承認の質を保てない**と `review` が指摘した。**実行順の計画を承認前に算出する方式への再設計**と、再審査が要る（§5.2）
- 独立 `review`（BLOCKER 2・MAJOR 5・MINOR 4）は、実物のコードで確かめて妥当だった（§10）
- 利用者の決定: 巡回を先・リスクのあるパスを含む件も一括に含める（まとめの画面に明示）・1 回の上限は 8 件。**巡回の導入後に、一括が要るかを再評価する**（§7）

## 2. 目的と非目的

**目的**: 承認の**質**（何を承認したかを、利用者が見て判断する）を保ったまま、承認の**操作数**を減らす。

**非目的**: 承認の自動化（時間切れでの実行・モデルによる承認）。承認の対象の拡大（承認できる操作は、今のアダプターだけ）。並列の実行（排他ロックは 1 本のまま）。

## 3. 現状

- `approvePending(id)`（`pending-approve.ts`）: 記録を読む → `authorize` → 計画（`adapter.plan`）→ 画面（`presentConfirm`。承認して実行・全文を見る・保留のまま閉じる・破棄。**初期選択は先頭の「承認して実行」**）→ `authorize` を再判定 → `beginApproval`（CAS）→ `runApproved`（排他ロック → 再検査 → 実行 → 結果の記録）
- 入口は `/pending`（`pending-command.ts`）。引数なしは候補から選び、承認の候補は**古い順**（`pending-pick.ts`）。戻り値は `Reply`（文面と表示レベルだけ）
- 再検査は、画面を出した時点の計画（統合先の OID を含む）との一致を要求する。**1 件目の実行で統合先が進むと、同じ画面で見せた 2 件目の計画とは食い違う**
- **結果の扱い**: 排他の操作が**停止を確認できない**（`unconfirmed`）ときだけ、結果を書かず running とロックを残す。**停止確認済みの `unknown`**（実行器の検証失敗など）は、結果を `done` に保存し、**ロックを解放する**（試験が要求している）。結果の通知は `triggerTurn: true` で**モデルを起こす**
- 計画の `files` は 200 件・`risks` は 50 件で切られ、画面は `risks` を 8 件・「全文」は `files` を 40 件に省略する。統合の結果は、hook が tree やメッセージを変えても `success` になる

## 4. 守る条件

- **B1 同意の単位は、表示した事実。** 件ごとに、統合元・統合先の完全な ref と OID・方法・後片付け・メッセージ・**変更の中身の識別**・リスクのあるパス・衝突なし、を承認前に利用者が読める形にする。**上限で切れて完全に読めない項目は、一括の対象にしない**（理由を出す）。出していないものを実行しない
- **B2 実行は、承認した「実行順の計画」を超えない。** ファイル名の集合の包含では足りない（内容・追加か削除か・mode・変更の箇所が違いうる）。承認前に、**選択した順に squash した後の状態を仮に計算**し、各件の**実際に予定する残差**（tree）を表示する。実行時は、各件の統合先 tree・結果 tree が期待と一致するときだけ進む。**hook が tree やメッセージを変えたら、その件は既存の扱いで記録し、残件の承認は失効させる**
- **B3 対象の識別と、統合先の連鎖。** 統合先の ref・worktree・common-dir・設定の識別が、承認時と同じであること。統合先の OID は、**初回は表示時の OID、2 件目以降は直前の件の自分の成功試行の結果コミット**に固定する（別のブランチが同じ OID を指す反例を塞ぐ）。ロック取得後の再検査は、既存どおり厳密にする（B3 のために緩めない）
- **B4 止まるときは、残りを実行しない。** 失敗・結果不明（`unknown`）・B2・B3 の不一致・保存の失敗・後片付けの失敗・中断で止まり、**この処理から残りへ進まない**（他のセッションが並行して変えた状態までは、保証できない。正本から表示する）。`unconfirmed` は従来どおり running とロックを残す。**停止確認済みの `unknown` も、一括では「続けない」**（結果は従来どおり記録し、ロックを解放する）
- **B5 1 件ずつ・既存の経路。** 項目ごとに `authorize`・`beginApproval`（**表示した記録の OID** で）・`runApproved` を通す。一括のために新しい実行経路を作らない
- **B6 利用者だけ。** `/pending` の利用者専用（TUI）。モデルは呼べない
- **B7 上限 8 件。** 依存の順は、選択した**固定の統合元 OID 間の厳密な祖先関係**で決め、独立な件は古い順にする。計画できない・完全に表示できない件は選べず、理由を出す
- **B8 巡回・一括の初期選択は、承認ではない。** 「承認して実行」を先頭に置くと、直前の Enter の勢いで次の画面を承認する（誤承認）。巡回・一括の**承認の画面では、先頭を「ここで終える（保留のまま）」にする**。承認の対象と検査は、単件と同じ
- **B9 結果の通知で、モデルを起こさない。** 巡回・一括の途中は、モデルへの結果の通知の**起床を終わりまで遅らせる**（各件の保存と利用者への進捗は即時）。各件の前と画面の後に、`ctx.isIdle()` を確かめ、予期しない起床があれば止める
- **B10 取消。** 中断（Esc）で、巡回・一括の全体を止める。「見送り」と「Esc・例外」を**区別して扱う**（Esc で止めたのに次の画面を開かない）。実行中の取消は、1 つの `AbortController` を、選択の開始から終わりまで保持して接続する
- **B11 固定した承認の対象（snapshot）。** 計画の分離では、記録の OID・検証済みの記録・対象の識別・表示した計画を持つ**不変の snapshot** を返す。実行後の結果は、成功・見送り・破棄・取消・拒否と、outcome・停止確認・保存の成否・結果の記録の識別を**構造化して**返す（文面の解析と暗黙の成功判定をしない）

## 5. 設計

### 5.1 段 1: 巡回（先行。B8〜B11 が条件）

- `/pending approve`（ID 省略・または一覧から選んだ後）で、1 件の処理が**終わったら**、まだ見ていない承認待ちのうち最も古いものの画面を続けて開く。画面に「巡回 2/5」を出す
- **選択肢の先頭は「ここで終える（残りは保留のまま）」**（B8）。「承認して実行」「全文を見る」「保留のまま閉じる（次へ）」「破棄」は、その下
- 結果は、次の画面の前に通知する。モデルへの結果の通知は、巡回の終わりまで遅らせる（B9）。失敗・結果不明・取消で止める（B4・B10）。上限は 8 件
- 実装: `approvePending` を「計画（snapshot を返す）」と「承認後の実行（構造化した結果を返す）」に分け、`pending-command.ts` が巡回のループを持つ（B11）
- **実装で決めたこと（2026-11-01）**:
  - 始まる条件: TUI・ID を打たない（一覧から選ぶ・引数なしの `/pending` で「承認」を選ぶ）・承認待ちが 2 件以上。ID を指定した `approve` と、承認待ちが 1 件だけのときは単件のまま
  - **最初の 1 件目から、先頭が「ここで終える」の巡回の画面**を使う（一覧の選択の直後の Enter でも、B8 の誤承認が起きうるため）
  - 止める: 終える・Esc・中断・成功以外（`unknown` は停止確認済みも）・保存の失敗・後片付けの残り・計画や再判定の拒否・モデルが起きた。「保留のまま次へ」と「破棄」は続ける
  - `巡回 i/N` の N は、始めたときの承認待ちの件数（上限 8）。途中で増えた分を増やさない（表示だけ。上限は見た件数で数える）
  - 単件の承認にも、画面の後に `isIdle()` の確認を足した（モデルが起きていたら実行せず、保留のまま）
  - **実行中の Esc**: 実行は止めない（統合の途中で止めるのは危険）。`onTerminalInput` で検知し、その件の後で巡回を止める。取消 (`AbortController`) が実行器へ届くのは、終了・reload (`session_shutdown`) のときだけ
  - **全文表示中の Esc**: 全文を閉じて同じ画面に戻る（巡回の画面の先頭は「ここで終える」。もう一度 Esc で止まる）。選択中の Esc はそのまま巡回を止める
  - snapshot は、計画と記録を**複製して深く固定**する（複製できない形は画面の前に断る）。実行するのは、表示した計画
  - 補助の失敗（モデルへの通知・フッターの更新）は、記録した結果を変えず、巡回と通知の出力を妨げない

### 5.2 段 2: 一括（再設計と再審査のあと）

初版の案（`facts`・`within` による部分集合の判定）は、**捨てる**。再設計の方向:

1. 選ぶ（`select` の ✓ 切り替え。**既定は空**）→ 選択順の**実行順の計画**を、算出専用の部品（`integrate-plan.ts` から切り出す。保護 ref・実 index・作業ツリーを動かさない）で仮に計算する
2. **まとめの画面**に、件ごとの実際の残差（B2）・リスクのあるパス・後片付け・メッセージ・警告を出し、詳細は既存の `text-viewer.ts` で件ごとに読めるようにする。上限で切れる項目は対象外
3. 実行は B1〜B11 のとおり。実行時の照合は、B2 の期待 tree と B3 の連鎖
4. 一括に対応できないアダプターは、一括から外れる。表示用の事実と、照合用の完全な事実は分ける

## 6. 試験の方針

反例を先に書く。実 git で、次を確かめる。

- B2: 同じパスの異なる変更・削除・mode 変更・同じファイルをさらに編集する積み重ね・**hook が内容を変えたとき**。ファイル集合が一致しても、予定外の残差なら止まる
- B3: 同じ OID の別の統合先 ref・設定を変えて checkout・同じ統合元 OID の別 ref・初回の直前の統合先の更新
- B4: 2 件目が失敗・`unknown`（停止確認済みと未確認の両方）・保存の失敗・後片付けの失敗 → 3 件目以降は始まらない
- B5・B11: 一括が 1 件ずつと同じ記録・ロック・通知を作る。画面の間の破棄・記録の置換・別の承認で、古い表示を承認しない
- B6: 非 TUI・モデルの実行中・無効（キルスイッチ）では出ない・断る
- B7: 9 件目以降・計画できない項目・依存の順（同一 OID・循環）
- B8: 先頭が「ここで終える」・連続の Enter と全文ビューアを閉じた直後の Enter で承認されない
- B9: モデルの起床の遅延（`tellModel` を並べるだけでなく、idle の状態を変える）。子の完了通知の割り込み
- B10: 選択中・全文表示中・項目の間・merge／commit／後片付けの最中・reload 中の取消。Esc の後に巡回が再開しない
- 変異試験: B2 の照合・B3 の連鎖と識別・B4 の停止・B8 の初期選択・B9 の遅延・B10 の取消を、1 つずつ外して落ちることを確かめる

## 9. 却下・避けること

- 時間切れでの自動の一括実行。モデルによる一括の開始。承認の画面を省略して、件名だけで承認すること。**長いときに、承認に必要な事実を省略すること**
- 並列の実行（排他ロックを複数にすること）。失敗しても続ける設計。一括のための新しい実行経路
- 「全部承認」の 1 タップ。承認を先頭の選択にして、直前の入力の勢いで承認させること
- ファイル名の集合の包含だけで、実行を許すこと

## 10. 独立 review の反映

別系統の `review`（BLOCKER 2・MAJOR 5・MINOR 4。静的な審査）。**実物のコードで確かめて、主要な指摘は妥当だった**（停止確認済みの `unknown` の扱い・`triggerTurn: true`・計画の `files`/`risks` の上限と画面の省略・初期選択が先頭）。反映した点:

- B2 を「ファイル名の集合」から「承認前に計算した実行順の残差（tree）」へ。hook の変更を、残件の承認の失効にした
- B3 に対象の識別（ref・worktree・common-dir・設定）と、初回・以降の基点を足した
- B4 の `unknown` の記述を、現状（`unconfirmed` だけがロックを残す）に合わせ、一括では停止確認済みでも続けないと定めた
- B8（初期選択）・B9（通知でモデルを起こさない）・B10（取消）・B11（不変の snapshot と構造化した結果）を足した
- 段 1 を条件つきで先行、段 2 は再設計・再審査のあとにし、巡回の後の再評価を段階計画に入れた
- 未確認: `review` は試験を実行していない（静的な審査）。実機の操作感・実 git での積み重ねの再現・実行時間は未確認

### 10.1 段 1（巡回）の実装の review（2026-11-01）

別系統の `review`（BLOCKER 0・MAJOR 2・MINOR 5。静的な審査）。実物のコードで確かめて、**どれも妥当**だった。「見ずに承認される経路」は見つからなかった。

| 指摘 | 対応 |
| --- | --- |
| MAJOR B10: 実行中の取消が実際の入力と繋がっていない（`abortAll` は終了時だけ） | 実行中の Esc を `onTerminalInput` で検知し、**実行は止めず**、その件の後で巡回を止める（統合の途中で止めるほうが危険）。全文表示中の Esc は「全文を閉じて同じ画面に戻る」（先頭は「ここで終える」なので安全）として文書に明記 |
| MAJOR B11: スナップショットの凍結が浅い | 計画と記録を、複製して**深く固定**。複製できない形は画面の前に断る。実アダプターの計画（`IntegratePlan`）は純粋なデータで、計画を書き換える箇所は無いことを確かめた |
| MINOR: 通知の例外が、保存済みの結果を unknown に読み替える | 通知は補助。失敗しても、記録した結果を変えない |
| MINOR: 結果の記録の識別が、構造化した結果に無い | `doneOid` を返す（保存できなかったときは無い） |
| MINOR: フッター更新の例外が、巡回と通知の出力を妨げる | フッター更新は補助。例外を握りつぶす |
| MINOR: ロック解放の失敗を「再現困難」で未試験にしている（「次の件のロック取得で断られる」は B4 の代替にならない） | 排他の fake と、ロックを別の値にして解放を失敗させる試験を足した |
| MINOR: 終了中の通知でモデルを起こす可能性 | **未対応**。終了中の起床の競合は実機での確認が要る（推測で抑制しない） |

実機の見え方・複数の pi の同時巡回・終了時の通知の競合は未確認。
