# CHG-0019: OpenCode のハーネスを pi で作り直す価値があるかを判断する

- **状態**: In progress
- **更新日**: 2026-10-08
- **基準**: pi v1.1.0（`~/.pi/agent/install/releases/1.1.0`）、OpenCode v2.0.22、コミット d6ea76f、WSL2 (Ubuntu)

## 目的と非目的

このリポジトリが OpenCode のために持っているハーネスを、pi（earendil-works/pi）の上で作り直すと、
**複雑なロジックが減って保守しやすくなるか**を判断する。ハーネスとは、permission の生成、
guide plugin、checkpoint plugin、子エージェント、`ocs`（OpenCode を Fence で囲って起動する
ランチャー。[仕様](../spec/opencode-sandbox.md)）を指す。

判断の前提（利用者の指定、2026-10-08）:

- **実装の量と作り直しの費用は問わない。** コードは AI が書くものとする
- **いちばん重く見るのは、複雑なロジックが要るかどうかと、保守のしやすさ**

受入条件（移行する価値があると判断する条件）:

- 今の OpenCode のハーネスが守っているものを、pi でも下げずに守れる（「評価基準」の必須条件）
- 守るためのロジックが、上流の挙動を実測して追いかける形ではなく、自分のコードと単体テストで
  確かめられる形になる
- 比べる相手は、今の OpenCode だけでなく、CHG-0018 を終えた後の OpenCode も含める

非目的:

- 利便性の軸での pi / oh-my-pi の評価（[CHG-0006](0006-pi-harness-trial.md) が持つ）
- 移行の実施。この案件は判断までで、移行するなら別の案件を起こす
- Claude Code / Copilot CLI の設定を変えること

**移行しても、pi の内部の挙動に頼る点が 4 つ残る。** どれも pi の公開の約束ではなく、版が変われば
変わりうる。上流を追う作業は消えず、小さくなるだけである。ただし 4 つとも、偽のモデルの試験で
変化を検出できる。

1. `/reload` は、直前に有効だったツールを名前で有効にし直す。ハーネスのツールを別名にして、
   ハーネスが抜けたら無くなるようにしている（E1）
2. 圧縮の直前のイベントの `preparation` が、そのまま既定の要約に渡る。別名のツールのファイルの操作を

3. bash の `details.truncation.content` に生の出力が入る。`details` も伏せている（E3）
4. 設定と認証を読むときにも agent 置き場に `.lock` を `mkdir` する。境界では agent 置き場を書けるようにし、
   守るものを個別に塞ぐ（E4）

- 実際のモデルで長い作業をしたときの使い勝手、skill が `bash` / `read` を名指しする箇所
- checkpoint を `session_before_compact` で作り直すこと（E2 で圧縮のイベントに手を入れられることは確かめた）
- 確認画面の説明（今の `ask_description`）・`git commit` の件名と本文の表示・`/fleet`・キーバインド・Orca・Windows

### 見立て（2026-10-08、段 3 の後）

**段 3 の試作で、候補 C2 は BLOCKER の 3 件を構造で塞げた。ただし「ツールを組み込みに無い名前で
登録する」ことが条件になる**（[試作の記録](../research/agents/pi-harness-spike.md)）。

- 組み込みと同じ名前（`bash` / `read`）で登録すると、`/reload` でハーネスが抜けたときに
  組み込みのツールが同じ名前で戻り、判定なしで実行した。`-nbt` でも防げない。別名
  （`guarded_bash` など）ならツールが 0 個になる
- 判定の後の入力の書き換えは、`execute()` の中で判定し直すことで拒否できた
- 判定器の異常（空・不正な JSON・異常終了・タイムアウト・形の違う出力）はすべて拒否になった

これで C2 を見送る理由は無くなった。移行の価値は、段 4 で残りの自前の部分（確認を 1 件ずつ
出す仕組み・子プロセス・伏字化の経路・Fence）が自分のコードと単体テストで収まるかで決まる。
別名にしたことで新しく確かめることも出た（「未解決点」）。

### 見立て（2026-10-08、段 2 の後）

**移行の価値は条件付きである。** 条件は、段 3 の試作で「ツールを自分で持つ構成」
（「候補比較」の C2。組み込みのツールを無効にし、自分の拡張だけがツールを登録する起動）が
BLOCKER の 3 件を構造で塞げると確かめられること。
塞げなければ、pi では permission の実行基盤（確認の順番待ち・入力の再検査・読み込み失敗時の停止）を
自前で持つことになり、OpenCode より単純とは言えない。

価値の中身は「コードが短くなる」ことではない。**保守の仕方が変わる**ことにある。

- 今の OpenCode のハーネスは、上流の挙動を実測して追いかける形で保守している。
  `docs/research/opencode/` の調査記録の多くは、後勝ちの連結・plugin の登録先・
  `parentID` の取り方・variant の扱いといった上流の挙動の実測で、上流が変わるたびに測り直しになる
- pi では、判定もツールの実行も自分のコードの中にある。挙動は単体テストで固定でき、
  上流への依存は拡張 API（`tool_call` / `registerTool` / `session_before_compact`）に絞られる

一方で、CHG-0018（共通の禁止を policy にし、allow / ask を役割ごとに分ける）の試作は、
OpenCode の最大の複雑さの源（後勝ちの連結）をかなり減らしている。14 エージェント中 9 つで
判定が全件一致し、`explore` の補修も外せた（[CHG-0018](0018-opencode-policy-role-split.md) の段 2）。
**pi への移行の価値は、CHG-0018 の後に残る複雑さとの比較で決まる。**

### OpenCode のハーネスの複雑さの源

1. **規則が後勝ちで、4 段に連結される。** 「基底 → 組み込みエージェントの方針 → 全体の規則 →
   エージェントの規則」の順で、最後に一致したものが勝つ。allow → ask → deny の並べ替え、
   `restate_global_deny`（全体の deny をエージェント側へ写し直す）、deny の例外と ask の交差
   （`wildcard_intersection`）、CHG-0017 / CHG-0018 はここから来る
2. **規則の表現力が足りない。** glob に `**` が無い。`grep` / `glob` ツールに read の deny が効かない。
   webfetch の resource は URL 全体
3. **plugin の置き場と寿命が分かれている。** サーバ側と TUI 側で登録先が違う（`opencode.json` /
   `cli.json`）。Orca では `cli.json` が読まれない。常駐サービスの再起動とポートの衝突。
   plugin の読み込みに失敗すると plugin 無しで続く
4. **エージェントの関係を後から推測している。** bypass の子かどうかを `parentID` で親を引いて
   判定し、一覧が 4 つある（[bypass から呼べる子エージェント](../spec/agent-config-generation.md#bypass-から呼べる子エージェント)）
5. **プロジェクトの設定がグローバルに勝ち、`.opencode/plugins/` は自動で読まれる。**
   `ocs` でプロセスごと囲う理由の 1 つ
6. **保存した承認の DB、variant の癖、圧縮の hook の印の状態管理**

### pi での対応（段 1 の見立てを段 2 のレビューで直したもの）

| 今のもの | pi では | 評価 |
| --- | --- | --- |
| 後勝ちの規則の生成と CHG-0017 / 0018 | `tool_call` で判定する。最初の `block` で確定し、後続は解除できない（`dist/core/extensions/runner.js` の `emitToolCall`） | **規則の順番の問題は消えるが、変換・判定・実行の順番の問題に移る**。許可した後に別の handler が `event.input` を書き換えても再検査されない（Astra の指摘 2） |
| `explore` / `plan` の組み込み制限の上書き | pi に組み込みエージェントは無い | **消える**。ただし役割の権限設計は自前になる。`--tools` は権限の一覧ではなく、MCP・codemode からは届く（指摘 6） |
| bypass の 4 つの一覧 | 子は自前で起動する pi のプロセスで、親のモードを明示的に渡せる | 単純化するが、**今と同じ仕様ではない**。親の今のモードではなく起動時のモードで決まる。「子の ask は全部 allow」にすると `production.env` の確認まで消える（指摘 7） |
| 確認画面の分担（`index.js` / `tui.ts` / `cli.json` / Orca への注入） | 拡張 1 つで `ctx.ui.confirm` を出す | 分担は消えるが、**`confirm` には順番待ちが無い**。並列のツール呼び出しで確認が重なると、後の確認が先の確認を置き換える（指摘 4） |
| 常駐サービス・ポート・`service.json` | 無い。拡張は `/reload` で読み直す | **消える**。ただし `/reload` は読み込みに失敗した拡張を飛ばして動き続ける（指摘 1。下の「確かめたこと」） |
| 保存した承認と `oc-utils approvals` | 「常に許可」の仕組みが無い | **消える** |
| モデルの階層と variant の癖 | `modelThinkingLevels`、子は `--model` / `--thinking`、`enabledModels` | 単純化 |
| checkpoint plugin | `session_before_compact` で要約を差し替え、その要約が文脈に残る | **再注入用の印の管理が消える**。要約の材料の組み立て、繰り返しの圧縮、分岐の要約は残る（指摘 11） |
| 作業ツリーの外の読み取り（`external_directory`） | パスで判定するコード | 単純化。ただし cwd・`..`・symlink・未作成のパス・大小文字を、ツールのパス解決とそろえる必要がある（指摘 9） |
| `grep` / `glob` の結果フィルタ、shell 出力の伏字化 | `tool_result` で加工する | **同程度ではなく、出力の経路ごとに要る**。`tool_result` の例外は処理を止めず生の出力が残る。途中経過の出力と、長い出力の退避ファイルは加工されない（指摘 8） |
| formatter | edit / write の後に `format-file.sh` を呼ぶ | Markdown が欠ける（今の `markdownlint` 相当が無い）。編集の順番待ちの外で走るので競合しうる（指摘 12） |
| MCP | pi 1.1.0 は `mcp.json` で対応する（`docs/mcp.md`） | 単純。[CHG-0006](0006-pi-harness-trial.md) の「Pi は MCP を持たない」は古い |
| プロジェクトの設定がグローバルに勝つ問題 | project trust を承認したときだけ、プロジェクトの拡張・設定・MCP を読む | 一部が消える。ただし「ユーザの拡張で常に拒否」はできない。CLI の `--approve` が先に効き、拡張の中では最初に答えたものが決める。`sessionDir` と `AGENTS.md` は拒否しても読まれる（指摘 5）。ランチャーで `--no-approve` を固定する |

### Python の判定器の共有について

段 1 では「pi の拡張から `check_bash.py` を Claude 形式で呼べば、3 つの CLI で判定器を 1 つにできる」
としたが、**そのままでは使えない**（指摘 3）。`check_bash.py` が何も出力しないのは
「Claude の判定に任せる」という意味で、「安全なので許可」ではない。pi で allow と読むと、
今の OpenCode が未掲載のコマンドを ask にしている安全網が消える。`[bash] allow` も今の OpenCode の
allow より広い。

共有するなら、CLI に依存しない判定 API を別に用意する。

- allow / ask / deny と理由を必ず返す
- 不正な入力・タイムアウト・異常終了・不正な出力は拒否にする
- 未掲載のときの既定・役割・隔離の有無を引数で明示する
- bash 以外（ファイル操作・外部のパス・未知のツール）も網羅する

これは pi だけの利点ではない。OpenCode の plugin から同じ判定 API を呼ぶこともできる（指摘 10）。

### 確かめたこと（静的な読み、2026-10-08）

- **起動時に拡張の読み込みに失敗すると、pi は終了する。** `dist/main.js` は拡張の読み込みエラーを
  診断に入れ、エラーがあれば `process.exit(1)` する。段 1 で「fail-open の可能性」としたのは誤り
- **`/reload` は失敗した拡張を飛ばして動き続ける。** `dist/core/agent-session.js` の `reload()` は
  古い拡張の runner を無効にしてから読み直し、読み込めたものだけで新しい runner を組む。
  読み込みエラーで止める処理は無い。実機では未確認
- `tool_call` の handler の中の例外は、ツールを止める（`docs/extensions.md` の「Errors and cleanup」）

## 次の調査・実験

段 3 は完了した。試作は `scripts/pi-harness-spike/`（`run.sh` で回る。モデルは偽物で通信しない）。
段 3 で確かめたのは次の 3 つ（結果は[試作の記録](../research/agents/pi-harness-spike.md)）。

| 試験 | 合格条件 |
| --- | --- |
| `pi -nbt -ne -e <ハーネス>` で、ハーネスに構文エラーを入れて起動・`/reload` | 起動は止まる。`/reload` の後はツールが 1 つも無い |
| ハーネスの `tool_call` で許可した後に入力を書き換える（試験用に 2 つ目の拡張を `-e` で足す） | `execute()` の中の検査が書き換え後の入力を拒否する |
| 判定 API に、何も返さない・不正な JSON・異常終了・タイムアウト・未掲載のコマンドを与える | どれも allow にならない |

段 4 で試すもの（Astra の表から）:

| 優先 | 試験 | 合格条件 |

## 評価基準

**必須**（1 つでも欠ければ移行しない）:

- 今の OpenCode のハーネスの保護を下げない: 秘密ファイルの read / edit の deny、未掲載の shell の
  確認、作業ツリーの外の edit の確認、`grep` / `glob` の結果フィルタ、shell 出力の伏字化、
  bypass の子の起動制限、`ocs` の境界（ADR-0012）
- 判定とツールの実行が、拡張の読み込み失敗・入力の書き換え・判定器の異常のどれでも
  許可側へ倒れない
- 守るためのロジックを単体テストで固定でき、上流の挙動の実測に頼る箇所が今より減る

**望ましい**:

- Claude Code / Copilot CLI と判定器を共有できる
- `generate.py` の OpenCode 専用の生成（後勝ちの並べ替え・glob の変換・写し直し）が要らなくなる
- Orca・Windows でも同じ構成で動く

**採用しない基準**: 実装の量、作り直しの費用（利用者の指定）
