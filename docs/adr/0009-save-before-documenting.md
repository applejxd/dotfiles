# コンテキスト圧縮に備えて、保存と文書化を分ける

- **ステータス**: Accepted
- **日付**: 2026-09-19
- **決定者**: applejxd

## コンテキスト

長い作業セッションで context compaction が走ると、探索の経緯・決定・残作業が
失われる。当初の要望は「圧縮の直前に `docs/` を最新化し、引き継ぎ記録を作り、
圧縮の直後に再注入する」だった。

調査の結果、この形のままでは成立しないことが分かった。

**1. hook からモデルを動かせない。**

`PreCompact` は `command` / `http` / `mcp_tool` のみに対応し、`prompt` / `agent`
hook は非対応。つまり hook 自身が docs を書くことはできず、モデルに書かせる別の
入口が要る。

**2. 圧縮の直前では間に合わない経路がある。**

`Stop` はターン終了時にしか走らない。ツールを何度も呼ぶ長い 1 ターンの途中で
自動圧縮が発火すると、`Stop` が走る前に圧縮される。

**3. 圧縮の直前にまとめて書く設計は、順序が逆になっている。**

「記憶を失う前に保存する」という処理の前に、分類・索引整備という時間も判断も
要る作業が並んでいた。

**4. 保存先として使える永続領域が、両 CLI に無い。**

| | パス | 単位 |
| --- | --- | --- |
| Claude `scratchpad_dir` | `/tmp/claude-<uid>/<project>/<session>/scratchpad` | セッション |
| Copilot session-state | `~/.copilot/session-state/<id>/files/` | セッション |

どちらもセッション単位で、リポジトリ単位で永続する共有の置き場は無い。
一方 compaction はセッションを終わらせないので、**圧縮を跨ぐだけなら使い捨ての
領域で足りる**。

## 検討した選択肢

### 選択肢 1: 圧縮の直前に一括で記録する

`PreCompact` を主軸に、docs と引き継ぎ記録をまとめて更新する。

- **利点**: 発火点が 1 つで分かりやすい
- **欠点**: hook からモデルを動かせない。ターン途中の圧縮に間に合わない。
  保存が判断の要る作業に依存する

### 選択肢 2: 重要な区切りでその都度保存し、文書化は後から行う

保存を 3 相に分ける。

| | 対象 | 必須か |
| --- | --- | --- |
| A1 | 実行状態（使い捨て領域のセッション別ファイル） | 必須・即時 |
| A2 | 共有状態（`docs/change/` の案件） | 共有知識が生まれたとき |
| B | 文書化（`research/` `adr/` `spec/` 索引） | 任意 |

- **利点**: 保存が文書化に依存しない。ターン途中の圧縮にも耐える。
  失敗したときの損失が小さい
- **欠点**: 相が増えて、どこまでやったかの管理が要る

### 選択肢 3: サブエージェントに記録から復帰までを任せる

- **利点**: 親の文脈を使わない
- **欠点**: 子は返り値でしか親に介入できず、親の compaction を観測もできない。
  親のライフサイクル制御は原理的に不可能

## 決定事項

**選択肢 2 を採用する。**

理由: 目的は「記憶を失う前に保存すること」であり、分類の正しさではない。
保存を文書化から切り離せば、docs の構造に迷っても索引が壊れていても、
復帰用の記録だけは残せる。

あわせて次を決めた。

- **強制の層を 3 つに分ける。** 圧縮を跨いで生き残るのは指示ファイルだけなので、
  恒久ルールはそこに置く。手順はスキル、発火の確実性は hook が持つ
- **引き継ぎ記録を書くのは親だけ。** `fork` は分岐時点のスナップショットを継承する
  ので、親が先に進むと古い内容で上書きしてしまう。`fork` には文書化の下書きだけを
  任せ、ファイルは書かせない
- **保存先は常にセッション別の名前にする。** 固定名を奪い合わないので、ロックも
  所有権の交渉も要らない。復帰は必ず自分のファイルだけを読む
- **セッション横断の削除をしない。** 件数や日数で消すと、稼働中の別セッションの
  記録まで消える
- **鮮度はその要求の固定境界と比べる。** 「現在の会話地点」と比べると、保存や検査
  そのもので境界が進み、正しく保存しても永久に一致しない

## 決定の確認方法

- [x] 引き継ぎ記録の保存が、docs の整合検査の成否に依存しないこと
- [x] 古い記録（境界 `msg-42`）に新しい要求（`msg-99`）を与えると検査が落ちること
- [x] 繰り返し保存しても、別セッションのファイルが変化しないこと
- [ ] 圧縮の直後、作業を再開する前に記録が届くこと（実機で未確認）

## 結果

### ポジティブな結果

- 保存が即時に完了するので、圧縮のタイミングに左右されない
- 保存先を分離したことで、同一 worktree で複数セッションが動いても干渉しない
- 所有権の交渉を捨てたぶん、実装が単純になった

### ネガティブな結果

- 相が 3 つに増え、「どこまで保存したか」を表す状態が要る
- 共有知識が案件へ昇格していない状態を、記録側で示す必要がある
- Copilot の圧縮直後の注入は Claude より 1 ツール分遅れる（同じターン内には届く）

> **訂正 2026-09-20**: 当初ここには「Copilot では圧縮直後の自動注入ができず、
> best-effort に留まる」と書いていたが、誤りだった。`postToolUse` が
> `additionalContext` を返せるため、`PreCompact` が印を置けば自動注入は成立する。
> 詳細は [compaction-hooks.md 記録 E7](../research/agents/compaction-hooks.md)。

### 中立的な結果

- 引き継ぎ記録は使い捨て領域に置くため、セッションを跨ぐ知識は `docs/` 側が
  正本になる。記録はあくまで実行状態の置き場になった
