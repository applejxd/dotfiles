## 結論
**coi の上に載せる・置き換えるのは不適。kcage は継続し、coi の良い点だけを借りる。** そして coi の調査から、**kcage 自身の欠陥**（`mv .git` による ro の迂回）が見つかった（下記）。

## coi が kcage の要件を満たさない点（ソースで確認）
| 要件 | coi |
| --- | --- |
| 制御面の分離（利用者を incus-admin に入れない） | **逆**。install.sh が incus-admin に入れ、`NOPASSWD: nft` の sudoers も入れる（引数制限なし） |
| GPU（/dev/dxg・libcuda・入れ子の Docker の GPU） | **無い**（`gpu|nvidia|dxg|cuda` が 0 件。コミュニティの skill に「0.15.0 で GPU」とあるが本体の実装は確認できず） |
| proxy-only（NIC なし）・offline | **無い**（open / restricted / allowlist の nft のみ。NIC は既定の incusbr0） |
| WSL2 | コード・文書に言及なし（wiki は「experimental・未試験」） |
| pi をフルガードの拡張つきで起動 | **旗を渡せない**（`pi`/`pi --continue` だけ。`[tool] binary` を箱の中のラッパーにすれば回避可）。`~/.pi/agent` は settings・models・**auth.json**・AGENTS.md の 4 つを複製（extensions は複製しない） |
| 認証の broker（箱にトークンを入れない） | 無い。ツールの認証ファイルを箱へコピー（`[[sockets]]` で proxy デバイスを足せる） |
| 許可表（root 所有）＋要求ファイル（締める方向だけ） | 「信頼しない設定」を禁止項目の**列挙**で削る方式。`mode=restricted` の緩和など、allowlist を緩められる可能性がコードから読める（未実行） |
| 規模・保守 | Go 56k 行（kcage Python 6.4k）。**bus factor 実質 1**（上位 1 人が 91%）。0.x で破壊的変更が毎リリース。SECURITY.md・CONTRIBUTING なし。ただし活発（月 60〜320 commits・実 Incus の CI 23 レーン・セキュリティ修正が 0.15 以降も継続） |

## coi から借りる価値のある点
1. **親ディレクトリの pin**（`.git` を自分自身へ bind）。→ kcage の欠陥の修正（下記・#217）。
2. **保護パスの拡張**: `.pi` は coi にも無いが、**ホストの AI ツール・git が自動で読む設定**を ro にする。coi の既定: `.git/hooks`・`.git/config`・`.git/config.worktree`・`.git/info/attributes`・`.husky`・`.vscode`・`.coi`・`.claude/settings{,.local}.json`・`.codex/config.toml`（無いものは空の placeholder で塞ぐ）。kcage は `.git` の 3 つだけ。追加の候補: `.pi/`・`.claude/settings*.json`・`.codex/config.toml`・`.vscode/`・`.husky/`・`.envrc`・`.mcp.json`・`.pre-commit-config.yaml`。
3. submodule（`.git/modules/**`）と入れ子の git（深さ 3）の hooks・config・config.worktree・info/attributes の ro。
4. NIC の防御（`ipv4_filtering`・`mac_filtering`・`port_isolation`）・`security.guestapi=false`・`security.idmap.isolated`・`security.syscalls.deny`（io_uring・bpf・userfaultfd・keyctl。docker を使わない箱向け opt-in）・`max_duration`・停止→起動で NIC が作り直されたときの隔離の再適用（veth 再生成で IPv6 の遮断が外れた問題。kcage の NIC なしモードには関係しないが、nat には要確認）。
5. ブランチガード（reference-transaction の hook）は事故防止で、coi 自身が `--no-verify` などで回避できると述べている。優先度は低い（kcage はフルガードがある）。

## kcage の欠陥（coi の調査で発覚。#217 で修正中）
- **`.git` 自体がマウントポイントでない**ため、箱の一般ユーザーが `mv .git .git.old` → `.git` を作り直して、ro の重ねを外せる（ホストの git が箱の書いた config/hooks を読み、脱出）。bwrap で再現（`.tmp/keep/box-verify/mv-git-test.sh`）、pin で EBUSY を確認（`mv-git-test2.sh`）。
- **推測（未検証）**: 箱の `ubuntu` は docker グループで、入れ子の Docker により箱の root 相当になれる。root 相当は自分のマウント名前空間で ro・pin を `umount` できる可能性がある（coi も bind の ro は root で外せると述べ、ホスト側の `chattr +i` を併用）。実機で確かめる。方針の候補: (a) kcage-root が `up` で `.git/config` 等へ `chattr +i`（ホストの `git config`・`git flow` は箱を止めて解除が要る）、(b) rootless Docker（大きな設計変更）、(c) 許容して記録（フルガードと同じ「うっかり防止」）。

## 実機での評価
今は行わない（主ディストロに kcage があり、coi の `health --fix` が nft・sudoers を書く／同じ WSL の別ディストロは共有ネットワークで衝突）。必要になれば、あなたのネイティブ機（CHG-0064 N2）か、kcage を外した状態で。
