# CHG-0013: commit エージェントを計画役にし、コミットは親が行う

- **状態**: In progress
- **更新日**: 2026-10-06
- **基準**: `d74d6b7`

## 目的と非目的

**目的**: OpenCode でコミットを任せたとき、利用者がメッセージの全文を切れずに読める状態で、
コミット前の承認を 1 回にする。差分を読む重い作業は、引き続き子エージェントに任せる。

これまでの `commit` エージェントは、子がステージとコミットまで行い、`git commit` の確認画面を
承認の場にしていた。次の問題があった。

- 確認画面ではメッセージが長いと途中で切れる。仕様は「親が任せる前に全文を見せて承認を得る」と
  定めていたが、全文を作るには差分を読む必要があり、「差分を読む作業を子に移す」狙いと矛盾した。
  実際に 2026-10-05〜06 のセッションでは、親がこの手順を飛ばしていた
- 子からは確認画面が見えず、承認の有無を推測させない指示が要った
- pre-commit の lint で失敗すると、子はファイルを直せず止まり、親が直して再依頼する往復が生じた

**非目的**:

- Claude Code / Copilot CLI のコミットの流れ（`commit` エージェントは OpenCode 専用。スキルの
  既定の「提示して承認を得る」は変えない）
- 同じファイルの中をハンク単位で分けるコミット（親が対話なしに扱えない。単位をまとめて扱う）

## 現在地

新しい流れ（2026-10-06 に利用者と合意）:

- **子（`commit`。読むだけ）**: commit スキルに従って `git status` / `git diff` / `git log` で変更を読み、
  ファイル単位で論理単位に分け、単位ごとに「対象のパス」と「メッセージの全文」を返す。ステージも
  コミットもしない。同じファイルの中を分ける必要があれば、単位をまとめるか、その旨を書く
- **親**: 子の計画（単位の一覧とメッセージの全文）をそのまま返答に表示する（プレビュー。利用者の
  操作は求めない）。単位ごとに `git status` で計画外の変更が混ざっていないかを確かめ、
  `git add -- <パス>` → `git commit -m '<件名>' -m '<本文>'` を実行する。**承認は `git commit` の
  確認画面の 1 回だけ**。拒否されたら以降の単位はコミットしない。pre-commit で失敗したら親が直して
  やり直す。最後に `git status --short` が空であることを確かめる。push はしない
- **起動の仕方による違い**: 通常起動は `git commit` の確認が出る。bypass は確認なしで通る（利用者が
  確認を省くと選んだ起動）。隔離起動も確認が出る（段 2。利用者の選択）

## 未解決点

- 親が「`git commit` の確認を承認の場にしてよい」と知る手段は、`commit` エージェントの説明
  （親から見える）と、スキルの手順 4 の上書き規定に頼る。親のモデルがこれに従うかは段 5 で確かめる
- guide 規則による `git -c … commit` の誘導は、コミットメッセージの中に同じ形の文字列があると誤って
  止める（`git commit -m "x; git -c a commit"` など）。実害が出たら除外条件を足す
- モデルの見直し（`docs/spec/model-lineup-review.md`）の `routine` の課題は、子がコミットまで行う
  旧方式を前提に採点している。次の見直しの前に作り直す（仕様に注記済み）

## 評価基準

- 必須: 子はステージもコミットもできない（権限で塞ぐ）
- 必須: 通常起動と隔離起動で、親の `git commit` に確認が出る
- 必須: 隔離起動で `git -c … commit` が確認なしに通らない
- 望ましい: 利用者がメッセージ全文を、確認画面より前に親の返答で読める

## 実装・検証
