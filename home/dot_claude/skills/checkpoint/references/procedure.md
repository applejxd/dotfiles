# A2 / B の手順

A1（実行状態の保存）を終えた**後**に読む。A1 はセッション内で失う文脈を守るもの、
ここから先はセッションを跨いで残す知識を `docs/` へ移す作業。

> **先に A1 を終える。** ここは判断が要るので、圧縮に間に合わなくなる。
> [ADR-0009](../../../docs/adr/0009-save-before-documenting.md) の分離はそのため。

| 相 | 対象 | いつ |
| --- | --- | --- |
| A2 | `docs/change/` の案件 | 共有すべき知識が生まれたとき |
| B | `docs/research/` `docs/adr/` `docs/spec/` と索引 | 任意。落ち着いたとき |

**頼まれたことだけをやる。** 「checkpoint して」は A1 だけ。A2 / B は
「案件を更新して」「docs に反映して」と言われたとき、または自分で
区切りと判断したときに行う。

## 共通の原則

- **最初に一致した行き先で打ち切らない。** 1 つの実験結果が、`research/` の証拠と
  案件の比較表の両方に要ることは多い
- **未検証を不合格扱いしない。** 逆に、期待を確認済み扱いしない。
  どちらも後から「調べたはず」と誤読される
- **読み取り専用の作業中は書かない。** レビューや「現状を教えて」で docs を
  書き換えない

## A2: 案件（`docs/change/`）の更新

案件は**現在の総合判断の正本**。ここを読めば今どこにいるか分かる状態を保つ。

1. 該当する案件を探す。無ければ `references/change-template.md` で起こし、
   `docs/change/index.md` へ掲載する
2. **候補比較表**を更新する。新しい根拠・反証・未検証点を該当行へ入れる。
   扱い（有望 / 保留 / 見送り）が変わったら、変わった理由も書く
3. **「現在地」**を書き換える。分かったこと / まだ分からないことを最新にする
4. 決定や方針が変わったら**「重要な更新」**へ 1 行足す（日付・変更・理由）
5. 実測したら**「実装・検証」**へ、コマンドと結果を書く

**見送りを消さない。** 「なぜ採らなかったか」が残っていないと、同じ検討を
やり直すことになる。

## B: 文書化

### `docs/research/` — 実測の記録

- **1 記録 = 1 回の調査。** 観測日と一次情報の URL を必ず書く
- 雛形は `references/research-template.md`
- **過去の節を書き換えない・消さない。** 訂正は**新しい記録**として追加し、
  どの記録のどこを訂正したのかを明記する
- 実行したコマンドと出力を載せる。推測は「推測」と明示する
- 陳腐化しても消さない。「いつ時点か」が分かれば価値がある

### `docs/adr/` — 設計判断

手順は SKILL.md の「ADR の作成・更新」にある。`docs/adr/` 以外に書かない。

### `docs/spec/` — 現行の仕様・運用

- **今どうなっているか**を書く。歴史的経緯は `research/` と案件が持つ
- ただし**現在の運用に必要な判断基準・理由は書いてよい**。
  「なぜこうするのか」が無いと、読み手が善意で壊す
- **意図した契約と実装が食い違っていたら、食い違いとして記録する。**
  どちらかに寄せて書かない

### 索引

- 文書を足したら、**その category の `index.md` と `docs/index.md`** を更新する
- 索引の検査（`scripts/lint_docs.py`）が未掲載を落とす

## 仕上げ

```bash
mise exec -- python3 scripts/lint_docs.py
uv run pre-commit run --all-files
```

どちらも出力を根拠として示す。実行していないチェックの結果を書かない。

## やってはいけないこと

- `research/` の過去の節を書き換える・消す
- 終了した案件を削除する
- 未検証を不合格として書く／期待を確認済みとして書く
- 子エージェントに `docs/` を書かせる（親が確認して書く）
- A1 を終える前にここへ着手する
