# OpenCode の `/fleet` の作業役（`fleet-worker`）への指示を足した前後の計測

<!-- 現在の総合判断は docs/change/ の候補比較表が正本。
     ここは「いつ何を観測したか」を積む場所 -->

> **現行の仕様**: [並列作業（/fleet）](../../spec/agent-config-generation.md#並列作業fleet)

## 結論

- `fleet-worker` の `system` に「変えた関数の呼び出し元を探して、壊れる所や誤りを前提にした所が
  無いか確かめ、報告に書く」を足すと、`bugfix` の罠（担当外の `cli.py` が `paginate` の誤りを
  打ち消している）に触れた報告が **0/2 → 2/2** になった（`claude-sonnet-5.5#medium`）。
  `claude-opus-5.5#medium` でも 1/1。3 回とも `cli.py` の該当行・ずれ方・必要な直し方まで書き、
  `cli.py` は編集しなかった。同じ日に足す前の版で測り直した対照は 0/2 のままだった
- 合格率（sonnet 14/14、opus 7/7）・担当外の編集（0 回）は変わらなかった
- 誘導（`cat` / ヒアドキュメント / `cd` を拒んで道具を案内する）は 14 回 → 1 回、確認のうち
  `pytest` 以外は 4 回 → 1 回に減った。確認の合計は 19 回 → 18 回でほぼ変わらない。
  確認の大半は依頼文の確認方法の `pytest` で、指示では減らせない
- 作業ツリーの外への書き込みと、一時ファイルの残りは 0 回だった。opus の `refactor` は、
  前の計測では元の実装を作業ツリーの外へ書き出して比べた（2 回とも）が、今回は `python -c` の
  中で `git show HEAD:…` を読み込んで比べ、ファイルを作らなかった（1 回）
- 所要時間は sonnet で変わらない（中央値 21 s → 20 s / 48 s → 43 s）。opus は難しめの課題と
  `multi` で長くなった（1 回ずつなので、混み具合の差と区別できない）

## 記録 E1 — 2026-09-30

- **対象バージョン**: opencode v2.0.14
- **環境**: WSL2 Ubuntu / 基準コミット `0cdf263` の作業ツリーで `common.toml.tmpl` の
  `[opencode.agents.fleet-worker]` の `system` と `[opencode.commands.fleet]` の手順 5 を変えたもの

### 問い

`fleet-worker` の `system` に次を足すと、前の計測
（[階層に当てるモデルと effort の計測](tier-models.md)）で見えた弱点は減るか。質と速さを落とさないか。

- 変えた関数・振る舞いの呼び出し元への影響を確かめて報告する（前の計測では 14 回中 0 回）
- 確かめ用・比較用のファイルを作らない。要るなら作業ツリーの `.tmp/` の下に作って消す。
  作業ツリーの外へ書かない（前の計測では haiku が直下に残し、opus が外へ書いた）
- 読み書きは道具で行い、確認方法のコマンドは渡された形のまま単独で実行する（確認と誘導を減らす）

### 事前の予想

- 罠への言及は増えるが、呼び出し元を探す分だけ手数と時間が少し増える
- 外への書き込みと一時ファイルの残りは減る
- 確認は、`pytest` が allow に無いので、ほとんど減らない。誘導は減る

### 方法・条件

- 仕組みは前の計測の worker の条件と同じ（課題 7 種類・隠しテスト・採点・隔離・計装・親から
  依頼文をそのまま渡す形。置き場は `.tmp/opencode/fleet/`。課題・作業リポジトリの元・venv は
  `.tmp/opencode/tiers/` のものをそのまま使った）。`session.synthetic` は使っていない
- 設定は作業ツリーの `common.toml` から生成し、`fleet-worker` の `model` だけ差し替えた。
  足す前の版から生成した設定は、plugin と skills の置き場のパスを除いて、前の計測の
  `sonnet medium` の設定と一致した（`diff` で確認）。足した後の版との差は `system` と
  `/fleet` の template だけ
- 組:

  | 組 | モデル | `system` | 回数 |
  | --- | --- | --- | --- |
  | 前（E1 の値） | `claude-sonnet-5.5#medium` | 足す前 | 7 課題 × 2（前の計測の `sonnet medium` をそのまま使う） |
  | 後 | `claude-sonnet-5.5#medium` | 足した後 | 7 課題 × 2 |
  | 対照 | `claude-sonnet-5.5#medium` | 足す前 | `bugfix` × 2（同じ日に測り直し、モデル側の変化で罠への言及が変わっていないかを見る） |
  | opus 前（E1 の値） | `claude-opus-5.5#medium` | 足す前 | 7 課題 × 1（前の計測の 1 回目。`refactor` はやり直した回） |
  | opus 後 | `claude-opus-5.5#medium` | 足した後 | 7 課題 × 1 |

- 並行は 5 本で、組と課題の順は乱数で混ぜた（後の `bugfix` 1 回目だけ、仕組みの確かめを
  兼ねて先に 1 本で走らせた）
- 数え方（`analyze.py`）:
  - 罠に触れた報告: `fleet-worker` の最後の報告に `cli.py` / `tk list` / `--page` /
    `呼び出し元` / `打ち消` などが出るか。当たった報告は全文を読んで確かめた
  - 一時ファイルの残り: 作業ツリーの未追跡のファイルのうち担当外のもの
  - 作業ツリーの外への書き込み: `write` / `edit` の対象と、shell のリダイレクトの先が作業ツリーの外か。
    実行ごとの `TMPDIR` に opencode 自身のもの以外が残っていないかも見た
  - 確認・誘導・所要時間・手数は前の計測と同じ

```console
uv run -q --no-project --with pytest --with pyyaml python gen.py after fleet-worker 'github-copilot/claude-sonnet-5.5#medium'
xargs -P 5 -L 1 bash run_worker.sh < jobs.txt     # 22 本。10:56〜11:00
python3 analyze.py "before(E1)=…/tiers/runs/ws-medium-*" "after=runs/after-[bfmrsti][a-z]*-[0-9]" \
  "before-ctl=runs/before-*" "opus-before(E1)=…/tiers/runs/wo-medium-*-1" "opus-after=runs/after-opus-*"
```

- **罠**: 後の 3 回（sonnet 2・opus 1）とも、`paginate` の呼び出し元を探して `cli.py` を読み、
  報告の「呼び出し元への影響」に `cli.py` 35 行目の `paginate(items, args.page - 1, …)` が誤りを
  打ち消していること、直した後は `--page 2` で 1 ページ目が出ること、必要な直し方を書いた。
  opus は、直すと `--page 0` 以下が ValueError になる振る舞いの変化も判断が要る点として挙げた。
  3 回とも `cli.py` は編集していない。前と対照の 4 回は、`cli.py` を読んでいない
- 罠の無い課題でも「呼び出し元への影響」の項目は必ず書かれた。新しいファイルやテストの追加では
  「影響なし」の 1 行で、`refactor` の sonnet 2 回は「探していない（名前・引数・出力を変えて
  いないので影響は無いと見た）」と書いた
- **確認**: `pytest` 以外の確認は、前の 4 回（`ls; ls src/tk tests; head …` の連結した読み取り）が
  後は 1 回（`printf … >> src/tk/durations.py` で追記した。指示に反する）になった。`pytest` の
  確認が 15 回 → 17 回に増えたのは、難しめの課題で 2 回走らせた実行が増えたため。確認方法の
  形は、前は 15 回とも `2>&1 | tail -N` を付け、`multi` の 2 回はテストの追記（`printf … >>`）と
  1 つのコマンドにつないでいた。後は 17 回とも依頼文のまま単独だった
- **誘導**: 前の 14 回はヒアドキュメントでのファイル作成 7 回・`cd` 3 回・`cat` / `head` 4 回。
  後はヒアドキュメント 1 回（`refactor` の 1 回で `python3 - <<'E'` を使い、`write` へ案内された）
- **opus**: `refactor` は `.venv/bin/python -c` の中で `git show HEAD:src/tk/report.py` を読み込み、
  新旧の出力を乱数の入力で比べた（確認 1 回。ファイルは作らない）。難しめの課題 2 回は、最初に
  `git status --short; git ls-files | head -50` を実行した（確認 1 回ずつ）

### 考察

- 呼び出し元への影響は、effort でもモデルでも補えなかった（前の計測で 14 回中 0 回）が、
  `system` の指示と報告の項目で拾えるようになった。回数は少ない（3 回）が、対照が同じ日に 0/2 の
  ままなので、モデル側の変化ではなく指示の効果と見てよい（推測。回数が少ない）
- 一時ファイルと外への書き込みは、前の sonnet medium でももともと 0 回で、差は見えない。
  opus の 1 回は外へ書かずに比べたが、1 回なので効果とまでは言えない。haiku（前の計測で直下に
  残した）では試していない
- 誘導は大きく減り、手数と出力トークンも少し減った。ヒアドキュメントで作ったファイルを
  誘導が拒み、`write` でやり直す往復が無くなったため（推測）
- 確認の合計は減らない。確認方法を単独の形にそろえても、`pytest` は allow に無いので 1 回ごとに
  確認が出る。減らすには権限を変える必要があり、この変更の範囲の外（次の問い）
- `/fleet` の template では、手順 5 で取りまとめ役が「呼び出し元への影響」の報告を受けて作業を
  切り直すよう足した。依頼文の項目に「呼び出し元」「一時ファイル」を足すことはしなかった。作業役の
  `system` が常に指示するので、取りまとめ役が書き忘れても効く。この変更は、依頼文を固定した
  今回の計測では確かめていない

### 次の問い

- 確認の大半を占める確認方法（`pytest` など）の確認を減らすか。案（どれも未実施・未計測）:
  - `fleet-worker` の `permissions` にだけ、依頼文の確認方法の形（例 `.venv/bin/python -m pytest -q`）を
    allow として足す。任意コード実行になる点は全体の allow と同じで、作業役の範囲に限るだけ
  - 取りまとめ役が作業役に確認方法を実行させず、波の終わりに自分で 1 回だけ実行する
    （作業役の確かめが弱くなる）
- haiku（Bedrock の今の worker）で、直下に残す一時ファイルが減るか。未確認
- TUI の `/fleet` で、取りまとめ役が「呼び出し元への影響」の報告を受けて作業を切り直すか。未確認
