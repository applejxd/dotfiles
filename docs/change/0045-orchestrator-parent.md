# CHG-0045: 親をオーケストレーターに寄せる（実作業は子へ、親は対話・判断・委譲・承認）

- **状態**: Exploring
- **更新日**: 2026-10-28
- **基準**: コミット 6c7822b 以降、pi 1.4.0

## 目的と非目的

**目的**: 親エージェントを、**利用者との対話・判断・委譲・承認・ToDo の管理**に専念させ、調査・計画・実装・検証などの実作業は、子（`guarded_task`）へ任せる設計にする。
親の文脈を、重い読み物・実行の出力・ログで占めないことと、親のモデルを既定のまま保つことが狙い。今後のオーケストレーター設計（保留中の orchestrator ロール・待ち合わせ・DAG・予算。[調査 O1](../research/agents/pi-orchestrator-survey.md)）の**前段**に当たる。

- スキルは、**工程**に分け、各工程の担当（親の判断・子の成果物・実行する役割・次へ進む条件）を決める。対話の工程は親、実行の工程は子（自己完結の依頼文で渡す）
- 子が確認なしで動けるように、子の権限（実効の許可）と、質問・承認の経路を整える。**境界は弱めない**（下の不変条件）
- 親の道具を絞る（作業のツールを持たせない）かどうかは、実測で決める

**不変条件**（どの案でも守る）: 共通の deny、役割のツールの制限、明示の ask、`mustConfirm`（bypass でも確認が要る操作）、OS の境界（サンドボックス）。委譲のために、これらを緩めない。

**非目的**:

- 利用者との対話そのもの（質問・承認・設計の詰め）を子に任せること。対話は親に残る
- 子から子を作る入れ子（今の基盤は不可。指揮役の工程は親に残る）
- 公開の子エージェント拡張の導入（[ADR-0016](../adr/0016-pi-extensions-own-first.md)。自作を優先する）
- 「実行はすべて子」という純粋な分離。**承認に結び付いた限定操作**（`git commit`・GitHub への書き込み）は、子に実行する役割が無いので、親側のハーネスが実行する例外にする（下の「実行主体の問題」）

## 現在地

- **利用者の方針**（2026-10-28）: 親で、あまりいろいろな作業をする設計にするのをやめたい。今後のオーケストレーション設計の前段にする
- **今の子の基盤**（[pi の子エージェント](../spec/guard/pi-subagents.md)）: 役割は `explore`・`review`・`plan`・`commit`・`worker`。並列は 4 本、1 往復の上限は役割ごと（既定 15 分、`plan` は 30 分）、背景の完了は通知で受ける。結果は要約で返る
- **スキルの調査**（2026-10-28。全 20 スキルを子 4 本が読み、親が確かめた。[記録 F3](../research/agents/skill-fork-enforcement.md#記録-f3--2026-10-28スキルごとの-fork-と-allowed-tools-の調査)）: `context: fork` をそのまま付けられるのは `fix` だけ。多くのスキルは対話と実行が混ざっている。指揮役のスキルは親に残る
- **`/plan` の穴は塞いだ**（[CHG-0044](0044-plan-agent.md) 段 4）。計画の間、書き込みの子の**新規起動・追加依頼・steer** は拒否される（すでに走っている子は止まらない）。この仕組み（モードごとの子の制限）は、orchestrator ロールにも使える
- **CHG-0026 の段 1c**（`context: fork` をハーネスで解釈する）は、この案件に統合した

### 子が止まる条件（判定器の順序。2026-10-28 に `decide.ts` で確認。`review` の指摘 R1-1）

| 条件 | 今の扱い |
| --- | --- |
| allow（規則・許可） | 確認なしで実行 |
| 規則に当たらず、役割の既定が ask、**かつ証明済みの境界の内側**（bash だけ） | **bypass に関係なく、確認なしで実行**（日常の shell の確認だけを外す） |
| 上以外の ask（git commit・MCP・明示の ask の規則など） | 子では承認されず blocked。bypass が引き継がれていれば allow |
| `mustConfirm`（確認が要る外部への送信・公開など） | **bypass でも確認が要る**。UI の要求を出す前に、子（`CHILD`）は拒否される |
| deny・役割に無いツール | 承認しても使えない |

**前の記述の訂正**: 「`worker` は bypass の継承でしか、linter を通せない」は誤りだった。境界が証明されていれば、bypass が無くても通る。

### 実機の予備実験: `fix` を `worker` へ委譲（2026-10-28）

親が依頼文（目的・前提・守る条件 C1〜C3・返答の形式）を作り、`worker` の子へ渡した。対象は、ruff の指摘がある小さな Python プロジェクト（`.tmp/exp_fix/proj/`）。

| 条件 | 結果 |
| --- | --- |
| この対話のとき（子が親の状態を引き継ぐ。確認の画面は出なかった。**境界・bypass の実効状態は記録していない**） | 確認で止まらず完了（13 秒・4 呼び出し）。2 件を直し、返答は標準形。`.venv` を作ったことも開示した。修正前の差分は「git 禁止のため未確認」と正直に書いた |
| 確認を出せない形（`-p`。bypass なし・境界の指定なし。実際の子と同じ引数・環境。**RPC の子とは、確認要求の扱いが違う**） | 最初の linter の実行（`uv run ruff check --fix`）で止まった。理由は `not approved: どの規則にも当たらない (役割 'worker' の既定)`。子は、ファイルを読んだだけで何も変えず、迂回せず、守る条件 C3 のとおり、親が実行すべきコマンド 3 つを返した |

読み取れること（1 回ずつの観測。条件の確定は段 2）:

- **子の「止まり方」は良い**。止まった理由と、親が実行すべきコマンドを、そのまま返した。依頼文の C3 が効いた
- 止まった原因は、linter のコマンドが `worker` の許可の規則に無く、境界も無かったこと。**境界が証明されていれば、通る**（上の表）
- 通常のモード（境界なし・bypass なし）で委譲すると、実作業は進まず、親がコマンドを実行する話に戻る
- 依頼文の形式（目的・前提・守る条件・返答の形式）は、子に守られた。型 A の依頼文の雛形として使える

### 実行主体の問題（`review` の指摘 R1-3）

承認を中継しても、**実行する役割が無い操作**がある。`commit` の子は計画だけを返し、ステージもコミットもしない。`worker`・`committer` は `git add`・`git commit` などを禁止され、`worker` に `action` は無い。
`guarded_action` は子では登録されず、実行の本体も子を拒否する。親から `bash` を外し、子の権限も維持すると、`git commit`・GitHub への書き込みを実行する者がいない。

→ **承認に結び付いた限定操作は、親側のハーネスが実行する**（子は対象・本文・検証資料を準備する）。汎用の `bash` ではなく、対象パス・状態の検査を持つ限定操作として設計する。当面は、利用者の操作に残す。

## 未解決点

- 依頼文の質（目的・前提・守る条件・対象のパス）を、型 B・C でどう保つか。`plan` 役は返答側の検査を持つ。依頼側の雛形と検査が要る
- 承認の経路（下の候補比較）の設計。承認要求は、job・往復・要求 ID に結び付け、一回限りで、期限切れ・取消し・close・bypass の変更・セッション終了のあとの応答を無効にする。利用者に見せるのは、**実行対象そのもの**（親が要約し直したものではない）。「質問への『はい』」が、操作の承認にならないこと
- 質問の中継は、まず「子が根拠・選択肢・途中結果を返し、親が利用者へ聞き、回答を付けて再依頼する」形で足りるかを測る（停止・再開の中継は、足りないと分かってから）
- 親の道具を絞ると、小さな頼みが遠回りになる。**どの大きさから委譲するか**の基準と、親が詰まったときの逃げ道（利用者専用の解除。モデルが勝手に権限を戻す経路にしない）
- 子の結果の確認: 「通った」を、別の検証の子と、実行記録で、親が照合する形（親の重複実行を減らす）
- 費用・待ち時間: 委譲の往復が増える。Copilot は費用が無制限だが、待ち時間が増える

## 評価基準

**必須**:

- 受入条件の達成（成果の正しさ）。**未実行を成功扱いしない**。範囲外の変更の検出。合意した条件の欠落の検出
- 親の文脈の増え方が、親が直接作業するより小さい
- 利用者への質問・承認は、親側が出す（子が黙って止まらない）。承認は実行対象そのものを見せ、一回限り
- 不変条件を保つ（共通の deny・役割のツール・明示の ask・`mustConfirm`・OS の境界）
- 子の起動ができないとき、停止理由を返す（親が勝手に自分で実行へ戻らない）

**記録する**: 待ち時間・利用者への質問と承認の回数・親の介入の回数・総使用量・再作業の回数

**望ましい**:

- 小さな頼みで、遠回りにならない（委譲しない基準が明確）
- 型 A・B のスキルで、依頼文の雛形が再利用できる
- 故意に誤った成功報告・失敗した検証を混ぜても、検収で止まる（別の検証の子と実行記録の照合）

## レビューの反映

`review`（`gpt-6.1-sol`）の 1 回目（2026-10-28）。BLOCKER なし、MAJOR 6、MINOR 3。

- R1-1 `worker` の停止条件に、境界による緩和が抜けていた（`decide.ts` で確認）→ 停止条件の表を追加し、前の記述を訂正。予備実験の `-p` は RPC の子と条件が違うと明記。実測は段 2
- R1-2 承認の案は「承認経路」だけでなく承認ポリシーの変更。(d) は宣言を権限の正本にすると危険 → 不変条件を具体化。(a) を非推奨、(d) を積集合に
- R1-3 承認を中継しても、`git commit` などの実行主体が無い → 「承認に結び付いた限定操作は親側のハーネスが実行する」例外を追加（段 4c）
- R1-4 中継には、質問と承認の分離・状態遷移・応答権限が要る → 質問は再依頼から、承認は親側ハーネスから利用者の画面へ直接。一回限り・期限・取消しなどを未解決点へ
- R1-5 型 D が実作業を親へ残し、割り当てが工程を覆っていない（`imozuru`・`oss-research` が抜けていた）→ 型は工程ごとの組み合わせとし、段 5 で工程表へ展開。spec の割り当ても直した
- R1-6 評価基準が、未完了を増やして文脈だけ減る設計を合格にする → 成果・範囲外の変更・未実行の扱い・合意条件の欠落などを必須に。限定試作（段 3）を先に
- MINOR: 「計画の間、書き込みの子は動かない」を、新規起動・追加依頼・steer の禁止（既存の実行は継続）に直した。`pi-decide.md` の `reader` の記述と、spec の「fork 可能性」と「便益」の混在は、直す予定
