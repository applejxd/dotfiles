# friction-review

セッションログ(`~/.pi/agent/sessions/`)を集計し、**利用者が後から指摘した点を、事前に拾える形**にする。
出力は `.tmp/friction/<日付>/` にだけ置く。**ログには勤務先の情報や秘密が入り得るので、リポジトリには、一般化した結論だけを書く**(`AGENTS.md` の「公開リポジトリ」の規則)。

## いつ使うか

- まとまった作業の区切り(案件を閉じるとき、週の終わりなど)。
- 利用者が「使いにくい」「また同じ指摘をした」と感じたとき。
- 新しい機構(ガード・ツール・指示)を足した後に、体験が悪化していないか見たいとき。

## 手順

1. **集計する**(決定的。親が実行):
   `python3 .agents/skills/friction-review/scripts/friction_scan.py --since <YYYY-MM-DD>`(最新だけなら `--session latest`)。
   → `.tmp/friction/<日付>/report.md` と `report.json`。内容は、エラーが多いツール、同じ形のエラー、承認されなかった実行、二重承認の候補(投稿・コミットの直前の `ask`)、利用者の発話の抜粋(「ちょっと待って」「ごめん」「やばい」など。偽陽性を含む)。
2. **分類する**(子エージェント。`scout`。**レポートだけを渡し、生ログは渡さない**):
   次の分類で、各手がかりを分け、根拠(件数・抜粋)を付ける。
   - **前提の確認不足**: 利用者が前提を訂正した(「会社では〜しか使えない」「それは公開されるのでまずい」)。事前に質問すれば防げたか。
   - **承認・確認の流れ**: 二重承認、確認の過多・不足、確認画面の見づらさ。
   - **ツール設計**: 誘導 deny、引数のエラーの繰り返し、使いにくい引数、説明の不足。
   - **指示の衝突**: グローバル指示・スキル・ツール説明の食い違い。
   - **速度・待ち**: 「なんで時間がかかった」、待ちの設計。
   - **理解のずれ**: 説明が長い、用語が分からない、判断待ちが見えない。
   - **偽陽性**: 不満ではない(質問・方針の指示)。
3. **検証する**(親): 子の主張を、`report.md` の件数と抜粋で確かめる。足りなければ、該当する時刻のセッションログを、**親が**必要な範囲だけ読む。
4. **提案する**(親): 不満ごとに、解決策(新機能・設定・指示・スキル)を、「効果 × 費用 × リスク」で並べる。既存の仕組み(ツール定義 → 設定 → 指示の順に、強制力の強い側から)を優先する。**「何も作らない」も選択肢**に入れる。
5. **判断を仰ぐ**: `ask` で、採用する提案を尋ねる。採用したものは、`sdd-docs` で案件(`docs/change/`)に起票する(一般化した表現で。ログの引用は入れない)。
6. **次回の基準**: 件数の指標(二重承認、誘導 deny、エラーの繰り返し)を、案件に記録し、導入後に同じスクリプトで再計測する。

## 確認の結果の集計 (承認・拒否・時間切れ)

**このスクリプトは、pi の権限設定に阻まれず、確認なしで動く。** 「ログは作業ツリーの外だから ask になる」と思って、使えないと判断しない。
権限の判定が見るのは、ツール(`read`・`grep`・`bash`)に渡したパスだけで、`python3 <スクリプト>` の中での読み取りは判定の対象外 (2026-11-14 に、`~/.pi/agent/sessions/` と審査ログの両方を、確認なしで読めたことを確かめた)。
一方、**親が `read`・`grep`・`bash` で `~/.pi/agent/sessions/` や `extensions/*/logs` を直接読むと ask になる**。直接読まず、必ずこのスクリプトを通す。

審査ログ (`~/.pi/agent/extensions/pi-permission-system/logs/pi-permission-system-permission-review.jsonl`) を、`--approvals` が標準で読む (`--review-log <パス>`、`none` で読まない)。規則の単位は `<surface>:<matchedPattern>`。
**`<surface>:*` は、許可リストに無く既定の ask に落ちたもの**で、許可・拒否のどちらかをポリシーに足す候補になる。`規則で拒否` と `セッション承認で省略` は、利用者に確認を出していない。ask の件数は `承認` + `拒否` + `時間切れ`。

規則ごとの区分別の件数だけを見たいとき (CHG-0054 段 1)。ファイルは書かず、標準出力へ出す。

```sh
python3 .agents/skills/friction-review/scripts/friction_scan.py --approvals [--json] [--since 2026-10-01]
```

- 区分: 承認 / 拒否 (利用者が断った) / 時間切れ / 規則で拒否 / セッション承認で省略 / 保留に保存・確認なしで実行・不明 (旧形式のログだけ)
- 旧形式のセッションログには規則名が無いので、ツール名で代替する (旧 `guarded_action` のログは action 名を使う)。審査ログには規則 (`matchedPattern`) がある
- 規則あたり 20 件未満は「下限未満」。統計的な判断には使えないが、**1 日のログで「何が ask になったか」を見る用途には、件数が少なくても使える** (旧形式の `拒否` は規則による自動拒否も含む)
- `report.md` にも同じ表が入る。報告に載せるのは件数だけで、コマンドの文面は載せない

## 注意

- 利用者が明示していない不満を、断定しない。「〜の可能性がある」と書く。
- 抜粋の偽陽性が多い。語の一致だけで不満と判断しない。
- 不満を言わずに諦めている操作は、ログに出ない。取りこぼしがあることを、報告に書く。
- 出力・抜粋を、公開リポジトリにそのまま貼らない。
