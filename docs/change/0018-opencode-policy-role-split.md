# CHG-0018: OpenCode の権限を「共通の禁止」と「役割ごとの権限」に分けて生成する

- **状態**: Exploring
- **更新日**: 2026-10-08
- **基準**: OpenCode v2.0.22、コミット e22b365、WSL2 (Ubuntu)

## 目的と非目的

[CHG-0017](0017-builtin-agent-restrictions.md) では、組み込みエージェント（`explore` / `plan`）の
制限が全体の `permissions` に上書きされる穴を、個別の deny や写し直しで 1 つずつ塞いだ。
穴が個別に出続ける原因は構造にある。OpenCode の規則は「全エージェント共通の基底 →
組み込みの追加方針 → 全体の `permissions` → エージェントの `permissions`」の順に連結され、
最後に一致したものが勝つ（[調査記録](../research/opencode/permission/builtin-agent-override.md)）。
全体の `permissions` には `build` 向けの allow / ask を置いているので、同じ規則が `build` には
制限として、`explore` には緩和として働く。

この案件では、生成の構造を次の 2 つに分け、写し直しが要らない形にできるかを確かめる。

- **共通の禁止**: 秘密ファイルの保護など、どのエージェントにも解除させない禁止。OpenCode の
  `experimental.policies`（<https://opencode.ai/v2/docs/policies>）へ出す。policy の `allow` は、
  先に書いた policy の deny を解除するだけで、エージェントに操作の権限を与えない
- **役割ごとの権限**: shell の allow / ask、edit、作業ツリーの外へのアクセスなど。全体の
  `permissions` から、`build` などのエージェント別の `permissions` へ移す

受入条件（実装前の期待動作）:

- `build` の振る舞いは変わらない（今の全体の規則と同じ順序・効果を `build` 側に持つ）
- `explore` は、補修の deny が無くても、shell / edit / 子の起動 / question を使えない
- `plan` の計画ファイルの allow が、共通の秘密ファイルの禁止を解除しない
- `.env.example` は `build` から今までどおり扱えるが、`explore` には編集の権限を与えない。
  `.ssh/.env.example` は例外で開かない
- plugin が読めなくても、保存した承認があっても、共通の禁止は残る
- Claude Code / Copilot CLI の生成結果は変わらない

非目的:

- 組み込みエージェントを自作で置き換えること（自作は基底の全部許可から始まるので、根本解決にならない）
- `ocs` を境界にして permission を簡素にすること（同じプロセスの中では役割ごとに分けられない）
- CHG-0017 の独自の方針（`plan` の子の許可リストと shell の ask、`bypass` の子の許可リスト、
  `git log --output` の抑止、親が `bypass` の子の外部読み取り）を変えること
- 保存した承認の扱い、`review-loop` の子の名前、引数で書けるコマンド（CHG-0017 の未解決点 2・3・7）

## 現在地

2026-10-08 に、CHG-0017 の未解決点を個別に片付ける前に、根本的な解決があるかを別系統の
モデル（GPT-6 Astra）に相談した。推奨は「候補比較」の B で、段 1 の試作から始める。
回答は静的な評価で、提案した構成の動作は確かめていない。

- `ocs` では、すでに permission の policy を生成している（`scripts/agents/generate.py` の
  隔離版の生成）。全く新しい仕組みではない
- policy は実験的な機能で、正しくない書き方の規則は警告だけ出して捨てられる
- policy にはエージェントで分ける条件が無い。`bypass-worker` を起動する deny のように、
  一部のエージェントからは解除したい deny は policy に移せない
- 段 1 を終えた（2026-10-08、[調査記録](../research/opencode/permission/policies.md)）。秘密ファイルの
  read / edit の deny 155 件と例外を policy へ移した試験用の設定で、受入条件のうち秘密ファイルに
  関わるものは実機ですべて満たした
  - `build` の判定は対照と全件一致し、`.env.example` を今までどおり扱えた
  - `plan` の edit の写し直しを外しても、計画ディレクトリの中の `.env` / `a.key` / `secrets/x.md`
    は拒否された。今と違い、計画ディレクトリの中の `.env.example` は作れるようになる
    （写し直しは例外を写さないので、今は拒否している）
  - `.ssh/.env.example` は開かず、plugin を外しても、承認を保存しても禁止は残った
  - `explore` の 4 つの deny は外せなかった。全体の `shell * ask` や `git log *` の allow が
    流れ込む。全体の allow / ask をエージェント別へ移す段 2 が前提になる
  - 正しくない statement は警告付きで捨てられ、余分なキーは黙って通る。生成器で形を検査する
- 段 2 を終えた（2026-10-08、[調査記録 E2](../research/opencode/permission/policies.md#記録-e2--2026-10-08)）。
  全体の `permissions` を `bypass-worker` / `bypass-fleet-worker` の起動 deny 2 件だけにし、
  shell の deny 101 件と秘密ファイルの禁止を policy へ、残りの allow / ask を次のプロファイル
  （役割ごとの規則の束。生成器の中の呼び名）へ移した試作で、969 件の操作を今の設定と比べた

  | プロファイル | 中身 | 当てるエージェント |
  | --- | --- | --- |
  | 実装役 | `shell * ask`・shell の allow と ask・開けた場所の外部アクセスの allow・edit の ask・read の例外の allow | `build` / `general` / `compaction` / `fleet-worker` / `bypass-fleet-worker` / `bypass` / `bypass-worker` |
  | 読み取り役 | 開けた場所の外部アクセスの allow・read の例外の allow | `explore`。`plan` / `review` / `commit` は自前の規則の前に置く |
  | なし | 組み込みの `* * deny` のまま | `title` / `summary` |

  - 14 エージェント中 9 つで判定が全件一致した。`explore` も 4 つの deny を外して一致した
  - `title` / `summary` は、全体の allow / ask が流れ込んでいた 283 件ずつが deny になる（厳しくなる）
  - `plan` は、計画ディレクトリの中の `.env.example` の edit だけが緩む（段 1 で分かっていたもの）
  - どのプロファイルも当てない子（試験用のダミー）は、基底の全部許可がむき出しになった。
    policy の deny（`git push` など）は効いた
  - 段 1 の取りこぼし: read の例外（`.env.sample` / `.env.template`）を policy に移すだけだと、
    基底の `read *.env.* ask` に戻って ask になる。policy の allow は権限を与えないので、
    プロファイルにも read の allow を置く
  - `bypass` / `bypass-worker` を V2 の `agents` へ移しても判定は一致した

## 未解決点

- **どのプロファイルも当てない子をどう守るか（利用者の判断待ち）。** 作業先のリポジトリが
  定義する子は、自分の `permissions` で全体の規則を上書きできるので、今の全体の `shell * ask` が
  守っていたのは「`permissions` を書かなかった子」だけだった。段 2 で比べた対策は次の 4 つ
  1. 全体に `shell * ask` などの最小の既定を残す: 組み込みの制限を上書きするので、`explore` の
     補修が外せず、`title` / `summary` にも流れ込む。受入条件を満たさない
  2. 全体を `* * ask` などの広い既定にする: 1 よりさらに組み込みの制限を上書きする
  3. 全体は deny だけにし、生成器で宣言したエージェントと既知の組み込みの全部にプロファイルを
     必須にする（**推奨**）。今後足す自作は生成器の検査で塞ぎ、OpenCode の更新で増える組み込みは
     `/api/agent` の一覧を既知の一覧と突き合わせる試験で拾う。それ以外の子は基底の全部許可に
     なるが、policy の deny は効く
  4. 3 に加え、guide plugin の `evaluate` で、生成した一覧に無いエージェントの allow を ask に下げる。
     plugin が読めないと効かない。未試験
- shell の deny を policy に移すと、規則の deny と違って guide の `evaluate` の後に効く。
  `git push` などで確認の説明をモデルで作ってから拒否されるので、早期停止の対象を policy から
  作るなどの手当てが要る（段 4）。拒否の文面も `Blocked by configuration policy` に変わる
- `compaction` / `title` / `summary` が実際にツールを呼ぶかは未確認。`compaction` は組み込みの
  追加方針が無く基底のままなので、今と同じ判定にするため実装役を当てた
- `explore` は試作でもツールの一覧に subagent が残った（評価上は deny）。気になるなら読み取り役の
  末尾に `subagent * deny` を 1 件置く
- V1 の `agent` と V2 の `agents` を同じ ID で併用したときの合成は未確認（生成器が今は禁止している）
- Claude Code / Copilot CLI の生成結果が変わらないことは、生成器を変えるまで確かめられない
- 配置済みの `ocs` の設定の `agents` が 3 つだけだった。古い apply の結果かは未確認
- `read` の policy は、`grep` / `glob` の結果や shell 経由の読み取りまでは守らない。
  結果のフィルタと `ocs` は残る
- CHG-0017 の `restate_global_deny`（全体の deny をエージェントの規則の後ろへ写し直す処理）は、
  例外まで厳しくしていた。policy に置き換えると、`plan` は計画ディレクトリの中の `.env.example`
  を作れるようになる（段 1）。この緩みを受け入れるかを段 4 で決める
- policy の照合は `~` を展開しない（コードを読んだだけ）。生成時に絶対パスへ展開する
- `ocs` の設定（`~/.config/opencode-sandbox/opencode.json`）にも秘密の policy を出すか

## 評価基準

- 必須: 受入条件をすべて満たす。CHG-0017 の補修（`explore` の 4 つの deny、`plan` の edit 制限の
  写し直し、`restate_global_deny`）のうち少なくとも 1 つが不要になる
- 望ましい: 生成器の分岐が減る。全体に allow を足しても制限のある役割に配られないことを
  テストで固定できる
