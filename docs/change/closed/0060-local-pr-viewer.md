## 2. 目的と非目的

| 区分 | 内容 |
| --- | --- |
| 目的 | リモートが無くても、差分とコメントを PR のように読み書きし、pi と速く往復できる |
| 重視する体験 | 差分とコメントの読み書きのしやすさ・pi との往復の速さ |
| 非目的 | アプリが統合の実行器を持つこと（実行は窓口の pi。C1・C8） |
| 非目的 | 複数人のレビュー・組織向けの機能（使い手は利用者 1 人 + pi） |
| 非目的 | 制約のある環境（認証つきプロキシが必須など）を設計の前提にすること |

## 5. 設計

### 5.1 構成 C

| 役割 | 担当 | 内容 |
| --- | --- | --- |
| 状態の正本 | git の ref（`refs/pi/…`） | コメント・サマリー・レビュー状態。アプリが落ちてもデータは安全。pi は git だけ読めば動ける |
| 画面と入力 | 別アプリ（ユーザー単位で 1 つ。全リポジトリを 1 つのポートで扱う） | `127.0.0.1` で待ち受け、tailnet へは Tailscale の serve で HTTPS 公開（1 つの URL） |
| pi との連携 | 薄い拡張（道具 2〜3 個） | `pr_summary`（完了サマリーの投稿）・`pr_comments`（読む・返信・解決）。レビュー送信後は、次のプロンプトの前（`before_agent_start`）に ref を読んで注入 |
| 承認・統合 | 窓口の pi（実行器） | アプリが承認を窓口の pi に指示し、窓口の pi が既存の実行器で実行する（§5.7）。段 4 までは従来どおり `/pending` |

利点（設計上の期待。実装で確かめていない）:

| 避けたいこと | 構成 C で避けられる理由 |
| --- | --- |
| ポート衝突（複数プロジェクトで pi を同時に開く） | サーバは 1 つ |
| pi の再起動・圧縮の影響 | 状態は ref にあり、pi の外 |
| サンドボックス（Fence）からの到達 | 結合が ref だけ（ネットワーク不要） |
| 他のエージェントとの共有 | [オーケストレーター（CHG-0056）](0056-orchestrator.md)や他のエージェントも同じ ref を読み書きできる |

**前提の修正（独立 review）**: ref は保存・結合の手段であって、**安全境界ではない**。ネットワーク結合をなくしても、アプリが ref の内容（パス・コマンド）を実行すれば、Fence の外への実行経路になる（C9）。

### 5.2 画面

| 項目 | 内容 |
| --- | --- |
| 入力の入口（5 つ） | 行コメント・スレッド返信・PR 全体のコメント・サマリーへの反応・レビューを送る |
| 送信の扱い | コメント単体は保存だけ（pi に渡らない）。レビューを送るときだけ pi に渡る（D3） |
| 状態表示 | 主状態のチップ 1 つ + 注意が要るものだけの 1 行。既定値（未解決 0 など）は出さない |
| 主状態の優先順位 | 検査失敗 → 変更依頼 → 承認待ち → 未レビュー → 承認 → 統合済み |

### 5.3 データ

ref のスキーマは [spec §3](../../spec/pr-viewer.md) に確定した（2026-11-03）。載せる項目:

| 項目 | 備考 |
| --- | --- |
| コメント・スレッド | `comment` イベント |
| サマリー | D1・D2。`summary` イベント |
| レビュー状態 | `submit` の種別から導く |
| 既読 | ref には持たない（UI の便宜） |

### 5.4 pi との接続

| 経路 | 内容 |
| --- | --- |
| pi → 画面 | `pr_summary` が ref へ書く。画面が読む |
| 画面 → pi | 「レビューを送る」で ref に書く。次のプロンプトの前（`before_agent_start`）に pi が読んで注入 |
| 統合 | アプリが「保留に保存する」。承認は窓口の `/pending approve`（[CHG-0055](0055-async-approval.md)） |

### 5.5 pi とアプリの分担（移譲の検討。2026-11-03）

方針: アプリが担うのは**閲覧・入力・状態の可視化**。**判定・承認・実行・モデルの文脈**は pi に残す。

#### 移譲の仕分け（今 pi にある機能）

| 今の機能（pi 側） | 仕分け | 内容・理由 |
| --- | --- | --- |
| `/board`（盤面） | 共有 | 集める処理（`board-collect.ts`）を共有ライブラリにし、アプリの一覧・盤面が同じ処理を使う。pi の `/board` は、端末だけの環境の最小表示として残す |
| `/pending show`（保留の中身の表示） | 表示だけ移譲 | 差分・理由・証拠の閲覧はアプリの詳細画面へ。承認画面（TUI）には URL を添える |
| `/pending approve`・`git_integrate` の実行・後片付け | **移さない** | 承認境界（C1）・ロック・CAS・実行後の確認 |
| 保留の作成（`git_integrate` の保存） | 一元化案（未決） | harness だけが `refs/pi/pending` 系を書く。アプリは「レビューで承認」の印だけを書き、窓口の `/pending` がそれを統合の依頼として候補に出す案。アプリが保留を直接書く案より、書き込み権限が小さい |
| 子の結果の全文・worker の完了報告 | 投稿に変える | 完了報告の中身が `pr_summary` の材料。チャットの最終報告は、要点と URL に短くできる |
| 検査の実行（`verify`・`feature_gate.py`・`parallel_check.py`） | 移さない（結果の表示だけ移譲） | 実行は pi・スクリプト。結果を ref に記録し、アプリの検査パネルが読む |
| `ask`（選択肢の質問） | 一部移譲 | 急ぎでない確認（設計の分岐・確認してほしい点）は、サマリーの「確認してほしい点」に投稿し、利用者がアプリで返信する非同期の質問にする。pi は待たずに独立した作業を続ける。作業を止める確認は `ask` のまま |
| 修正依頼の自由文（チャットに書く） | 構造化して移譲 | 行コメント・スレッドとして書く。スマホでも書きやすい。pi は次のプロンプトの前に読む（D3） |
| 子・pi の状態（`/agents`・フッター） | 公開だけ追加 | pi が状態（待機/対応中）を ref に出し、アプリが表示する。`/agents`・フッターは pi に残す |
| 完了通知（`child-finished`・`bg-job-finished`・`pending-result`） | 移さない | モデルを起こす仕組みで、pi の内側 |
| ガード・サンドボックス・子エージェント・`todo`・圧縮・モデルの割り当て | 移さない | 実行の文脈そのもの |

#### 結果として pi が担う機能

| 区分 | 機能 |
| --- | --- |
| 判定・承認・実行 | ガード・サンドボックス・`/pending approve`・`git_integrate` の実行と後片付け（不変） |
| 作業の実行 | モデルの呼び出し・子エージェント・worktree・`todo`・圧縮 |
| PR への書き込み口（新） | 道具 `pr_summary`・`pr_comments`（読む・返信・解決）。検査結果と pi の状態を ref に記録 |
| レビューの受け取り（新） | 「レビューを送る」の後、次のプロンプトの前に ref を読んで注入（D3） |
| 端末の最小表示 | `/board`・承認画面・`/pending`（アプリの URL を添える） |
| アプリの入口（新） | `/pr`: 起動と URL の表示（薄い） |

#### アプリが担う機能（pi は担わない）

| 区分 | 機能 |
| --- | --- |
| 閲覧 | 差分・複数リポジトリの PR 一覧・盤面・pi/検査/保留の可視化 |
| 入力 | 行コメント・スレッド・PR 全体のコメント・サマリーへの反応・レビューを送る |
| 状態 | コメントとレビュー状態の保存（ref）・統合の依頼（レビューでの承認） |
| 公開 | 認証・tailnet への公開 |

#### 設計への影響（§7 の未決に反映）

| 項目 | 内容 |
| --- | --- |
| 共有ライブラリ | ref の読み書き・盤面の集計を、pi とアプリで共有する。置き場所の決定に影響する（このリポジトリ内なら共有が容易。別リポジトリなら配布が要る） |

### 5.6 独立 review の指摘（2026-11-03）

結論: **構成 C を否定する BLOCKER はない。条件つきで進めてよい**（pi と UI の寿命を分け、承認を窓口に残す方向は当。A・B の却下理由を覆す必要はない）。代替案（SQLite・git notes）で C を置き換える利益は示されていない。根拠のパスと行は、親が実物で確かめた。

| 重要度 | 指摘 | 反映先 |
| --- | --- | --- |
| MAJOR | アプリの権限が未限定。許すのはレビュー用 ref と、要求専用の API による保留作成まで | C8 |
| MAJOR | 全リポジトリを扱うプロセスが、ref 経由の実行代理になりうる | C9 |
| MAJOR | HTTPS・tailnet 到達性だけでは API の認可にならない | C10（利用者の判断で縮小。§5.7） |
| MAJOR | D3 と配送の契約が不足（送信の batch・宛先・再配送） | C11 |
| MAJOR | レビューした版と現在の版が結び付いていない（既存の統合は承認時に再計画する） | C12 |
| MAJOR | ref だけでは同時更新・保持を保証しない | C13 |
| MAJOR | 本文がブラウザとモデルの両方へ入る（XSS・プロンプト注入） | C14 |
| MINOR | 起動方式: Fence 外のユーザーサービスとして常駐を推奨。`/pr` は URL の案内 | §7 |
| MINOR | ref の保存内容は通常の clone/push で同期されない・mirror で流出しうる・ref 削除は即時消去ではない | §7 |

未確認（review）: Tailscale Serve の認証・ヘッダー処理、Windows、Fence 内の実動作、配送の実機。

### 5.8 設計案の独立 review（2026-11-03）

設計案（[spec](../../spec/pr-viewer.md)の元）を別系統のモデルが review した。結論: 段 1〜3 は条件つきで進めてよく、段 4〜5 は下の M1〜M5 を反映してから。構成 C は撤回しない。

| # | 指摘 | 採否 | 反映 |
| --- | --- | --- | --- |
| M1 | 承認の指示が `{instrId, requestId}` だけでは、承認した記録を固定できない | 採用 | 指示は `{instrId, prId, requestCommit, requestId}`。その commit のイベントだけを読み、構造化して完全一致を確かめる。`changesOf` は拒否の正本にしない |
| M2 | モデルがアプリの API を直接呼ぶ経路への対策を後段に送れない | 採用（段 4・5 の開始条件） | 判定器で、アプリのポートへの curl・wget の変更系を**拒否**にする。段 5 はこれが入るまで有効化しない |
| M3 | 既存経路を呼ぶだけでは、終了・reload 時の取消を継承しない | 採用 | `pr-control.ts` が AbortController を持ち、`session_shutdown` で中断を伝える。実行直前にも期限・セッション・設定を確かめる |
| M4 | 「結果なしで期限超過 = 届かなかった」は成立しない | 採用 | 実行前に `merge_started` を追記（失敗なら実行しない）。UI は pending / running / done を表示。自動の再実行はしない |
| M5 | PR の branch と受け手の HEAD の一致を要求すると、親が develop・作業が worker の運用に合わない | 採用 | 配送先を `worktreeId` で分ける。既定は主 worktree |
| MINOR | `by` は自己申告 | 採用 | 表示用。レビュー状態は `submit` の種別から導く |
| MINOR | claim を伴う poll が GET | 採用 | POST にする |
| MINOR | 同名ブランチの再利用 | 採用（v1 は非対応） | 統合済みの PR への書き込みは断る |
| MINOR | stale が source だけ | 採用 | source・target・base を比較する |
| MINOR | 上限で終端記録が書けない | 採用 | 1900 件を超えたら終端記録以外を断る |
| MINOR | `unknown` と running の混同 | 採用 | `ExecutionResult` の `saved`・`kept`・`termination` を使う |
| 切る提案 | `seq`・`ack`・起動時の全件検査・全ペアへの配布・300 行の試験 | 採用（切る） | v1 から外す。`--repo` の撤去は採らない |

### 5.7 承認とペアリング（2026-11-03 の方針）

経緯: 利用者の指摘「承認が `/pending` からしかできず、アプリで閉じないのが不便」「パスキーは過剰」。当初の「画面から承認を飛ばさない」（C1）を、次のとおり**改訂**した。

| 項目 | 方針 |
| --- | --- |
| 遠隔の通信路 | **tailnet が保証する**。アプリでの追加の認証（端末の鍵・パスキー）は置かない |
| ペアリング | **pi セッション側から**、同じマシンで動いているアプリへ要求する。ペアリングしたセッションだけを、アプリが管理する（リポジトリ・worktree・PR・配送先） |
| 開始できる人 | 利用者専用の TUI コマンド（例 `/pr pair`）。モデルは呼べない（今の `/pending` と同じ構造） |
| 解除 | セッションの終了（生存確認）か `/pr unpair` |
| 制御の通信（新） | 同じマシンの中だけ（ペアリング・生存確認・承認の指示）。データの正本は引き続き ref（C2）。アプリが落ちても pi は ref だけで動く |

承認の流れ:

| 順 | 内容 |
| --- | --- |
| 1 | アプリで PR をレビューし、承認する |
| 2 | アプリが、ペアリング済みの**窓口の pi**（統合先の worktree で動く pi）に「この保留を承認せよ（ID・計画の digest）」と指示する |
| 3 | 窓口の pi が、`/pending approve` と同じ経路（再計画・再検査・実行器）で実行し、結果を ref に記録する |
| 4 | アプリが結果を表示する |
| 窓口の pi が居ないとき | 承認ボタンは押せず、理由を表示する |

| 項目 | 内容 |
| --- | --- |
| 実行器 | pi のまま。アプリには持たせない（承認者が二重になるのを避ける） |
| 残るリスク | tailnet 内の端末が乗っ取られると、承認できる。利用者の判断で許容する。誤承認の影響は、ローカルの develop への squash 統合で、`git push` は別の手動操作（共通 deny）。reflog・revert で戻せる |
| 外せないこと | 承認境界を動かすので、**設計書の後に独立 review** |

### 5.9 実装の独立 review（2026-11-03）

実装（段 1〜3）を別系統のモデルがコード review した。結論: 承認・統合を直接実行する経路は無く、CSRF・XSS・ref の CAS も問題なし。実際の不具合を次のとおり指摘し、M6 以外を修正した。

| # | 指摘 | 状態 |
| --- | --- | --- |
| M1 | git の自動 fetch（partial clone で足りないオブジェクトを読むと ssh 等を起動する）が未禁止（C9） | 修正済み（環境変数を固定。アプリと pi 側） |
| M2 | branch 名が注入の囲みの外に出る（C14） | 修正済み（入力由来の文字列はすべて囲みの中） |
| M3 | 見ていない新しい版を「承認」できる（C12） | 修正済み（`expect` と 409 `stale_view`） |
| M4 | 長いコメントの後半を pi が読めない | 修正済み（`pr_comments` の list は全文。注入はプレビュー） |
| M5 | 最後にレビューした source を保持しない（C13） | 修正済み（最初の記録から追加の親にする） |
| M6 | ブランチを消すと保存済みの PR が見えない（§2 の和集合を実装していない） | **未対応**（大きいので判断待ち） |
| M7 | バイト上限で終端記録（`receipt`）が書けなくなる（C11・C13） | 修正済み（末尾 32 KB を終端専用にする） |
| MINOR | 別の blob の同じ行へのコメント・pi の stale 判定・再送ボタンの欠如 | 修正済み |
| 文書 | Host の仕様の不一致（spec: 設定した 1 つの名前だけ / 実装: `*.ts.net` を既定で許可） | spec を実装に揃えた |

## 6. 守る条件（案）

| # | 条件 |
| --- | --- |
| C1（改訂） | アプリは承認を窓口の pi に**指示**でき、実行は窓口の pi が既存の実行器で行う。アプリは実行器を持たない。承認の指示は、ペアリング済みのセッションにだけ届く（C15）。段 4 までの承認は `/pending approve` |
| C2 | 状態の正本は git の ref。アプリが落ちても、pi は git だけで動ける |
| C3 | コメントは「レビューを送る」のときだけ pi に渡る。コメント単体は保存だけ |
| C4 | アプリは `127.0.0.1` で待ち受け、tailnet へは Tailscale の serve で 1 つの URL に公開する（遠隔の認証は tailnet に任せる。C10） |
| C5 | 画面に出す diff・コメントは、サニタイズして描画する（XSS を防ぐ） |
| C6 | 他の実装のコードは複写しない。公開リポジトリには架空の例だけを書く |
| C7 | pi の拡張は薄く保つ（道具と注入だけ）。アプリの障害が pi の動作を止めない |
| C8（改訂） | アプリは統合・復旧を自分では実行しない（実行は窓口の pi の実行器。承認の指示は C1・C15）。レビュー状態を、それだけで実行許可に使わない。書けるのはレビュー用の ref と、要求専用の API（承認・実行側を import しない。試験で固定）による保留の作成まで。`running`・`done`・`lock` の更新と、統合・cleanup の実行は禁止（承認は窓口の pi への指示としてだけ送る） |
| C9 | アプリは登録されたリポジトリ（canonical な common dir）だけを扱う。ref の中の `cwd` やパスを信用しない。git は固定の argv で、hook・fsmonitor・外部 diff・textconv・外部 filter を止めた専用の実行器で実行する（承認の前に外部のコードを動かさない。[保留](../../spec/guard/pi-pending.md)） |
| C10（縮小） | 遠隔の通信路は tailnet が保証する（利用者の判断。2026-11-03）。アプリでの追加の認証（端末の鍵・パスキー）は置かない。残す衛生: GET の副作用禁止、diff・コメントのサニタイズ（C14） |
| C11 | 「レビューを送る」で、本文・コメントの版を固定した batch（不変・原子的）を作る。宛先は repo + PR ID + 担当 worktree。永続的な受領記録と batch ID で再配送を重複排除する。未送信の内容を pi に返さない。「次の入力まで届かない」ことを UI に明示する |
| C12 | コメント・レビュー・サマリー・検査結果を source / target / base の OID に結び付け、更新されたら stale / outdated を表示する。「レビュー承認」と「統合承認」を分ける。行のアンカーは path・side・blob・範囲を持つ |
| C13 | ref の更新は CAS（期待 OID・`--no-deref`）。PR ID ごとのスキーマと書き手を定める。競合は再読して操作を再適用する。旧差分の OID は到達可能に保持する。サイズ・履歴・保持期限を制限する |
| C14 | 全本文を非信頼入力として扱う。diff はテキスト描画、Markdown は raw HTML・危険な URL・外部画像を制限する。モデルへは、送信済みの構造化データとして渡し、引用と利用者の依頼を分ける。プロンプト注入の完全な防止は保証しない。承認の指示は、ペアリング済みのセッションにだけ届ける（C15） |
| C15 | ペアリングは **pi セッション側からの要求**で、利用者専用の TUI コマンド（例 `/pr pair`）だけが開始できる（モデルは呼べない）。要求先は**同じマシンで動いているアプリ**。アプリは、ペアリング済みのセッションの範囲（リポジトリ・worktree・PR・配送先）だけを管理する（C9 の登録済みリポジトリ）。セッションの終了で解除する |

## 9. 却下した案

| 案 | 理由 |
| --- | --- |
| A. pi の拡張として、各 pi がサーバを持つ | pi の再起動・圧縮で UI が落ちる。ポート衝突。pi 以外の変更を見られない |
| B. 別アプリだけ（pi との連携は手動） | pi との往復が遅く、重視する体験を満たさない |
| 既存ツールの導入・複写（local-review は GPL v3 など） | [ADR-0016](../../adr/0016-pi-extensions-own-first.md)。要件を全部満たす実装が無い（[調査記録](../../research/agents/local-pr-viewer-survey.md)） |
| vibe-kanban 系のエージェント管理アプリ | GitHub 前提・pi 非対応・運営が終了（調査記録の追加調査） |
| Forgejo を 1 人用に立てる | サーバ + DB + 認証で重く、pi 連携が無い |
| 画面からの承認（トークンだけ・フラグ・digest） | 利用者が押した証明にならず、承認境界を弱める（過去に却下した案と同じ理由）。**2026-11-03 に、ペアリング済みの窓口の pi への指示という形に改訂**（§5.7） |
| パスキー（署名つきの Web 承認）・端末の鍵 | 利用者の判断で過剰（ガードは「うっかり防止」の水準で、遠隔は tailnet が保証する） |
| アプリが統合の実行器を持つ案 | 承認者が二重になる。実行は窓口の pi に残す |
| SQLite・git notes で ref を置き換える | 現段階で C を置き換える利益が示されていない（review）。SQLite は検索・大量更新に有利だが、共有 DB の配置・Fence の許可・ロック管理が増える。git notes は配送・競合・版管理を解決しない |
| オーケストレーターの Web UI・常駐の監督プロセス（[CHG-0056](0056-orchestrator.md) §6 の却下） | 本案件は別件。ジョブの監督・配車をしない（ジョブ自体も撤去済み）、閲覧とレビューの画面。常駐させる場合も監督はしない |
