# 作業台帳を唯一の状態にして、継続・/goal・並列実行・通知を一体で自作する

- **ステータス**: Accepted（部品は実装済み。配線は既定無効の旗で、実 pi での確認の後に有効化する）
- **日付**: 2026-11-05（記録は 2026-11-06）
- **決定者**: applejxd（方針と「設計はお任せで実装」の指示）。設計の判定は計画役（子エージェント）、採用は親。

この文書は、**なぜ作ったか**を残す。仕様は [docs/spec/work/](../spec/work/ledger.md)、実装の履歴は [CHG-0062](../change-history/0062.md)。

## コンテキスト

- 2026-10-11 に [ADR-0016](0016-pi-extensions-own-first.md) で「pi の拡張は自作を基本とする」と決めた。2026-10-20 に [CHG-0025](../change/closed/0025-goal-autonomous-loop.md) で `/goal`（目標を渡す→自走→独立した監査）を起票した（非目的は公開拡張の導入）。
- 2026-11-05 に、利用者が `/goal` の実装計画と、公開の先行実装（pi-goal-x・pi-tasks・pi-dynamic-workflows）の網羅調査を依頼した。調査の途中で問いが「個別に入れるか」から「**総合して一体で自前実装するほうが良いか**」に広がった。
- 当時の状況（コードで確認した事実）:
  - **状態の持ち主が 7 つ以上**ある（todo の tool 結果・goal の entry・子と job の Map・隔離の記録ファイル・worktree の所有の印・autocheckpoint のクロージャ・plan モードの旗・モデルが書く `NEXT.md` など）。`globalThis` の暗黙の結合が 6 つあった。
  - **継続の取り合い。** `agent_before_settle` の `entries` は後勝ちで置換されるため、todo が autocheckpoint の保存指示を消す不具合が実際に出ていた。`/goal` を足すと 3 者になる。
  - **予算が 4 か所に分散**し（goal の使用量・子の RoundStats・評価役・隔離の Budget）、合算が無かった。同じ事実（誰が何を待つか）を出す面（`/board`・`/agents`・`/todos`・activity・todo・BEL）も乱立していた。
  - **並列度の律速は子の数ではなかった。** 実測（2026-11-03〜04 の運用）: 同時数は平均 約 1.7・最大 5、全件検査の失敗率は 12/45（27%）、費用は約 $14/時で取り消し系が約 37%。律速は、親の手順（7 手順）＞検証の直列＞統合の押下の順。待ちを機械で埋める仕組みは多くが死に機能（`/fleet` など）になり、効いたのは待ちの回数を減らす bundle だけだった。
- 利用者の要望（2026-11-05）:
  - 入力は最終ゴールと希望の機能が中心で、**並列化・タスク管理はハーネスが最適管理する**。ユーザーが個別に最適解を選べなくても、エージェント側で自動選択できる形が理想。
  - 公開実装を上回る完成度を目指す。**不要な既存機能は、削除・統合・変更してよい**。
  - これまで自前で並列度を高めようとして、うまくいかないことが多かった。todo は 114 件で依存関係が見づらい。内部通知（child-finished など）が認知ノイズになっている。

## 検討した選択肢

### 公開拡張を個別に導入する（goal-x・tasks・workflows）— 退けた

- 状態の持ち主が 3 重になる。継続の取り合いが増える（goal-x は 17 のイベントを購読する）。予算が分散する（goal-x は監査役の費用を予算に数えない）。名前が衝突する（`/goal`・`/tasks`）。
- 子や監査役が**フルガードの外**になる（dynamic-workflows は拡張なし・素の bash で子を起動する。`vm` は境界ではないことを実証した）。
- 追従が 3 つ別々に要る（直近 90 日の commit は goal-x 316・tasks 26・workflows 84。保守者は 1 人ずつ）。

### 公開拡張の vendor（検査してから取り込む）— 退けた

自作より初期費用・追従費用とも高い（推測: 自作の MVP が 30〜50 時間＋月 1〜2 時間、vendor が 55〜65 時間＋月 4〜8 時間）。goal-x は予算なしで自走し、保存がターン終わりの 1 回で、監査役がガード外。pi-tasks は循環を拒否しない（[goal-x](../research/agents/pi-goal-x-deep-dive.md)・[tasks](../research/agents/pi-tasks-deep-dive.md)・[workflows](../research/agents/pi-dynamic-workflows-deep-dive.md)）。

### 個別に自作する（todo・goal・scheduler・通知を別々に）— 退けた

継続の取り合い・状態の写しの増加・予算の分散・面の乱立が残る。「状態の写しが 1 つ」「継続の主体が 1 つ」は、一体の設計でしか構造的に保証できない。

### 最小案（調停・通知・`/goal` だけを直列で作り、台帳・スケジューラ・仕様は作らない）— 撤退先として保留

費用は約 1/3 だが、状態の持ち主が 3 つ以上残り、並列度は改善しない。段階の実測で、親の接触が律速でなければ、ここで止める。

### 現行の整理だけ — 退けた

並列度の律速に効かない。`/fleet` 型の再演になる。

### 外部の基盤・外部ループ（CHG-0025 の C 案）— 退けた

ガード・サンドボックスの外に置く必要がある。

## 決定事項

**一体で自作する。作業台帳（work ledger）を唯一の状態にし、継続の調停（`agent_before_settle` の継続を 1 か所に集める）・`/goal`・並列スケジューラ・宣言的ワークフロー・通知とパネルを、台帳の上の純関数と投影にする。**

- 公開の実装から借りるのは**仕様だけ**（パイプライン・予約・429 の AIMD・`writes` による自動直列化など）。コードは借りない（ADR-0016）。
- 入口は `/goal` 1 つと少数の動詞にし、重なる旧機能（`/fleet`・`/orchestrate`・`/agents`・`/worktrees`・`/board`・`/todos`・`todo`・`plan`・`delegate-nudge`・`activity`・`notify` など）は統合か廃止にする。撤去は旗を有効にする日にまとめる。
- 並列化の方式は、利用者が選ばず、決定的な方針表でハーネスが選ぶ。LLM が担うのは、分解・`writes` の宣言・依頼文・失敗の判断・要約だけ。
- **段階**: S0 journal（実測）→ S1 台帳と `work` ツール → S2 調停と通知 → S3 `/goal` → S4 スケジューラとドライバ → S5 宣言的仕様 → S6 撤去。各段は単独で価値を出す。
- **決定の経路**: 判定は計画役が行い（見立ての検証は A 節）、親が採用した。利用者の指示は「設計はお任せで、どんどん実装して」。利用者が明示的に答えたのは、範囲（全段を進める。統合は朝）・費用（無制限。ただし暴走は避ける）・成功の定常通知（1 行のまま。silent は実機で見てから）。入口を `/goal` に絞る・子の自動起動を権限の拡大として扱う・予算の既定（$5・90 分・並列 6〜10）・置き場・仕様の形式（JSON）は、計画役の推奨を親が採用した。

## 守る条件

- 新しい権限は**既定で無効の旗**で入れる（`journal`＝観測のみは既定で有効。`work_tool`・`arbiter`・`goal`・`scheduler` などは無効。`PI_WORK=0` で一括無効）。
- 独立 review が要る境界: `work` ツール・スケジューラ・実行を伴う検査と仕様・書き込みの許可範囲・台帳の置き場の保護。
- 台帳は追記専用・fsync・隔離して読み取り専用へ落とす回復で、単一障害点のリスクを下げる（[store](../spec/work/store.md)）。
- **撤退条件**: 段階 S0・S1 の実測で、親の接触が並列度の律速でなければ、最小案で止める。

## 位置づけ（2026-11-06 時点）

- 台帳は**実装済みで、これから使うもの**（利用者の言葉）。部品は新規ファイルの純関数で、配線は既定無効の旗。**実 pi での有効化の確認は未実施**（TUI・settle 中の圧縮・print モードは未実測）。有効化は実機確認の後。利用者は、再起動できる機会が限られるので、旗は大きな粒度でまとめて有効化したいと述べた。
- 利用者が見る面の撤去（S6）と宣言的仕様（S5）の扱いは、CHG-0062 の履歴を正とする。
- 2026-11-06 に Pi Durable（`@earendil-works/pi-durable`。実験的なライブラリ）を調べた。コーディングエージェントの機能ではなく、pi への接続点が無く、権限・サンドボックスは対象外なので、台帳の置き換えにはならない。pi のコーディングエージェント側が耐久実行を持つ形になったときに再評価する。借りられる考え方は、副作用の前に意図を記録する・再実行して安全なものだけ再実行する・要求 ID で重複を排除する、の 3 点。

## 結果・影響

- 利点: 状態の写しが 1 つ・継続の主体が 1 つ・費用の合算が 1 か所になる。親の手順の決定的な部分を機械採取の検査にできる。`NEXT.md` を台帳の投影にできる。
- 欠点・リスク:
  - 台帳スタック（`work/` と goal 系）は約 8,000 行で、ハーネス全体（約 27,700 行）の約 3 割。運用の実績はこれから。
  - [CHG-0062](../change/closed/0062-pr-hub-simplify.md) は「オーケストレーションを pi の外へ出し、pi を通常のコーディングエージェントへ戻す」方向も含む。台帳を pi の内側に置く現在の形は、実運用の結果で見直す余地がある。
- **見直しの条件**: 実機の運用で、台帳が並列度・費用・利用者の手間の指標（下記）を改善しない、または保守の費用が便益を上回ると分かったとき。縮小・撤去は、移行の費用を示して提案する（サンクコストを理由にしない）。

## 決定の確認方法

- 完成度の基準 Q1〜Q10 を機械で検査する（継続の主体が 1 か所・状態の写しが 1 つ・全ての子がフルガード下・遷移表が全セル試験されている・障害注入の試験・幅 40/46/80 の表示・`NEXT.md` が投影・費用の合算・自動メッセージが 1 行に畳める・モデルの文脈に入る内部通知の上限）。
- 効果の指標 M1〜M10 を journal から出す（親の接触回数・同時数と ready 充足率・全件検査の失敗率・待ち時間・見える自動メッセージの行数・費用・手戻り・利用者の介入回数）。ベースラインは上の実測。
- 実機で、旗を有効にして日常で使い、確認の結果を CHG-0062 の履歴に残す。
