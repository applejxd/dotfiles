# 並列度を保つ運用（見込みの並列・空きを埋める・接続）

> stock の pi では `subagent` に読み替える。凍結した custom の運用（`guarded_*` 前提）。stock の既定の運用は [SKILL.md](../SKILL.md)。

方針（利用者が確認した契約の範囲で、直列に待たず、見込みで並列に実装し、接続できる部品から接続して試す）は `AGENTS.md` と全リポジトリ共通の指示にある。
ここは、**並列度を実際に保つための手順**だけを持つ（子に任せる細部は [worker の共通の約束](worker-common.md)）。

## 何が並列度を決めるか（律速）

子の同時数（`guarded_task` は **6**）／全件検査の排他（約 9〜12 分・1 本ずつ）／利用者の承認（統合は PR ビューアの「統合する」・1 件ずつ）／共有ファイルの衝突／親のコンテキスト。
**空きを作らないこと**が最重要。空きは、子の完了・利用者の応答のたびに生まれる。

## 目覚めの手順（子の完了通知・利用者の発言・保留の結果のたびに）

1. `guarded_task {list:true}` で、生きている子と空きを見る。完了通知は取りこぼすことがある。終了済みの子へ `steer` すると `does not exist` になるので、`steer` の前に `list` で running を確かめる。
2. **空きを、キュー（`.tmp/keep/queue/`）の先頭で埋める。**（キューに入れるのは、契約が確認済みの依頼文だけ。決定待ちは入れず blocked） 1 回の呼び出しで済ませる（ファイルの内容をそのまま `task` に渡し、`todo` の ID を付ける）。
3. 完了した子の返答は、**結論・契約との食い違い・未確認・申し送り**だけを読む。詳細は全文のファイル（`.tmp/subagents/<番号>-job-*.md`）に任せる。長い返答を転記しない。
4. todo（blocked の note に待ち先の job ID）と `.tmp/keep/checkpoint/NEXT.md` を更新する。
5. 次に起動する依頼文が足りなければ、**空きを待つ間に先にキューへ書く**。

## キュー（`.tmp/keep/queue/<話題>-<役>.md`）

- 1 ファイル = 1 回の `guarded_task` の `task`。雛形（`.tmp/keep/<話題>/*-prompt-template.md` の `{WHO}` と `{SCOPE}`）を読ませる短い形にする。
- 起動したら `done-` を前に付けて残すか消す（使い回さない）。
- 優先順位: ① 他を待たせる枝（クリティカルパス）→ ② 前段が終わり次第接続できるもの → ③ 独立した調査・docs。

## 見込みの並列の作り方

1. **契約書**（`.tmp/keep/<話題>/api-contract-*.md`）に、API の形・関数の署名・担当ファイルの分担・守る規則を短く書く。ずれる前提で書く。
2. 継ぎ目（モジュール・`web/`・docs）で担当を切る。**共有されやすいファイル**（`server.ts`・`routes.ts`・`docs/spec/pr-viewer.md`・索引・golden）は持ち主を 1 人にする。
3. worktree ごとに worker を 1 つずつ、同時に起動する（1 worktree = 1 worker。子の同時数の上限まで）。担当ファイルは worker どうしで重ならない。後段に前段の完成を待たせない。

## 接続（前段が入ったら）

- 後段の枝へ、前段の枝・develop を取り込む（`cd <worktree> && git merge develop -m "merge: develop を取り込む"`）。実物どうしの試験（e2e を含む）を回し、I/F のずれは**後段の側で**直す。
- **接続の期日**: 前段が develop に入ったら、後段の枝は同日中に取り込む。放置すると衝突の負債になる。見込みの枝の一覧と接続の条件は、引き継ぎ資料（`.tmp/keep/checkpoint/NEXT.md`）に書く。
- 見込みの前提（上流の設計）が根本から変わったら、後段の見込みの部分は捨てる。

## 検査と承認の直列を減らす

- 全件検査は feature ごとに 1 回。日常は `mise run verify`。docs のみ・小さな変更は関連試験で代えてよい（その旨を報告に書く）。
- **worktree の所有**: worker を起動する直前に `python3 scripts/wt_owner.py claim <worktree の絶対パス> --kind worker --id <名前>`、worker 完了・commit 後に `release <絶対パス> --id <名前>`。**全件検査を回す前に `python3 scripts/wt_owner.py status`** で worker の lock が無いことを確かめる（検査中の編集による誤失敗を防ぐ）。残骸は `reap`。仕様: [orchestration.md](../../../../docs/spec/orchestration.md#worktree-の所有の表明)。
- 全件検査は `bg_run` で始め、待つ間に次の作業を進める。複数の枝が待つときは排他で順番待ちになる。
- 承認は直列になる。保存（`git_integrate`）は、検査が通った順にすぐ行い、承認の依頼は **1 つの応答に一覧**にして出す（保留の ID と中身の一言）。
- 複数の feature を 1 本の統合用の枝にまとめて、検査と承認を 1 回にする方式は、まだ試していない（利用者の判断を待つ）。

## worker の返答の形

結論（3 行以内）・変更したファイルと公開した関数・通した検査（件数）・契約との食い違い・未確認・次の担当への申し送り。長くなる詳細は報告のファイルに任せ、親は先頭を読む。

## 並列にしないもの

実機の実測、利用者の承認が要る操作の実行、権限の境界の最終 review（実装の後・保存の前）、承認の境界を動かす設計判断。

## 躓きの既知

- 同じ worktree の他の担当の作業中の変更で lint が落ちる → 自分のファイルだけを個別に `ruff`・`pre-commit` にかけ、最後に親が全体を直す。
- worker が本体（worktree 以外）のファイルを編集する事故 → 依頼文に「本体は編集しない」と書く。
- 子の同時数の上限で起動が断られた → todo に blocked と待ち先を書き、依頼文をキューに置く。
