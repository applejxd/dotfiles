# 確認を「人が判断を足せる操作」に絞り、残りは境界で守る

- **ステータス**: Proposed
- **日付**: 2026-10-31
- **決定者**: applejxd

## コンテキスト

pi のフルガードは、判定器が、ツール呼び出しを allow / ask / deny に振り分け、bypass が ask を allow にする、という作りだった（[ADR-0014](0014-bypass-as-ask-upgrade.md)。bypass の意味の再定義）。`pis` は、サンドボックス（Fence）を標準にし、緩和は境界が証明されたときだけ効かせる（[ADR-0018](0018-pis-sandbox-default-relax-only-when-proven.md)）。守る目的は「エージェントのうっかり」で、悪意への耐性までは求めない（[ADR-0012](0012-ocs-boundary-for-accidents.md)）。

実際の運用は、次のとおりだった（利用者の報告と観測。[調査記録 AC1](../research/agents/approval-containment-survey.md) の観測 9〜11）。

- `pis` だけでなく、素の `pi` でも、**常に bypass** で運用している（確認が煩雑なため）。
- 使い捨ての Python やワンライナーの承認は、内容を素早く読めないので、**実質、素通し**。
- 観測を取ったセッションは、**Fence の外**だった。つまり、実際には「境界なし + bypass」。
- 承認の時間切れ（5 分）が、各所の確認で起きる（[CHG-0046](../change/0046-guarded-action-timeout.md)）。

公開資料では、承認は、利用者の約 93% が承認する（承認疲れ）ので監督として弱く、**境界で「できること」を制限する**方が、強い、とされる。境界が固ければ、監督を緩めてよい（Anthropic、2026-05-25）。複数のエージェントを束ねる運用では、人の確認は、スケールしない。

## 検討した選択肢

### 選択肢 1: 現状維持（モードと ask 層を残す）

bypass のオン / オフと、`[bash] ask` の一覧を、そのまま運用する。

- **利点**: 変更が無い。境界の無い起動では、ask が、最後の防波堤になる。
- **欠点**: 実際には、常に bypass なので、ask は働いていない（形だけ）。モードという、使われない軸が残る。承認の時間切れが、解けない。

### 選択肢 2: ask 層を残したまま、bypass を既定にする

- **利点**: 実運用に合う。小さな変更。
- **欠点**: ask が、何のために残るのか、不明確になる。境界が無い起動で、守りが弱いことを、隠す。

### 選択肢 3: 封じ込めを主にし、確認を絞り、ask 層とモードを廃止する（提案）

- **利点**: 「届く範囲」は境界が強制し、確認は「人が情報を足せる」ものに絞れる。承認疲れが減り、残る確認の価値が上がる。複数エージェントの運用に合う。
- **欠点**: 境界が無い起動（素の `pi`、Windows ネイティブ、macOS）の扱いを、別に決める必要がある。静的な判定器には穴がある（Python の内部、別のプロセス）ので、境界が無いと、守りが静的な判定器だけになる。

### 選択肢 4: モデルによる自動承認（分類器）を入れる

Anthropic の自動モード型。操作ごとに、別のモデルが、承認の要否を判定する。

- **利点**: 境界が無いときにも、先走りの行動を、高い割合で捕まえる（Anthropic は約 83%）。
- **欠点**: 確率的で、100% にならない。費用と遅延が、毎回かかる。分類器の設計と保守が重い。境界を作る方が、確実。

## 決定事項

**選択肢 3 を、方向として採る**（実装の可否は、段階ごとに、データで確かめる。実装は [CHG-0054](../change/0054-containment-and-async-approval.md) が持つ）。具体的な原則は、次の 5 つ。

1. **確認は、人が情報を足せる操作だけに出す。** 条件は、「外に出る、または取り消せない」かつ「対象や範囲をエージェントが推測しうる」。例: 他人に見える投稿、保護ブランチへの統合、リモートの削除、実際のホームを変える操作。
2. **境界（OS）が、届く範囲を強制する。** 境界の内側は、素通し。境界の外へ出る要求は、「境界を広げる依頼」として確認する。
3. **拒否は、正当な用途が無いもの、または防御そのものを壊すものだけ。** 承認で通せるものは、拒否ではなく確認にする。
4. **強度は、環境（境界の有無）で決める。利用者が選ぶモードにしない。** 境界が無い起動では、必須確認の範囲を自動で広げるか、境界の中でしか動かさない。
5. **残すつまみは、能力のプロファイル（`role`）。** 信頼できない内容を読むときは、確認を増やさず、能力を減らす（Rule of Two）。

この原則に沿って、すでに実装した例: feature の worktree の `git_commit` は、場所（リンクされた worktree の `feature/*`）で決めて確認を省略し、保護ブランチへの統合は必須確認（[CHG-0053](../change/0053-worktree-integration-gate.md)）。どちらも bypass と無関係。

**未決**（このADRでは決めない。CHG-0054 で扱う）: 素の `pi` の扱い、Windows ネイティブ（[CHG-0034](../change/0034-windows-native-pi-boundary.md)）、使い捨てコードの承認、非同期の承認の受け皿。

採用が確定し、bypass の再定義（ADR-0014）や、モードの廃止に進むときは、ADR-0014 を**部分改定**する新しい ADR を起こす（本 ADR のステータスは、そのとき `Accepted` に改める）。

理由: 確認の約 93% が承認されるなら、確認は、情報を足していない。境界は、承認疲れの影響を受けず、複数のエージェントにも同じに効く。分類器（選択肢 4）は、境界が作れない環境の補助としては有効だが、境界の代わりにはならない。

## 決定の確認方法

- 段 1 の集計で、ask の規則ごとの承認率を出す。承認率が高く、可逆な規則が、多数あれば、方向は妥当。承認率が低い（拒否が多い）規則があれば、その規則は、確認ではなく拒否の候補。
- 必須確認の件数と、承認 / 拒否の比を、運用で追う（件数が多すぎれば、絞りが足りない）。
- 実装の進捗は、ここに書かない（CHG-0054）。
