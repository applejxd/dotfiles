# CHG-0026: 専門スキルを、専用の子エージェント（migrator・writer）に持たせる

- **状態**: Paused
- **更新日**: 2026-10-20
- **基準**: コミット 0485d83、pi 1.3.0
- **注記**: 構想のみ。実装はしない

## 目的と非目的

**目的**: 移行・執筆のような専門的で長いスキル（`cuda-version-migration`・`uv-migration`・`ipynb-to-marimo-pages` など）を、
親の一覧から外し、専用の子エージェント（例: `migrator`・`writer`）だけが持つ形にできるかを整理する。

- 親の system prompt の一覧（今は約 4k トークン）を軽くする
- 長い手順と作業の履歴が、親の文脈を占めないようにする
- 役割ごとに、専用の system prompt・ツール・モデルの段（`tier`）を持たせる

**非目的**: `away-shift` を子へ移すこと（**親のスキルのまま残す**。利用者の決定。ハーネスの構築が安定したら大量に使う）。
`commit` は、すでに `commit` 役割の子が計画を作る形で、別の話。

## 実現できるか（確かめたことと推測を分ける）

**できる。新しい基盤は要らず、小さな変更で足りる**（推測を含む。実装は未確認）。

確かめた事実:

- 子は別プロセスで動き、親の `--skill` 引数を引き継ぐ（`home/dot_config/pi/harness/index.ts` の子の起動。`PI_HARNESS_ROLE` に役割の `profile` を渡す）
- 役割は `common.toml.tmpl` の `[pi.agents.<名前>]` で定義する（`profile`・`tier`・`description`・`system`）。
  すでに `commit` 役割の `system` が「commit スキルの書式に従って」と、スキルを名指ししている
- pi は `--skill <path>` で明示したスキルを、`--no-skills` のときも読む（`docs/skills.md`・`cli.md`）。
  `disable-model-invocation: true` のスキルは、自動選択の一覧から外れる
- フルガードの一覧は、`disableModelInvocation` のスキルを載せない（`index.ts` の `before_agent_start`）

必要になる変更（案）:

1. `[pi.agents.<名前>]` に `skills = [...]` を足し、生成器が `rules.json` へ出す
2. 子の起動で、その役割の `skills` を `--skill` に足す
3. 専用のスキルは、**pi が自動で探さない場所**（例: `home/dot_config/agents/skills/<名前>/`）へ置く。親の一覧に出ず、子にだけ渡る

## 制約（実装前に決める）

| 制約 | 内容 | 影響 |
| --- | --- | --- |
| 子は子を作れない | 子エージェントでは `guarded_task` が登録されない | 分担翻訳のように、スキルの中で子を使うもの（`arxiv-paper-ja`）は、子へ移せない |
| 子は利用者に質問できない | 承認や質問は `blocked` として親へ返る。**中継は未実装**（下の「前提: 子の質問の中継」） | 対話しながら進めるスキル（`powerpoint-studio` の設計の確認など）は、中継ができるまで向かない |
| 1 往復の上限 | 15 分で打ち切る | 長い移行は、続けて依頼するか、上限の見直しが要る |
| 結果は要約で返る | 途中の様子は、`/agent`・`status` でしか見えない | 利用者が途中経過を見たい作業は、親の方が向く |

## どのスキルが向くか（description と行数だけからの推測。中身は読んでいない）

| スキル | 向き | 理由 |
| --- | --- | --- |
| `cuda-version-migration` | 向く | 実行と確認が中心。質問は少なそう |
| `uv-migration` | 向く（質問の中継があれば） | 実行中心だが、方針の確認が入る |
| `ipynb-to-marimo-pages` | 向く | 変換と整形が中心 |
| `arxiv-paper-ja` | 向かない | 分担翻訳で子を使う（子は子を作れない）。親が指揮役のまま |
| `powerpoint-studio` | 保留 | 対話が多い。質問の中継の後 |
| `away-shift` | **移さない** | 親のスキルのまま。離席中に反復し、再開・停止の手段を親が持つ |

## 実装案（防御の強さの違う 3 案）と、利用者の操作の変化

| 案 | 内容 | 塞ぐもの／残るリスク |
| --- | --- | --- |
| 体験案 | 移さない。専門スキルは `disable-model-invocation: true` にして一覧から外し、`/skill:名前` で呼ぶ | 一覧は軽くなる。文脈の分離は得られない。自動選択を失う |
| 標準案 | 上の `skills` 方式。`migrator`・`writer` は既存の `worker` と同じ判定器・サンドボックスで動かす | 子の書き込み範囲は担当の作業ツリーまで。スキルの内容は chezmoi 管理で改ざんされにくい。質問の中継が無い間は、対話の要るスキルが使えない |
| 堅牢案 | 標準案に加え、役割ごとに書き込み範囲をパスで絞り、スキルのディレクトリを読み取り専用に固定し、子のネットワークを許可リストにする | 想定外の書き換えは減る。設定が増え、役割ごとの調整が要る |

推奨は**標準案**（構想の段階の判断。実装時に再評価する）。

| 観点 | 今 | 標準案のあと | 良くなる / 悪くなる |
| --- | --- | --- | --- |
| 親の一覧 | 専門スキルの description が毎回載る | 載らない | 良くなる（約 1k トークン。数は見込み） |
| 自然な言い方での発動 | スキルの description で自動 | 役割の description で、親が子へ委任 | 同程度（委任の判断は親のモデル次第。未確認） |
| 進行の見え方 | 親の画面で逐次見える | 要約が返る。途中は `/agent`・`status` | 悪くなる |
| 対話（確認・質問） | その場で答えられる | 中継ができるまで不可 | 悪くなる（段 2 が前提） |
| 長い作業の文脈 | 親の文脈を占める | 子の文脈に閉じる | 良くなる |
| 並列・背景での実行 | しにくい | `background` で並列にできる | 良くなる |

## 前提: 子の質問の中継（ask-user 段 2 の構想）

利用者との合意（2026-10-20）。親の `ask_user`（段 1）の実装後に、実機で使い勝手を見てから着手する。

1. 子の `ask_user` を UI へ出さず、親へ中継する。RPC の対話の要求は、応答があるまで子の側でブロックするので、
   親の `Job` が要求の id を持ち、`guarded_task {jobId, answer}` で答えると、子は同じ文脈で再開できる
2. 親のモデルが答えられなければ、親が `ask_user` で利用者に聞き、その答えを `answer` で渡す
3. 質問には**推奨**（`recommended`）を必須にし、`blocking: true` の質問は、時間切れでも自動で進めず停止として返す
4. 利用者への質問が時間切れ（既定 10 分、仮）なら、推奨で進めて `defaulted: true` を結果に残す。
   子が親に長く答えられなければ、`Job` が子の推奨で自動回答する（待ち上限は 20 分、仮。利用者への質問より長くする）。待つ間は 15 分の計時を止める
5. 親が答えるのは、子の選択肢の範囲内を原則とする。子の承認待ち（ask）は、今までどおり `blocked` で返し、親は代行しない
6. 未確認: RPC ホストの `select` の `timeout` の実装、時間切れと Esc の区別

## 再開の条件

1. 子の質問の中継（ask-user 段 2）が使えること
2. 圧縮の修理が済み、親の文脈の管理が安定していること
3. 専門スキルの利用が増え、一覧の費用や文脈の占有が実際に気になること

## 未解決

- 子の上限（15 分）で足りるか
- `writer` の対象（`arxiv-paper-ja`・`powerpoint-studio` を含めるか）
