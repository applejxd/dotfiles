# 隔離の単位は「開発環境」にする（用途別の 3 パターン。WSL は開発単位の専用ディストロ）

- **ステータス**: Accepted（方針）。実装・検証は未了（下の「未決」）
- **日付**: 2026-11-06
- **決定者**: applejxd

## コンテキスト

他のリポジトリで AI コーディングエージェント（pi）を動かす隔離方式を選び直した（[調査と試作の記録](../research/agents/isolation-reselection-2026-11.md)）。実機の試作と調査で分かったこと:

- **プロセス単位の OS サンドボックス**（Fence・nono・OpenShell など）は、docker・compose・GPU・apt を使う開発と両立しない。Claude Code の公式 docs も、docker はサンドボックスの外で実行する案内（`excludedCommands`）。OpenShell は apt・compose を設計上満たさず、rootless Docker は未対応。nono は WSL2 で、ホストの実行経路（WSL interop・docker のソケット）に内側から届いた。
- **microVM** は WSL2 で GPU と両立しない（GPU は VFIO が前提で、WSL2 は `/dev/dxg`）。
- **rootless Docker のコンテナ**（`pisd`）は、GPU・Web 公開・画像・apt・永続・認証の分離・外向きの許可リストまで、実機で通った。一方、**コンテナの入れ子**（compose を内側で動かす）は特権の sidecar が要り、入れ子の中の GPU は WSL2 では未検証。
- 主流（クラウド型エージェント・開発環境・devcontainer）は、**環境（VM・コンテナ）ごと隔離し、エージェントも docker もその中で動かす**。守りの中心は、資格情報を環境ごとに限定する（読み取り専用・短命）・成果をブランチで取り出す・外向きを絞る・破壊的な操作を確認する、であり、環境の中に入れ子のサンドボックスを作る例は見当たらなかった。

用途の事情（この環境の利用者）:

- **SLAM の開発**: WSL 上で行う。**AI の推論（GPU）が必須**で、**rerun と ROS は外部との通信が前提**（ROS の DDS・rerun のビューア・センサなど）。
- **別のシステムの開発**: `docker compose` 構成で、サービスのコンテナが GPU を使い、認証つきのレジストリからイメージを pull する（具体は公開リポジトリに書かない）。
- **外部のコードを動かす通常のリポジトリ**: 認証を内側に入れず、外向きを絞りたい。
- **dotfiles 自身**: 未コミットの変更とホストの道具が要る（[ADR-0025](0025-dotfiles-dev-without-os-sandbox.md)）。

## 検討した選択肢

- **A. すべてを `pisd`（コンテナ）に寄せる**: compose と GPU に、特権の入れ子（DinD）が要り、ROS の DDS と rerun の外部通信は、内部網と proxy の構成と合わない。
- **B. Fence（OS サンドボックス）を続ける**: docker・compose・GPU・apt と両立しない。WSL2 で、自作の層が重い（約 4,500 行）。
- **C. microVM・OpenShell**: 上記のとおり、この環境の要件を満たさない。
- **D. 開発単位の環境で切る（採用）**: 主流と同じ形で、compose・GPU・ROS・rerun・apt が素直に動く。

## 決定事項

**隔離の単位は「環境」にする。用途ごとに 3 つのパターンを使い分ける。**

| パターン | 用途 | 隔離と守り |
| --- | --- | --- |
| P1 | 自分の信頼できるリポジトリ（dotfiles） | フルガードのみ（ホストの pi） |
| P2 | 外部のコードを動かす通常のリポジトリ | `pisd`（rootless Docker のコンテナ。認証は Envoy の sidecar だけが持ち、外向きは squid の許可リスト。独立 clone）。apt が要る作業は名前つきの永続コンテナ |
| P3 | **開発単位の環境**（SLAM・AI の推論・compose・ROS・rerun・認証つきレジストリの pull） | **WSL は開発単位で専用ディストロを切る**（ネイティブ Ubuntu は Incus などのシステムコンテナが候補）。エージェント・docker・GPU を同じ環境に置く。環境は作成・削除が容易で（テンプレートの export/import）、資格情報は環境ごとに限定する（読み取り専用・短命）。成果はブランチで取り出す。フルガードは併用する |

補足:

- **`pisd` の範囲は P2 に絞る。** コンテナの入れ子（`--dind`）と入れ子の中の GPU は作らない（実装は保留の枝に残す。再開の条件は、専用環境で足りないと分かったとき）。
- **Fence（OS サンドボックス）は縮小の方向。** 縮小・撤去は別の案件で、費用つきで段階的に提案する（棚卸しでは、置き換わる部分が約 45%、正味の削減が約 2〜3 割と見込まれる）。
- **WSL2 の制約を設計で吸収する**: 全ディストロが 1 つの VM とカーネルを共有する（VM の境界ではない）、`.wslconfig` の上限は全体で 1 つ、mirrored のネットワークでは単位間でポートが衝突する（単位ごとに割り当てる）、GPU は共有。
- **LLM の認証の置き場**: 環境の中のエージェントから読める位置に置かない案として、mirrored のネットワークで共有されるホストの `localhost` に、認証ブローカー（Envoy）を常駐させて使う（未検証）。

## 未決

案件は [CHG-0064](../change/0064-dev-environment-isolation.md)（ネイティブ Ubuntu 側は保留で、ネイティブ機のセッションで継続する）。

- エージェント（pi）を環境の中で動かすか、ホストの pi が `ssh` で操作するか（[専用 WSL2 の評価](../spec/sandbox/wsl-sandbox.md)。ホストからの操作は `remote_exec` の緩和が展開後にも効くかの確認が要る）。
- 認証ブローカーの常駐化と、環境からの到達範囲。認証つきレジストリの資格情報の置き場。
- 開発単位の作成・削除のコマンド（`dev-new`・`dev-rm`・`dev-ls`・`dev-snap`。バックエンドを隠した同じ形）と、WSL 版（既存の `create.ps1` の拡張）の実機の確認。
- ネイティブ Ubuntu 側（Incus の導入前の調査）。

## 見直しの条件

専用環境で、資格情報の限定・外向きの制御・作成削除の速さのいずれかが実用にならないと分かったとき。ネイティブ Ubuntu で OS サンドボックスや Incus の入れ子が実用になると分かったときは、P2・P3 のバックエンドを見直す。

## 決定の確認方法

- 開発単位の環境で、compose・GPU・ROS・rerun・認証つきレジストリの pull が通ること（実機）。
- 環境の作成と削除が、手順 1 つで繰り返せること。
- 環境の中のエージェントから、ホストの認証・ファイルへ届かないこと（否定試験）。
