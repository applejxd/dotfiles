# 親を「計画・判断・委譲」に絞る仕組みの設計（`plan` の子の案）

観測日: 2026-10-30。依頼: 親エージェントを、命令（プロンプト）ではなく仕組み（ツールの分離・権限・フック）で、計画・判断・委譲・承認に絞る設計。
作成: `plan` の子（深く考える階層）。pi 本体の docs（作業ツリーの外）は、子の権限で読めず、挙動は、このリポジトリでの使用実績と試験に基づく（**未確認**）。
案件は [CHG-0045](../../change/0045-orchestrator-parent.md) 段 6。今の実装の仕様は [親の絞り込み](../../spec/guard/pi-subagents.md#親の絞り込みorchestrate)。

## 核となる仕組み

- `[pi.profiles.orchestrator]` を許可リストとして 1 つだけ定義し、その `tools` から、(1) 見えるツール（`setActiveTools`、毎ターン再適用）と、(2) 実行（判定器の「役割に無いツールは deny」）の両方を絞る。別の keep-list は持たない。許可リストなので、将来増えたツールも既定で隠れる（fail-closed）
- 判定器の `role` を実行時に切り替えられるようにする（`bypass` と同じく関数渡し）
- 利用者専用の `/orchestrate on|off`（モデルは呼べない）で、いつでも通常の親へ戻せる
- 強制できないもの: 依頼文の質・判断の中身（`auditFormat`・`check_conditions` は警告止まり）。強制できるもの: ツールの有無・引数とパスの制限・回数の予算・結果の大きさ・子の起動条件（推測。実装前）

## 3 案

| | 弱: 通知・統計 | 中: opt-in の `/orchestrate`（**選んだ**） | 強: 既定 ON |
| --- | --- | --- | --- |
| 仕組み | `delegate-nudge` に注記を足す。ツールは変えない | 許可リストと判定の二重化。親は読み取りを残す | 中に加え、起動時 ON・`read` の制限（`.tmp/subagents/**` だけ、または 1 ターンの読み取り予算）・結果の上限・親専用の検査操作 |

| 実装 | 小 | 中 | 大 |
| リスク | 効かない | 詰まる場面（検証・コミット）に代替経路が要る。`/plan` との競合 | 親が詰まる。`/bypass on` で通そうとする誘惑 |

## ツールの分離（案）

| 区分 | ツール | 備考 |
| --- | --- | --- |
| 親専用 | `guarded_task`・`guarded_action`・`ask`・`todo` | 子には登録されない |
| 親の読み取り | `guarded_read`/`grep`/`find`/`ls` | 中は全部残す。強は `read` を `.tmp/subagents/**` に限る |
| 子の作業 | `guarded_bash`/`edit`/`write` | `worker` に置く。親では隠れる |
| 親専用の検査操作（`[[pi.actions]]` に追加） | `check_verify`（`mise run verify`）・`check_lint_docs` など、引数なしの固定 argv | 結果は末尾 8000 字に限られ、親の文脈を守れる。確認は bash と同等（素の `pi` では確認あり。`pis` で境界が証明されたときだけ省く）。**承認ポリシーに触れるので、実装の前に `review`** |

## 環境別の変化

| 環境 | 変化 |
| --- | --- |
| `pis`（境界あり・bypass 既定 ON） | 親が絞られる。`worker` の shell は境界の緩和で通る。最も向く |
| 素の `pi`（Unix） | 同じ絞り。ただし `worker` の shell は ask で止まる。検証は親の `check_*` に頼る。**親の `/bypass on` が前提**（親の直接実行は防ぐが、委譲先の権限は縮まらない。bypass は `worker` に継承される） |
| Windows | 対象外（`guarded_task` が無い） |

## 段階的な導入と元に戻す手順

1. 役割と生成器（実装済み）。2. 実行時の切り替え `/orchestrate`（実装済み）。3. `check_*`（`review` を通してから）。4. 計測（`delegate-stats` に印。3 種類のタスクで、親が直接 / orchestrator を比べる: 親のトークン・読み取り量・待ち時間・再作業・拒否の回数）。5. 数値が出たら、強案（読み取りの制限・結果の上限・既定 ON）を足すか判断する。
元に戻す: 利用者が `/orchestrate off`。全体は `[pi.orchestrate] default = "off"` にして `chezmoi apply`、またはコミットを revert。

## リスク

親が詰まる（特に素の `pi` での検証）/ モデルが隠れたツールを呼び続け、拒否の往復が無駄になる / 親の文脈は、子の結果（1 件あたり最大 2 万字）で別に膨らむ / 小さな頼みが遠回りになる / 確認の疲れで `/bypass on` を使う誘惑 / `plan` と `ask` が `setActiveTools` を上書きし合う / `/reload` で ON が黙って外れる。
