# 「長い文脈は要らない」（NVIDIA ほか）の要点と、圧縮の方針への含意

- **日付**: 2026-11-09（調査）。論文の公開は 2026-11-03。
- **出典（調べて確かめた）**:
  - 論文: Belcak ほか「You don't need long context」、arXiv:2611.05306（cs.AI、2026-11-03、技術報告 31 ページ。<https://arxiv.org/abs/2611.05306>、HTML 版 <https://arxiv.org/html/2611.05306>）。数値は HTML 版の本文・表から。
  - 紹介の投稿（外部の二次情報。結論の根拠にはしない）: alphaXiv の投稿（2026-11-06）と、別の個人の投稿（2026-11-05。「Claude Code が状態表示を短いメモに変えた」という記述は**未確認**）。どちらも、この論文を指している。
- **目的**: 圧縮（コンパクト化）の方針を、論文の知見・pi 本体と package の調査結果・自分の運用の集計から決める。この文書は**論文の要点・集計・確定した方針**。方針は下の「確定した方針」。

## 論文の主張（確かめた事実）

1. **後ろのトークンほど、生成の費用が高い。** 自前で配備した 3 つのオープンなモデルで、文脈窓を 256K から 16K へ縮めると、生成 1 トークンあたりの費用が 3.6〜7 倍下がる（GLM 3.6 倍・Kimi 5.6 倍・Qwen 7 倍）。生成の遅延も、文脈が長いと約 2 倍になるモデルがある。**ただし小売の API の価格は、文脈の長さによらず 100 万トークン単位で一律のため、利用者にはこの差が見えない**（論文の説明）。
2. **頻繁な圧縮でも、精度はほぼ保たれる。** 6 つのベンチ（SWE-bench Verified・Terminal-Bench・SWE-bench Multilingual・FRAMES・BFCL・Tau2）で、文脈の上限を 48K〜6K まで下げ、圧縮の回数を増やしても、全履歴を持つ基準との差は Opus 4.5 で −3.7〜+5.6 ポイント、GPT 5.6 Sol で −3.3〜+4.4 ポイント。22 設定のうち、2 ポイントを超えて下がるのは各モデルで 5 以下。
3. **推定の費用は 2.2〜8.8 倍下がる**（Opus 4.5 が 2.2〜8.8 倍、GPT 5.6 Sol が 2.4〜5.0 倍）。これは、上の 1 の費用の差を式で当てはめた「推定の最適化された小売費用」で、**実際の請求ではない**。圧縮で「やり直し」が増えて総トークンが増える懸念は、実験では概ね起きなかった。
4. **長い入力も、長い文脈は要らない。** 長い資料をファイルとして置き、`sed`・`awk` などで**選択して読む**形にすれば、長入力の作業は、長い作業の問題に帰着する。
5. **行動ごとの圧縮でも保てる**（SAC。1 回の文脈で行動を 1 つだけ行い、状態の要約だけを次へ渡す）。Opus 4.5 は SWE-bench Verified で 70.0 → 70.2（ほぼ同じ）、Terminal-Bench で +4.6 ポイント。GPT 5.6 Sol は −2.0・−3.3 ポイント。作業中の最大の文脈は 130〜200K から 15〜37K に下がる。
6. **履歴が要る作業はある。ただし長い文脈とは別。** 圧縮は不可逆で、圧縮の圧縮では情報がさらに落ちる。全履歴をファイルに残し、選択して読む手段を持たせれば、履歴の参照は長入力の問題に変わる。

### 自分の運用での集計（2026-11-09。1 人・単一の運用）

論文の根拠は、**人が介在しない小さな実験**（ベンチ・bash 中心の小さな harness・2 つのモデル）に偏っている。人が頻繁に指示する運用では、論文の主張（長い文脈は品質を下げる）は**確認できなかった**。過去のセッション（104 件・assistant ターン 22,428・圧縮 54 件。sonnet-5.5 が 98%）を集計した。

- **文脈の長さ別の指標**（claude-sonnet-5.5。[ ] は 95% 信頼区間）:

| 文脈 | ターン数 | 実エラー率 | 訂正率 | 不満手がかり率 | 取りこぼし |
| --- | --- | --- | --- | --- | --- |
| 0-50K | 612 | 10.0% [7.9-12.6] | 1.8%（2/111） | 6.3%（7/111） | 0/111 |
| 50-100K | 836 | 6.4% [5.0-8.2] | 3.0%（4/133） | 6.8%（9/133） | 0/133 |
| 100-150K | 1,829 | 4.6% [3.8-5.6] | 2.4%（4/164） | 9.8%（16/164） | 0/164 |
| 150-250K | 3,573 | 4.2% [3.6-4.9] | 5.2%（14/271） | 9.2%（25/271） | 0/271 |
| 250-500K | 7,411 | 3.6% [3.2-4.0] | 3.3%（16/484） | 6.8%（33/484） | 0/484 |
| 500K 以上 | 7,728 | 3.7% [3.3-4.1] | 2.6%（14/536） | 6.5%（35/536） | 0/536 |

- 文脈が 25 万を超えるターンが **69%**。長さに沿った品質の低下は見えない。実エラー率は、むしろ短い側のほうが高い（セッションの序盤に偏るため）。ターン番号で層別（T400 以降）しても、3.8% → 3.5% で平ら。
- **取りこぼし**（「さっき言った」の類）は、判定した利用者の発話 1,716 件で **0 件**。圧縮の後 10 回の発話でも 0 件。
- 応答の遅延の中央値は 3.5 秒 → 7.5 秒と増えるが、出力 1,000 トークンあたりの秒は 9〜10 で平ら。長さそのものではなく、出力の増加・tool 呼び出しの前処理に由来する可能性が高い。
- **圧縮の分布**（54 件）: 圧縮の前の文脈の中央値は **約 79 万**（最小 約 21 万・最大 約 98 万。50 件が 60 万超）。圧縮の直後の文脈の中央値は約 10 万（縮小率の中央値 0.12）。要約の長さの中央値は約 2.2 万字。同一セッション内の圧縮の間隔の中央値は 350 ターン。
- **圧縮の前後**（前後 5 ターン・20 ターン）: 実エラー率に差は無い（2.3% → 2.8%・3.0% → 3.3%）。**不満の手がかりは、圧縮の直後に増える傾向**がある（前 5 ターンで 4.8% → 後 20 ターンで 11.3%）。ただし件数が少なく、信頼区間が重なる（有意ではない。要約の取りこぼしの可能性は、推測）。
- **限界**: 1 人・単一の運用。500K 超に達したセッションは 11 件で、ターンはその少数に集中する。圧縮が 60 万〜98 万でしか起きていないため、「短く圧縮したほうが良いか」の比較対象が無い。判定の規則は粗い（「ok」「統合して」のような発話が大半で、訂正を言わずに諦めた場合は記録に出ない）。

## 「良い圧縮」の特徴（付録 A。実装に直接使える）

- 圧縮を、通常の**要約**として扱うと最適ではない。要約は全部の事実に等しい重みを置き、繰り返しの多い部分に偏る。
- 最も精度を保つ圧縮は、実行の**物語**ではなく、**これからの作業のために選び抜いた brief**。次を含む:
  1. 依頼の**逐語に近い写し**。
  2. 現在の作業・意図・**次の手**。
  3. 将来の実行に直接関わる成果物: **分解した計画**・**完了の条件**・参照すべき情報や成果物への**ポインタ**。
- 圧縮の指示（付録 G）の項目: 目的（1 行）／確かめた事実（正確なパス・コマンド・値・エラー。観察と未検証の考えを分ける）／加えた変更（ファイルごとに、検証済みか）／検証（実行した検査・結果・障害と回避策）／**行き止まり**（繰り返さない失敗）／残りの計画（順序・次のコマンドか編集・完了の条件）。切り詰められた出力には、取り直す狭いコマンドを書く。観察を作らない。
- **人が介在する運用**では、人の指示・好みも、圧縮に含める必要がある（人の次の指示で、続きの作業が変わるため）。

## 限界・注意（鵜呑みにしない）

- 実験は、bash 中心の小さな harness（mini-swe-agent 系）・ベンチ・2 つのフロンティアモデルで、**人が頻繁に指示する対話は対象外**。pi の運用（人の承認・子エージェント・長い対話）にそのまま当てはまるとは限らない。上の集計でも、確認できなかった。
- 費用の減少は**推定**で、小売価格が一律なら、請求の減少としては見えない。**確実に得られるのは、遅延の低下と、文脈の肥大による品質の低下の回避**（論文の主張の範囲では、精度は同等）。サブスクリプションの上限（リクエスト数）では、圧縮の回数が増えると、むしろ消費が増える可能性もある（推測）。
- 圧縮の質は、圧縮の指示とモデルに依存する。指示の改善は、論文の付録 A・G が出発点。

## 我々への含意

- 自作の運用で、圧縮の前に決まった保存（引き継ぎ文書・docs の反映・todo）を行い、圧縮の後に再開していた。これは、論文の「選び抜いた brief」＋「全履歴をファイルに残して選択して読む」と同じ方向だった。
- stock の pi で再現するには、(a) 圧縮の**しきい値**、(b) 圧縮の**指示**を brief の形にする、(c) 圧縮の**前後**に処理を挟む、の 3 点が論点。pi 本体の標準で足りる範囲は、下の「調査の結果」。

## 調査の結果（stock の pi の圧縮。2026-11-09）

出典は、pi 1.5.0 本体の文書（`compaction.md`・`settings.md`・`extensions.md`）と、候補 package の tarball（`npm pack` を展開して読んだだけで、実行なし）。13 件を評価し、原文は archive の pi-eval。

- **既定のままだと遅すぎる**: pi の自動圧縮は「窓の残りが `reserveTokens`（既定 16,384）を切ったとき」に始まる。既定のモデル（Claude Sonnet 5.5。窓 1,000,000 トークン）では、**約 98 万トークンまで圧縮されない**。窓の上限に近すぎる。
- **本体の設定で足りるもの**: しきい値（`compaction.reserveTokens`・`compaction.modelOverrides`。窓の残りで指定）、手動の `/compact [指示]`、要約の構造（Goal / Progress / Next Steps / 読んだ・変えたファイル）。
- **足りないもの**: ① 要約の指示の**恒久設定**（本体に設定項目がない）、② しきい値を**絶対のトークン数・%で**指定すること、③ 圧縮の前の保存、④ 圧縮の後の再開。
- **候補の評価**（一部）:
  - **`@thgilciffart/pi-compaction`（0.3.1。MIT。月間 DL 445。2026-11-01 公開。73 KB。実行時の依存なし。ネットワーク・子プロセスなし）**: ①②を満たす。`defaults.instructions`（要約への追加の指示）、`auto.thresholdTokens`（絶対）または `thresholdPercent`、モデル別の方針、`style: custom`（要約のプロンプト全体の差し替え）、`onError: "default"`（失敗したら本体の既定で圧縮）。本体の `session_before_compact` を使うので、要約を置き換える package と併用できない。→ **採用（指示の恒久設定だけ。しきい値は使わない）**。
  - `pi-cached-compaction`（0.2.0。要約を prompt cache を読んで作る）: 実利が大きいが、アイドル時の自動圧縮が離席中の運用と干渉しうる。→ 保留（試用してから）。
  - 除外: `pi-blackhole`・`pi-observational-memory`・`pi-hermes-memory`・`pi-memory`（記憶系で目的が別。課金される背景 worker・ネイティブ依存・外部送信のいずれか）、`po-autocompact`（BUSL・alpha）、`pi-voluntary-compaction`（組み込みの bash を置き換える）、`@henryqw/pi-auto-compact`（本体の圧縮の無効化が必須）ほか。
  - **圧縮の前の保存と圧縮の後の再開を、両方満たす package は、調べた 13 件に無かった。**

## 確定した方針

利用者が決めた（2026-11-09）。**自作なし**（[ADR-0031](../../adr/0031-evaluate-existing-extensions-first.md)）。しきい値を下げる根拠は、上の集計に無い。**これまでの運用（約 79 万で圧縮）に近い 70 万へ寄せ、要約の質（brief の指示）に気を配る。**

1. **しきい値: 70 万トークン（窓の 7 割）。本体の設定だけで行う。**
   - `compaction.modelOverrides["github-copilot/claude-sonnet-5.5"].reserveTokens = 300000`（`reserveTokens` = 窓 − 発動点。1,000,000 − 300,000 = 700,000 で発動）。
   - 窓が 100 万の他の常用モデル（`claude-opus-5.5`・`claude-sonnet-5`・`gpt-6-sol`・`gpt-5.3-codex`・`gemini-3.8-flash`）にも、同じ 300,000 を補う（窓の 3 割。`models-store.json` の `contextWindow` で確認）。窓が違うモデル（`claude-haiku-4.5` は 20 万）には補わない。
   - `@thgilciffart/pi-compaction` の `auto.thresholdTokens`・`thresholdPercent` は**設定しない**（作業の区切りでの圧縮と、途中の安全網という二段は採らない。区切りの圧縮を足す根拠は、集計に無い）。
2. **要約の指示**: `@thgilciffart/pi-compaction` の `defaults.instructions` に、brief の指示（日本語）を**恒久設定**する。論文の付録 A・G と、人が介在する運用の注記に基づく。
   - 経過の物語ではなく、続きの作業のための brief にする。
   - 項目（この順）: ① 利用者の依頼・目的（ほぼ逐語）② 利用者の指示・好み・制約・確定した決定（最新のものだけ）③ 未回答の判断・確認待ち ④ 現在の作業・次の一手・完了の条件 ⑤ 残りの計画・todo ⑥ 確かめた事実（観察と未検証の推測を分ける）⑦ 変えたファイルと検査の結果 ⑧ 行き止まり ⑨ 実行中の子・背景ジョブ ⑩ 参照すべきファイル。
   - 観察を作らない。切り詰められた出力は、取り直す狭いコマンドを書く。利用者の指示と好みは、削らない。
   - 全文はリポジトリの `home/dot_pi/agent/modify_compaction.json.py.tmpl`（正本）。
3. **失敗の安全策**: `onError: "default"`（要約に失敗したら、本体の既定で圧縮する）。要約のモデル・思考量は会話のままにする（`model`・`effort`・`style`・`auto` は設定しない。思考を `off` にすると過去に 400 エラーになった記録がある。[記録](pi-compaction-400-history.md)）。
4. **圧縮の「保存」と「再開」は自作しない。** 要約が brief になるので、同じセッションの中の保存は要らない。セッションをまたぐ引き継ぎは、pi のセッションの再開（`/resume`・`pi -c`）で足りる。**長い自走の途中の圧縮の後に、止まって待つ**ことが実際に起きたら、そのときに約 10 行の自作（`session_compact` で `sendUserMessage`。ADR-0031 の例外の条件）を検討する。
5. **文脈を短く保つ運用**（論文の含意）: 大きな出力はファイルに出して選択して読む（`read` の offset・limit、`grep`、`pi-background` のログ）。長い調査・レビューは子（`pi-subagents`）に任せ、親の文脈を短く保つ。

配備の仕組みは [エージェント設定の生成](../../spec/agent-config-generation.md) の「圧縮の設定（stock）」。
