# 修理の進め方（既存の拡張・ガード・起動の不具合）

作る場合の段 1〜5 とは別の流れ。**直しが、防御の強さや利用者の操作（確認の回数・通知・拒否・表示）を変えるときだけ**、
[提案のひな形](proposal-template.md) の 3 案と操作の変化の評価を出して承認を待つ。挙動を変えない不具合の修正は、
原因・直し・固定を報告すれば足りる（ただし、変わる挙動は必ず報告する）。

## 進め方

### R1. 症状を切り分ける

次を 1 つずつ確かめて書き出す。

- 起動の違い: `pis` か素の `pi` か。サンドボックスの内か外か。`-ne` / `-nbt` / `--no-approve` で何が外れているか
- pi の版（`pi --version`）。[pi-upstream.md](../../../../docs/spec/pi-upstream.md) の**該当する行の「確認した版」**（表全体ではなく）と比べ、違うときは変更履歴を先に読む
- **決定的か、ときどきか。** どの PC でも出るなら、環境や一時的な通信の問題より、**共通するもの（pi の版、設定、自作の呼び出しの経路、モデル・認証の条件）を先に列挙し**、
  とくに自作側の呼び出しの形と設定を疑う。仮説を早く固定しない。
  環境ごとに違うなら、配置・PATH・プロキシ・サンドボックスの写し漏れを先に疑う
- 利用者の画面だけに出て、記録に残らないものは、まず全文を取れる形にする（通知・ログ）

### R2. 先に広く調べる

原因の分からない不具合は、手元の調査より前に、まず pi 本体の該当の仕様を読み（[読む順序](pi-spec-guide.md)。文書・型・ソース・変更履歴）、
公式の Issue・変更履歴・ドキュメントと、同じ症状の報告を検索する
（エラー文・症状・環境の語で。検索語と当てた先を報告に残す。反例も隠さない）。そのあとで、このリポジトリの既存の知見に当たる。

- [pi の公式仕様と実測の棚卸し（表 B）](../../../../docs/spec/pi-upstream.md): 公式に書かれていない挙動で、実測して頼っているもの
- [pi の内部の挙動に頼る点](../../../../docs/spec/pi-guard.md#pi-の内部の挙動に頼る点)と
  [実機で確認する項目](../../../../docs/spec/pi-guard.md#実機で確認する項目)
- 下の「既知のパターン」

### R3. 再現する（症状に合う経路を選ぶ）

- **記録を読む**（どの症状でも最初）: セッション記録（`~/.pi/agent/sessions/**/*.jsonl`）には、圧縮の要約やツール結果の実データがある。事実の根拠になる
- **偽のモデル**: ロジック・判定・ツール結果・圧縮・子の不具合に向く。`test/agents/pi/faux.ts` に、必要な応答（例: 出力の上限で切れた応答）を出す環境変数を足す。通信なしで回る
- **小さな実セッションで実際のモデル**: 提供元やモデルとのやり取り（圧縮・認証・リクエストの形・エラーの文面）の不具合に向く。費用は小さい。
  **この種類の症状は、ソース読みや検索より先にこれを試す**（圧縮の失敗は、実モデルで 1 回回しただけで失敗の全文が取れた）。大きな文脈の再現は費用がかかるので最後
- **表示・確認画面の不具合**: tmux で対象の `pis` を起動して観察する（申し送りと画面の写し取り）。
  `scripts/pi-harness-spike/tui-run.sh` は**試作の並列確認画面専用**で、既存拡張の表示はそのままでは見られないが、tmux の使い方の型になる
- **利用者の実機**: 環境固有の症状。使い捨ての agent 置き場で行い、**本物の `~/.pi/agent` を汚さない**（調べる準備で空ファイルを作った前例がある）

### R4. 原因を確定する

- 確かめた事実と推測を分ける。ソースにどう書かれているかは事実だが、**実行時にそうなるかは、実測するまで「読みからの推測」**と書く（[pi 本体の仕様を当たる方法](pi-spec-guide.md)）
- 候補が複数残るなら、**直す前に観測手段を足す**（失敗理由を全文で出す、頻度を数える）。費用の大きい再試行を、原因が分からないまま足さない
- 出所の分かる手がかり（エラー文の先頭、呼び出しの引数の差）を、pi 本体のソースと**自作の呼び出し**で突き合わせる。
  自作の呼び出しが、本体の経路と違う引数（渡していないもの）を持っていないかを見る

### R5. 直す

- 小さく直す。同じ型の別の箇所（同種のツール、同じ関数の別の呼び出し）がないかを探して、一緒に直す
- 直しで、利用者の操作が変わるなら、先に評価して報告する

### R6. 固定する

- **自動試験が組める修理は、試験を足し、直しを外すと落ちることを確かめる**（変異確認）。落ちない試験は、何も守っていない。
  見た目など、自動試験で捕まえられない症状は、再現の条件・直しの前後の観測結果・未確認の範囲を残す
- 試験の補助が、異常を「許可・成功」と読んでいないか（クラッシュの見逃し）
- 偽のモデルで確かめられないもの（実モデルの挙動、TUI の見え方、Windows）は、
  [実機で確認する項目](../../../../docs/spec/pi-guard.md#実機で確認する項目)へ未確認として足す
- 仕様・実測は `docs/` を更新する（表 B、`pi-guard.md`、判定器なら `pi-decide.md` と golden）。確認した版を書く
- 実行: 下の「使える手段」の試験と、`uv run pre-commit run --files <変更したファイル>`

### R7. 報告する

症状 → 原因（事実と推測を分けて）→ 直し → 固定したもの → **実機で確認したか**。原因が未確定なら、そう書き、次に何を見れば確定するかを残す。
節目ごと（原因の確定後、直しの後）に、**別系統モデルのレビューと、一歩引いた見直し（なぜ見逃したか、同型が他に無いか、やったことが必要十分か）**を入れる。

## 修理に入る前の確認

1. 版と、起動の違い（R1）を書いたか
2. 公式の Issue・変更履歴を検索したか（R2）
3. 表 B の該当項目と、固定している試験を回したか
4. 判定の経路が、`tool_call` と `execute()` の二重になっているか。伏字化が 3 か所に掛かっているか
5. 判定器が、前の呼び出しの状態を持っていないか
6. サンドボックスの内側の環境を実測したか（環境変数、agent 置き場、`bin/`、`.lock`、書き込み可否）
7. 偽のモデルで見られる範囲と、実機でしか見られない範囲を分けたか
8. 会社の機械など、手元で再現できない環境固有の事情を、再現できないと書いたか
