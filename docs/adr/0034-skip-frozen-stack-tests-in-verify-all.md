# 凍結したスタックの試験は、`verify:all` から外す

- **ステータス**: Proposed
- **日付**: 2026-11-11
- **決定者**: applejxd
- **関係**: [ADR-0030](0030-freeze-agent-stack-return-to-stock-pi.md)（自作基盤の凍結）の帰結。検証の層の考え方は [CHG-0051](../change/0051-verification-tiers.md)。

## コンテキスト

- 自作基盤（フルガード・`pis`・kcage など）を凍結したあとも、その試験（約 1 万 3 千件のうち、凍結スタック分が大半）が `verify:all` で毎回走り、**12〜13 分**かかった。
- 実測（2026-11-10。全件 12 分 14 秒・8 並列。[仕様](../spec/development.md)）で、1 秒以上かかるテストの CPU 時間の **97% が凍結スタック**だった。今の作業の中心は stock の pi で、凍結したコードは変わらない。
- 検証が長いと、コミット前の検証が重く、小さな変更を重ねにくい。

## 検討した選択肢

### 案 1: 全件を毎回走らせる（現状）

- **欠点**: 12〜13 分。凍結して変わらないコードの試験に、時間の大半を使う。却下。

### 案 2: 並列化だけで速くする

- すでに `pytest-xdist`（`-n 8`）で並列化している。これ以上は小さな効果。却下。

### 案 3: 凍結スタックの試験を、記録（アーカイブ）へ移す・削除する

- **欠点**: 凍結を解く（再開する）ときに、試験が無く、品質の裏づけが失われる（[CHG-0065](../change/closed/0065-agent-stack-freeze.md) の再開の手引きと矛盾）。却下。

### 案 4（採用）: 凍結スタックの試験を、`verify:all` の全件の段階（T2）から省く

## 決定

**案 4 を採る。**

- `scripts/verify.py` に、stock の pi の試験（`STOCK_PI_TESTS`）と、凍結スタックの試験（`FROZEN_TESTS`。約 122〜123 ファイル）の一覧を持つ。`test_pi_*`・`test_pr_viewer_*` の分類漏れは試験（`test/test_verify.py`）で検出する。
- `mise run verify:all`（コミット前に 1 回）は、凍結スタックの試験を省く。結果の印の `scope` は `no-frozen`。
- **省かない場合**: 変更したパスに当たる凍結スタックの試験は、変更に応じた選択（T1）で回る。削除・未一致・全件領域の変更・基準が不明のときは、省かない。
- **全件が要るとき**: `mise run verify:full`（省略なし）。`main` への統合前（`git flow integrate develop`）と、凍結したコードに触れるときに回す。

## 結果

### ポジティブな結果

- `verify:all` は **1 分 55 秒**（6090 passed。2026-11-11 時点の `develop` では 2 分 15 秒・6178 passed）。12〜13 分から約 1/6。`verify:full` は 12 分 29 秒（13021 passed）。
- 日常の作業のたびに、凍結したコードの試験を待たなくてよい。

### ネガティブな結果・トレードオフ

- 凍結スタックの退行は、`verify:full`（`main` への統合前）まで見つからない可能性がある。凍結しているので、変わるのは稀。
- 一覧（`STOCK_PI_TESTS`・`FROZEN_TESTS`）の維持費がある。新しい `test_pi_*`・`test_pr_viewer_*` の試験は、どちらかに分類する必要がある（漏れは試験で検出する。ほかの名前の試験は検出の対象外）。

### 今後の見直し条件

- 凍結を解く（再開する）とき → 一覧を見直し、`verify:all` に戻す。
- `verify:full` で、省いた試験の失敗が頻繁に見つかるようになったら、省略の範囲を狭める。
