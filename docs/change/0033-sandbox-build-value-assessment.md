# CHG-0033: 自作したサンドボックスに価値があったかを、サンクコストを除いて判定する

- **状態**: Exploring
- **更新日**: 2026-10-23
- **基準**: 現行の `pis`（Fence 0.1.67 + `ocs` + ハーネス + 子の worktree/Landlock）、コミット `0573900`。比較の相手は、[調査記録 O1](../research/agents/openshell-comparison.md) の時点（2026-10-23）の既製品

## 目的と非目的

**目的**: 今回自作したサンドボックス（`ocs`、`pis`、ハーネスの判定器とガードツール、子エージェントの worktree 隔離、各 CLI の hook の生成）に、**価値があったか**を、**エビデンスに基づいて、サンクコスト（過去に使った時間・費用・コード量）を除いて**判定する。結論は、次の 3 つのうち 1 つ: **維持**、**部分的に置き換える（既製品の仕組みを取り入れる）**、**全面的に置き換える**。

**非目的**:

- 過去の支出を理由に、現行を正当化も否定もしない（サンクコスト）
- 既製品を、この案件の中で導入する・実装する（判定の後、必要なら別の案件にする）
- 「安全か」の絶対的な評価（独立した検証が無いものは、ベンダーの主張として扱う）

## 現在地

**調べて分かったこと**（[記録 O1](../research/agents/openshell-comparison.md)。OpenShell は動かしていない）:

- OpenShell は、判定する側を境界の外に置き、資格情報をエージェントに渡さず、ネットワークを実行ファイル単位・API 単位で縛り、方針の変更を形式検証する、という設計を**文書の上では**持つ。一方、実行環境はコンテナか VM で、ホストの道具をそのまま使えない。WSL2 は experimental で、実際の不具合報告がある。2026-08 に重大な脆弱性が 2 件公表された（修正済みの版は不明）
- 「資格情報を持たせない」設計には、OpenShell より軽量な先行例がある（nono、Anthropic の sandbox-runtime）。つまり、**資格情報の代理だけを現行に取り入れる**道が、全面的な乗り換えとは別にありうる
- 比較記事（第三者）は、現行で使っている Fence も、OpenShell と並べて評価している

**現行について分かっていること**（リポジトリのファイルで確かめたもの）:

- 目的は「エージェントのうっかり（外部への誤送信、ワークスペース外の破壊、秘密の誤読）を止める」こと。精査していないリポジトリを安全に開くことまでは求めない（[ADR-0012](../adr/0012-ocs-boundary-for-accidents.md)）
- `pis` は、pi の認証ファイルなどを、境界用の agent 置き場へ写して使う（`home/dot_local/share/ocs/pi.py` の `COPY_FILES`）。つまり、**資格情報は境界の内側から読める**。保護対象のパスの読み取り拒否で守っている
- ガード（判定器・ハーネス）は、エージェントと同じサンドボックスの内側で動き、境界が効いているかを起動時のカナリアで確かめる（[pi-guard](../spec/pi-guard.md)）
- ホストの道具（`mise`・`uv`・dotfiles）をそのまま使える。WSL2 で動く。GPU は `devices.allow` で通せる（[CHG-0029](0029-worktree-isolation.md) の実測）
- 子エージェントの隔離（worktree + Landlock）は、先行する既製品に、同じ機能の記述を**今回の調査では見つけていない**（探した範囲）

**まだ分からないこと**: 現行の保守の費用（段 P3 で実測）、各候補が要件を満たすか（段 P4）、現行の「使われた実績」（事故を防いだ件数など。記録があるか）。

## 評価基準

**判定の原則**（利用者の指示、2026-10-23）:

1. **サンクコストを判断に使わない。** 過去に使った時間・費用・コード量は、理由にしない。比べるのは「今から先」の費用と便益
2. **過去の実測は、将来の予測の証拠として使ってよい。** 保守の頻度、事故の件数、試験の量、使えた機能は、サンクコストではなく、将来の費用と便益を見積もるための観測
3. **2 つの問いを分けて答える。** (a)「今、ゼロから選ぶなら、何を選ぶか」、(b)「今から乗り換えるなら、何が得で、何を失うか（乗り換えの費用を含む）」。(a) だけで判定しない
4. **エビデンスの種類を区別する。** 実測・一次情報（公式 docs・issues・NVD）・第三者の評価・ベンダーの主張。根拠が無い判断は「不明」と書き、推測で埋めない
5. **結論は、維持 / 部分的に置き換え / 全面的に置き換え のうち 1 つ。覆る条件を書く**（例: 「候補 X の WSL2 の不具合が解消し、費用が現行の保守の半分以下と実測できたら、全面的な置き換えを再検討する」）

**決定規則**（段 P5。段 P4 の結果を見てから、基準を変えたら変えたことを「重要な更新」に残す）: 必須の要件をすべて満たす候補のうち、将来の費用（保守 + 運用 + 乗り換え）が最小のものを選ぶ。必須の要件を満たす既製品が無ければ、現行を維持し、既製品の仕組みで取り入れられるものを別の案件にする。
