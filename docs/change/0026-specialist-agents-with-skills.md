# CHG-0026: スキルを、役割（子エージェント）へ割り当てる（まず移行の調査役）

- **状態**: Exploring
- **更新日**: 2026-10-27
- **基準**: コミット aa01bad、pi 1.4.0
- **注記**: 設計の段階。2026-10-27 に Paused から再開。実装は、設計の review の後

## 目的と非目的

**目的**: 専門的で長いスキル（移行・調査など）の**重い読み物と作業の文脈**を、親でなく専用の子（役割）に持たせられるようにする。
あわせて、スキルを役割へ割り当てる表を `common.toml.tmpl` に 1 つ持ち、「どのスキルを誰が使うか」を設定で決められるようにする。

- 親の文脈を軽くする（スキルの `references/` は大きい。親が読むと、その分が親の文脈に残る）
- 役割ごとに、専用の system prompt・ツール・モデル（`tier`）・スキルを持たせる
- 親の system prompt のスキル一覧を、割り当てに応じて減らせるようにする（副次。効果は小さい。下の「効果の見積もり」）
- **割り当ては「案内・優先指定」であって、権限の境界ではない**。子は、割り当て外のスキルも、明示の `/skill:名前` やファイルの読み取りで使える（[R1-5](#レビューの反映)）

**非目的**: `away-shift` を子へ移すこと（親のまま）。`commit` は、すでに `commit` 役割がある（別の話）。
**移行の実行（ビルド・検証・利用者への確認）を子に移すこと**は、今は目的にしない（下の「なぜ実行は親に残すか」）。

## 今の事実（2026-10-27 に確かめた）

- 子は別プロセスで、`--mode rpc -nbt -ne -e builtin:mcp -e <ハーネス>` で起動する。**`--no-skills` は付けない**ので、子も pi の自動発見で同じスキルを見つけ、
  親の `--skill`（`pis` が足した作業先の `.agents/skills`）も引き継ぐ（`home/dot_config/pi/harness/index.ts` の子の起動、829–831 行付近）。つまり**今でも、子は任意のスキルを使える**。
  足りないのは、「どのスキルをどの役割へ」という割り当てと、親の一覧からの除外
- スキルの一覧は、ハーネスの `before_agent_start`（`index.ts` 236–256 行付近）が `options.skills` から作る。`disableModelInvocation` のスキルは載せない。
  割り当て表による絞り込みは、ここ 1 か所に足せる（推測。未実装）
- 役割は `[pi.agents.<名前>]`（`profile`・`tier`・`description`・`system`、`worker` は `inherit_bypass`）。今は `explore`・`review`・`commit`・`worker`。`commit` の `system` は、すでにスキルを名指ししている
- 子へ渡る役割の情報は `PI_HARNESS_ROLE`（= `profile`）だけで、**役割の名前は渡らない**（割り当てに要る。足す必要あり）
- 子は子を作れない。子は利用者に質問できない（質問の中継 = ask-user 段 2 は**未実装**。ハーネスに `ask_user` 自体が無い）。1 往復は 15 分で打ち切る。
  実行の権限は**場合による**（R1-3）: `worker` は `inherit_bypass = true` で、親が bypass のとき、判定器は通常の確認（ask）を許可に変える。
  bypass でないとき（通常・サンドボックス内の既定の確認）は、pytest・uv・mise・python スクリプト・git は確認になり、子は止まる（`worker` の `system` の記述はこの場合）。
  必須の確認（`mustConfirm`）と質問の中継の欠如は、bypass でも残る。環境ごとの実判定は、実機の子プロセスの試験で確かめる（未確認）
- 移行系スキルの中身（読んで確かめた。以前の構想は description だけからの推測だった）:

| スキル | 行数 | 実行 | 対話 | 子への向き |
| --- | --- | --- | --- | --- |
| `cuda-version-migration` | 155（+ `references/` 4 本・`scripts/`） | ビルドと数値検証が中心（GPU・長時間） | 少ない | **調査は向く。実行は向かない**（15 分の上限と、確認の扱いが場合による） |
| `uv-migration` | 162（+ `references/` 5 本・`scripts/`） | `uv sync`・検証スクリプト。利用者に同期手順を案内する | 方針の確認が入る | 調査は向く。実行と方針は親 |
| `ipynb-to-marimo-pages` | 350（+ `references/` 7 本・`scripts/`） | 変換・HTML 化 | **作業前の確認と有料 API の合意が必須**（スキルが「fork しない」と明記） | 向かない（対話が本体） |

以前の構想は、この 3 つを「向く」としていた。実際に読むと、**実行と対話が本体**で、スキルごとに「完了の条件」が複数ある（CUDA は、ビルド由来・SM・ABI・数値検証を別々に確かめる）。
丸ごと子に渡す形は、質問の中継・必須の確認・15 分の上限に当たる（bypass の有無で、実行の確認だけは変わる）。

## 設計（C）

### 調査役 `migration-analyst`（案）

- **プロファイルは `reader`（bash を持たない）**（R1-2）。`explorer` は bash を持ち、共通の `skill_scripts` の許可（例: `away_guard.py` の `init`・`log`・`snapshot`）が通るので、
  「作業しない」を system の指示だけでは強制できない。Git の情報が要るときは、親が取って渡す。代償: 子が `git diff`・`wc` を直接使えない。
  `tier` は `explore` と同じ（親に追従）か、`routine`
- 受け取るもの: 対象のリポジトリ、移行の種類（CUDA 12/13・uv・marimo）
- 返すもの（標準形）: **影響箇所（パスと行）・必要な変更の一覧・実行すべき検証コマンドの案・利用者に確認すべき点・参照した資料の出典（パス・節）と未確認**。
  親は、出典・対象・権限・副作用を確かめてから実行する（「そのまま実行」はしない）。スキルの完了条件は、親が `SKILL.md` で確かめる。回答が切り詰められたら、未完了と扱う
- 作業はしない（編集・実行・git の変更をしない）。結果の完了報告は既存の標準形（結論・根拠・未確認・次の候補）

### 割り当て表（段 2）

`common.toml.tmpl` に、スキルと役割を結ぶ宣言を 1 つ足す（形は案。review で決める）。

```toml
[pi.agents.migration-analyst]
profile = "reader"
skills = ["cuda-version-migration", "uv-migration"]
skills_exclusive = false   # true にすると、親の一覧からそのスキルを外す
```

- 生成器が `rules.json` へ出し、ハーネスが、親の一覧（`before_agent_start`）から `skills_exclusive` の分を除く。
  子には、その役割の `skills` を `--skill` で足し、一覧は役割の分に絞る（子に渡す役割の名前の環境変数を足す）
- スキルの置き場は動かさない（`home/dot_claude/skills/` のまま。Claude Code・OpenCode と共有）。pi だけの絞り込みを、ハーネスの 1 か所で行う
- 未知のスキル名・存在しないスキルは、生成時に拒否する（typo を黙って通さない）

### なぜ実行は親に残すか

- 質問を中継できず、必須の確認と 15 分の上限がある（上の「今の事実」。実行の確認だけは、bypass なら通る場合がある）。移行の実行は、ビルド・検証・利用者の確認の連続で、子では止まりうる
- `ipynb-to-marimo-pages` のように、スキル自身が「対話が本体」と宣言しているものがある
- 15 分の上限は、CUDA のビルドに足りない見込み
- **再開の条件**: 質問の中継（ask-user 段 2）が入り、必須の確認と長い実行（15 分）の扱いが決まること。そのとき `migrator`（B）を再検討する

## 宣言による強制（`context: fork` / `agent:`）の実験（2026-10-27）

「委任せよ」と本文に書く（指示）のではなく、Claude のスキルの `context: fork` のような**宣言を仕組みで強制**できるかを、実機の pi（偽のモデル）で試した。
詳細は[実験の記録 F1](../research/agents/skill-fork-enforcement.md)。

- **作れる**。pi 本体は `context` / `agent` を解釈しない（`Skill` の型に無い）が、ハーネスが `SKILL.md` の宣言を読み、2 つのフックで強制できる
  - `/skill:名前`: `input` イベントは展開の**前**に来る。`{action: "handled"}` を返すとモデルも展開も走らず、ハーネスが子を起動して結果を `sendMessage`（`triggerTurn`）で親へ返せる。**モデルを介さない強い強制**（RPC・対話で確認。`-p` は不可）
  - モデルが自分でスキルを読む: `tool_call` で、そのスキルのディレクトリ配下への読み取り系のツールを**ブロック**できる（理由の文は、モデルへ返る）。親は本文を読めない。ただし**委任はモデルしだい**（誘導）
  - シェル経由の読み取りは**塞げない**（`grep -n .` は許可される）。強制の目的は親の文脈を守ること（ワークフロー）で、悪意への防御ではない
- 未確認: 実際の子の起動（`spawnChild`）を `input`・`tool_call` から呼ぶ形、実モデルでの子の動作、依頼文の決め方、Windows・Claude Code。Claude の役割名（`general-purpose` など）→ pi の役割の対応表が要る
- **この案件への含意**: 段 1b（調査役）と段 2（割り当て表）の前に、「段 1c: `context: fork` / `agent:` のハーネス対応」を置ける。
  共有スキルは、宣言だけで Claude Code と pi の両方に効く（役割名は、ハーネス側の対応表）。pi 専用の役割名を本文に書く必要が無く、レビューの R1-4 とも整合する

## 効果の見積もり（推測。実測前）

- 親の一覧: 専門スキルの description は 1 つにつき数百トークン。**3 つを外しても 1k 前後**で、一覧全体（約 4k）の一部。**主な利点は、一覧の削減ではなく、`references/` を親が読まなくて済むこと**
- 親の文脈: 移行の調査で読む `references/` と、対象のコードの洗い出し（数十ファイルの読み）が、子の文脈に閉じる
- 悪くなる点: 調査の往復が 1 回増える。調査の質は、役割の `system` に依存する。`skills_exclusive` を使うと、親が手順を見ずに実行する形になるので、**移行の実行スキルには使わない**（R1-1）

## レビューの反映

`review`（terra）の 1 回目（2026-10-27）。MAJOR 5・MINOR 4。

- R1-1 親が手順を読まずに実行する設計は危険 → 親は `SKILL.md` を読み続ける。`skills_exclusive` は実行スキルに使わない。調査役は出典と未確認を返す
- R1-2 `explorer` は bash と `skill_scripts` の許可を持つ → 調査役は `reader`（bash なし）。判定器の試験で確かめる
- R1-3 実行の権限の断定が誤り（`worker` は bypass で通る） → 「今の事実」を場合ごとに書き換え、B の評価を「対話・必須の確認・時間制限のある全工程」に限定
- R1-4 共有スキルに pi だけの役割名を書くと、他の CLI・Windows で破綻 → 段 1 は pi 専用の指示で、共有本文は変えない
- R1-5 段 2 の意味と評価基準が未確定 → 再評価のゲートにし、「案内であり権限境界ではない」と明記、仕様にする項目を列挙
- MINOR: `references/` の数の修正、案 D と段 1 の不一致の解消、「そのまま実行」の削除、実際に使うかは未確認、を反映
