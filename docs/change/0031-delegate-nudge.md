# CHG-0031: 親エージェントが委譲を忘れないよう、読み取り量に応じた注記（ナッジ）を出す

- **状態**: Exploring
- **更新日**: 2026-10-24
- **基準**: コミット 171cf25、pi 1.3.0。委譲の原則は `home/.chezmoitemplates/agent-instructions.md` の 1 節だけで、機械的な契機は無い

## 目的と非目的

- **目的**: 親エージェントが、調査・読み取りを自分で積み上げて文脈を埋める前に、子（`explore`）へ委譲する契機を、**機械的に**作る。
  「委譲を促す注記」を、親の読み取り量が増えたときだけ出す（**ナッジ**）。効果は測って確かめる
- **非目的**: 委譲の強制（親の読み取りの拒否・読み取り専用の親）。`explore` の品質の改善。子の結果の形式検証（別の項目）。
  公開拡張の導入（[ADR-0016](../adr/0016-pi-extensions-own-first.md)）

## 実施計画

段ラベルは `N1`〜`N3`（ナッジの段）。状態は 2026-10-25 時点。

## 現在地

- **問題の事実**（このリポジトリ）: 2026-10-22 の長い会話で、調査・読み取りを親が自分で行う場面が繰り返された。委譲の指示は system prompt の 1 節で、
  会話が数百往復になると、その節の優先度は下がる（観察。測定はしていない）。`guarded_task` の `todo` 必須化は「委譲するときの規則」で、「委譲を促す規則」ではない
- **外部の同じ問題**: [openai/codex #18105](https://github.com/openai/codex/issues/18105)（2026-04-16、Closed。本文と最初の数件のコメントを読んだ）に、
  「親は、特にコンテキストが埋まった後ほど、自分で何でもやる。`AGENTS.md` の明示でも防げない」とある。要望は、親を読み取り専用にするモード、委譲の理由の表示
- **先行例の設計**（いずれも 2026-10-22 に取得）:

  | 出典 | 内容 | 借りる点 | 注意点 |
  | --- | --- | --- | --- |
  | [`context-nudge`](https://github.com/Doot-Workspaces/context-nudge)（MIT。README 全文） | `UserPromptSubmit` と `PostToolUse` で、トークン数が帯（300k・350k）を超えたとき注記を**各帯 1 回だけ**出す。拒否しない。状態はセッションとサブエージェントごと。エラー時は黙って終了 | 帯・1 回だけ・失敗しても止めない | 対象はトークン数 |
  | [ClaudeKit の hook 一覧](https://docs.claudekit.cc/docs/engineer/configuration/hooks/)（一覧の抜粋） | `post-edit-simplify-reminder`: 編集が繰り返されたら `code-simplifier` を促す回数ベースの注記 | 回数ベースの契機 | 文脈を足す hook は v2.19.0 から既定では入れず、更新時に掃除される。入れすぎのコストを作者も認めている |
  | `pi-advisor-flow` 0.14.2（配布物を `dist.integrity` と照合して読んだ。`README.md`、`src/tools/loop-gate.ts`、`gate-policy.ts`。取得物は削除済み） | `tool_call`（実行前）で同じ署名のツール呼び出しの繰り返しを数え、閾値で助言役の LLM を呼ぶ。結果は、ツールの拒否またはセッションの停止。失敗時の方針は設定で選べる。注記は `pi.sendMessage({customType, content, display}, {deliverAs: "steer"})`。残りの呼び出し回数は、画面に出さない会話メッセージでモデルに知らせる。セッションあたりの上限を持つ | 独立したメッセージとしての注記、上限（予算） | 拒否まで行うのは、助言役の LLM が要るため重い |

- **pi の拡張 API**（`explore` が型定義と runner の実装を読んで確認。結果の全文は会話内の通知）:
  - `tool_result` ハンドラは `{ content: [...event.content, {type:"text", text}] }` を返して、結果の末尾に注記を足せる。ハンドラは読み込み順に順次 await され、フィールドごとに上書きされる（連結ではない）。
    例外は捕まえられ、そのハンドラの変更が反映されないだけ（fail-open）。`content` だけを返すと `structuredContent` が落ちるので、`event.structuredContent` を添えて返す
  - `guarded_*` の結果にも、別の拡張の `tool_result` は呼ばれる。自作のフルガードの `tool_result` が `guarded_*` を早期に抜けるのは、そのハンドラの中だけの話
  - 子は `-ne` で起動されるので、`own_extensions` の拡張は読まれない。親だけで動く（`PI_HARNESS_CHILD` の判定は要らない。念のため入れてもよい）
  - 利用者の発言ごとのリセットは、`todo` 拡張と同じく `before_agent_start` の `messageType === "user"`。拡張が起こした続行（`custom`）は区別できる
  - `appendEntry`（モデルの文脈に入らない永続データ）で統計を残せる。ファイルへの書き込みは、`harness/index.ts` の `.tmp/subagents` への保存（シンボリックリンクの拒否・排他的作成）の書き方を使える
  - 注記を `content` に足すと、モデルにも画面にも出る。画面に出さない方法は見つからなかった
- **未確認**: `sendMessage` の steer の配信のタイミング（ツールの途中か、ターンの後か）と、`display: false` でモデルにだけ見せられるか。
  並列のツール呼び出しでの `tool_result` の順序。`agent_before_settle` の続行が `before_agent_start` を通るか。実機での効き目
- **出し方**: 結果の末尾に足すと、**モデルが注記を本文の最終行と取り違えて、次の `edit` の `oldText` に混ぜる危険**がある（`review`。別の `content` 要素にしても、モデルに渡る同じツール結果なので解消しない。先頭への追加は取り違えを増やす）。独立した `sendMessage` は結果を汚さないが、配信時点が未確認。N1b の比較試験で決める
- **統計の項目**（効果を判定できる形。`review` の指摘）: 内容・パス・依頼文は保存しない。発言単位の匿名 ID、時点とセッション内の順序、方式と有効・無効、帯への到達と実際の配信、配信後の親の追加の読み取り数、`guarded_task` の**新規**の `explore` / `review` 呼び出しとその成否（`status` / `steer` や子の結果の受け取りは除く）、発言の終了理由。これでも、「注記あり」と「なし」を同じ種類の依頼で比べないと、因果は言えない
- **状態の設計**: 並列の結果の到着順（`tool_result` のハンドラは順次合成されるが、兄弟の結果を順序付ける保証は無い）、一つの結果で 2 つの帯を超えたときの回数、エラー結果を数えるか、`/reload`・セッション切替・分岐、統計の書き込みの失敗をどう扱うか（結果を壊さず、しかし欠損に気づける。利用者向けの警告）を仕様にする

## 未解決点

- **注記が効くか**: 記録の範囲では、「注記が無視された」も「効いた」も実測が見つからなかった。N2 で測るまで、効果は不明
- **出し方**: 結果の末尾に足す（`tool_result`。確認済み）か、独立したメッセージ（`sendMessage` の steer。`pi-advisor-flow` 方式）か。後者はタイミングの確認が要る
- **帯の値**: 暫定は、第 1 帯＝1 回の発言で読み取り系ツール 8 回、または結果の合計 400 行。第 2 帯＝その 2.5 倍。実測の前の見積もり
- **数える範囲**: `guarded_read` / `guarded_grep` / `guarded_find` / `guarded_ls` の結果。`guarded_bash` の読み取り（`cat` などは拒否されるので少ない）は数えない
- **ノイズ**: 帯ごとに 1 回でも、毎発言で出ると煩わしい。上限（セッションあたりの回数）を設けるか

## 評価基準

- **必須**: 拒否しない（親の読み取りを止めない）。親だけで動く。失敗しても止めない（例外は黙って無視し、結果を変えない）。
  注記は 1 回の発言あたり最大 2 回。注記と統計に、読んだ内容（秘密を含みうる）を入れない（回数・行数・ツール名だけ）。統計はローカルだけ
- **望ましい**: 注記の後に、`guarded_task` の件数が増える。注記の文脈が理由（読んだ量）を示す。環境変数で止められる

## 重要な更新

- **2026-10-22**: 案件を起こした。先行例（`context-nudge`・ClaudeKit・`pi-advisor-flow`・Codex #18105）と、pi の拡張 API の確認結果をまとめた。拒否せず、帯を超えたとき 1 回だけ注記する方針で、`review` の後に N1 を試作する。
- **2026-10-22（`review` を反映）**: 拒否しない方針と、注記なしの計測を先にする方針は妥当とされた。MAJOR 3 件を受けて、`tool_result` 末尾を推奨として確定するのをやめ、N1 を N1a（統計だけ）・N1b（出し方の比較）・N1c（注記を出す版）に分けた。帯と除外は一律に除外せず、種類別の分布を見てから誤報が多い種類だけを対象外にする。
- **2026-10-24**: 親が検索・取得を自分で続け、子に任せなかった事例があった（[CHG-0033](0033-sandbox-build-value-assessment.md) の再調査）。原因は 2 つ: (1) `imozuru` の SKILL.md が「pi の子は Web 検索できない」と書いていたが、実機では `explore` の子が `websearch.py search` を確認なしで実行できた（2026-10-24。`[pi.skill_scripts.allow]` が役割を問わず効く）。記述を訂正した（[imozuru](../spec/imozuru.md)）。(2) 親が読み取り・検索の量を意識しなかった（本案件の対象）。**scout 役（検索できる子）を足す案は、不要と分かって起票しない**。候補に「親が `websearch.py` / `imozuru` の検索を一定回数以上、直接呼んだときの注記」を足す（読み取り量の帯と同じ仕組みで数えられるか、N1b の後に検討）。
