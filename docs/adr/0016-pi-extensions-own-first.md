# pi の拡張は自作を基本とし、外部の拡張は条件を満たす例外だけを導入する

- **ステータス**: Accepted
- **日付**: 2026-10-11
- **決定者**: applejxd

> **用語の注記（2026-10-15）**: 決定は変えない。本文の「ハーネス」は、現在の「フルガード」（`pis` で効くガード）を指す。対応は [pi のガード](../spec/guard/pi-guard.md#用語)。

## コンテキスト

pi のハーネス（`pis`）は `-ne` で起動し、拡張を自動では読まない
（[pi のガード](../spec/guard/pi-guard.md#起動)）。この構成は、[CHG-0020](../change/0020-pi-migration.md) の
設計の過程で AI が提案し、**利用者が十分に理解しないまま承認したもの**で、「拡張は足さない」という方針として
扱われてきた。利用者が決めた方針ではない。

2026-10-11 に、次のことが分かった。

- 明示した `-e` の拡張は、`-ne` でも読まれる。そのツールは役割の `tools` と既定の確認、結果の伏字化を通り、
  同名のツールの差し替えは pi が起動の失敗で止める（[実測](../research/agents/pi-extension-under-harness.md)）。
  拡張を足すこと自体は、仕組みの上で成立する
- 一方、拡張は読み込まれた時点で任意のコードを実行でき、ハーネスはそれを囲えない
- 公開されている pi の拡張（`pi-package`）は多く、Web 検索だけでも 90 件ほどある。ただし週間のダウンロードが
  数十〜数百件の小さな保守者のものが大半で、鍵とネットワークと外部入力を扱う。中身は監査していない

「全面禁止」は、仕組みの制約ではなく、理解が伴わない既定だった。一方で「自由に導入」は、供給網の危険が大きい。

## 検討した選択肢

### 選択肢 1: 拡張を足さない（従来の事実上の方針）

- **利点**: 攻撃面が最小
- **欠点**: 利用者の判断ではなく、必要なときに選択肢が無い。実際に足せることが分かった

### 選択肢 2: 公開されている拡張を自由に導入する

- **利点**: 手間が小さい
- **欠点**: 拡張は任意のコードで、鍵・ネットワーク・外部入力を扱う。保守者が小さく、更新のたびに追従と審査が要る

### 選択肢 3: 自作を基本とし、条件を満たす外部の拡張だけを例外として導入する

- **利点**: 自分で読めるコードに保ち、必要なときの逃げ道もある。判定・伏字化の仕組みはそのまま使える
- **欠点**: 例外のたびに審査と記録の手間がかかる

## 決定

**選択肢 3 を採る。**

1. **自作を基本とする。** 足りない機能は自分で作る。入口は**必要な能力を満たす最小のもの**を選ぶ（優先順位ではない）。
   単純な呼び出しは skill + CLI、型付きの結果や常駐する状態は MCP、pi の内部への介入は拡張。比較は [入口の選び方](../spec/guard/pi-extensions.md#入口の選び方)
2. **外部の拡張は、次の 3 つを全て満たすときだけ導入する。**
   - どうしても必要である（skill + CLI・MCP・自前の拡張で代えられない、または代えるのが著しく不利なことを記録する）
   - 自前で実装するのが困難である（理由を記録する）
   - 振る舞いを十分に確認している（下の手順）
3. **対象はこのリポジトリが配る拡張。** `pis` の起動に足すものと、chezmoi が配るものである。素の `pi` で利用者が手で試すものは対象外
   （ただし鍵を扱う拡張は、同じ審査を勧める）

### 例外の手順

| 段 | 内容 |
| --- | --- |
| 1. 必要性と困難さ | 代替が無い理由と、自作が困難な理由を [pi のガード](../spec/guard/pi-extensions.md#外部の拡張) の表へ書く |
| 2. 審査 | 導入する版のソース全体を読む。依存、`install` 系のスクリプト、ネットワーク・ファイル・子プロセス・環境変数の使い方、鍵の扱い、ライセンス、供給元と更新の履歴を確かめる |
| 3. 版の固定 | 版（と取得物のハッシュ）を固定する。自動更新しない。更新は再審査 |
| 4. 振る舞いの確認 | 偽のモデルの試験で、判定（役割の `tools`・既定の確認）、結果の伏字化、同名ツールの差し替え、ファイル・ネットワークへの副作用を確かめる。実際の鍵を使う前に、ダミーで確かめる |
| 5. 配備 | ツール名を `[pi.profiles.*].tools` に足し、確認なしで通すなら規則を足す。`pis` の起動引数に `-e <パス>` を足す（`-ne` は維持する） |
| 6. 記録 | 名前・版・ハッシュ・理由・審査日を、[外部の拡張](../spec/guard/pi-extensions.md#外部の拡張) の表へ書く |

保護が要る作業では、`pis --boundary`（Fence）で囲う。

## 結果

### ポジティブな結果

- 「足せない」という誤解が解け、必要なときの手順が明確になる
- 自作を基本にするので、コードを読めて、鍵と外部入力の扱いを自分で決められる
- 判定・伏字化の仕組みは変えずに使える

### ネガティブな結果・トレードオフ

- 外部の拡張を入れるたびに、審査と記録の手間がかかる
- 審査しても、拡張の読み込み時の処理は囲えない（任意のコード）。残る危険は、審査と版の固定で下げるだけである
- `-ne` を維持するので、自動発見は無い。足すものは必ず明示する

### 今後の見直し条件

- 例外が増えて表が膨らんだときは、取り込み方（ベンダリング、自前フォーク）を見直す
- pi が拡張の権限を制限する機構を持ったときは、審査の重さを見直す
