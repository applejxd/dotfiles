# docs を「段階」ではなく「情報の役割」で分け、案件を中心に置く

- **ステータス**: Accepted
- **日付**: 2026-09-19
- **決定者**: applejxd

## コンテキスト

このリポジトリの開発は研究開発の性格が強い。最初に目的は決まっていても、
方法や仕様は定まっていないことが多く、複数の手法を並行して試し、より良いものを
選んで仕様を更新していく。

実際、`research/sandbox-capabilities.md` は「設定を触るたびに知らなかった機能が
出てきた」と書いており、`research/agent-harness-comparison.md` は複数候補の比較
そのものになっている。

docs に期待するのは 2 つ。

1. ユーザーが現状と計画を把握できること
2. AI がセッション間でコンテキストを共有できること

当初は `research`（調べる）→ `adr`（選ぶ）→ `change`（計画する）→ `spec`（仕様に
する）という**段階モデル**で設計した。しかしこれは直線で、その手前にある
**「目的は共有されているが、複数候補と未解決事項が継続的に存在する状態」**を
置く場所が無かった。研究開発ではこれが常態になる。

## 検討した選択肢

### 選択肢 1: 4 段階の直線モデルを維持する

- **利点**: 各ディレクトリの役割が単純
- **欠点**: 未決着の比較状態を置く場所が無い。1 つの候補の経緯が複数の
  ディレクトリに分散する

### 選択肢 2: `change/` を「探索開始から使う案件」に広げる

実装の合意を待たず、目的ができた時点で案件を作る。候補比較・評価基準・
未解決事項の正本にし、現在の理解へ更新し続ける。

- **利点**: 新しいディレクトリを増やさずに、未決着の状態を扱える。
  1 つの目的に関する情報が 1 箇所に集まる
- **欠点**: 「実装計画」という当初の語感からは広がる

### 選択肢 3: トピックごとの単一文書に状態を持たせる

Oxide の RFD のように、1 つのアイデアを 1 文書で扱い、状態遷移で表す。

- **利点**: 移送が要らない。並行候補を状態で一覧できる
- **欠点**: 既存の ADR 8 件と `spec/` の独立した価値を壊す。
  「今の仕様」を知るのに committed な文書を全部読む必要が出る

### 選択肢 4: 完了した案件をファイルごと削除する

成果を `spec/` と `adr/` へ移したうえで、案件の本文を消す。

- **利点**: 古い計画が現在の指示として誤読されない
- **欠点**: 研究開発では、当初の期待・変更した判定条件・試さなかった候補・
  実際の結果との差にも価値がある。一度もコミットされなければ git 履歴にも残らない

## 決定事項

**選択肢 2 を採用する。** あわせて選択肢 4 は採らない。

4 つのディレクトリは「開発の段階」ではなく**情報の役割**で分ける。

| | 答える問い | 単位 | 更新の仕方 |
| --- | --- | --- | --- |
| `change/` | この目的をどう達成するか（探索中を含む） | 1 つの目的 | 現在の理解へ上書き |
| `research/` | 何を観測したか | 1 回の調査・試行 | 追加のみ |
| `adr/` | なぜその選択をしたか | 1 つの決定 | 不変 |
| `spec/` | 今どうなっているか | 1 トピック | 置換 |

要点は **記録単位と統合単位を分ける**こと。`research/` は観測を追加するだけで
過去を書き換えず、`change/` が現時点の総合判断を上書きする。混ぜると、過去の
結論と現在の判断が同じファイル内で混ざる。

**終了した案件は削除せず、状態と終了日を付けて同じパスに残す。** 目的（古い計画を
現在の指示として誤読しない）は、索引の「活動中」から外すだけで達成できる。
別ディレクトリへ退避する必要も無い。

**`docs/index.md` の冒頭を現在地ダッシュボードにする。** 目的 1 を満たす中心が
無かったため。詳細の正本は案件で、ダッシュボードには要約だけを置く。

## 決定の確認方法

- [x] 索引に載っていない文書を検査が検出すること
- [x] 終了した案件が「活動中」に残っていると検査が落ちること
- [x] 欠番があっても検査が合格すること（終了で欠番は正常に生じる）
- [x] 4 種類が揃っていないリポジトリでも検査が落ちないこと

## 結果

### ポジティブな結果

- 未決着の複数候補を置く場所ができた
- 情報の移送が減り、移送漏れの機会も減った
- ユーザーが `docs/index.md` の冒頭だけで現状を把握できる

### ネガティブな結果

- `change/` の語感が「実装計画」から広がるため、説明が要る
- 終了した案件が増えると、索引の「終了」区分が伸びる

### 中立的な結果

- 全ての作業が 4 種類を生産するわけではない。誤字修正や単純な設定変更には
  案件も比較表も要求しない
