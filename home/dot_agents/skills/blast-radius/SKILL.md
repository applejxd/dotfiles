# 差分の波及を根拠で押さえる

危険な可能性を列挙するだけでなく、安全と言える前提を一つ選べ。依頼が影響調査だけなら、製品コードを変更しない。

1. 変更前後の振る舞いと、影響を受け得る既存の利用者を特定する。
2. 直接の呼び出し元だけでなく、必要に応じてデータ形式、設定、版の違い、タイミング、保存済みデータを追う。差分と関係のない既存問題は分ける。
3. 「この事実が成り立つなら、最も大きい懸念を除ける」を一文にする。例: 古い行番号を持つ指摘でも、現在の台本で同じ本文の行に保存される。
4. 既存のテスト、読み取り専用の確認、または許可された一時環境で、その前提を判定する最小の実行を選ぶ。期待した失敗・成功と出力を区別する。実行できない場合はソースの根拠を挙げ、未確認とする。
5. 確認済み・否定できた懸念・残る影響を分ける。コマンドと結果、または根拠のファイル位置を示す。

レビュー役が読み取り専用なら、実行が必要な確認を親へ返す。実行のために権限を広げたり、独立レビューや承認の契約を置き換えたりしない。
