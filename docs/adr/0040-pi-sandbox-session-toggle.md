# pi の囲いと YOLO を、セッションの途中で `/sandbox` で切り替える

- **ステータス**: Accepted
- **日付**: 2026-11-15
- **決定者**: applejxd（2026-11-15 に、次を承認した: 小さな自作の拡張で、実行中に囲いを切り替える。素の `pi` で起動したときも使える。引数なしはトグル。囲いを入れたら YOLO も入れ、外したら YOLO も切る）
- **関係**: [ADR-0036](0036-pi-sandbox-shell-wrap-and-tool-policy.md) の「強さの切り替えは起動時に選ぶ（実行中は切り替えない）」を**改める**。「昇格の仕組みは作らない」（エージェントが囲いの外を要求できる仕組みは作らない）は保つ。[ADR-0031](0031-evaluate-existing-extensions-first.md)（自作の記録）に沿う

## コンテキスト

- ADR-0036 は、囲いの強さを起動時に選ぶ（`pi`・`pib`・`pib --offline`）と決めた。囲いの外が要る作業（`gh`・`git push`・docker）は、別のターミナルか `pi` で行う。セッションの途中では変えられず、文脈を捨てずに囲いだけを入れる・外すことができない。
- 利用者は、他のハーネスのように、セッション中に切り替えたい（利用者の要望。他のハーネスの仕様は未確認）。
- 実測（2026-11-15、pi 1.5.0）:
  - pi は、コマンド（bash ツール・`bg_run`・利用者の `!`）を起動するたびに、pi プロセスの環境変数を読む（`dist/core/tools/bash.js` の `env ?? getShellEnv()`、`pi-background` の `{...process.env}`）。`pib-shell` は `PIB_SANDBOX` が立っているときだけ囲う。
  - 拡張が pi プロセスの `process.env.PIB_SANDBOX` を書き換えると、pi を再起動せず、次のコマンドから囲いが入る・外れる（RPC の `bash` で、`MISE_STATE_DIR` と `/mnt` の見え方が、囲いなし → あり → なしと変わるのを確認した）。
- 公開の package（`carderne/pi-sandbox`・`stegmannb/pi-agent-sandbox`・`@oddsjam/pi-sandbox`・`Jeffrey-deng/pi-permission-modes` v3.0.0 など）には、実行中に切り替えるものがある（検索結果の説明文で確認した範囲）。ただし、bash ツールだけを包む型で、ADR-0036 が退けた理由（`bg_run`・`!` が抜ける。GPU を通せない）がそのまま残る。
- YOLO（`pi-permission-system` の `ask` の自動承認）は、設定ファイルの `yoloMode` にあり、`/permission-system` のモーダルでしか切り替えられない（外から呼べる API は無い。42.0.0 のソースで確認）。拡張は、毎ターンの開始時（`before_agent_start`）に、この設定ファイルを読み直す。

## 検討した選択肢

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **A（採用）** | 小さな拡張が、pi プロセスの `PIB_SANDBOX` を書き換える。囲い自体は `pib-shell` と runner のまま | `bg_run`・`!`・子の bash も一緒に切り替わる。拡張は約 260 行 |
| B | 公開の package（上の 4 つ） | bash ツールだけを包む型で、ADR-0036 の問題が戻る。評価した範囲では、置き換えにならない |
| C | 状態ファイルを `pib-shell` が読み、別のターミナルで `pib mode off` | pi の中から切り替えられない。状態ファイルを、ファイルの道具から守る規則が要る |

## 決定

1. **`/sandbox [on|offline|off|status]` を、ローカルの package（`home/dot_pi/agent/local-packages/pi-sandbox-toggle`）で配る。** Linux だけ（囲いが Linux 専用）。引数なしは、囲いなし ⇄ 囲いあり（`on`。通信は開いている）のトグル。`offline` は通信を遮断する。
2. **切り替えは、利用者が打った `/sandbox` だけ。** モデルが呼べる道具は登録しない（登録すると、外部の文章の指示で囲いを外せてしまう。試験で固定する）。囲いを外すときは確認を出す。
3. **囲いを入れるとき**は、`shellPath` が `pib-shell` であること（`pib` と同じ規則）を確かめ、環境変数を書き換えたあと、pi の bash と同じ経路で**試し実行**して、囲いの内側の印が見えることを確かめる。見えなければ元に戻す（効いていない囲いを残さない）。
4. **YOLO は囲いに従う。** 囲いを入れたら YOLO を入れ、外したら YOLO を切る。順序は安全側にする: 入れるときは囲いが先、外すときは YOLO が先（ターンの切れ目まで待つ）。YOLO を切れなければ、囲いを外さない（信頼済みのプロジェクトの設定が `yoloMode` を on にしているときを含む。permission-system は、プロジェクトの設定を global の後に重ねる）。YOLO を入れるのは、囲いと権限の設定を守るパス（9 件）への書き込みが、実効の方針（global・信頼済みプロジェクト・agent を重ねたもの）で、**明示の規則が一致した** deny であると（既定の deny は、`write`・`edit` の path ゲートが何もせず通すので数えない）、permission-system の公開の判定 API（`checkPermission`）に確かめられたときだけ（囲いの外の `write`・`edit` が、囲いの設定を書き換えられないことが、YOLO の前提のため。規則の評価は再現しない: 監査で、後置した ask の規則・プロジェクトの `path`（`path_write` へ展開される）など、再現の抜けが続けて見つかった）。確かめられなければ囲いだけ入れ、残っている YOLO（前回・手動）も切る。YOLO は設定ファイルに残るので、**起動時**（`/new`・`/resume`・`/reload` ではない）にも、囲いの状態に揃える。起動時は、囲いが効いていると確かめられたときだけ YOLO を入れる（囲いなしの `pi` に、前回の YOLO を持ち越さない）。
5. **切り替えは一度に 1 つ。** 途中（確認・idle 待ち・試し実行）に別の `/sandbox` が割り込むと、「`off` のあとに YOLO が入る」食い違いが出る（監査で指摘された）ため、実行中は次の `/sandbox` を断る（起動時の確認も同じ枠を使う。pi は起動の途中から入力を受け付けるため。起動時の確認は、先行の `/sandbox` の終了を待つ）。
6. **`pib-shell` は、囲いなしのときも、元の `PATH`（`PIB_ORIG_PATH`）を渡す。** `pib` で起動して囲いを外したとき、venv の `bin` などが見えなくなるのを避けるため。普通の `pi` は何も変わらない。
7. **`~/.pi/agent/local-packages` を `path_write` で拒否する。** ここの拡張は、囲いの外の pi 本体で実行される。ファイルの道具（`write`・`edit`）が書き換えられると、囲いの切り替えを含む任意のコードを仕込める（これまで、この場所は拒否の対象になかった。反例の試験を先に足して、落ちることを確かめた）。

### 自作の記録（ADR-0031 の 3）

| 項目 | 内容 |
| --- | --- |
| (a) 既存で満たせない理由 | 公開の package は bash ツールだけを包む型（上の「コンテキスト」）。pi 本体の標準機能に、囲いの切り替えは無い（`shellPath` は起動時の設定）。skill + CLI は、pi の中の `/` コマンドにならない |
| (b) 維持費 | 拡張 約 540 行（コメントを含む）と試験 約 700 行。追従が要る上流は 4 点: pi が起動のたびに環境変数を読む挙動、`pi-permission-system` の設定ファイル（`yoloMode`）・毎ターンの読み直し・プロジェクトの設定を global の後に重ねる順序と読み方（YOLO を切れるかの確認。置き場 2 か所。コメントを除いて JSON として読む）・公開の判定 API（`globalThis` の `Symbol.for` の置き場と `checkPermission`）と `permissions:ready`、runner が囲いの内側だけに設定する `MISE_STATE_DIR` |
| (c) 撤去の条件 | pi 本体が、実行中に切り替えられる sandbox を標準で持ったとき。上の 4 点のどれかが変わって、2 回続けて保守の負担になったとき |
| (d) 承認 | 利用者が、方式（環境変数の書き換え）・範囲（素の `pi` でも使える）・YOLO の連動を承認した（2026-11-15） |

## 結果

**得るもの**:

- 文脈を捨てずに、囲いを入れる・外す。囲いの外が要る作業（`git push`・`gh`・docker）に、別のターミナルへ移らずに入れる。
- 囲いを入れると YOLO も入り、確認で止まらない。

**失うもの・限界**（詳細は [仕様](../spec/sandbox/pi-sandbox-runner.md#実行中の切り替え)）:

- **YOLO が入ると、強制 ask が自動承認になる。** 外部への投稿・変更の確認（`gh` の変更系など）は、YOLO では働かない（`deny` は残る）。囲いの内側の `gh` は認証が無く失敗するが、MCP・ファイルの道具・囲いの外で動く pi 本体の操作は、囲いの外にある。YOLO を切って確認を戻したいときは `/permission-system`（囲いと YOLO は別に変えられる。次の起動までは、その値が保たれる）。
- **保護の確認は、YOLO を入れる時点のもの。** 信頼済みプロジェクトの設定は作業ツリーの中にあり、エージェントが書き換えられる。YOLO のあいだに `path_write` を緩める設定を足されると、次のターンで保護が外れうる（`pib` は `--no-approve` で、プロジェクトの設定を読まない）。agent ごとの方針は見ない。
- **YOLO を切る側の検査は、global とプロジェクトの設定ファイルの 2 か所だけ。** permission-system が実際に使っている値は、外から読めない（API が無い）。更新で重なり方が変わったら、見落とす。
- **YOLO は設定ファイル 1 つを共有する。** 複数の pi を同時に動かすと、一方の切り替えが、他方の次のターンから効く（囲いなしの pi が YOLO になりうる）。同時に使うときは、囲いを切り替えない・`/sandbox status` で確かめる。
- **素の `pi` から入れた囲いは、`pib` より弱い。** `pib` の起動時の検査（`--no-approve`・`PATH` の整理・`HOME` の検査）を通らない。プロジェクトの `.pi/settings.json` で `shellPath` を書き換えられても、検知しない（切り替えの時点の確認だけ）。守りたい作業は `pib` で起動する。
- すでに動いている背景ジョブ・子エージェントは、起動時の状態のまま。
- 試験は node と pi の代役で行う。実際の pi・TUI・bwrap を通した確認は、利用者の実機（仕様の「実機で確かめる項目」）。

## 見直しの条件

- 実機で、切り替えが `bg_run`・子エージェントの bash に効かないと分かったとき。
- 同時に複数の pi を使う運用が増え、YOLO の共有が問題になったとき（YOLO を囲いと切り離す。`/permission-system` に任せる）。
- 例外の自作が 3 件を超えたとき（ADR-0031。この拡張で 3 件。超えてはいない）。
