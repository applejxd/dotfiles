# sdd-docs スキル

セッションを跨いで残す知識を `docs/` へ移す。**判断が要る作業**なので、
文脈を失いかけているなら、先に今の文脈を引き継げる形で残す（下の注記）。

> **A1 とは別物。** A1 はセッション内で失う文脈を退避する作業で、
> ここから先は**人が判断して `docs/` へ書く**作業。
> A1 の手段は CLI で違う。OpenCode では `checkpoint` スキルが `.tmp/` の
> セッション別ファイルへ書き、圧縮フックが自動でも保存する（`checkpoint` と
> そのフックは OpenCode 専用）。他の CLI では、その環境に実在する引き継ぎの方法
> （対象のリポジトリの `AGENTS.md` の指示など）を確かめて使う。無ければ
> ユーザーに尋ねる。
> 分離の理由は、このスキルの配布元（applejxd/dotfiles）の ADR-0009
> 「save-before-documenting」。対象のリポジトリの ADR ではない。

| 相 | 対象 | いつ |
| --- | --- | --- |
| A2 | `docs/change/` の案件 | 共有すべき知識が生まれたとき |
| B | `docs/research/` `docs/adr/` `docs/spec/` と索引 | 任意。落ち着いたとき |

**頼まれたことだけをやる。** 「ADR を作って」なら ADR と `docs/adr/index.md`
だけ。案件整理やダッシュボード更新まで広げない。**ただし、指示なしで呼ばれたときは
次の「指示なしで呼ばれたとき」に従う**（呼ばれたこと自体が「docs を今の状態に整えて」という依頼）。

例外として、**コミットの依頼は A2 の依頼を含む。** commit スキルの
「コミット前の docs 反映」から呼ばれたときは、頼まれていなくても関わる案件を
更新する。B はそこでも書かない。

## 指示なしで呼ばれたとき（`/sdd-docs` 単発）

`/sdd-docs` のように、**スキル名だけで、具体的な依頼（「ADR を作って」など）が無い**ときの動作。
状態を機械で調べ、その結果で動作が決まる（先に調べずに書き始めない）。

**実行前に OS を確かめ、インタプリタを選ぶ。** 以下のコマンド例は `python3` で書いてある。
Windows（`$OS` が `Windows_NT`・パスが `C:\` 始まりなど）では `python3` が使えないので、
`py -3 -X utf8` に読み替える（Linux / macOS / WSL はそのまま `python3`）。

```bash
python3 ~/.claude/skills/sdd-docs/scripts/docs_state.py status
```

| `state` | 意味 | やること |
| --- | --- | --- |
| `absent` | `docs/` に構成（`index.md` と 4 つのカテゴリ索引）が無い | 下の「新規に作る」 |
| `partial` | 索引の一部だけ在る | `scaffold` で足りない索引だけ作り、下の「差分を反映する」 |
| `complete` | 構成が揃っている | 下の「差分を反映する」 |

**共通の守り方**（どちらの動作でも）:

- **確かめられたことだけを書く。** 根拠はリポジトリのファイル、コマンドの出力、
  今の会話で実際に起きたこと。推測・一般論・「たぶんこうだろう」は書かない。
  確かめていないことは「未確認」と書く。**空のカテゴリは空のままにする**（埋めるために作らない）
- **既にある文書を消さない・動かさない・書き換えで無かったことにしない。**
  文脈に無い過去の経緯を、想像で補わない
- **書いたらコミットしない。** 作成・更新したファイルと、書かなかったもの
  （と理由）を最後に報告する。コミットは commit スキルの領分
- 出力が大きい（コミットが数十件・ファイルが数十件を超える）ときは、
  優先順位（進行中の案件 → 変更に言及している文書 → 新しい機能）を付け、
  **扱わなかった分を「未反映」として報告する**。全部を一度にやろうとして雑にしない
- 終わったら「仕上げ」の検査を回し、出力を示す

### 新規に作る（`absent`）

1. **材料を集める。** 読むのは README・`AGENTS.md` / `CLAUDE.md`・ディレクトリの構成・ビルドやテストの定義
   （`package.json`、`pyproject.toml`、`Makefile`、CI の設定など）・直近の git 履歴。**今の会話の文脈**
   （決めたこと、実測したこと、まだ決まっていないこと）も材料。`status` が出した既存の `.md` は、
   消さずに取り込む（`spec/` の文書にするか、索引に載せる）
2. **骨組みを作る。** `docs_state.py scaffold --title <プロジェクト名> --purpose "<目的の 1 文>"`。
   目的は README などから確かめて書く（作るのは索引だけで、既存のファイルは上書きしない）
3. **材料から、確かめられた分だけを各カテゴリへ書く。**

   | カテゴリ | 書くもの | 書かないもの |
   | --- | --- | --- |
   | `spec/` | 今の構成・動かし方・テストの回し方・契約。リポジトリのファイルで確かめたこと。まず 1〜3 文書で足りる | 想像した設計意図 |
   | `change/` | 今の会話・履歴から分かる、**まだ決着していない取り組み**（候補・未解決点がある）。無ければ作らない | 終わった作業の経緯 |
   | `adr/` | 会話・README・コミットメッセージに**判断と理由が明示されている**決定 | 理由を推測した決定 |
   | `research/` | 今の会話で**実際に測った**もの（コマンドと出力・観測日・一次情報） | 一般的な知識の要約 |

4. **索引を整える。** 各カテゴリの索引の一覧に載せ、`docs/index.md` の「目的から探す」に、
   読み手が目的から探す文書だけを足す
5. 「仕上げ」の検査を回し、作ったもの・書かなかったものを報告する

### 差分を反映する（`complete`）

`status` の出力が、前回 docs を更新したコミット以降の差分（コミット・未コミット・未追跡・それに言及している文書・
進行中の案件）を示す。**前回以降に起きたことだけ**を反映する（全体を書き直さない）。

1. **各カテゴリの索引の冒頭の規約を読む。** 書き方はそちらが正本
2. **変わったことを行き先へ振り分ける**（最初に一致した行き先で打ち切らない）。
   材料は `status` の差分と、**今の会話の文脈**（決めたこと・実測したこと）:

   | 変わったこと | 行き先 |
   | --- | --- |
   | 進行中の案件に関わる進捗・判断・未解決点 | A2: その案件（現在地・未解決点・候補比較・重要な更新） |
   | 動作・構成・手順が変わった | `spec/` の該当文書を**置換**する（`status` の「言及している文書」が手がかり） |
   | 理由を伴う決定が下りた | `adr/`（新規。既存の決定を覆すなら Superseded、一部改定なら冒頭に案内） |
   | 実測した | `research/`（コマンドと出力・観測日。過去の節は書き換えず、新しい節を足す） |
   | 目的が決まったが方法が未定の取り組みが始まった | `change/` に新規の案件 |

3. **言及している文書は、実際に読んで、古くなっていれば直す。** 言及があっても古くなっていないなら触らない。
   コードと照合できないことは直さず、報告に「要確認」として残す
4. 終わった案件（会話や差分から明らかなものだけ）は「案件を終了するとき」の手順で閉じる。推測で閉じない
5. 反映するものが無ければ、**何も書かずに「反映する差分は無い」と報告する**（空の更新・日付だけの更新をしない）
6. 「仕上げ」の検査を回し、更新したもの・扱わなかったもの（未反映）・要確認を報告する

## 始める前に: 対象のリポジトリを確かめる

このスキルは次の構成を前提にする。**具体的な依頼（「ADR を作って」など）を受けたときに
無ければ、作り始めず、作るかどうかを尋ねる**（指示なしのときは、上の「新規に作る」で作ってよい）。

- `docs/index.md`（入口）
- `docs/change/` `docs/adr/` `docs/research/` `docs/spec/` と、それぞれの `index.md`

各 `index.md` の冒頭に規約（状態の既定値、記録の単位など）があれば、そちらが
正本。この文書と食い違ったら規約に従う。検証のコマンドも、対象のリポジトリの
`AGENTS.md` などに表があればそれに従う（下の「仕上げ」）。

作業の前に、参照の切れの控えを取っておく（「仕上げ」で比べる）。

```bash
python3 ~/.claude/skills/sdd-docs/scripts/check_refs.py --save
```

控えはリポジトリのルートの `.tmp/refs-before.txt` に置かれる（置き場のディレクトリが
無ければ作る）。commit しない。`.tmp/` が git に無視されているか
（`git check-ignore -q .tmp/refs-before.txt`）を確かめ、無視されていなければ
リポジトリの外の一時ディレクトリのパスを `--save <パス>` で渡し、「仕上げ」の
`--baseline` にも同じパスを渡す。

スクリプトは `python3 <パス>` でそのまま呼ぶ（パスを変数に入れない・`uv run` を
挟まない・リダイレクトや `2>&1` を付けない。OpenCode はこの形だけを確認なしに通す）。
スキルを別の場所に置いたときはパスを読み替え、Windows では `python3` を
`py -3 -X utf8` に置き換える。

## 共通の原則

- **前方参照を作らない。** 上から読んで分かる形にする。使う前に定義し、
  独自の呼称・略号（`ocs` / `規則 3` / `B5`）は**初出で 1 行説明する**。
  「下記」で先送りするなら、その場に 1 行の要約を添える。
  表の「理由」欄を参照で埋めない（飛ばされると一覧にならない）
- **最初に一致した行き先で打ち切らない。** 1 つの実験結果が、`research/` の証拠と
  案件の比較表の両方に要ることは多い
- **未検証を不合格扱いしない。** 逆に、期待を確認済み扱いしない。
  どちらも後から「調べたはず」と誤読される
- **読み取り専用の作業中は書かない。** レビューや「現状を教えて」で docs を
  書き換えない

## A2: 案件（`docs/change/`）の更新

案件は**現在の総合判断の正本**。ここを読めば今どこにいるか分かる状態を保つ。

1. 該当する案件を探す。無ければ `references/change-template.md` で起こし、
   `docs/change/index.md` へ掲載する
2. **候補比較表**を更新する。新しい根拠・反証・未検証点を該当行へ入れる。
   扱い（有望 / 保留 / 見送り）が変わったら、変わった理由も書く
3. **「現在地」**を書き換える。分かったことを最新にする
4. **「未解決点」**を書き換える。保留にしたものは**再開条件**を必ず書く
5. 決定や方針が変わったら**「重要な更新」**へ 1 行足す（日付・変更・理由）
6. 実測したら**「実装・検証」**へ、コマンドと結果を書く

**見送りを消さない。** 「なぜ採らなかったか」が残っていないと、同じ検討を
やり直すことになる。

### 節の順序を崩さない

読む頻度の高い順に並べる。詳細と雛形は `references/change-template.md`。

| ブロック | 節 |
| --- | --- |
| **いま** | 目的と非目的 → 実施計画 → 現在地 → 未解決点 → 次の調査・実験 |
| **判断** | 評価基準 → 候補比較 → 仕様への変更案 → 実装・検証 |
| **経緯** | 重要な更新 → 終了結果 |

**`## 実施計画` は段ラベル（`A1` / `段 2`）の定義表。** ラベルを本文で使うなら
必ず計画表より後に書く。節を足すときは**どのブロックに属するかで位置を決め**、
末尾に付け足さない。

### 案件を終了するとき

状態は既定値（`Exploring` / `Planned` / `In progress` / `Done` / `Paused` /
`Abandoned`）**そのまま**書く。`Done（採用・配備済み）` のように補足を付けると
`lint_docs.py` が落とす。補足は「終了結果」へ書く。

1. 「終了結果」を書く。次の 4 つをそろえる（雛形は `references/change-template.md`）
   - **最終的に採用したもの**（現行の形を 1〜3 行で）
   - **撤回・見送りしたもの**と、その理由（途中で採用して取り下げたものも含む）
   - **反映先**（仕様・実装・観測）
   - **移管した未完事項**と移管先（移管先が無いなら「未起票」と書く）
2. 冒頭に「この文書は当時の記録。現在の仕様は `spec/...`」の注記を置く。
   本文の途中の「現在地」「次の調査」などが最終結果と食い違うなら、
   **消さずに時点を添え**、最終結果は「終了結果」を見るよう案内する
3. `git mv` で `docs/change/closed/` へ移す（履歴を保つ）
4. **相対リンクを 1 段深く貼り直す**（`../` → `../../`）
5. 索引の行を「活動中」から「終了」へ移し、リンクを `closed/` 付きにする
6. 他ファイルの `see docs/change/NNNN-...` も `closed/` 付きへ直す

手順の根拠は、配布元（applejxd/dotfiles）の ADR-0011
「close-change-records-into-subdirectory」。

## B: 文書化

### `docs/adr/` — 設計判断

`references/adr-template.md` を使う。

- 番号は `docs/adr/` の最大値 + 1（4 桁ゼロ埋め）。ファイル名は `NNNN-kebab-case.md`
- **作成したら `docs/adr/index.md` の一覧へ 1 行追加する**（索引の検査が未掲載を落とす）
- **決定の受諾（`Accepted`）と実装の完了は別物。** 実装の進捗は ADR に書かず、
  `docs/change/` の案件が持つ
- 既存 ADR のステータスを変えるときは、変更理由を必ず書く
- 決定を覆すときは既存 ADR を書き換えず、新しい ADR を起こして古い方を
  `Superseded by ADR-NNNN` にする
- **決定の一部だけを改めるとき（部分改定）は `Superseded` にしない。**
  新しい ADR を起こし、旧 ADR は本文を残したまま**冒頭に改定の案内**
  （日付・改めた範囲・後継へのリンク・残りは有効であること）を置く。
  雛形は `references/adr-template.md` の冒頭、規約は `docs/adr/index.md`
  「部分改定の書き方」。同じ文書への追記で済ませてよいのは、決定を変えない
  補足だけ
- `docs/adr/` 以外にファイルを作らない

### `docs/research/` — 実測の記録

- **1 記録 = 1 つの問い。** 同じ問いの測り直し・掘り下げは、同じファイルへ
  日付の付いた節として足してよい。問いが変わったら新しい記録にする。
  観測日と一次情報の URL を必ず書く
- 雛形は `references/research-template.md`
- **過去の節を書き換えない・消さない。** 訂正・撤回は新しい節として足し、
  元の節の冒頭に訂正先への案内を置く。記録は割らず、見出しの文言も変えない
  （案件・仕様・コードが節番号と見出しで参照している）
- 後の観測や現行の仕様と食い違ったら、ファイルの冒頭に
  `> **後続の観測**: …` / `> **現行の仕様**: …` の案内を付ける
- 実行したコマンドと出力を載せる。推測は「推測」と明示する
- 陳腐化しても消さない。「いつ時点か」が分かれば価値がある

### `docs/spec/` — 現行の仕様・運用

- **今どうなっているか**を書く。歴史的経緯は `research/` と案件が持つ
- ただし**現在の運用に必要な判断基準・理由は書いてよい**。
  「なぜこうするのか」が無いと、読み手が善意で壊す
- **意図した契約と実装が食い違っていたら、食い違いとして記録する。**
  どちらかに寄せて書かない

### 索引

- 文書を足したら、**その category の `index.md` の一覧**に載せる。
  索引の検査（`scripts/lint_docs.py`）が未掲載を落とす
- `docs/index.md` は目的から辿る入口。読者が目的から探す文書のときだけ足す
  （索引の検査は `docs/index.md` への掲載を求めない）
- 見出しを変えたり文書を分けたりしたら、参照している側（他の文書・コードの
  コメント）を張り替える。切れたかどうかは `scripts/check_refs.py` で確かめる

## 子エージェントに分担させるとき

大きな整理は、担当する文書が重ならないように分けて子エージェントに任せてよい。
次を守る。

- **子は別の git worktree で書く。** 本体の作業ツリーを触らせない。コミットもさせない
- **索引（各 `index.md` の一覧と `docs/index.md`）は親だけが書く。** 子には
  掲載する行の案を報告させる
- 担当外の文書から張られたリンクが切れるなら、子には編集させず、
  「旧: ファイル#アンカー → 新: ファイル#アンカー」の対応表を報告させる
- 子に「中身をコードと照合し、照合できなければ直さず報告する」ことを約束させる
- 子にも作業前の控え（`check_refs.py --save`）を渡し、`--baseline` で新しい切れが
  無いことを確かめさせる
- 親は取り込む前に差分を読み、全員の分を当ててから、対応表で張り替え、
  索引を足し、「仕上げ」の検査を通す
- 全体にまたがる整理（用語の統一など）は、分担を取り込んだ後に 1 本で行う

## 仕上げ

```bash
python3 ~/.claude/skills/sdd-docs/scripts/lint_docs.py --docs docs
python3 ~/.claude/skills/sdd-docs/scripts/check_refs.py --baseline
```

対象のリポジトリに検証の表（`AGENTS.md` など）や pre-commit があれば、それも回す。
どれも出力を根拠として示す。実行していないチェックの結果を書かない。

## やってはいけないこと

- `research/` の過去の節を書き換える・消す
- 終了した案件を削除する（`closed/` へ移す）
- 未検証を不合格として書く／期待を確認済みとして書く
- 子エージェントに本体の作業ツリーの `docs/` を直接書かせる・索引を書かせる
- 具体的な依頼を受けたのに、前提の構成が無いリポジトリで、尋ねずに `docs/` の構成を作る（指示なしで呼ばれたときは作ってよい）
- 確かめていないことを、材料が足りないまま推測で書く（指示なしのときも。空のカテゴリは空のままにする）
- 指示なしのときに、書いたものをコミットする
- 文脈が逼迫しているのに、A1（OpenCode なら `checkpoint`）より先にここへ着手する
