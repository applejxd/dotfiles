# CHG-0023: 「ハーネス」の呼び方を整理し、`pis` をサンドボックス既定にする

- **状態**: In progress
- **更新日**: 2026-10-25
- **基準**: コミット c0bf603、pi 1.1.0（実機の試験時。のち利用者が更新）、Fence 0.1.67、WSL2 (Ubuntu)

## 目的と非目的

**目的**:

1. 利用者の感覚（pi 本体を含む仕組み全体が「ハーネス」）と、このリポジトリの呼称（pi に足す判定の拡張を「ハーネス」）の食い違いをなくす。
   判定の層は「ガード」、OS の隔離は「サンドボックス」と呼び分ける
2. `pis` を、サンドボックス（Fence）つきの起動を既定にする。サンドボックス無しの選択肢をなくせるかを決める

**非目的**: 識別子（`PI_HARNESS_*`・`~/.config/pi/harness`・テスト名・`--boundary`）の改名（段 4 で別に判断）。
過去の案件・調査記録・ADR の本文の書き換え（当時の記録なので触らない）。

## 用語

| 用語 | 指すもの | 旧称 |
| --- | --- | --- |
| ハーネス | pi 本体を含む仕組み全体（一般の用法。このリポジトリでは特定の拡張を指さない） | （拡張を指していた） |
| ガード | ツール呼び出しを判定し、allow / ask / deny に振り分ける層 | ハーネス（拡張の意味のとき） |
| フルガード | `pis` で効く、役割・確認・伏字化まで含むガード | ハーネス |
| 簡易ガード（廃止） | 素の `pi` に付いていた、deny と伏字化だけのガード（段 3f で廃止） | 素の pi のガード |
| サンドボックス | Fence による OS レベルの隔離。ガードとは別の層 | 境界 |

正本は [pi のガード](../spec/guard/pi-guard.md#用語)。

## 評価基準

ocs（OpenCode の隔離起動）の実装に引きずられず、pi の守り方として何が理想かを、コストを度外視して考える。次で比べる。

0. **緩和はサンドボックスが証明されたときだけ**（決定。下の「設計原則」）
1. **責務が分かれ、残余リスクが埋まっている**: 境界が止めるものと、ガードが判断するものが、重なりすぎず、抜けもない
2. **宣言が 1 か所**: 拡張・読み取りの許可・起動引数を、足すたびに複数箇所を直さずに済む（3a がその失敗例）
3. **失敗が安全側**: 境界を張れない・検査に落ちたら、弱い守りへ降格せず止まる（または、明示した脱出口へ誘導する）
4. **内外で同じ動き**: サンドボックスの有無で、読み込まれるもの（拡張・指示・キーバインド・プロンプト）が変わらない
5. **日常の使い勝手**: 履歴・認証・Orca・このリポジトリでのふだんの作業を損なわない
6. **脅威モデル**: ADR-0012 のとおり「エージェントのうっかり」を止めることが目的。悪意あるリポジトリへの耐性までは求めない

## 目標の構成（仕様への変更案）

レビュー（下の「重要な更新」）を受けて改めた。

### 設計原則（決定。2026-10-14、利用者）

- **基準は保守的な側に置く**: サンドボックス無しの動きが基準で、確認（ask）は全部出し、deny・誘導・伏字化・役割は変えない。
  サンドボックス有りは、**基準に対して緩和を足す**だけ（日常の shell の確認を外すなど）。サンドボックス無しは、別の経路ではなく「緩和が無い設定」にする
- **緩和は、サンドボックスが証明されたときだけ有効にする**。証明は、起動前の事前検査と、拡張が内側で自分で行うカナリアの実測。環境変数だけを立てても有効にならない
- **厳密さの予算は、緩和のゲートに集中する**。ゲートが壊れると、黙って危険になる。基準（サンドボックス無し）が壊れても、「余計に聞く」側に倒れる
- **実装は 1 つ**: ガードの拡張は、別名ツール方式（今のフルガード）だけを残す。拡張が読み込めない・`/reload` で抜けたときに、組み込みのツールが戻らない（調査記録 E1）ので、
  サンドボックス有りの重要ケースで、フェイルクローズがすでに試験済み。簡易ガード（フック方式）を別に強化しない
- **サンドボックス無しは必ず可視化する**: 起動時の警告とフッターの常時表示

### 役割分担

- **サンドボックス**: pi のプロセス全体（pi 本体・拡張・MCP サーバ・`!` の直接実行）を入れる。許可した読み書き・通信の外に出る効果を、OS で止める。
- **ガード**: 境界の内側の判断。**サンドボックスの中でも、次はガードが残す**（境界は作業ツリーの中を守らないため）:
  - 作業ツリーの中の破壊的操作（`rm -rf .git`・`.` や `*` の再帰削除・`find -delete`。ADR-0013）
  - 作業ツリーの中の秘密の読み取り（`read_deny_globs`）
  - 役割によるツール制限、伏字化、MCP の確認、`git commit` の確認
- **サンドボックスの中で変わるのは、確認（ask）の一部だけ**: 日常の shell の確認を外す（CHG-0020 の `drop_shell`）。deny・誘導・上の保護は変えない。
- **境界の外のパスへの操作は、確認なしで通さず、説明付きの deny にする**（「境界の外。必要なら再起動で `read` を足す」）。OS も同じ場所で拒否するので使い勝手は変わらない。
  判定器が受け取るのは真偽値の `boundary` ではなく、**実際に開けた許可パスの一覧**にして、Fence の許可とガードの分類がずれないようにする。
- **素の `pi`**: ガードを持たない（Windows と同じ）。Orca・Zed は `pis`（必要なら `pis --no-sandbox`）から起動する形へ寄せる。制御ファイル・ガードの編集と復旧は `pis --no-sandbox`（基準のガード付き）で行う

### 部品

1. **拡張の一覧**: `common.toml` の `[pi] own_extensions` を唯一の宣言にし、生成器が `rules.json` へ出す。`rules.json` は今もサンドボックスの素材（`sandbox` キー）を持つので、
   新しい生成物（`launch.json`）は作らない。`[pi.sandbox] read` のうち拡張の分は、この一覧から生成する。**拡張を足すときは `common.toml` の 1 か所だけを直す**
2. **単一のランチャー** `pis`（`ocs` から独立）: 一覧を読む → agent view を作る → 起動場所を検査する → サンドボックスの検査 → Fence で pi を起動 → 後始末（どの段で失敗しても `finally` で認証を戻して置き場を消す）。
   `ocs` の Fence 設定の組み立て・起動場所の拒否・退避は、OpenCode に依らない共通のモジュールとして切り出して使う。起動は引き続き `-nbt -ne` と明示の `-e`（拡張の発見先を絞る仮定に頼らない）
3. **agent view**（今の境界用の agent 置き場）: 起動ごとの `~/.local/share/pi-sandbox/agent-*`。**写すものを一覧で決め、内外で同じものを読ませる**。
   `AGENTS.md`・`keybindings.json`・`prompts/`（`/fleet`）を写していなかったので足し、`bin/` を本物の `~/.pi/agent/bin` へのリンクにした（2026-10-15。実機の試験で見つけ、再試験で個人用の `AGENTS.md` の引用を確認した）
4. **検査**: 起動のたびに、(a) 同じ設定で動く事前検査（今の `ocs --check`。通信・保護対象・秘密の不可視を含む。設定と Fence の版が変わったときだけ再実行し、結果を覚える）と、
   (b) 実際に動く pi の中での**カナリア**（内側から秘密が読めない・境界の外へ書けないを実測し、失敗したらツールを 0 個にする。`rules.json` が読めないときと同じ流儀）を行う。
   Fence が通信の隔離（network namespace）を張れずに代替の動きになる環境では、**起動を拒否する**。`PI_HARNESS_BOUNDARY` は表示用の目印で、安全の根拠にしない
5. **起動の形**（決定）: 下の「起動の仕様」

### 起動の仕様

| 起動 | ガード | サンドボックス | 使う場面 |
| --- | --- | --- | --- |
| `pis`（標準） | フルガード（`boundary` = 真） | あり | ふだんの作業 |
| `pis --no-sandbox` | フルガード（`boundary` = 偽。基準の動き: 確認は従来どおり全部出す） | なし | 制御ファイル・ガードの編集、復旧、Orca・Zed、Fence が使えない・邪魔な作業。起動時に警告を 1 行出し、フッターに常時「サンドボックス無し」と出す |
| `pi`（素） | なし（簡易ガードは段 3f で廃止） | なし | Windows。`pis` が使えない最後の手段 |

- `--boundary` は互換のために受け付け、標準と同じ意味とする（識別子は段 4 まで変えない）
- サンドボックスを張れない OS（macOS・Windows ネイティブ）では、`pis` は**起動せず**、`--no-sandbox` の使用を案内する（黙って弱い守りに落とさない）
- 起動の順序と、失敗したときの扱い:

| 順 | 処理 | 失敗したとき |
| --- | --- | --- |
| 1 | 拡張の一覧・`rules.json` の読み込み | 起動しない |
| 2 | 起動場所の検査（`~`・`/tmp`・制御ファイルの置き場では起動しない） | 起動しない（素の `pi` を案内） |
| 3 | 事前検査（通信・保護対象・秘密の不可視。設定と Fence の版が変わったときだけ再実行） | 起動しない（`--no-sandbox` を案内） |
| 4 | 退避（起動前のバックアップ） | 起動しない |
| 5 | agent view の作成 | 起動しない |
| 6 | Fence で pi を起動し、内側でカナリアを実測 | ツールを 0 個にして理由を表示。pi は閉じる |
| 7 | 終了後: 認証を戻し、置き場を消す（どの段の失敗でも実行） | 戻せなければ置き場を消さず、警告して手動の復旧手順を示す |

- **ガードの判定**（サンドボックスが標準のとき）:

| 操作の場所・種類 | サンドボックスあり | サンドボックス無し（`--no-sandbox`・素の `pi`） |
| --- | --- | --- |
| 許可パスの外の読み書き | 説明付き deny | 従来どおり（作業ツリーの外の edit は確認） |
| 作業ツリーの中の破壊的操作・秘密の読み取り | deny（変えない） | deny（変えない） |
| 日常の shell | 確認なし | 確認 |
| `git commit`・MCP・役割の制限・伏字化 | 変えない | 変えない |

- **agent view が写すもの**: 写す（読み書き可）= `auth.json`・`models-store.json`。写す（読み取り専用）= `settings.json`・`AGENTS.md`・`keybindings.json`・`prompts/`。
  空で置く（読み取り専用）= `extensions/`・`mcp.json`・`trust.json`。本物へのリンク = `bin/`（`fd`・`rg`。pi が無いとダウンロードするため）

### 残る課題・保証の範囲

- **保護対象が書けないのは、保護対象の置き場から起動したときの、その Git の根の中**。別のクローンを追加の `write` で開いたときは対象外になる（`opencode-sandbox.md` の「制御ファイルの保護が効く範囲」）。保証を、配備先・このリポジトリ・別のクローンに分けて書く
- **認証**: 今は写しを内側に置き、終了後に有効期限が新しい分だけ本物へ戻す。複数の `pis` を同時に起動したときや、更新後の異常終了（SIGKILL）では失効しうる（推測。未試験）。
  同期に失敗したら置き場を消さず、警告して手動の復旧手順を示す。理想の**ホスト側の認証プロキシ**は、pi が接続先を差し替えられるかが未確認のため別案件。AWS 系（Bedrock）は `DROP_ENV` で落ちるので別に扱う
- **このリポジトリでの作業**: 保護対象（`home/dot_config/pi`・`home/dot_claude/hooks`・`home/dot_pi`・`scripts/agents`）は内側で書けない。**ガードの編集は `pis --no-sandbox`、検証は外のシェル**と運用が分かれる。
  素の `pi` はガードを持たないので、復旧にも `pis --no-sandbox` を使う。`uv run`・`pre-commit` が内側で通信できるかは未確認
- **MCP**: サーバは内側で動く。`npx` / `uvx` 系は許可ドメインが要り、`GH_TOKEN` が落ちるので GitHub 系は動かない（推測。未確認）
- **Orca・Zed**: 利用者は Orca のターミナルから `pis` を打って起動している。Orca の起動ボタンで立つ素の `pi` にはガードが付かない（段 3f）。サンドボックスの内側から Orca のローカルポートへ届くには、Fence の `allowLocalOutbound` に加えて**ポートの指定**が要り（資料から）、`ORCA_AGENT_HOOK_PORT` は起動ごとに変わる。Zed は未確認
- **macOS・Windows**: Fence は macOS の Seatbelt にも対応するので、「Fence が無い」のではない。制約は `ocs` 由来の Linux 前提（`/usr/bin/env`・`/tmp` など）。macOS は別案件にする。Windows は ADR-0017 のとおり変えない
- **セッションの置き場**: `pi.py` が pi の命名規則（`getDefaultSessionDirPath`）を再実装している。[pi の公式仕様と実測の棚卸し](../spec/pi-upstream.md)の「頼る点」へ足し、pi の更新時に再開の試験を入れる
