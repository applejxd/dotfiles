## 結論（軸の最推し）

- **最推し: どれも入れず pi-subagents（nicobailon 0.87.0）のまま。** 6 候補は全て、(a) 子に permission-system / cc-safety-net が効かない（子は `--no-extensions` 相当が既定）、または (b) pi-subagents と機能・ツール名が重なって二重になる、または (c) 外部の常駐物・大きな導入物を要する。
- **条件つきの足し算候補は `@trevonistrevon/pi-loop` の `MonitorCreate` だけ**（12 分の全件検査を背景で回し、終了で親を起こす）。ただし pi-loop 全体（loop・task・workflow）は過大。**保留**し、まず pi-subagents の背景実行・通知と、pi 本体の bash の背景で足りるかを実機で確かめる。
- `pi-gauntlet`（唯一「契約→並列実装→独立レビュー→検証」を一式で持つ）は、必須依存の `pi-cohort`（= nicobailon/pi-subagents の fork。同名の `subagent` ツール）と衝突するため、**入れ替えでしか使えない。保留**（入れ替えの評価は別軸）。

## 候補ごとの評価（指定の順）

### 1. @quintinshaw/pi-dynamic-workflows — 除外（重複 + 子に権限が効かない）

確かめた事実（README / `src/agent.ts`）:
- 仕組み: モデルが JS の orchestration script を書き、`agent()` / `parallel()` / `pipeline()` / `phase()` で多数の子セッションへ展開。`verify()`（複数の LLM 投票）・`judgePanel()`・`loopUntilDry()`・`gate(thunk, validator)`・`checkpoint()`（人の承認）・`isolation:"worktree"`・`tier: small|medium|big` のモデル振り分け・journal の再開。
- **(3) 子に権限が効かない**: 子は `DefaultResourceLoader({ noExtensions: true })`（`src/agent.ts` 約 992 行）で作られ、README にも「Subagents no longer load host extensions by default」とある。子は coding tool（`read` `bash` `edit` `write` ほか。`agent.ts` 1255 行付近）を持つので、**permission-system・cc-safety-net が子の bash に効かない**。`providerMiddlewareExtensions` の許可リストで拡張を選んで読ませられるが、「拡張全体を有効にするだけで、OS の sandbox ではない」と README が注意しており、permission-system の ask は子に UI が無い扱いになる（推測。未確認）。
- **(2) 完了の判定**: script は `vm` の中で fs・network・shell が使えない（README「Determinism and limits」）。`gate` の validator は JS 関数だが、テスト・lint コマンドを実行できないので、**機械的な検証は書けない**。検証は別の LLM 子への投票（`verify` / `judgePanel`）になり、子の自己申告の域を出ない。
- **(4) 費用の歯止め**: `maxAgents` 既定 1000・`concurrency` は最大 16 に切り詰め。`tokenBudget`・`agentTimeoutMs` は**既定で無制限**（`defaultTokenBudget` を設定すれば効く。soft な pre-call gate）。月 DL の多さに対し、既定は費用の暴走に弱い。
- ネットワーク: モデルのプロバイダ以外に、`deep-research` が `web-tools.ts` で Bing（`https://www.bing.com/search?q=`）と任意 URL を `fetch` する（検索語を外へ送る）。組み込み workflow を使わなければ呼ばれない（推測）。実行状態は `~/.pi/workflows/` に書く。
- 他との相性: 追加ツール `workflow` / `workflow_control`、コマンド `/workflows` `/effort` `/ultracode` など。**キーワード `workflow` の入力で自動的に武装する**（既定 on）ため、利用者の文面で意図せず多数展開されうる（`/workflows-trigger off` で止められる）。pi-subagents とは「子を作る」点で重複（README は `pi-subagents` を子で除外すると明記）。
- 判定: **除外**。「多数の子を安く広く回す監査・調査」には強いが、利用者の運用（1 worktree = 1 feature = 1 worker、権限は親の拡張で守る）と合わない。入れるなら権限の前提が崩れる。

### 2. pi-crew — 除外（重複 + 運用が重い）

確かめた事実（README / `src/runtime/model/pi-args.ts` / `src/schema/config-schema.ts`）:
- `team` という 1 ツールに 57 の action（run・status・steer・schedule・cleanup…）。子は本物の `pi` 子プロセス。チーム 6 種・workflow 11 種・agent 18 種（planner・executor・reviewer・verifier など）。`workspaceMode:"worktree"`、`async:true`（背景実行と完了通知）、`.crew/` に永続状態、`limits.maxConcurrentWorkers`（同時数の上限）、`runtime.requirePlanApproval`（計画→実装の境で承認待ち）、`action:"goal"`（worker → LLM 判定 → 再試行）。
- (1) 流れは「計画（planner）→ 並列実行 → review → verify」で**最も近い**が、計画の確認は承認ゲート（任意）で、契約を固定するのではなく planner が組む。
- **(3)** 子は既定で `--no-extensions`（`hermeticWorkers` 既定 true）。**ただし off-switch がある**: `runtime.hermeticWorkers:false`（または `PI_CREW_HERMETIC_WORKERS`）で周囲の package（permission-system 等）を子に読ませられる。読ませた場合の ask 待ちの挙動は未確認。
- **(2)** verifier / cold-verifier は LLM の agent。`completionMutationGuard` はあるが（`config/types.ts`）、検証コマンドの結果を契約として固定する仕組みは見つからなかった（未確認）。
- (4) 外部送信: webhook は既定で無効、設定は user config のみ（project 側は無視）。`classifierEnabled` は既定 false。inter-pi broker（unix socket。Linux/macOS 既定 on、native Windows は自動で off）。費用: 同時数の上限あり、token 予算は `.dwf.ts` 側。
- 注意: README 冒頭が「ほぼ全て AI が開発・第三者の監査なし・作者個人の運用向け」と明記。`.dwf.ts` は sandbox なし。11.5 MB・依存 7 個（esbuild など）。42 のスラッシュコマンドと UI（task list・dock）が枠を取る。
- 判定: **除外**。pi-subagents の上位互換を狙うが、利用者の運用に対して面積が大きく、権限の前提（hermetic を切る）も扱いにくい。AI 生成・単独保守の点も重い。

### 3. pi-gauntlet（+ pi-cohort）— 保留（入れ替え専用）

確かめた事実（README / package.json / pi-cohort の `src/extension/index.ts`・CHANGELOG）:
- 流れ: brainstorm（spec・worktree）→ **人の承認 1（spec）** → writing-plans（独立に検証できる atomic task を、触るファイルが重ならない wave に分ける）→ subagent-driven-development（実装 → spec-compliance review → code-quality review）→ verify → 完了前の conformance gate（元の依頼文と照合）→ **人の承認 2（merge/PR/破棄）**。**(1) の流れを最も近く提供**する。
- **(2) 完了の判定が自己申告でない**: verify は「**親が**計画の全件検証コマンドを実行し、通った場合だけ全 diff の review に進む。review の修正で結果は無効になり再実行」。`plan_check`（計画が spec と文法に合うか）、`phase-tracker`（pending task が残ると implement/verify を閉じられない）、`verify-before-ship` hook（テストを通さない push/PR に警告）。→ 利用者の運用（子の申告でなく親が検査）に合う。ただし conformance・review は LLM の子。
- **(必須依存) pi-cohort**: 他に代わりがない必須の peer。cohort は `nicobailon/pi-subagents` の fork（CHANGELOG に由来を明記、「upstream を追従しない」）で、ツール名が `subagent`、コマンドが `run` `chain` `parallel`。**すでに入れる pi-subagents と同じ名前で衝突する。二重に入れられない**。→ 入れる場合は pi-subagents を cohort に**入れ替える**。cohort の peer は coding-agent >=1.5.0（1.5.0 を満たす）。
- 子に権限が効くか: cohort は「親の拡張の CLI フラグを子へ転送」する（`forwardParentFlags`）。子が拡張を読み込むかの既定は未確認（nicobailon 版の子は既定で拡張を読むので、近い挙動の推測）。入れ替えを検討するなら、実機で permission-system が子で効くか要確認。
- 外部送信: `shape-ticket` / `linear` / `gatekeep-pr` / `check-delivery` が `gh` / `linearis` / Jira 等の tracker CLI を使う（使うのは明示起動の skill。起動しなければ呼ばれない）。`spec council` は複数モデルへ spec を送る。`postinstall` が `bin/install-agents.mjs` で agent 定義をユーザの agent ディレクトリへ symlink/copy する（package 内のコードを実行する。`PI_GAUNTLET_AGENT_DIR` で変更）。telemetry は repo に YAML を書く（外部へは送らない。ローカル）。
- 運用との差: 利用者の運用では**親が計画して契約を固め**、計画の承認は 1 回。gauntlet は spec 承認と merge の 2 回の人の承認が前提で、brainstorming を入口にした流れ全体を採用する形（「他の運用と混ぜにくい」と README も `opinionated` と書く）。worktree の作り方・feature 台帳・feature-orchestration の skill と**二重の規約**になる。費用: council・2 段 review・conformance で多数の子を呼ぶ（同時数・予算の上限は cohort 側。未確認）。
- 判定: **保留**。設計は利用者の運用に最も近く、skill 側の「親が検証コマンドを実行して通るまで次へ進めない」は取り込む価値がある。だが入れるには pi-subagents の入れ替えと運用の置き換えが要る。**まず自前の feature-orchestration に gate の考え方（verify 後だけ review、review 修正で verify を無効化）を取り込む案を推す**（package は入れない）。

### 4. @trevonistrevon/pi-loop — 保留（MonitorCreate だけが関心）

確かめた事実（README / docs/REFERENCE.md / RUNTIME_CONTINUITY.md / USAGE_GUIDE.md）:
- 提供: `/loop`（cron・event・自走 goal）、`Workflow*`（phase つきの durable workflow）、`Task*`（`pi-tasks` が無いとき native の task を登録）、`Orchestration*`、`MonitorCreate/List/Stop`。
- **`MonitorCreate command="..." onDone="..."`**: 背景で shell コマンドを走らせ（detached な process group・出力を buffer）、終了・失敗・無出力の timeout で**親を起こす**。timeout は「無出力が続く時間」で、出力があれば延長される（総実行時間の上限ではない。既定 5 分、`0` で無効）。**これは利用者の「12 分の全件検査を背景で回し、終わったら起こす」にそのまま当たる。**
- 制約: 状態は **Pi が動いている間だけ**。monitor の handle・出力は memory のみで、プロセスが落ちると再接続できない（`RUNTIME_CONTINUITY.md`）。端末を閉じる・離席して session が終わる場合には効かない。
- **permission-system との関係**: `MonitorCreate` は **bash と別の経路で任意の shell コマンドを実行**する。permission-system の `shellTools` に **ツール名 `MonitorCreate`、`commandArgument: "command"`** を足さないと、判定（と cc-safety-net の網。safety-net が bash 以外を見るかは未確認）を**迂回する**。導入する場合の前提設定。引数名は USAGE_GUIDE の例（`MonitorCreate command="npm test" ...`）に基づく。スキーマ（dist の型）の確認は未実施。
- 重なり・衝突: `Orchestration*` は **`@tintinweb/pi-subagents` の protocol v2 を要求**する（USAGE_GUIDE: "requires ... `@tintinweb/pi-subagents` protocol v2"）。nicobailon 版では使えない（その機能は使わない）。`Task*` / `/tasks` は rpiv-todo の `todo` と役割が重なるが、ツール名は別（衝突の確認は未実施）。`Workflow*` は自作の feature 台帳と重なる。
- 保守: 個人 1 名。0.x。README に「研究のための設計で、予期せぬ設計に寄る恐れがある」と注記。unpackedSize 1.5 MB、依存は peer のみ。
- 判定: **保留**。`MonitorCreate` 単体の価値は高いが、package 全体の面積（loop・task・workflow・TUI status）が大きく、足すのは過大。先に、pi 本体の bash の background 実行や pi-subagents の背景実行 + 完了通知で「12 分のコマンド → 起こす」が足りるか実機で確かめる。足りない場合だけ導入を再検討し、その場合は上の `shellTools` 設定を前提にする。

### 5. @chankov/agent-fleet — 除外

確かめた事実（README）:
- 「Verification Contract」（受け入れ条件の assertion をディスクの台帳に置き、実装前に作る。orchestrator mode は `bash`/`edit`/`write` を外す）は設計として**関心が高く**、利用者の「契約を固める」に近い。専門 agent（planner・builder・reviewer・test-engineer・documenter）を `--no-extensions` で起動する（→ **子に permission-system が効かない**）。
- ただし、導入物が大きい: 152 MB、`npx ... setup` が repo に `.pi/` `.ai/` `justfile` を書く、herdr（端末の multiplexer）・Hermes Desktop・Telegram 経由のスマホ中継・MCP・音声（STT）・Claude Code の bridge（coms）が前提の構成。`pi-ask-user` を同梱しており、すでに入れる `@juicesharp/rpiv-ask-user-question` と二重（`ask_user` と `ask_user_question`）。
- 外部へ送るもの: Telegram 中継・STT プロバイダ（OpenAI / Groq / Azure）・複数のモデル提供元。Windows の対応は未確認。
- 判定: **除外**。検証契約の考え方だけ参考にする。

### 6. pi-herdsman — 除外

確かめた事実（README）: herdr（外部の端末 multiplexer）と pi の間の orchestration。Chief → Manager → Lead → Agent の階層・複数マシン間の federation（SSH）・Docker Compose の導入。peer に `@howaboua/pi-codex-conversion` を要求。導入は `curl ... | sh` が既定の案内。pre-1.0 で破壊的変更ありと明記。
- 判定: **除外**。herdr という外部依存・階層モデルが利用者の運用（1 親 → worker）と合わず、Windows 実機での前提も重い。

### 参考: @tintinweb/pi-subagents — 入れ替えの価値なし（概要のみ）

`Agent` ツール（nicobailon 版は `subagent`）。背景が既定・同時数の上限（既定 10）・完了通知・worktree 隔離（完了時に branch へ自動 commit）・`SubagentWorkflow`（JS script の orchestration）・cron の schedule・他拡張向けの RPC。機能は nicobailon 版と同系統で大きくは変わらない。入れ替える利点は、pi-loop の `Orchestration*` が使えること程度。**すでに決定済みの nicobailon 版から替える理由は見つからない**（子の拡張の読み込みは未確認）。二重には入れない。

## 推奨と設定

- **入れる: なし。** pi-subagents のまま。理由: 6 候補とも、利用者が必須とする「permission-system / cc-safety-net が子に効く」が確認できない・既定で逆（子は拡張なし）、または pi-subagents との二重・入れ替えになる。維持費の面でも、いずれも個人 1 名・0.x〜x の頻繁な更新（最終更新はすべて直近 2 週間以内）で追従の費用がかかる。
- 失うもの（入れない場合）: pi-gauntlet の gate の機械強制（phase-tracker）、pi-loop の再起床・monitor、dynamic-workflows の大規模 fan-out と journal 再開。いずれも現状の利用者の運用の必須ではない。
- **取り込む案（package でなく運用の変更）**: gauntlet の「verify が通るまで review に進まない・review の修正で verify を無効化」を feature-orchestration の手順に書く。
- 将来入れる場合の設定（今は推奨しない）:
  - pi-loop の `MonitorCreate` だけを使う場合: `pi-stock-packages` に `npm:@trevonistrevon/pi-loop@0.7.19`。permission-system の `shellTools` に `MonitorCreate`（`commandArgument: "command"`）を追加し、bash と同じ方針に通す。`PI_LOOP_CONTEXT=compact` でツールの説明を短くできる。`Orchestration*` は使えない（tintinweb 版が必要）。
  - gauntlet を使う場合: `npm:pi-cohort@7.6.8` + `npm:pi-gauntlet@8.4.3`（pi-subagents を外す）。`.pi/gauntlet-overrides.md` に検証コマンド・worktree の作り方（`.tmp/worktrees/<名前>/`）を書く。

## 判断した点

- 「子に拡張が効くか」を最重要の足切りにした（利用者の安全機構が前提のため）。
- gauntlet は設計が近いが、必須依存の cohort が pi-subagents の fork で同名のため、「足す」ではなく「入れ替え」と判定した。
- 月間 DL は人気の目安として扱い、安全性の根拠にしていない。
