# 案件テンプレート

`docs/change/NNNN-kebab-case.md` の雛形。下のコードブロックの中身を写して使う。書き方の規則は `markdown-style.md`。

## 作り方の約束

- 目的ができた時点で作ってよい。実装の合意を待たない
- 実装前の期待動作（受入条件）を先に書く。実装後の説明にすると、結果を仕様として正当化する運用になる
- 「現在地」と「候補比較」は、現在の理解へ更新し続ける。過去の観測は `research/` が持つので、上書きしてよい
- 未検証を不合格扱いしない。期待を確認済み扱いしない
- 経緯を物語にしない。本文は現在の姿だけ。変更は「重要な更新」の 1 行にする

## 節の順序

読む頻度の高い順に並べる。この順序を崩さない。

- いま（毎回読む）: 要約 → 目的と非目的 → 実施計画 → 現在地 → 未解決点 → 次の調査・実験
- 判断（方針を疑うとき）: 評価基準 → 候補比較 → 仕様への変更案 → 実装・検証
- 経緯（遡るとき）: 重要な更新 → 終了結果

- 案件固有の節は、属するブロックの位置に置く。末尾に付け足さない
- 「実施計画」は段ラベル（`A1`・`段 2`）の定義表を兼ねる。ラベルは計画表より後で使う

## 上から読んで分かるように書く

- 使う前に定義する。独自の呼称・略号は初出で 1 行説明する（リンクだけでは足りない）
- 「下記」「後述」で先送りしない。先に触れるなら、その場に 1 行の要約を添える
- 参照は節名で書く。`上記` `下記` を単独で使わない（節を並べ替えると向きが逆になる）
- 見出しの補足と計画表の状態を食い違わせない
- 表の「理由」欄を参照で埋めない。表は一覧性のためにある
- 各段は「解決したいこと」から書く
- 同じ語を言い換えない。言い換えると、読み手が別物かと考える

悪い例と良い例（先送り）:

| 悪い | 良い |
| --- | --- |
| `見送り（下記）` | `見送り（候補がほぼ全部、任意コード実行の経路だった）` |
