# CHG-0018: OpenCode の権限を「共通の禁止」と「役割ごとの権限」に分けて生成する

- **状態**: Exploring
- **更新日**: 2026-10-08
- **基準**: OpenCode v2.0.22、コミット e22b365、WSL2 (Ubuntu)

## 目的と非目的

[CHG-0017](0017-builtin-agent-restrictions.md) では、組み込みエージェント（`explore` / `plan`）の
制限が全体の `permissions` に上書きされる穴を、個別の deny や写し直しで 1 つずつ塞いだ。
穴が個別に出続ける原因は構造にある。OpenCode の規則は「全エージェント共通の基底 →
組み込みの追加方針 → 全体の `permissions` → エージェントの `permissions`」の順に連結され、
最後に一致したものが勝つ（[調査記録](../research/opencode/permission/builtin-agent-override.md)）。
全体の `permissions` には `build` 向けの allow / ask を置いているので、同じ規則が `build` には
制限として、`explore` には緩和として働く。

この案件では、生成の構造を次の 2 つに分け、写し直しが要らない形にできるかを確かめる。

- **共通の禁止**: 秘密ファイルの保護など、どのエージェントにも解除させない禁止。OpenCode の
  `experimental.policies`（<https://opencode.ai/v2/docs/policies>）へ出す。policy の `allow` は、
  先に書いた policy の deny を解除するだけで、エージェントに操作の権限を与えない
- **役割ごとの権限**: shell の allow / ask、edit、作業ツリーの外へのアクセスなど。全体の
  `permissions` から、`build` などのエージェント別の `permissions` へ移す

受入条件（実装前の期待動作）:

- `build` の振る舞いは変わらない（今の全体の規則と同じ順序・効果を `build` 側に持つ）
- `explore` は、補修の deny が無くても、shell / edit / 子の起動 / question を使えない
- `plan` の計画ファイルの allow が、共通の秘密ファイルの禁止を解除しない
- `.env.example` は `build` から今までどおり扱えるが、`explore` には編集の権限を与えない。
  `.ssh/.env.example` は例外で開かない
- plugin が読めなくても、保存した承認があっても、共通の禁止は残る
- Claude Code / Copilot CLI の生成結果は変わらない

非目的:

- 組み込みエージェントを自作で置き換えること（自作は基底の全部許可から始まるので、根本解決にならない）
- `ocs` を境界にして permission を簡素にすること（同じプロセスの中では役割ごとに分けられない）
- CHG-0017 の独自の方針（`plan` の子の許可リストと shell の ask、`bypass` の子の許可リスト、
  `git log --output` の抑止、親が `bypass` の子の外部読み取り）を変えること
- 保存した承認の扱い、`review-loop` の子の名前、引数で書けるコマンド（CHG-0017 の未解決点 2・3・7）

## 未解決点

- **どのプロファイルも当てない子の守り方は、2026-10-08 に対策 3 に決めた（利用者の判断）。**
  作業先のリポジトリが
  定義する子は、自分の `permissions` で全体の規則を上書きできるので、今の全体の `shell * ask` が
  守っていたのは「`permissions` を書かなかった子」だけだった。段 2 で比べた対策は次の 4 つ
  1. 全体に `shell * ask` などの最小の既定を残す: 組み込みの制限を上書きするので、`explore` の
     補修が外せず、`title` / `summary` にも流れ込む。受入条件を満たさない
  2. 全体を `* * ask` などの広い既定にする: 1 よりさらに組み込みの制限を上書きする
  3. 全体は deny だけにし、生成器で宣言したエージェントと既知の組み込みの全部にプロファイルを

     なるが、policy の deny は効く
  4. 3 に加え、guide plugin の `evaluate` で、生成した一覧に無いエージェントの allow を ask に下げる。
     plugin が読めないと効かない。未試験。**再開条件**: 対策 3 の下で、プロファイルの無い子による

- policy の照合は `~` を展開しない（コードを読んだだけ）。生成時に絶対パスへ展開する

## 次の調査・実験

- 段 4 は 2 つのコミットに分ける。先に所有の規則だけを入れ（今の宣言では出力が変わらない）、
  次に宣言と生成の変更を入れる。2026-10-08 に設計のレビューを受け、次を設計に加えた
  - **所有の規則（P）**: 宣言と逆の形式のエントリに、生成器が書かないキー（`model` / `request` など）
    が残っていたら、黙って消さずに移し方を示して生成を止める。モデルだけを割り当てた未宣言の ID
    もエラーにする。「出力が変わらない」の保証は、今のクリーンな生成とこの PC の実ファイルに限る
    （手書きの policy や `plan.color` を持つ入力では変わる）。宣言から丸ごと消した自作の ID は
    撤去しない（一般的な削除・改名までは扱わない）
  - **プロファイル（S）**: 必須の検査は、宣言したエージェント・既知の組み込み・モデルを割り当てた
    ID のすべてに掛ける。暗黙の既定値は置かない。`none` は当面 `title` / `summary` だけに許す。
    読み取り役は「外部アクセスと read の例外を足す規則」で、読み取り専用にする規則ではないので、
    自作に当てるときは自前の制限があることを試験する
  - **`ocs`**: エージェントの自前の規則は変換しない（プロファイルだけを変換して後ろに自前の規則を
    つなぐ）。skill の規則の除外も移す。パスの絞り込みは `~` のまま行ってから絶対パスへ展開する。
    `ocs` の policy は専用の一覧を合わせ、通常版のプロバイダの制限はそのまま写さない
  - **guide の早期停止**: policy の deny はエージェントの規則で外せないので、policy 由来の早期停止
    にはエージェントの免除を付けない。shell の policy は deny だけにする（生成器で保証）。引用符を
    含むコマンドなど、早期停止が見送る形は確認の説明を作ってから policy で拒否される（安全上の穴
    ではない）
  - **テスト**: 全体の `permissions` に起動の deny 2 件しか無いことを形で固定し、実装役の allow を
    増やしても読み取り役や `none` に流れ込まないことを判定で固定する。段 1 の評価器は、純粋な
    照合と判定に分けて基底と組み込みの規則を版付きの fixture にして取り込む。評価器だけで実効の
    動作の一致とはせず、plugin の node の試験と少数の実機の試験を残す
  - **apply の前の必須の試験**: Orca の上書き用の設定（`OPENCODE_CONFIG`）が重なる起動で、policy と
    V1 / V2 の切り替えが効くこと（plugin を外しても `.env` / `.ssh/.env.example` / `git push` が
    拒否される、別ファイルのモデルだけの定義と共存する）
  - **作業の順序**: 一度に任せず、生成器の中間表現・検査・所有処理 → 通常版と `ocs` の生成 →
    guide の生成と plugin の試験 → 全体の試験、の順に進める。`generate.py` を同時に複数で編集しない
  - 組み込みの `build` / `general` / `compaction` には `description` を書かない（組み込みの説明を
    上書きする）ので、V2 の宣言の `description` 必須の検査を組み込みには外す
  - `experimental.policies` を、`models` の有無に関係なく書く
  - V1 の宣言は空にするが、V1 を扱う処理は元に戻すときに備えて残す
  - P は実装した（2026-10-08、[配置済みの設定の所有](../spec/agent-config-generation.md#配置済みの設定の所有)）。
    設計に無かった追加が 2 つある
    - 逆の形式の V2 のエントリにある `model` のうち、値が階層のモデルのものは生成器の持ち物として
      消す（既存のモデルの整理と同じ考え方）。これが無いと、段 4 で V2 に移した `bypass` 系に
      階層のモデルを割り当ててから元に戻したときに生成が止まる
    - V1 の宣言に書けるキーを、生成器の持ち物と `bypass` に限った。持ち物の範囲がずれないようにするため
  - S の注意: `test_generate_opencode_ownership.py` の `test_clean_output_matches_the_generator_before`
    は、P の直前の生成器（d6ea76f）と出力を比べるテストで、S で宣言を変えると必ず落ちる。S で外す。
    `common.toml.tmpl` の `bypass` の `mode` の注記（既存の設定の `mode` が残る、という理由）も
    所有の規則の下では古いので S で直す
- 段 4 の見積もり（推測）: `generate.py` の全体の規則の生成を「policy の statement」「プロファイル」
  「全体の起動 deny」に分け、`restate_global_deny` とその免除の処理を外す。`ocs` の生成も
  プロファイル単位に変える。合わせて数百行。`test/agents/` の 9 ファイルが全体の規則か
  `restate_global_deny` を直接見ている

## 評価基準

- 必須: 受入条件をすべて満たす。CHG-0017 の補修（`explore` の 4 つの deny、`plan` の edit 制限の
