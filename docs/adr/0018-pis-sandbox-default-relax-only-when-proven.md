# pis をサンドボックス標準にし、緩和はサンドボックスが証明されたときだけ効かせる

- **ステータス**: Accepted
- **日付**: 2026-10-14
- **決定者**: applejxd

## コンテキスト

pi には承認の機能が無く、公式は OS・コンテナなどの境界で守る立場を取る（[調査記録](../research/agents/pi-isolation-options.md)）。
このリポジトリは、判定の拡張（ツール呼び出しを allow / ask / deny に振り分けるガード）と、Fence による OS の隔離（サンドボックス）の 2 層を持っていた。
`pis --boundary` が Fence の中で起動していたが、標準は Fence の外で、境界の中でのガードの動きは「受け取るだけで判定に使っていない」状態だった。
起動コマンドの組み立ては、`pis`（bash）と `ocs` の `pi.py` で別々に持ち、拡張を足すたびに 3 か所を直す構造だった（[CHG-0023](../change/0023-guard-terminology.md) の段 3a）。

守る目的は、[ADR-0012](0012-ocs-boundary-for-accidents.md) のとおり「エージェントのうっかり」を止めること。悪意あるリポジトリへの耐性までは求めない。
利用者の使い方は、普段は `pis` を打って起動し、制御ファイルの編集などサンドボックスが邪魔な作業だけ外で行う。
2 つのモデルによる設計のレビュー（2026-10-14）で、「境界で止まるものは確認しない」は広すぎること（作業ツリーの中の破壊・秘密は境界が守らない）、
緩和の切り替えを環境変数の自己申告にしてはいけないことが指摘された。

## 検討した選択肢

### 選択肢 1: 現状維持（サンドボックスは任意の `--boundary`）

- **利点**: 変更が無い
- **欠点**: 守りの中心である境界を、普段使いが通らない。境界の中でガードを緩められず、確認が多いまま。起動の組み立てが二重

### 選択肢 2: サンドボックス標準 + `--no-sandbox` を残す + 緩和はサンドボックスが証明されたときだけ（採用）

- **利点**: 守りが標準で効く。基準（サンドボックス無し）は保守的な動きで、緩和だけを足すので、厳密さをゲートに集中できる。Fence が壊れても、明示の脱出口がある
- **欠点**: 緩和のゲート（事前検査・カナリア）を作る必要がある。サンドボックスの中の環境（agent 置き場・環境変数）を作り込む必要がある

### 選択肢 3: サンドボックス無しの選択肢をなくす

- **利点**: 実装と運用が単純
- **欠点**: Fence が使えない・壊れたときに、利用者が素の `pi`（弱い守り）へ降格する。macOS・Windows では `pis` 自体が使えなくなる

### 選択肢 4: 別名ツール方式を畳み、フック方式（`tool_call`）の 1 実装にする

- **利点**: ガードの実装が最小になる
- **欠点**: 拡張が読み込めなかった・`/reload` で抜けたときに、組み込みのツールが判定なしで戻る（調査記録 E1）。フェイルクローズの再検証が要る

### 選択肢 5: bash ツールだけを Fence に通す

- **利点**: 認証が外に残り、agent 置き場の写しと認証の戻しが不要
- **欠点**: `read` / `edit` / `write`・MCP・拡張が境界の外になり、守りがガードの判定だけになる。ADR-0012 の「プロセス全体を囲う」を捨てる

## 決定事項

選択肢 2 を採用する。

1. **`pis` はサンドボックス（Fence）の中が標準**。`pis --no-sandbox` でフルガードだけの起動に切り替えられる（起動時の警告とフッターの常時表示）。
   サンドボックスを張れない OS では `pis` は起動を断り、`--no-sandbox` を案内する（黙って弱い守りに落とさない）
2. **基準は保守的な側に置く**。サンドボックス無しの動き（確認は全部出す）が基準で、サンドボックス有りは、基準に対して緩和を足すだけ。別の経路は作らない
3. **緩和は、サンドボックスが証明されたときだけ有効にする**。証明は、起動前の事前検査と、フルガードが内側で自分で行うカナリアの実測（読めてはいけないファイルが読めない・書けてはいけない場所へ書けない）。
   環境変数は「内側のはず」という期待にすぎず、緩和の根拠にしない。証明できなければ起動しない
4. **緩和の範囲は狭くする**。日常の shell（どの規則にも当たらず役割の既定の ask になったもの）の確認を外し、作業ツリーの外の読み書きは OS が開けた場所なら allow・外は理由つきの deny にする。
   ask の規則・deny・誘導・作業ツリー内の破壊的操作と秘密の保護・伏字化・役割・`git commit` と MCP の確認は変えない
5. **ガードの実装は 1 つ**（別名ツール方式のフルガード）。素の `pi` の簡易ガードは廃止し、素の `pi` には `commit-confirm` だけを残す。厳密さの予算は緩和のゲートに集中する

理由: 守りの本体は OS の境界なので、普段使いがそれを通る形にするのが最も効く。緩和を「証明されたときだけ」にすると、ゲートが壊れたときの失敗が「余計に聞く」側に倒れ、
黙って危険になる場所をゲートに限定できる。選択肢 3 は降格を招き、選択肢 4 は再検証が要り、選択肢 5 はプロセス全体を囲う方針を捨てるため、採らない。
サンドボックス無しを残すのは、Fence が壊れたときに明示の脱出口が無いと、利用者が無防備な入口へ流れるため（レビューの指摘）。

- [ ] `PI_HARNESS_BOUNDARY=1` だけを立てて（許可の一覧・カナリアが無いまま）フルガードを起動すると、起動しない（`test_pi_harness.py`。自動試験のみ。実機は未確認）

- [ ] `pis --no-sandbox` では確認が全部出て、警告とフッターの表示が出る（`test_pi_boundary.py`。フッターの実機は未確認）

## 結果

### ポジティブな結果

- 普段使いで境界が効き、日常の確認が減る。緩和が効く条件が、検査で証明されたときに限られる
- 起動の組み立てとガードの実装が 1 系統になる

### ネガティブな結果

- サンドボックスの中の環境（agent 置き場・環境変数・`fd` などの道具）を作り込む必要があり、実機で見つかる不具合が出る（記録 S1 の 3 件）
- 素の `pi`（Orca の起動ボタンなど）にはガードが付かなくなる。`pis` を打って起動する運用が前提
- サンドボックスの内側では Orca の状態表示が使えない見込み（推測）

### 中立的な結果

- `PI_HARNESS_*` などの識別子、`--boundary`（互換の別名）は旧称のまま残る（CHG-0023 の段 4 で要否を決める）
