# CHG-0037: `pis` の使い勝手を、他のプロジェクトで常用できる水準に上げる（と、運用の記録を取る）

- **状態**: Exploring
- **更新日**: 2026-10-24
- **基準**: 現行の `pis`（Fence ＋ `ocs` ＋ ハーネス）、コミット `5ffd835`。[ADR-0018](../adr/0018-pis-sandbox-default-relax-only-when-proven.md)（既定は境界つき。緩めるのは、必要が実証されたときだけ）

## 目的と非目的

**目的**: これまでの `pis` は使い勝手が悪く、**サンドボックスなしでの起動がほとんど**だった（利用者の訂正、2026-10-24）。他のプロジェクトで境界つきで常用できる水準まで使い勝手を上げ、**運用の記録を取る**。常用されて初めて、サンドボックスの便益（止めた事故、誤検出の費用）を測れる（[CHG-0033](0033-sandbox-build-value-assessment.md) の段 P6）。

**非目的**:

- 境界の強さを下げる（ADR-0018 の原則。緩和は、必要が実証されたものを、最小の範囲で）
- 資格情報の代理など、境界の仕組みの置き換え（[CHG-0036](0036-nono-trial-on-wsl2.md) など別の案件）

## 使わなかった理由（利用者の回答、2026-10-24）

1. **読めないパスや、許可の追加が面倒**（データセットなど）
2. **`pi` の開発中に、境界が邪魔になる**（`pi` 自体の作り込みに集中していた）
3. **新しく入れた `pi` の機能が、境界の中で動くかを、まだ確認できていない**。すぐに使いたいときは、境界なしにする
4. **ネット調査を、境界の中で安定して行えるか、確認できていない・不安**

（この案件を起こした調査の全期間も、境界なしで行っていたとみられる。この環境のユーザー名前空間の対応表 `/proc/self/uid_map` が恒等の対応で、Fence のユーザー名前空間の中ではなかった。つまり、**境界つきでの調査の動作は、本セッションでは未検証**）

## 通信の方針（利用者の方針と調査結果、2026-10-24）

ドメインの許可リストで絞る今の形は、調査の妨げになる。**調査に支障を出さない範囲で、境界線を引き直す**。

| 項目 | 会社（Bedrock・AgentCore） | 家（GitHub Copilot・検索 API） |
| --- | --- | --- |
| ドメイン | **拒否リスト型**。拒否は数サイトだけ。イントラネットも読める | 同じ（拒否は数サイト） |
| 検索クエリ・社外秘の漏洩 | 気にしない（Bedrock は学習に使われず、AgentCore の検索のクエリは AWS の外へ出ない。一部のモデルは最大 30 日保持。[記録 D1](../research/agents/web-search-data-handling.md)） | 気にしない（Brave はクエリを最大 90 日保持。Copilot の学習への利用は設定で opt-out できるが、既定値は不明） |
| 認証キーの漏洩 | **防ぐ** | **防ぐ** |
| GET | 無条件で許可 | 同じ |
| POST | **制御する**（何を送るか不明なため） | 同じ |

**実現の見通し**（Fence の公式 docs・スキーマで確認。ベンダー資料。実機では未検証）:

- **ドメイン**: Fence は `deniedDomains` を `allowedDomains` より先に評価し、裸の `*`（全許可。空なら全遮断）と `*.example.com` を使える。ただし `*` は「緩和モード」で直接接続を許し、**`deniedDomains` が効くのはプロキシの環境変数を使うプログラムだけ**（「Apps that ignore `HTTP_PROXY` will bypass `deniedDomains` filtering entirely」）。数サイトのブロックは、事故防止の水準では足りるが、確実な遮断ではない
- **会社（社内プロキシが必須）**: `defaultAction: "proxy"` と `upstreamProxy` で、「拒否リストに当たらない通信は社内プロキシへ」とする形が使える見込み（推測。未検証）。現行の自作の中継（`ocs/relay.py`）は、許可リストに `*` が入ると使われない仕様（`pi-guard.md:385`）で、ここが食い違う
- **POST**: Fence は「リクエストの内容を検査しない」（L7・秘密の検出は設定項目に無い）。**境界の層では POST を見分けられないので、判定器の層が担う**。現行: `curl`/`wget` の POST・body 送信は ask、センシティブなファイルや環境変数の送信は deny。**未整備**: Python・Node のインラインコードの HTTP POST、トークン形式（`ghp_` など）の検出（見つからなかった）
- **イントラネット**: Fence のプライベート IP の扱いは、原文に記述なし。`websearch.py fetch` は非公開 IP を拒否する仕様なので、会社では許可する設定が要る
- **会社の検索（`agentcore-websearch`）**: 境界の中では、(1) 資格情報（`~/.aws` が読み取り拒否、`AWS_*` は子へ渡さない）、(2) ドメイン（AgentCore の Gateway と `uvx` の取得）、のうち、とくに (1) で動かない可能性が高い（ドメインは方針の変更で解消する見込み。実機では未確認）
- **`aws`・`gh` の CLI**: 同じ理由で、境界の中では認証が要る操作ができない（意図した設計。通信の方針を変えても、資格情報の保護は変わらない）

## 認証の方針（暫定。利用者の希望、2026-10-24）

- **会社は長期で複雑な問題を解くことが多い**ので、12 時間で失効する短期 API key（G1）では足りない（確認済み: AWS の文書）。かつ、「**短命の本物のキーでも、漏れたときの被害は残る。漏れても何ともない代替キーの方が安心**」。したがって、**ホスト側のブローカーが本物の認証情報を持ち、内側にはダミー（入場用の乱数）だけを渡す**形（G2）を、**採用方向（暫定）**とする
- **`pi` は、この形を最初から想定している**（`pi-ai` の Bedrock プロバイダー。pi 1.3.0 の `node_modules/@earendil-works/pi-ai/dist/api/bedrock-converse-stream.js` を読んだ）:
  - 「**認証が要らないプロキシ**に対応」: `AWS_BEDROCK_SKIP_AUTH=1` で、ダミーの認証情報を設定する（`:66`、`:93`）
  - カスタムのエンドポイント（VPC・プロキシ）は、`model.baseUrl` が標準の AWS のものでなければ、そのまま使う（`config.endpoint = model.baseUrl`。`:63`）
  - ベアラートークンは `AWS_BEARER_TOKEN_BEDROCK`（`:69`）。入場用の乱数として使える
  - SDK（`@aws-sdk/client-bedrock-runtime` 3.1127.0、`@smithy/core`）は、`AWS_ENDPOINT_URL_BEDROCK_RUNTIME` と `AWS_ENDPOINT_URL` の環境変数を解決する（確認済み: `getEndpointUrlConfig.js`）。ただし pi はプロバイダーの `baseUrl` で上書きできるので、環境変数は不要とみられる
- **設計（LiteLLM の「二層の認証」を真似る。[記録 D3](../research/agents/agent-auth-delegation.md)）**:
  1. **ブローカーは `pis` と同じ寿命で起動・終了する**（`ocs/relay.py` の型。常駐のデーモンは不要）。`127.0.0.1` の空きポートで待ち受ける
  2. **入場用の乱数**を、起動ごとに生成し、内側へ `AWS_BEARER_TOKEN_BEDROCK`（または MCP の `Authorization` ヘッダー）として渡す。ブローカーは、これを検証して除去し、上流へ送らない
  3. **本物の認証情報は、ホスト側の AWS の既定の連鎖から読む**。**会社は SSO ではなく、IAM ユーザーの長期のキーを `aws configure` で保存している**（利用者の回答、2026-10-24）。有効期限が無いので、**長いセッションでも失効しない**。キーを更新（ローテーション）したら、ブローカーが、次の要求（または定期的な再読み込み）から新しいキーを使い、`pi` の再起動は要らない。SDK はクライアントの作成時にキーを読んで保持するので、ブローカーは、要求ごと（または一定間隔）に認証情報を再読み込みする
  4. **宛先を絞る**: `bedrock-runtime.<region>.amazonaws.com` と、`AGENTCORE_GATEWAY_URL` のホストだけ。それ以外の宛先・サービスには署名しない（署名プロキシは、Host ヘッダーの宛先に署名するので、実質の制限は、宛先の許可リストと、専用ロールの IAM の権限）
  5. **AgentCore の検索（MCP）も同じブローカーで中継**する: `pi` の MCP を `http://127.0.0.1:<port>/agentcore/mcp`（ヘッダーに入場用の乱数）に向け、ブローカーが SigV4 で Gateway へ転送する。**内側の `uvx mcp-proxy-for-aws-cli`（起動のたびに PyPI から取得する外部パッケージ）が不要になる**（サプライチェーンの面も減る）
  6. **実装の順（既製品を優先する。[記録 D5](../research/agents/agent-auth-delegation.md)）**: (0) 専用の最小権限ユーザーのキーを、そのまま内側へ渡す（作り込み 0。漏れたときの被害は費用の不正利用で、IAM の権限・モデルの絞り込み・予算の警告で上限を絞る。**ただし、通信を拒否リスト型にして緩めると、キーの持ち出しの経路が増える**）、(1) **Envoy の `aws_request_signing` を、設定だけで使う**（コード 0。ストリーミングの透過は Envoy の前提。Bedrock の設定例は無く、**実験が要る**）、(2) (1) が不可なら、小さな自作のストリーミング対応プロキシ（Python と `botocore`。`uv.lock` でハッシュ固定）。**`aws-sigv4-proxy` は、応答のストリーミングがバッファされる（Issue #250、Open）ので、`ConverseStream` に向かない可能性が高い**。入場用の乱数は、同じ OS ユーザーなら価値が小さく、省ける
- **必要な追加（現行に無い）**: (1) Fence の `allowLocalOutbound` ＋ `allowLocalOutboundPorts`（現行の設定生成は出さない）、(2) 内側へ渡す環境変数の例外（`AWS_BEARER_TOKEN_BEDROCK` は名前に `TOKEN` を含むので、現在は落とされる。ブローカーの入場用の乱数だけを、例外として渡す）、(3) `pi` の設定生成の、`models.json` への `baseUrl` の上書きと、http の MCP の `headers`（現行は `url` しか出さない）

**未確認（実験で測る）**: (a) Bedrock の `ConverseStream` が、ローカルの `http://` のプロキシ経由で動くか（SDK の既定のハンドラーは HTTP/2 で、プロキシが HTTP/1.1 のみだと、`NodeHttpHandler` へ切り替わる経路を使う必要があるかもしれない）、(b) 会社の IAM ユーザーの権限の範囲（Bedrock と AgentCore 以外にも及ぶか。専用の最小権限のユーザーを作れるか。できないなら、ブローカーの宛先とパスの許可リストが、実質の制限になる）、(c) ストリーミングの応答の透過、(d) AgentCore の MCP（streamable HTTP）の中継。

## 受入条件（期待動作）

1. **許可の追加が軽い**: 読み取りの許可を、1 コマンド、または 1 セッションの一時許可で足せる。永続の許可は、設定ファイルへの明示的な追加で足す（現在は `PIS_EXTRA_READ` と `.opencode/sandbox.toml` の `read` / `write` / `devices`）。足す前に、何が許可されるかを確かめられる
2. **`pi` の開発用の使い方**がある: ハーネスや拡張を開発するときに、境界が邪魔にならない、かつ、緩める範囲が明示され、ADR-0018 の原則と両立する
3. **境界の中での動作確認が 1 コマンド**でできる: 新しい `pi` の機能・拡張が、境界の中で動くかを、起動前に確かめられる（起動時のカナリアとは別に、拡張の動作の簡単な通し確認）
4. **ネット調査と POST の方針**: 上の「通信の方針」どおり、ドメインは拒否リスト型、GET は制限なし、POST は判定器が確認する（認証キーを含む送信は拒否）。境界の中で、`websearch.py` の検索・取得と `imozuru` の取得が通る（会社は AgentCore の検索も）。拒否された場合は、理由と、拒否リストの該当が分かる
5. **運用の記録**: 境界つきの起動と境界なしの起動の比率、拒否・確認の件数と理由、誤検出の報告、起動の待ち時間を、後から集計できる

## 現在地

- 理由は 4 点（上）。いずれも、**境界の強さではなく、運用の摩擦と、動作の未確認**に由来する
- 現状の仕組み（リポジトリのファイルで確かめたもの）: 許可の追加は `PIS_EXTRA_READ`（環境変数）と `.opencode/sandbox.toml`。通信は、ドメイン単位の許可リスト（`ocs/boundary.py` の `allowedDomains`）。`imozuru` の仕様は「任意のドメインの原文を取るには、許可リストを足すか `--no-sandbox` が要る。実機では未確認」と書く（`docs/spec/imozuru.md:102`）
- **読み取りの範囲は、worktree に限られていない**（確認済み: 任意の起動 cwd が読み書き可で、`work_read`（`~/src`・`~/worktrees`・`~/papers`・chezmoi のリポジトリ）と、`PIS_EXTRA_READ`・`.opencode/sandbox.toml` で足す。`boundary.py:244,255`）。理由 1 の摩擦は、worktree の実装でほぼ解消する見込み（利用者の見立て）。他のプロジェクト（例: `~/projects/foo`）で実際に起動して確かめる
- 本セッションで、多数のドメイン（公式の docs、GitHub、個人のブログ、NVD など）の取得が通った（境界なしでの実行とみられる。境界つきでは未検証）。したがって、**境界つきで同じ調査ができるかは、実測が要る**
- **状況のまとめ（2026-10-24。圧縮の前の要点）**: ① サンドボックスは使い勝手が悪く、境界なしの起動がほとんどだったので、便益を測れていない（[CHG-0033](0033-sandbox-build-value-assessment.md) の段 P6）。この案件はその前提の整備。② **通信**は、許可リスト型から、**拒否リスト型**（GET は無条件、POST は判定器が確認、会社と家で別）へ引き直す。Fence は `deniedDomains` 優先・`*` は緩和モード・L7 なし。③ **認証**は、**ホスト側のブローカーが本物の認証情報を持ち、内側にはダミーだけ**を渡す方向（G2）。LiteLLM は、サプライチェーンの対策は取れるが、Bedrock の忠実度・重さ・Copilot の DB なしの不確かさで見送り（G5）。④ **会社の AWS は IAM ユーザーの長期キー**（`aws configure`）。**専用の最小権限ユーザーは作れる**（利用者の回答）。⑤ **Copilot（家）**は、`pi` が認証を実装済みで、内側に残る長期トークンの権限は `read:user` だけ。実験は Copilot（段 U7a）から。⑥ 自作は最小にする規則: **既製の汎用部品 → 設定だけ → 接着 → 最後に自作**
- 道具は `PIS_COPILOT_BROKER=auto`（`ocs/broker.py` と `ocs/envoy-copilot.yaml`。`pis` と同寿命で Envoy を起動）。実機（WSL2、境界あり）で応答 OK。使い捨ての手順書は撤去
