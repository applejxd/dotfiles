# pi-extension-dev

このリポジトリの pi 拡張は**フルスクラッチで自作する**（[ADR-0016](../../../docs/adr/0016-pi-extensions-own-first.md)）。
このスキルは、拡張を作る・直すときの**進め方と調べ方**だけを持つ。仕組みの正本は `docs/` にある。

## 原則

1. **pi 本体の理解が先。** 作る前も直す前も、入れている版に合う一次の情報（文書・型定義・ソース）で確かめる。思い込みで作らない
2. **自作が基本。** 公開されている拡張は設計の参考として読むだけで、導入しない
3. **事実と推測を分ける。** 実機でしか分からないもの（TUI・実際のモデル・Windows）は、未確認と書く
4. **防御と使い勝手の両方を評価する。** 既定の脅威モデルは「エージェントのうっかり防止」。防御に偏って操作を悪くしない
5. **正本は `docs/`。** 知見は `docs/` へ記録し、修理で見つけた型だけをこのスキルへ戻す（下の「終わるとき」）
6. **試験で固定する。** pi が無い環境の skip は通過ではない。skip 件数を必ず報告する

## 呼び出し

pi 自身は、フルガードの下でスキルの一覧をモデルへ渡さない（[pi-upstream 表 B の 16](../../../docs/spec/pi-upstream.md#b-明示が無いここに書く)）。
このスキルは作業先の `.agents/skills`（`pis` が `--skill` で足す）から読まれ、一覧はフルガードがモデルへ渡す。
明示して呼ぶなら `/skill:pi-extension-dev`。作業中に編集したら `/reload` で反映する。

## 全体の流れ

```text
段 0 pi 本体を理解する（共通・最初）
   ├─ 作る・変える: 段 1 要望 → 段 2 公開拡張の調査 → 段 3 ハーネスとの相性 → 段 4 提案（承認待ち）→ 段 5 実装と試験
   └─ 直す:        修理の進め方（切り分け → 検索 → 再現 → 原因 → 修理 → 固定）
   （仕様を調べるだけの依頼は、段 0 で報告して終わる）
終わるとき（共通）: 記録 → 還流
```

各段で、次へ進む前に結果を短く報告する。

## 段 0. pi 本体を理解する（共通）

[pi 本体の仕様を当たる方法](references/pi-spec-guide.md)に沿って、これから触る機能に関する**仕様を先に読む**。
順序は、版の確認 → 文書 → 型定義 → ソース → 同梱の例 → 変更履歴 → 上流の Issue → 実測。
話題から読む文書を選ぶ索引がある。公式に明示がある項目・無い項目の棚卸しは
[pi-upstream.md](../../../docs/spec/pi-upstream.md)が正本で、頼ろうとする挙動がそこに載っているかを先に見る。
表の**該当する行の「確認した版」**を、入れている版と照合する（表全体の対象版ではない）。違うなら、インストール済みの文書・実装・試験で確かめ直す。

**調べるだけの依頼**（「pi の仕様を調べて」）は、この段で終えてよい。確かめたこと・出典・未確認の点を報告し、
段 1 以降や修理、ファイルの編集には進まない（必要なら、調べた結果を `pi-upstream.md` へ記録するかを利用者に尋ねる）。

## 作るか、直すか

- **作る・挙動を変える**: 下の「進め方」の段 1〜5。
- **不具合を直す**: [修理の進め方](references/repair-guide.md)を読む（症状の切り分け → 先に広く検索 → 再現 → 原因の確定 →
  修理 → 試験で固定）。過去の修理から拾った「既知のパターン」と、修理に入る前の確認がある。
  直しが防御の強さや利用者の操作を変えるときだけ、段 4 の提案を出す。
- 作るか直すか分からないとき（「この機能をこうしたい」と「これが動かない」が混ざっている）は、先に修理を済ませ、その後に機能を足す。

## 進め方（作る・変える）

**段 4 は利用者の承認を待つ**（承認なしに実装へ進まない）。

### 1. 要望を整理する

目的・使う場面・成功条件・やらないことを 1 つずつ書き出す。曖昧なら利用者に確認する。
あわせて、拡張が本当に要るかを [入口の選び方](../../../docs/spec/guard/pi-extensions.md#入口の選び方) で判断する
（skill + CLI や MCP で足りるなら拡張にしない）。

### 2. 公開拡張の動向を調べる（導入はしない）

[公開拡張の調べ方](references/public-research.md)に沿って、ハブを上から順に全部当たる（1 回の検索で済ませない）。
見る観点は、**方式**・**挙動の流儀**（通知・状態・UI）・**既知の不具合と反例**・**pi の版への依存**。
読むだけで、取得・実行・コードの複写はしない。結果には出典 URL・日付を付け、事実と推測を分ける。

### 3. 現行のハーネスとの相性を確かめる

次を `docs/spec/guard/pi-guard.md` と実コードで確認する。

- **判定と伏字化**: 拡張のツールは `guarded_*` の判定を通る。役割（`implementer` など）の `tools` に載せるか、判定の規則が要るか。
  `bash` を置き換える方式は、判定を迂回しないかを必ず見る
- **bg_run のようにコマンドを扱うツール**: bash と同じ判定（`decide`）に通すか
- **起動の違い**: `pis` は `-ne`（自動発見なし）で、自作は `[pi] own_extensions` から `-e` で足す。素の `pi` は自動発見で読む。
  サンドボックスの読み取り許可も一覧から生成される
- **システムプロンプトへの露出**: ツールには `promptSnippet`（必要なら `promptGuidelines`）を付けないとモデルが使い忘れる
- **pi の内部に頼る点**: 増やすなら [pi の内部の挙動に頼る点](../../../docs/spec/guard/pi-guard.md#pi-の内部の挙動に頼る点) へ足す
- **Windows**: プロセス停止やパスの扱いが違う。実機で回せないなら未検証と明記する
- 既存の拡張（`todo` / `plan` / `btw` / `activity` / `subagents`）と機能・名前が重ならないか
- **同じ脅威を既存の仕組み（サンドボックス・判定器・確認）がすでに防いでいないか。** 防いでいるなら、段 4 で重ねない
- 新機能が、利用者の今の操作（確認の回数、入力、表示）のどこを変えるか。段 4 の評価の材料として、ここで洗い出す

### 4. 利用者へ提案する（承認を待つ）

[提案のひな形](references/proposal-template.md)に沿って、1 回にまとめて出し、**承認を待つ**。ひな形は、この段に入ったときに読む。

- 要望の整理（段 1）
- 調べた方式の比較（出典付き）
- **防御の強さの違う 3 案**（堅牢案・標準案・体験案）と、その**推奨**。案の定義と書く項目は、ひな形が正本
- **利用者の操作の変化の評価**（良くなる点と悪くなる点）。
  近ごろの機能追加は防御に偏って使い勝手を度外視しがちだったので、使い勝手の悪化は黙って入れず、評価に書いて承認を求める
- ハーネスとの相性で見つけた制約と、その対処
- 作るもの・触るファイル・試験の方針・未確認として残る点

段 1 の結果が「拡張にしない」（skill + CLI や MCP を推奨）でも、**その実装案について 3 案と操作の変化の評価を出す**。
拡張にしない理由は、方式の比較の中で示す。

### 5. 自作して試験する

- 置き場: `home/dot_pi/agent/extensions/<名前>/index.ts`。一覧は `home/dot_config/agents/common.toml.tmpl` の `[pi] own_extensions` の 1 か所
- 判定器のルールや誘導を変えたら、`docs/spec/guard/pi-decide.md` と golden（`scripts/agents/export_decide_golden.py`）も合わせる
- 偽のモデル（`test/agents/pi/faux.ts`）で、決まったツール呼び出しを通信なしに出させて試す。
  既存の試験（`test/agents/test_pi_harness.py` / `test_pi_harness_extensions.py` / `test_pi_subagents.py`）が型になる
- 試験する観点: ツールがシステムプロンプトに載る / 判定（allow・deny・ask）/ 伏字化 / `/reload` 後の状態 / 異常系
- **使い勝手の観点**: 段 4 の評価で挙げた、確認の回数・メッセージの分かりやすさ・失敗時の回復が、見込みどおりかを確かめる。
  数えられるもの（確認の回数など）は試験で数える。数えられないものは、実機で確かめる項目へ足す
- 実行（pi が無い環境では skip になる。**skip は通過ではない**ので、skip 件数を必ず報告する）:

  ```bash
  uv run --with pytest --with pyyaml --no-project pytest test/agents/ -q
  uv run pre-commit run --files <変更したファイル>
  mise exec -- python3 scripts/lint_templates.py
  ```

- 偽のモデルで確かめられないこと（TUI の表示、実際のモデルの使い分け、Windows）は、
  `docs/spec/guard/pi-guard.md` の「実機で確認する項目」へ未確認として足す。確かめていない結果を書かない

## 終わるとき（共通）

1. **記録する。** 公式に明示が無い挙動を実測したら `pi-upstream.md` の表 B へ（**原則は試験で固定。自動試験が組めないときは、再現の条件・手動で見た結果・未確認の範囲を残す**）、明示があるものは表 A へリンクだけ。
   自作の拡張は `guard/pi-guard.md`（自作の拡張の表）、実機でしか確かめられないものは「実機で確認する項目」へ。必要なら `docs/index.md` も
2. **還流する。** 修理で、既知のパターンに無い型を見つけたら、[修理の進め方](references/repair-guide.md)の表へ 1 行足す。
   このスキルの手順が実際と食い違っていたら、その場で直す（`skill-creator` の手順で）
3. **利用者へ伝える。** `chezmoi apply` が要るか、実機で確かめてほしい点、未確認として残る点
