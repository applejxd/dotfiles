# CHG-0004: OpenCode の保護を OS のアクセス制御へ移す

- **状態**: In progress
- **更新日**: 2026-09-23
- **基準**: OpenCode V2（`v2.0.12`）/ `@anthropic-ai/sandbox-runtime` v0.0.76
- **対象 OS**: **Ubuntu / WSL のみ**（macOS と Windows は [CHG-0002](0002-opencode-ask-by-default.md) の方針を維持）

## 目的と非目的

**目的**: 列挙型の規則では任意コード実行の権限境界を作れないので、
**OS のアクセス制御を保護の主役にする**。自動許可は事前承認した作業範囲に
限り、実ホームへの適用と外部への作用は別の権限として扱う。

**非目的**:

- macOS / Windows の設計変更。bwrap が無いので現行方針を維持する
- Claude Code / Copilot CLI の設計変更
- **「sandbox を入れたので全部 `allow`」にすること**。境界はファイルの話で、
  通信・認証情報・公開操作は別に扱う（[判断の根拠](#なぜ切り替えるか)）

## 発端

[CHG-0002](0002-opencode-ask-by-default.md) は「境界は無い」という前提で
plugin に安全網を積んできた。段階 3 まで配備した時点で次が見えた。

| 観測 | 内容 |
| --- | --- |
| 規則が単調増加している | 誘導 5 本・伏字化 9 本・パターン 71 本。誤爆のたびに除外条件が増える |
| 誤爆の原因が構造的 | 「コマンドとして使う」と「文章として書く」をシェルの構文解析なしに区別できない。1 日で 3 件踏み、うち 1 件は**コミットそのものができなくなった** |
| **書き込み保護が成立していない** | write deny の 38 glob は `edit` ツールにしか効かず、shell のリダイレクトには**一切効かない** |
| 塞げない経路が残る | `printf` / `tee` / `python3 -c "open(...)"`、`> $VAR`、`base64` / `tr` |

決定打は 3 番目。**保護の中核が動いていなかった**。

## なぜ切り替えるか

判定の問いが変わる。

| | 列挙型 | 境界がある場合 |
| --- | --- | --- |
| 各コマンドに問うこと | このコマンドは何ができるか（**shell では答えられない**） | 効果は境界の外に出るか |

後者は答えられる。列挙の対象が「許すもの（約 300 件）」から
**「越えるもの（10 件程度）」**へ縮む。

### 境界を過信しない

外部レビュー（Astra）の指摘を採る。**sandbox は許した範囲内の事故を防がない。**

| 危険 | 境界で防げるか |
| --- | --- |
| 秘密の読み出し・持ち出し | **防げる** |
| 境界外への書き込み | **防げる** |
| 未コミット成果物の破壊 | **防げない**。git が唯一の網 |
| ネットワーク経由の送信 | 許可ドメインの範囲でのみ可能 |
| リポジトリ自身への細工 → 後日の `chezmoi apply` で実環境へ | **防げない**。適用時の差分確認が唯一の網 |

最後が効く。**このリポジトリは「ホーム全体を書き換える source state」**なので、
境界内で自由に書けることは「後で実環境へ反映される内容を自由に書ける」ことと
同義になる。だから `chezmoi apply` を境界の外に置き、そこで差分を見る。

## 期待される効果

移行後の見込み（実履歴 1,128 呼び出しで算定）。

| 区分 | 対処前 | **対処後** |
| --- | --- | --- |
| 自動で進む | 91.6% | **98.7%** |
| 承認で止まる | 1.3% | **1.3%** |
| 失敗で止まる | 7.1% | ほぼ 0% |

**承認が要るのは `chezmoi apply` / `re-add`（13 件）と `git push`（2 件）だけ。**
どちらも意図的に人が見る操作なので、残すことが目的にかなう。

「対処」はドメイン許可リストへの追加と読み取り専用 PAT の配置（段階 4）。

上乗せの待ち時間は**コマンドごとには掛からない**（隔離は起動時 1 回）。

> **「自動」は「境界内で成功する」前提。** ワークスペース・`/tmp`・`~/.cache`
> 以外へ書くコマンドは失敗する。実運用で洗い出す。

### 段階 0: `srt` の成立確認と構成の決定（完了）

`@anthropic-ai/sandbox-runtime` は Claude 専用ではなく**汎用**で、seccomp の
ために**既に導入済み**だった。実地で次を確認した
（[調査記録](../research/opencode/permission/sandbox-runtime.md)）。

| 検査 | 結果 |
| --- | --- |
| `~/.ssh` / `~/.config/gh` / `~/.git-credentials` | 拒否 |
| ワークスペースの読み書き | 成功 |
| **`git push`** | **`could not read Username`** |
| **`gh auth status`** | **未ログイン扱い** |
| 許可ドメイン / 許可外ドメイン | `200` / **遮断** |
| `cmd.exe`（WSL の脱出経路） | **拒否**（seccomp） |
| **`chezmoi`（snap）** | **internal error** |

**認証情報を見せないだけで `git push` と `gh` の書き込みが止まる。**
コマンド文字列の判定は 1 つも要らない。

#### 構成の決定: サービスではなく**実行ごと**に包む

当初は `opencode serve --service` を包む想定で、**いったん不成立と判断した**。

サービスは TCP `127.0.0.1` で待ち受け、TUI がそこへ接続する。Linux の `srt` は
**ネットワーク名前空間を丸ごと除去する**ため、内側で待ち受けても外から届かない
（実測: 内側の `bind` は成功、外側からの接続は `TimeoutError`）。

> **この結論の一般化は誤りだった（2026-09-23 に訂正）。** 当てはまるのは
> **境界をまたぐ構成だけ**。`opencode --standalone` は TUI とサーバが
> **同一プロセス**なので、またぐ接続が発生しない。実測で成立した
> （[調査記録 19 節](../research/opencode/permission/sandbox-runtime.md)）。
>
> ネットワーク名前空間が除かれる性質は、境界としては**利点**でもある。
> 内側の OpenCode は**外側の共有サービスへ到達できない**ので、
> 「TUI だけ包んで共有サーバでツールを実行する」抜け道が自動的に塞がる。

この訂正により、途中で検討した 2 案は**どちらも破棄**した。

| 破棄した案 | 破棄の理由 |
| --- | --- |
| A: plugin が `execute.before` でコマンドを差し替える | 後続の権限評価が**書き換え後**を見るため、静的 allow 5 件と deny が一致しなくなる（実測） |
| B: 設定の `shell` にラッパーを指定する | 権限評価は生き残るが、**コマンド文字列で sandbox を解除する**構造になる。外部レビューが「認可の設計として不適切」と判定 |

**この構成の代償**は次の 2 点。計画に織り込む。

| 代償 | 影響 |
| --- | --- |
| ワークスペースは境界が守らない | 段階 3 で `allow` + snapshot による復旧として扱う |
| **保護機構そのものが書き換えられる** | 権限設定もランチャーのソースも全て書ける（実測）。`denyWrite` と**人間の差分審査**で守る |

#### 分かった癖（導入時の注意）

- **`allowWrite` の祖先を `allowRead` に載せると無効化される**（内側で `EROFS`）。
  書きたい領域は**根ごと** `allowWrite` に載せ、祖先を `allowRead` に載せない。
  完全一致なら問題ない
- **どちらにも載っていない領域への書き込みは、成功したように見えて消える。**
  最も危険。設定を書いたら必ず実体を確認する
- **`denyRead` は「広く deny → `allowRead` で戻す」でしか効かない。**
  ピンポイントの deny は黙って無視される
- `denyWrite` はディレクトリ単位で機能し、`allowWrite` より優先される
- 広い `denyRead` の下では `$HOME` が差し替わる。`$HOME` 直下に書けても
  実ホームには現れない（境界の破れと誤読しない）
- PATH の `srt` は**別物**（Python の字幕処理ツール）。実体を直接叩く
- 版は `latest` の浮動指定で **Claude Code と共有**している。片方の都合で
  上がると両方の挙動が変わる

規則の導出は[調査記録](../research/opencode/permission/sandbox-runtime.md)。

#### 復旧経路は境界の外だが、**同じ作業コピーを開いてはいけない**

当初は、境界の内側から抜けるための `bypass` エージェントを用意する計画だった。
**実行主体ごと包む構成では要らない。** 境界はランチャーが張るので、
ランチャーを使わなければそれが境界の外になる。

**ただし「通常版を起動して直す」は、そのままでは危険。**

OpenCode は起動時にプロジェクト設定を探索し、設定には plugins・MCP・
formatter・LSP という**実行経路**がある。隔離側が変更した作業コピーを
通常版で開くと、**審査に入る前にそのコードが動きうる**。

| やってはいけない | 代わりに |
| --- | --- |
| 未審査の作業コピーを通常版の OpenCode で開く | **テンプレートを評価せず、データとして読む** |
| **未審査のまま `chezmoi diff` を実行する** | テンプレートと参照先を審査した**後**に実行する |
| 作業コピー内の mise タスクや検証スクリプトを先に走らせる | 審査を済ませてから |
| ランチャーを作業コピーから起動する | `~/.local/bin/` の実体から起動する |

##### 審査コマンド自体が実行経路になる

**`chezmoi diff` は安全な審査手段ではない。** テンプレートを評価するため、
`output` 関数が**外部コマンドを実行する**。未審査の `.tmpl` に対して
ホストで実行すれば、避けたかった「審査前のホスト実行」が別経路で成立する。

`git diff` も無条件に受動的ではない。**外部 diff・textconv・pager** の設定
次第で外部プログラムを起動し、その設定は作業コピー側から変更できる
（`.git/config` を残す理由でもある）。

したがって審査は 2 段にする。

| 段 | 内容 |
| --- | --- |
| 1 | **テンプレートを評価せず、データとして読む。** Git の未信頼設定による外部プログラム起動も排除する |
| 2 | テンプレートと参照先の審査が済んでから `chezmoi diff` を実行する |

審査対象は `git diff` の出力に限らない。**固定した信頼済み基準からの変更**と、
**未追跡ファイルを含む展開対象全体**を見る。

**審査は、対象の設定・plugin・タスクを読み込まない環境で行う。**
審査した内容と、実際にホストで実行・展開する内容を一致させる
（審査後に隔離側が書き換えたものを適用しない）。

> `bypass` は subagent として起動できない（実測で
> `Agent bypass cannot run as a subagent` を確認）。
> [bypass エージェント](../research/opencode/permission/bypass-agent.md)の記録は
> 残すが、この計画では使わない。

#### ランチャーが境界を張るまでの信頼の鎖

**境界が成立する前にホストで動くものは、すべて信頼対象。**
ここに可変な入力が混ざると、保護は境界の前で迂回される。

| 守ること | 理由 |
| --- | --- |
| ランチャーは**絶対パス**で実体を呼ぶ | `PATH` の差し替えを防ぐ |
| **mise タスクを経由しない** | タスク定義はワークスペース内＝可変 |
| 設定・チェックスクリプトも `allowRead` 側の実体を参照する | 作業コピーを読ませない |
| シェル起動設定（`.bashrc` 等）に依存しない | 可変 |

`denyWrite` の対象は、この鎖を辿って**導出する**。ファイル名の列挙では足りない。

| 辿る先 | 例 |
| --- | --- |
| 生成器とその import 先・テンプレート | `scripts/agents/generate.py` とその依存 |
| 設定の参照先 | `common.toml` の該当入力 |
| 起動チェック自体 | チェックスクリプトの実体 |
| 実行ファイルの解決 | `PATH`、ランチャーが呼ぶ各バイナリ |

**直接編集だけでなく、再生成・親ディレクトリの置換・rename・参照先の
差し替えによる迂回も検証対象**にする。

### 段階 1: `chezmoi` を snap から外す（完了）

snap 版は bwrap 内で動かない。ブートストラップの 1 行を差し替えた。

```sh
# README の変更
- sudo snap install chezmoi --classic
+ sh -c "$(curl -fsLS get.chezmoi.io)" -- -b "$HOME/.local/bin"
```

**mise 先行には変えない。** `chezmoi` が `mise` を入れる一方向の依存を保つ。
逆にすると `chezmoi apply` の最中に mise 自身を更新する場面が自己参照になる。

#### snap を外して分かったこと（2026-09-22）

**`chezmoi = "latest"` は既に mise で宣言されていた**（`config.toml.tmpl`）。
`/snap/bin` が PATH で mise の shim より前にあり、**それを覆い隠していただけ**
だった。snap を外した時点で mise 管理版へ切り替わった。

したがって公式インストーラが要るのは**初回の bootstrap だけ**で、以降は
mise が引き継ぐ。`~/.local/bin` のコピーは残さなくてよい（重複するので削除した）。

#### 完了の確認

| 確認 | 結果 |
| --- | --- |
| 削除前の安全性（`status` / `diff` の出力） | snap 版と公式版で**完全一致**（151 行） |
| 設定の置き場 | `~/.config/chezmoi/`。snap の外にあり失うものなし |
| 現在の解決先 | `~/.local/share/mise/installs/chezmoi/latest/chezmoi` |
| **境界内での動作** | `--version` / `source-path` / `execute-template` / `data` **全て成功** |

`chezmoi apply` の実行は利用者の判断に委ねる（`status` に未適用の差分がある）。

### 段階 2: `opencode --standalone` ごと `srt` で包む（完了）

このリポジトリ専用のランチャーが、境界を張ってから OpenCode を起動する。

```sh
srt -s <境界の設定> -c "opencode --standalone"
```

`--standalone` は **TUI とサーバが同一プロセス**なので、境界をまたぐ接続が
発生しない。コマンド文字列に一切触れないので、**permission の allow / deny が
そのまま生きる**。

| 得られるもの | 内容 |
| --- | --- |
| 覆う範囲 | shell だけでなく `read` / `edit`・plugin・LSP・formatter も境界内 |
| 固定費 | **コマンドごとには掛からない**（隔離は起動時 1 回） |
| 外側の共有サービス | ネットワーク名前空間の除去で**到達できない**（実測） |

#### 境界の設定

| 区分 | 対象 |
| --- | --- |
| `allowWrite` | ワークスペースの根 |
| `allowRead` | `opencode` 本体、mise、`~/.local/bin`、`~/.config/opencode`、**プロジェクトごとの許可パス** |
| `denyRead` | `/home/<user>`、**`/mnt`**、**`/tmp`**、`/var/tmp`、`/dev/shm` |
| `network` | 許可ドメインのみ（proxy 経由） |

`denyRead` は「広く deny → `allowRead` で戻す」形で書く。ピンポイントの deny は
**黙って無視される**。

> **`/mnt` と `/tmp` は実測で開いていた。** `denyRead: /home/<user>` は
> **WSL の Windows 側を守らない**。`/mnt/c/Users` まで読めていた。
> `/tmp` はホストと共有されていた。どちらも `denyRead` に入れて塞ぐ。
> `/tmp` は**空の書き込み可能な tmpfs で覆われる**ので道具は壊れない。

#### 安全網の保存先（`XDG_DATA_HOME`）

**これを外すと安全網が消える。** snapshot の実体は
`$HOME/.local/share/opencode/` に置かれるが、そこは境界内では**隠されて
消える領域**なので、境界を抜けた瞬間に復元用データが失われる。

捕捉は成功したように見えるため、**気づけない**。`XDG_DATA_HOME` を
`allowWrite` 配下へ向けること。実測で復元まで確認した。

#### 隔離用の DB

`--standalone` は専用サーバを意味するが**専用 DB は意味しない**。
共有すると他プロジェクトの会話が境界内へ入る。`OPENCODE_DB` で分ける。

作り方は「実 DB を複製 → 資格情報と `migration` 以外を消す → `vacuum`」。
**`migration` を消すと壊れる**（スキーマ管理の記録）。

#### ランチャーの置き場と保護

**ワークスペースに置いてはいけない。** 書き換えられたうえで次回**外側で**
実行されると、境界の前にコードが走る。

| 対象 | 置き場 | 内側から |
| --- | --- | --- |
| ランチャー本体 | `~/.local/bin/` | `allowRead` のみ → 書けない |
| 境界の設定 | `~/.config/opencode/` の隣 | 同上 |
| それらのソース | ワークスペース（chezmoi source state） | 編集できる |

chezmoi 管理のままにする。AI はソースを提案できるが、**自分で有効化できない**。

`denyWrite` の対象は「**次回の隔離起動時に、実行コード・境界設定・緩和設定の
選択を決定する入力一式**」とする。ファイル名の列挙では足りない。
生成器（`generate.py`）や `common.toml` の該当入力、起動経路を決める
mise タスクも含む。**保護対象を、変更できる生成器から次回上書きできるなら
保護は迂回されている。**

#### 起動時の境界チェック（fail-closed）

**値は根拠にしない。** `/proc/self/status` の `Seccomp:2` は「何らかの filter が
付いている」ことしか示さず、親環境由来のものでも同じ値になる。

**拒否されるはずの操作を実際に試し、1 つでも通ったら起動を中止する。**

| # | 確認 | 検出する劣化 |
| --- | --- | --- |
| 1 | `~/.ssh` / `~/.git-credentials` / `~/.config/gh` が読めない | `denyRead` の漏れ |
| 2 | `/mnt/c/Users` / `/mnt/c/Windows` が読めない | WSL の Windows 側 |
| 3 | ホストの unix socket へ繋がらない | **seccomp の実効性** |
| 4 | 許可外ドメインへ出られない | proxy の設定漏れ |
| 5 | `XDG_DATA_HOME` が永続領域にある | 安全網の消失 |
| 6 | 作業領域へ書ける | 設定ミスで作業不能になるのを防ぐ |
| 7 | **許可外への書き込みが拒否される** | `allowWrite` の広すぎ |
| 8 | **`denyWrite` の保護対象を変更できない** | 保護機構の自己改変 |

##### 「拒否された」と「試験できなかった」を区別する

**混同すると、穴が開いているのに合格になる。** 対象が存在しない・
接続先が止まっている・名前解決に失敗した場合も「繋がらなかった」に見える。

**エラーコード単独で合否を決めてはいけない。**

| 誤りやすい判定 | 理由 |
| --- | --- |
| `ECONNREFUSED` を隔離の証拠にする | **サービスが待ち受けていないだけ**かもしれない |
| `EACCES` を隔離の証拠にする | 元からのアクセス権による拒否かもしれない |
| `ENOENT` を失敗と見なす | **対象を隠す方式では、これが正しい隔離結果**（今回の `denyRead` がそう） |

したがって次の形で判定する。

| 要件 |
| --- |
| 試験対象は**存在することが分かっている無害なもの**を使う |
| **対照条件（境界の外）では利用できる**ことを確かめ、内側の結果と対応付ける |
| 採用した隔離方式で**期待される結果**を事前に決め、それと突き合わせる |
| **原因を判別できなければ停止する**（判定できない ≠ 合格） |

ネットワークの試験は、**管理下の無害な待受先**を使い、単なるサービス停止を
合格扱いしない。具体的な試験対象の選定は実装時でよい。

##### 永続性は隔離をまたいで確かめる

**5 は内側だけでは確認できない。** 隔離の中では「書けた」ことしか分からず、
外へ出たときに残るかは別（これが実際に踏んだ罠）。
**隔離の終了後・再起動後に実体を検査する**手順を持つ。

##### チェック後に条件が変わらないこと

事前チェックと本体実行で設定や入力が違えば、検査した意味がない。
**同じ設定・同じ入力で本体を起動する**（チェック後に再生成しない）。

実測で、硬化した設定は合格・弱い設定は不合格になり、**`srt` は内側の終了コードを
そのまま外へ伝える**（`exit 42` → `42`）。fail-closed が成立する。

> **チェックの結果をパイプへ通さないこと。** `| grep` を挟むと終了コードが
> パイプ末尾のものに置き換わり、**失敗を取りこぼす**（実際に踏んだ）。

#### `chezmoi apply` は境界の外（人間の責務）

境界の内側からは実行できない（ホーム全体への書き込みが要るため）。
**コマンドを例外として通す案は採らない。** 完全一致にしても、
`chezmoi apply` が何をするかは source state とスクリプトが決めるので、
エージェントがそれらを編集できる以上、1 回の承認で書き換えた内容が実行される。

- エージェントは **source state の変更まで**
- **適用は差分確認のうえ人間が行う**

**`chezmoi apply` は単なるファイル複製ではない。** 変更されたコードを
ホスト権限へ移す操作なので、審査の対象には設定だけでなく**実行されるコード**
（`.chezmoiscripts/`・mise タスク・シェル起動設定・Git hooks・ランチャー）が入る。

#### この構成が覆わないもの

| 残余リスク | 内容 |
| --- | --- |
| **審査前のホスト実行** | mise タスク・Git hooks・検証スクリプトは `chezmoi apply` より先に外側で動きうる。**通常版で作業コピーを開くだけでも起きる**（上記の審査手順で塞ぐ） |
| ワークスペースの破壊 | 境界は作業場を守らない（段階 3 で扱う） |
| 境界内の資格情報 | モデルの OAuth は境界内から読める（下記） |
| 許可ドメイン経由の送信 | ドメイン許可は**送信内容も相手アカウントも制限しない** |
| 計算資源 | bwrap は CPU・メモリ・ディスク・課金の上限を保証しない |

##### 境界の外で実行されるものを棚卸しする

**「内側から到達できない」は D-Bus 1 つの拒否からは一般化できない。**
有効な各ツールについて、**実際の実行場所**と**使う資格情報**を数え上げ、
境界の外で動くものは独立した権限として扱う。

| 洗う対象 | 備考 |
| --- | --- |
| `/run` 配下の他の unix socket、**抽象 unix socket**、継承した FD | 3 の試験対象を D-Bus だけにしない |
| localhost・ホスト側アドレスの既存サービスや実行 API | TCP 直結は塞がる（実測）が、それ以外は未確認 |
| **リモート MCP・ブラウザ操作など、隔離の外で処理されるツール** | 境界内から呼べても**実行はホスト側**になりうる |
| WSL の Windows 相互運用 | interop は塞がっていた（実測）。版が変われば再確認 |
| `/proc` 経由の他プロセス情報・FD | 未確認 |

**完了条件**: 通常の作業が境界内で回り、起動時チェックが合格し、
境界を弱めるとチェックが不合格になることを実地で確認できること。
外で実行されるツールの棚卸しが済んでいること。

#### 完了の確認（2026-09-23）

| 確認 | 結果 |
| --- | --- |
| 起動時チェック | **全 13 項目合格**・終了コード 0・所要 2.9 秒 |
| 境界を弱めたとき | 不合格で**起動を中止**（`/mnt` を開けた設定で検出） |
| ランチャー経由の通し起動 | **TUI が起動した** |
| 境界の実在（起動後） | `ls ~/.ssh` が失敗する |

#### 実地でしか出なかった不具合（3 件）

設計と単体の検証では見つからず、**実際に起動して初めて出た**もの。

| 症状 | 原因 | 教訓 |
| --- | --- | --- |
| DB 作成直後に停止 | `node` を mise の **shim** から解決していた。shim は `mise` 本体への symlink で、呼ぶたびに版解決とネットワーク確認が走る | **信頼の鎖の要件（mise を経由しない）に実装が違反していた。** 文書に書いた規律が実装で守れているかは別途確かめる |
| 2 回目以降、必ずゲートで落ちる | ランチャーが作る `.opencode-sandbox/` を ignore していなかった | 生成物は ignore する |
| ネットワークの項目だけ不合格 | srt の proxy（`localhost:3128`）は**境界の生成直後はまだ待ち受けていない**。1 回目の要求が `rc=7` で落ち、対照条件が失敗する | 起動待ちを入れる（最大 30 秒リトライ） |

3 件目を追ったことで、**`api.githubcopilot.com` が許可リストに無く `403 CONNECT tunnel failed` になる**ことも判明した。そのままではチェックを通してもモデルへ到達できなかった。

> **「判別できなければ止める」が働いた。** proxy 未起動を「到達しない＝合格」と
> 読んでいたら、穴が開いたまま素通りしていた。エラーコード単独で判定しない
> という外部レビューの指摘が、実地で効いた事例。

#### 起動後に再現した既知の問題

`ls ~/.ssh` に対しモデルが**「存在しない」と報告した**。境界が隠していることは
伝わらない（[調査記録 20 節](../research/opencode/permission/sandbox-runtime.md)）。
段階 3 のシステムプロンプトで対処する。

### 段階 3: 隔離版の設定系統を分け、規則を作り替える

#### 設定を 2 系統に分ける

**緩和を隔離版だけに閉じ込める。** 通常版まで緩めてはいけない。

| 系統 | 設定の場所 | 規則 |
| --- | --- | --- |
| 通常版 | `~/.config/opencode/` | 現行 225 件を維持 |
| 隔離版 | `OPENCODE_CONFIG_DIR` が指す別ディレクトリ | 緩和する |

どちらも `common.toml` から生成する。**ディレクトリを分けただけでは足りない**
ので、実効設定・policy・DB が本当に隔離版になっていることを版ごとに確認する。

#### 規則の作り替え（225 件の全件対応）

現物は deny 193 / ask 27 / allow 5。処遇を**全件に割り当てる**
（取りこぼし 0 を機械的に検査する）。

| 分類 | 件数 | 処遇 | 根拠 |
| --- | --- | --- | --- |
| ホスト絶対パスの秘密（`~/.ssh` など） | 42 | **捨てる** | `denyRead` が到達させない |
| **ワークスペース相対の秘密 glob**（`*secret*` `*/.ssh/*` など） | 約 60 | **残す** | **OS 境界はワークスペースを守らない** |
| **`.git/hooks/*` / `.git/config`** | 4 | **残す** | **後でホストで実行されるコード** |
| `systemctl` / `sudo` / `mkfs` / `crontab` | 17 | **捨てる** | 境界内から到達できない |
| `git config --global/--system` | 2 | **捨てる** | 境界外の設定を触れない |
| `git config --local` | 7 | **残す** | hooks / filter で後日のホスト実行に関わる |
| `docker` / `aws` / `kubectl` など | 13 | **残す** | 到達性（socket・リモート・環境変数）の確認が済むまで |
| `git push` / `gh release` / `gh repo delete` | 13 | **残す** | 運用上の禁止。資格情報の有無とは別 |
| 履歴破壊（`reset --hard` / `rebase` / `filter-branch`） | 9 | **残す** | 境界内の履歴を壊せる |
| `.env` の read / edit | 4 | **残す** | 境界内の秘密 |

##### 「残す」規則の強さを区別する

**permission は任意コードへの境界ではない。** `policies` について認めたことを、
permission にも一貫して適用する。

| 強さ | 意味 | 例 |
| --- | --- | --- |
| **OS でも強制** | shell・任意プログラムからも阻止される | ホスト絶対パスの秘密（`denyRead`） |
| **ツール操作上の禁止のみ** | `read` / `edit` ツールは止まるが、**shell からは読める・書ける** | ワークスペース相対の秘密 glob、`.git/hooks/*` |

対応表には**この区別を列として持たせる**。「残したから守られている」と
読めてはいけない。

本当に読み出し・改変を阻止したい対象は、**OS 側でも保護するか、
そもそも作業コピーに含めない**。検証も、専用ツールだけでなく
**shell 経由の読み書きの両方**で行う。

> **snapshot・DB・ログにできた複製にも経路がある。** 元のパスを保護しても、
> 複製を読める経路は別に確認する。

##### 対応表に持たせる項目

前回の指摘（元 225 件との対応が追えない）を満たすため、各規則に次を持たせる。

| 項目 |
| --- |
| 元規則の action と resource |
| 残す / 統合 / 削除と、その理由 |
| **強さ**（OS でも強制 / ツール操作上の禁止のみ） |
| 代替する保護、または受容する喪失 |
| 変更後の規則との対応と、**マージ順序を踏まえた期待動作** |

> **「大幅削減」ではない。** 当初は 20 件程度まで減ると見込んだが、
> **秘密の deny の多くはワークスペース相対の glob** で、境界の外の話ではない。
> 現実的な着地は 130〜150 件。

#### ワークスペースの破壊は `allow` + 復旧で扱う（ただし保証ではない）

**OS 隔離はワークスペースを守らない。** `git reset --hard` を deny にしても、
`rm`・スクリプト・通常の書き込みで同じ破壊ができる。守るべき優先順位は
**まず復元できない未コミットの作業**で、履歴ではない。

確認を挟まずに復旧手段を持つ形にする。

| 確認 | 実測 |
| --- | --- |
| snapshot は **shell の `rm`** を捕捉するか | **する**（ファイルシステム単位のため） |
| **未追跡・未コミット**も戻るか | **戻る**（2 MiB まで） |
| 復元 | `/undo`、または revert API |

##### snapshot を確認削減の根拠にしない

**snapshot は日常の取り消し機能**であって保全策ではない。次の 3 つが理由。

| 限界 | 内容 |
| --- | --- |
| **復旧データ自身が破壊できる** | 保存先は `allowWrite` 配下でなければ捕捉できず、**同じ shell から消せる**。作業と復旧データを一度に失いうる |
| 捕捉は best effort | 公式仕様。失敗しても会話は続くので**気づけない** |
| 復元が上書きしうる | 後から人間が加えた編集を潰すことがある |

対象外も残る。

- `.gitignore` されたファイル、2 MiB 超の未追跡ファイル
- 作業ディレクトリの外
- ファイル以外の副作用（プロセス・DB・ネットワーク）

##### 独立した復旧元は「信頼済みリモートへ push 済み」のもの

**クリーン判定は保全ではない。** 同じ shell から `.git` のオブジェクトや参照を
消せるので、**コミット済みの履歴もローカルでは失いうる**。ignored ファイルの
状態もクリーン判定では見えない。

| 対象 | ローカルの破壊で失うか | 備考 |
| --- | --- | --- |
| **信頼済みリモートへ push 済み** | **ローカルの破壊だけでは失われない** | **復旧にはリモート側の保持と可用性が要る** |
| ローカルの履歴（未 push） | **失いうる** | `.git` は `allowWrite` の中 |
| 未コミット・未追跡 | **失いうる** | 同上 |
| ignored ファイル | **失いうる** | snapshot の対象外でもある |

**この喪失を受容する。** 起動時のゲートは保全ではなく
**「未保存の変更を持ち込んでいないか」の確認**と位置付ける。

| 状態 | 挙動 |
| --- | --- |
| クリーン | そのまま起動 |
| **未コミット / 未追跡あり** | **中止**。コミット（できれば push）するか、明示的に承知して起動 |

##### 「push 済みなら安全」と言い切らない

境界内からの `git push` と `gh` の書き込みは失敗する（実測）。
確認できているのは次の範囲にとどまる。

- 指定した資格情報ファイルを内側から読めない
- **試した** `git push` と `gh` の書き込みが失敗した
- 確認したトークンは `read:user` の権限しか持たない

**これはリモートを変更する経路がすべて無いことの証明ではない。**
環境変数のトークン・SSH 鍵と agent socket・別の credential helper・
認証済みサービスの有無は、この根拠からは分からない。ある push の失敗は、
同じ資格情報による別の ref 操作や API 経由の変更まで否定しない。
リモート側の喪失（他者による削除・履歴改変）も別の話。

##### 復旧先と基準を境界の外に固定する

`.git` を変更できるなら、**remote の URL も remote-tracking ref も変更できる**。
`origin` と呼ぶだけでは復旧先がすり替わりうる。

| 境界の外に記録するもの |
| --- |
| 信頼するリモートの識別情報（URL） |
| **push 済みであることを確認した基準コミット ID** |

コミット ID の記録は履歴そのものの保全ではないが、
**復旧先や基準のすり替えを防ぐために要る**。

> **`worktree` を切ることは保全ではない。** 新しい worktree は元の未コミット
> 変更を自動保存せず、Git の共通メタデータも共有する（外部レビューの指摘）。

**確実にしたいなら「原本を書き込み範囲外に置き、破棄可能な作業コピーだけを
渡す」形にする。** 現時点では採らず、上記の喪失を受容する。

> 誤った `stage` を `commit` すると**セッションが切り詰められ、復元機会が
> 消える**（実地で壊した）。`/undo` は取り消せるが `commit` は戻せない。

#### `policies` は運用上の禁止だけ

グローバル設定に置くと**プロジェクト設定から解除できない**。

| 置くもの | 例 |
| --- | --- |
| 運用上の禁止 | `shell:git push *`、`shell:gh repo delete *` |
| 人間専用と決めた展開操作 | `shell:chezmoi apply *` |
| 使う provider 以外 | `provider.use` を全体 deny → 使うものだけ allow |
| 同じ作用を持つ MCP ツール | `git push` だけ禁じて MCP が通るのは不統一 |

**任意コードに対する境界ではない。** permission 検査を通る操作にしか効かず、
plugin のコードを sandbox しない。不正な statement は**警告付きで破棄される**
ので、置いた事実ではなく**有効性**を確認する。

`external_directory:*` の全面 deny は、意図的に開けた `/mnt` の参照先も
止めうるので、許可パスと整合させる。

#### 境界をエージェントへ伝える

**隠すことと存在しないことをエージェントは区別できない。** 実測では
`ls ~/.ssh` の `ENOENT` を見て「存在しないので作れます」と誤診した。
実行していれば鍵は消える領域へ書かれていた。

システムプロンプトで伝える（**説明上の対策であって、書き込み失敗を
保証するものではない**）。

1. ホスト HOME の大部分は隠されている。`ENOENT` はホスト上の不存在を意味しない
2. 成果の永続化先は指定のワークスペース。他の永続化先・読み取り専用の例外は
   明示されたものに限る
3. 一時領域への書き込みはホストの同名パスへの反映を意味せず、隔離終了時に破棄される
4. 鍵生成・認証設定・ホストへの展開は境界の外で行う
5. 内側の観測だけでホストへの反映を報告しない
6. 拒否されたアクセスを、別パス・symlink・別ツールで回避しない
7. ホストで実行されるコードを変更したら、対象と**実行される契機**を報告する

**完了条件**: 225 件すべてに処遇が割り当たり取りこぼしが 0 であること。
隔離版の緩和が通常版に波及しないこと。snapshot の保存先が永続領域にあること。

### 段階 4: 許可リストを `common.toml` で単一ソース化

パスとドメインの両方を `common.toml` から生成する。

#### プロジェクトごとのパス許可

chezmoi 管理下でも機密でないパス（`~/.config/shell` など）は、
プロジェクト単位で開けられることを実測した。

| パス | 設定 | 結果 |
| --- | --- | --- |
| `~/.ssh` / `~/.config/gh` / `~/.config/opencode` | 未許可 | **拒否** |
| `~/.config/shell` / `~/.config/mise` | `allowRead` | **読める** |
| `. ~/.config/shell/shellenv.sh` | — | **読み込み成功** |

> **許可リストをプロジェクト側のファイルに置かないこと。** 敵対的な
> リポジトリが `~/.ssh` を自分で許可できてしまい、
> [プロジェクト設定がグローバルに勝つ問題](../research/opencode/permission/gaps.md)と
> 同じ穴になる。`common.toml` にプロジェクトパスをキーとして持たせる。

#### ドメイン

`[sandbox] claude_network_allow` は現在 **Claude 専用**（Copilot にドメイン単位の
制御が無いため）。OpenCode でも使えば同じリストを共有できる。

実履歴で不足が判明しているものを先に足す。

| 追加するもの | 根拠 |
| --- | --- |
| `opencode.ai` | 許可外で 50 件が失敗する見込み |
| `claude.ai` | 同 3 件 |
| `mise.jdx.dev` | 実地で警告が出た（`mise-versions.jdx.dev` はある） |

不足しても破綻はせず接続が失敗するだけなので、追記で回復できる。

#### GitHub の認証情報は当面入れない

**境界内には追加の資格情報を置かない。** 実履歴では 25 件がこれで失敗する
見込みだが、必要が生じるまで持ち込まない。

##### すでに境界内にあるもの

「認証情報を一切入れない」は**不正確**。モデルの OAuth は DB にあり、
**境界内の任意コードから読める**ものとして扱う。実測した権限は次のとおり。

| 項目 | 実測 |
| --- | --- |
| 種別 | `github-copilot` の OAuth（`gho_`、refresh トークンあり） |
| **GitHub での権限** | **`read:user` のみ**（`X-OAuth-Scopes`） |

`gho_` は GitHub の OAuth トークンなので「モデル専用だから他に使えない」とは
**推定できない**。実際に `api.github.com` へ当てて範囲を確かめた。
**リポジトリの読み書きも `git push` もできない。** 残るリスクはモデル推論の
実行（課金・枠）とプロフィールの読み取り。

> **provider を替えたら測り直す。** 別のトークンが入る。

##### 棚卸しの対象（2 ファイルだけではない）

| 経路 | 扱い |
| --- | --- |
| `~/.git-credentials` / `~/.config/gh/hosts.yml` | `denyRead` で不可視（実測で `git push` / `gh` 書き込みが止まる） |
| 継承した `GH_TOKEN` / `GITHUB_TOKEN` 等 | ランチャーが**環境変数を絞って**起動する |
| SSH agent / credential-cache の socket | `denyRead` と seccomp。起動時チェックで確認 |
| Git の remote URL に埋まった資格情報 | ワークスペース内なので境界外の話ではない |
| DB 内の OAuth・MCP 認証情報 | 上記のとおり境界内にある |

##### 必要になったときの選択肢

当面は**境界の外で必要な取得を済ませ、内側には取得済みのデータを渡す**のが
最も単純（外部レビューの助言）。それでも足りない場合の候補は、対象を絞った
fine-grained PAT、読み取り専用 deploy key、権限を絞った GitHub App の
短寿命トークン。いずれも組織ポリシー次第。

**classic PAT は使わない。** 読み取り専用にできないため。

**完了条件**: 検証コマンド（`uv run` / `pre-commit` / `mise`）と `gh` の参照・
`git fetch` が境界内で通ること。失敗で止まった件数を記録し、許可リストへ
追記していく運用が回ること。

### 段階 5: 誘導の向きを反転し、不要になった層を捨てる

境界ができると、**保護されている経路と、されていない経路が入れ替わる**。

| 経路 | いま | 境界の導入後 |
| --- | --- | --- |
| shell | 保護が弱い | **OS が強制する** |
| `grep` / `glob` | 結果フィルタ（事後の除去） | **変わらず弱い** |
| `read` / `edit` | permission の deny（実測で効く） | 変わらず効く |

そこで**ファイルに触る経路を shell へ寄せる**。

| ツール | 扱い | 手段 |
| --- | --- | --- |
| **`grep` / `glob`** | **無効化する** | **`tools: {"grep": false, "glob": false}`**（設定 1 行） |
| `read` | 残す | permission の deny が実測で効く |
| `edit` | 残す | 確実な代替が無い。shell で書かせると信頼性と確認負担が悪化する |

**plugin は要らない。** 実測では**モデルにツールが提示されず**、自分から
shell の `grep` へ切り替えた。誘導メッセージも不要
（[permission の穴](../research/opencode/permission/gaps.md)）。

> `permissions` 配列に `{action:"grep", effect:"deny"}` を書いても**効かない**。
> V2 の配列は `grep` / `glob` をアクションとして持たず、**黙って無視する**。

**これで「事後の除去に頼る経路」が消える。** 基準 2 の担保が最も弱い箇所を
無くせるのが狙いで、確認回数の話ではない。

#### 層ごとの判断

| 層 | 現在 | 移行後 | 理由 |
| --- | --- | --- | --- |
| 誘導（`cat` → `read`） | 2 | **0** | shell から秘密が見えなくなる |
| 誘導（`cd` / ヒアドキュメント） | 3 | 3 | 作法と負担。境界と無関係 |
| 結果フィルタ | 37 | **0** | ツールを無効化するので不要 |
| 伏字化: パス参照 | 34 | **0** | shell から到達できない |
| 伏字化: 内容の形 | 9 | 9 | 境界内の `.env` などに効く |
| `tools` の無効化 | 0 | **2** | 設定値 |
| permission（通常版） | 225 | 225 | 隔離しない経路は現状維持 |
| permission（隔離版） | — | **130〜150** | ワークスペース相対の秘密 glob は残す（段階 3） |

**「規則が減ること」を成果としない。** 減った分は OS 側へ移したのであって、
守る対象が減ったわけではない。評価は基準 2（組み合わせごとの阻止機構と検証根拠）
で行う。

#### 代償

`grep` は実履歴で最も多い残存呼び出し（114 件）。これが全て shell 経由になるが、
**隔離は起動時 1 回なので上乗せは無い**。

**完了条件**: 事後の除去に頼る経路がゼロになること。

## 評価基準

**必須:**

1. Claude / Copilot / Codex / Gemini の生成物に diff が出ないこと
2. **保護対象 × 禁止操作 × 実行経路の組み合わせごとに、禁止操作を阻止する機構と
   検証根拠があること。** 阻止できない組み合わせは残余リスクとして明示し、
   受容を判断すること
3. **境界が起動していないとき、確認が減らないこと**（fail-closed）
4. **包めないときは実行を止めること。** 通常の shell 実行へ落ちるなら境界ではない
5. `chezmoi apply` を実行する手順が残っていること
6. 短いコマンドの実測遅延が、先に決めた許容値以内であること

**基準 2 の数え方。** 読み取り・書き込み・外部送信を分けて見る。
**結果フィルタは「実証できた情報開示の抑制」だけを担保として数え、
アクセス拒否とは同列に扱わない**（件数・エラー・集約に情報が残りうるため）。

> **削減目標は未達。** 当初の必須基準「規則と除外条件の総数が減っていること」は
> 達成できない。組み込みツールが境界の外に残り、それを守る規則を捨てられない
> ため。**安全性の改善を優先して必須条件を差し替えた。**
> 総数は補助指標として追い続ける（現在 310 件）。
>
> 「Claude Code も同じ構造だから健全」という論拠も**撤回した**。実装上の前例では
> あるが、残余リスクを受容してよい根拠にはならない（外部レビューの指摘）。

## 候補比較

| 候補 | 支持する根拠 | 不利な点 | 扱い |
| --- | --- | --- | --- |
| **`srt` で shell の実行ごとに包む** | 汎用・導入済み・proxy と seccomp が同梱。実地で成立 | 組み込みツールが外に残る。固定費 | **採用** |
| サービスごと包む | 組み込みツールも覆える | **不成立**。ネットワーク名前空間の除去で TUI から届かない。`--stdio` も不可 | **見送り** |
| **`grep` / `glob` を `tools` で無効化する** | 事後の除去に頼る経路を消せる。**設定 1 行で済み、モデルに提示すらされない**（plugin 不要） | `grep` は最多の呼び出し（114 件）で固定費が乗る（合計 約 4.6 秒） | **採用**（段階 5） |
| `grep` / `glob` を plugin の例外で止める | 同じ効果。実測で成立 | ツール定義のコンテキストを消費し、失敗の 1 往復が生じる | **見送り**（`tools` が上位互換） |
| `permissions` 配列で `grep` を deny | 既存の仕組みで済む | **効かない。** V2 の配列は `grep` / `glob` をアクションとして持たず黙って無視する | **不可** |
| `read` / `edit` も無効化して shell へ寄せる | 全ファイル操作が境界の内側になる | `edit` に確実な代替が無い。信頼性と確認負担が悪化する | **見送り** |
| bwrap を自作でラップ | 依存が減る | proxy と seccomp を自作することになる | **見送り** |
| Landlock | mount namespace を作らない | ファイル制限だけで通信・IPC を覆えない | **見送り** |
| 列挙型を続ける | 追加費用ゼロ | 書き込み保護が成立せず、規則と誤爆が単調増加 | **打ち切り** |
| `gh` を文字列で fetch のみ許可 | 実装が小さい | `gh api -X POST` で抜ける | **見送り**。認証情報を渡さないことで代替 |

## 保留にしたもの

[CHG-0002](0002-opencode-ask-by-default.md) 段階 4 以降のうち、次は**保留**する。
境界ができれば不要になるか、作り直しになるため。

| 保留するもの | 理由 |
| --- | --- |
| リダイレクト先を分解して `edit` の判定表に当てる | 境界が同じことを OS 側で行う |
| `claude_write_deny_globs` にシェル起動ファイルを追加 | 境界の内側に入れなければ足りる（macOS / Windows では別途必要） |
| 少数の静的 allow を増やす | 反転すれば不要 |

## 次の調査・実験

| # | 減らしたい不確実性 | 方法 |
| --- | --- | --- |
| P1-1 | 異常時の挙動（並行実行・キャンセル・異常終了） | 実装時に確認する |
| P1-2 | 「境界内で書けずに失敗する」コマンドの洗い出し | 実運用で失敗件数を記録し、許可パスへ追記する |

| P1-5 | **審査前のホスト実行経路** | mise タスク・Git hooks・検証スクリプトが外側で動く契機を洗う |
| P1-6 | 隔離版の実効設定が本当に分かれているか | 版ごとに設定・policy・DB を突き合わせる |

決着済み（[調査記録](../research/opencode/permission/sandbox-runtime.md)）:

- **P0-1 成立**。`opencode --standalone` ごと包める（TUI 含む実測）。
  「サービスごと包むと届かない」は**境界をまたぐ構成に限った話**だった
- **P0-2**。`chezmoi apply` は完全一致の例外では不十分。適用を人間の操作へ寄せる
- **P0-3**。版は `latest` の浮動指定で Claude Code と共有している
- **境界の外に残る経路**。`/mnt` と `/tmp` が開いていたので `denyRead` で塞いだ
- **境界内の資格情報の権限**。`read:user` のみ
- **snapshot が shell の `rm` を捕捉・復元できる**こと（`XDG_DATA_HOME` が条件）
- **起動時チェックの挙動ベース化と fail-closed**（`srt` は終了コードを伝える）
- プロジェクト単位のパス許可の粒度と、`/mnt` の狙い撃ち・symlink 越しの読み取り
- **保護機構そのものが書き換えられること**
