# dotfiles リポジトリの開発では OS のサンドボックス（pis の既定）を使わない

- **ステータス**: Accepted
- **日付**: 2026-11-05
- **決定者**: applejxd

## コンテキスト

[ADR-0018](0018-pis-sandbox-default-relax-only-when-proven.md) は `pis`（Fence の中で pi を起動する）を標準にした。前提は「普段は `pis` を打つ。制御ファイルの編集など、サンドボックスが邪魔な作業だけ外で行う」で、
dotfiles のリポジトリを作業ツリーにしたときは、制御ファイルの書き込みを塞ぎ、「ここの編集は `ocs` を使わずに行う」とする設計だった（[Fence 境界の組み立て](../spec/sandbox/fence-boundary.md)）。

2026-11-05 に、「dotfiles の開発（編集・試験・コミット・worker・統合）はサンドボックスの中でもできる」と判断して、初めて実際に内側で通して作業した。この判断は誤りだった。出た問題は次のとおり。

| 症状 | 原因 |
| --- | --- |
| 秘密のテンプレート（`home/dot_config/sops/age/private_keys.txt.tmpl` など）・秘密の一覧の docs と試験が、内側から読めない・触れない | 秘密を隠す規則が**名前や場所の一致**（`**/sops/age/**`・`*secret*` など）で、リポジトリの追跡ファイルまで巻き込む |
| 本体の `git status` が常に dirty。`git merge`・`git flow feature finish` が `stash failed` で失敗する | 隠したファイルが `/dev/null` の文字デバイスや欠落に見える。git 2.43 の `git merge` は統合の前に必ず `git stash create` を呼ぶ（`GIT_TRACE` で確認。`--no-autostash` でも同じ） |
| 実物の Fence・GPU・公開ポート・画像の試験が内側で検証できない | このリポジトリの主題はサンドボックスとガードの設定そのもの。入れ子の Fence は動かない（ユーザー名前空間が無い） |
| `uvx` の hook、24 件の試験、`~/src` への書き込みが失敗する | 実行環境への依存（直した） |

**根本の食い違い**: サンドボックスは「秘密は作業ディレクトリの外（ホーム）にあり、作業ツリーは安全に見せられる」ことを前提に作られている。
dotfiles は、作業ツリーの**中**に、秘密の名前・テンプレート・一覧と、それらを検査する試験・docs を持つ。名前で隠す規則と、直す対象が重なる。
しかも主題がサンドボックスとガードの設定なので、検証は内側では完結しない。

一方、このリポジトリに実際の秘密（鍵の中身）は含まれず（テンプレートと参照だけ）、読み取りは判定器と確認（フルガード）が止めている。OS 層の防御が追加で守る範囲は限られる。

## 検討した選択肢

### 選択肢 1: dotfiles はサンドボックスなし（フルガードだけ）で開発する（採用）

`pis --no-sandbox`。サンドボックスは、外部のコード・依存・Web アプリ・GPU を実行する、ほかのリポジトリで使う。

- **利点**: 費用が小さい。git・試験・統合が素のまま動く。この日までの運用と同じ
- **欠点**: dotfiles の作業中、外部の文書に仕込まれた指示（プロンプトインジェクション）への OS 層の防御が無い。判定器と確認は残る

### 選択肢 2: サンドボックスを dotfiles に合わせる

隠す規則を絞る・例外を足す・内側から統合する道具を持つ。実際に、stash を使わない統合スクリプト（`feature/sandbox-merge`）を作り、独立 review を 3 回行って確認規則の穴（コメント・リダイレクト・オプションの値の読み飛ばし）を塞ぎ続けた。

- **欠点**: 継続の保守費用が大きい（規則・例外・確認の穴）。サンドボックス自身の検証は結局外で行う。隠す規則を絞るほど、守りが弱くなる

### 選択肢 3: コンテナ・VM で隔離する（将来案）

秘密を持ち込まない。隠す必要が無く、git・試験が素のまま動く。

- **欠点**: 構築費が大きい。GPU・公開ポート・WSL 固有の機能も別に整える必要がある。今は着手しない

## 決定事項

- **dotfiles のリポジトリ（このリポジトリ）の開発・保守は、`pis --no-sandbox`（フルガードだけ）で行う。サンドボックスの中（`pis` の既定）では行わない。**
  実装は feature の worktree で行い、統合は PR ビューアの押下で行う（[ADR-0024](0024-human-press-merges-in-app.md)）。起動の組み立ては [pi のガード](../spec/guard/pi-guard.md)。
- サンドボックス（`pis` の既定）は、外部のコード・依存・Web アプリ・GPU を実行するほかのリポジトリで使う。ADR-0018 の「サンドボックス標準」は、そちらでは有効のまま。この ADR は dotfiles への適用だけを例外にする（部分改定。ADR-0018 の冒頭に案内を置いた）。
- `feature/sandbox-merge`（stash を使わない統合スクリプト）は統合しない。枝は残す。
- **「`pis`（サンドボックスあり）で dotfiles を開発できる」「内側で統合できる」と言わない・判断しない。** 内側で `git status` が dirty に見える・隠れたファイルがある、といった症状が出たら、サンドボックスの内側で作業している合図。作業を止めて、サンドボックスなしの起動へ切り替えるよう、利用者に伝える。

## 結果

- 汎用の修正は活かす: 受け箱（`PIS_IMAGE_INBOX`。ほかのリポジトリで Windows 側の画像を貼るとき）、試験の環境遮断（`PI_WORK*`・`WEBSEARCH_*` など）、`UV_TOOL_DIR`、サンドボックスの内側でも通る試験。
- 内側で本体の作業ツリーに `git add -A`・`git commit` をしない（隠れたファイルの削除や空の状態を記録する恐れ。[症状と対処](../spec/troubleshooting-agents.md#pis-の内側で本体の-git-status-が-dirty-に見える)）。
- `AGENTS.md`（このリポジトリ）に規則を 1 つ置いた。

## 再検討の条件

次のいずれかが満たされたら、この ADR を見直す。満たされない間は従う。

- 秘密を隠す規則が、作業ツリーの外の場所だけに絞られ、追跡ファイルを巻き込まなくなった。
- 入れ子にならない形で、サンドボックス自身を検証できる（コンテナなど。選択肢 3）。
- 内側から安全に統合する手段ができ、確認の穴を塞ぎ続ける必要が無くなった。

## 決定の確認方法

- dotfiles のリポジトリで、`pis`（サンドボックスあり）のまま作業が始まらないこと（利用者の運用と `AGENTS.md`）。
- `git status` が dirty に見えたとき、エージェントがサンドボックスの内側を疑って、起動の切り替えを促すこと。
