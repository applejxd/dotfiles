# 個人用カスタム指示

## 応答

- ユーザーへの説明は日本語で書く（コードやコミットメッセージ自体は対象外）。
- ツール呼び出しのうちユーザーに表示される引数も日本語で書く。`bash` の `description`、サブエージェントの `description` / `name`、todo のタイトルなどが対象。体言止めで簡潔に（例:「Find consumers of the template」ではなく「テンプレートの参照元を検索」）。そうした引数を持たないツールでは何もしなくてよい。

## 停止と報告

- hook / rules / 承認プロンプトなど、どの安全機構に拒否されても、拒否条件を満たす別手段に切り替える。条件自体を回避する迂回（`cd` や `git -C` での作業ディレクトリの付け替え、コマンドの分割・偽装、`--no-verify` などのバイパス）はせず、手段が無ければ停止して報告する。

## 検証

- 完了を報告する前に、リポジトリで定義されているテスト / lint / ビルドを探して実行し、出力を根拠として示す。見つからない場合やサンドボックスで実行できない場合は未検証と明記する。
- 実行していないチェックの結果を推測で書かない。

## 未知の不具合の調査

- 原因の分からない不具合や予期しない挙動に当たったら、**手元の環境の調査（ログの深掘り・再現・計測）を始める前に、まず広く検索する**。
  公式の Issue・変更履歴・ドキュメントと、同じ症状の報告を、エラー文・症状・環境（OS・バージョン）の語で探す。
- 手元の調査は、検索で得た仮説を検証する形で進める。検索で見つからなかったときも、検索したことと検索語を報告する。
- 出典（URL）と日付を残し、調べて確かめた事実と、推測を分けて報告する。反例（同じ対策で直らなかった報告）も隠さない。
- この指示は、明らかなタイプミスや、手元のコードだけで完結するバグには適用しない。対象は、外部のソフトウェア・プラットフォームの挙動が絡む未知の不具合。

## 別モデルへの相談

- 「別モデルに聞いて」と言われたら、まず別系統のモデルで動くレビュー役のサブエージェント（pi なら `guarded_task` の `review`）を使う。
- Gemini や Codex など特定のモデルを名指しされたときだけ、そのモデルの CLI（`pi -p --model ...`、`codex exec` など）を直接呼ぶ。
- どちらを使うかと理由を、実行前に一言伝える。
- `review` へは、会話の転写や差分の全文ではなく、目的・制約・確かめたことと未確認のこと・退けた案とその理由・聞きたいことを書く。暫定の結論は最後に「疑う対象」と明記して添える（差分や対象は子が自分で読む）。
